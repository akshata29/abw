## 10. Data flow and correlation

The platform has no single end-to-end identifier. Each hop stamps its own id, and the chain is rebuilt after the fact from a few keys that overlap in pairs: the APIM request id, the W3C trace id, the Entra token id and, for Storage only, a client request id (`observability/kql/AbwFullChainCore.kql:26-44#rids`, `src/mcp/abw_mcp/registry.py:195-201#setdefault`). This section follows the data: what crosses each boundary (10.1), which keys connect the records (10.2), how the `AbwFullChain` function stitches them (10.3), why records arrive late (10.4), where the chain breaks by design (10.5) and what is kept for how long (10.6). Authentication is section 6, authorization section 7, MCP internals section 8, scenarios section 9, the logging pack section 11 and the console that polls it section 12; they are not repeated here.

Provenance labels used below: **Implemented** (code), **Configured** (Bicep, policy XML, JSON), **Designed** (DESIGN.md or docs), **Platform behaviour** (a Microsoft Learn page, linked in the text).

### 10.1 Data flow of a governed tool call

What this section proves: which data crosses each hop of a governed call, which record each hop writes, and where ABW's own code deliberately keeps only identifiers, hashes and sizes (`src/mcp/abw_mcp/audit.py:178-216#build_event`). It also shows the one place where content is recorded outside ABW's control (Foundry agent tracing).

Diagram: docs/diagrams/03-request-data-flow.excalidraw

#### 10.1.1 Two ways in, one tool path

There are two entry paths and they converge on the same MCP tool path.

- **Direct path (Implemented, Configured).** A person, script or the Demo Console calls `https://apim-abw-demo-<region>-<u4>.azure-api.net/<server>/mcp` with a user token whose `aud` claim is the MCP API app. The research, wall, actions and vendor APIs are MCP-type APIs that take no APIM subscription key (`infra/05-apim-apis.bicep:123-148#mcpProperties`). The legacy API is the opposite on purpose: it needs a subscription key (`infra/05-apim-apis.bicep:169-180#subscriptionRequired`) and carries no user context (`infra/apim/policies/mcp-legacy.policy.xml:1-4#NO user context`).
- **Agent path (Implemented, Configured).** The user calls the APIM agent front door (API `abw-agent-frontdoor`, path `agents`) with a token for the Foundry data plane; APIM forwards the user's own token unchanged to the Foundry project endpoint, the agent runs, and each tool call goes to the same MCP APIs using OAuth identity passthrough (`infra/08-agent-frontdoor.bicep:51-58#abw-agent-frontdoor`, `infra/apim/policies/agent-frontdoor.policy.xml:9-11#forwarded`). How those tokens are obtained and exchanged is section 6; what each gateway layer decides is section 7.

Why two paths share one tool path: the demo's claim is that the agent never holds a stronger identity than the person, so the agent path adds a front door in front of Foundry but leaves the MCP side identical (`infra/apim/policies/agent-frontdoor.policy.xml:9-11#forwarded`).

Notes on the table.

- Hop 1: for the vendor API the policy deletes the user's `Authorization` header and injects the vendor key from a Key Vault-backed named value, so the user's token never reaches the third-party backend (**Configured**, `infra/05-apim-apis.bicep:75-79#x-vendor-key`). The other three JWT-governed APIs have no `Authorization` rewrite.
- Hop 3: the denial text includes `request_id` and a `note` aimed at the model ("do not retry, rephrase or look for a workaround"), so the id also reaches the person through the agent's answer (**Implemented**, `src/mcp/abw_mcp/registry.py:273-290#_error_payload`).
- Hop 5: the Cosmos read of the restricted list uses the server's managed identity, whereas orders use the user's OBO token when `COSMOS_OBO` is true (the default) (**Implemented**, `src/mcp/abw_mcp/servers/actions.py:91-96#use_user_token`, `src/mcp/abw_mcp/config.py:154#cosmos_obo`).
- Hop 6: stdout and the logger are two different paths to two different tables; the KQL pack reads only the stdout path (see Findings).

Why the request id is also embedded in the payload: Foundry is the only party that sees the tool result, so putting the id there lets the agent trace (which records the result) be joined back to the gateway and MCP rows (`src/mcp/abw_mcp/registry.py:198-201#setdefault`, `observability/kql/AbwFullChainCore.kql:20-25#toolRid`).

Why a set of keys and not one: the Entra token id exists before any ABW code runs, the APIM request id is created at the gateway, the trace id is created by whichever party starts the trace, and Search and Cosmos accept no caller-chosen id that ABW's queries can read back. The chain therefore bridges: request id to trace id through APIM telemetry and through the tool result text, request id to token id through the audit row, token id to session id through the Entra token row (10.3).

Trade-off / limitation: the MCP server trusts `x-abw-request-id` as given (`src/mcp/abw_mcp/auth.py:181-186#traceparent`). Behind APIM the header is overwritten by the policy (`infra/apim/policies/mcp-jwt.policy.xml:82-84#x-abw-request-id`); a caller that reaches a server without APIM (the private server, 10.5) chooses its own id.

### 10.3 How `AbwFullChain` stitches the chain

What this section proves: exactly which tables the full-chain card reads, in what order, on which key and in which time window, and what an empty step means. Two functions are involved: `AbwFullChainCore` (everything that lives in the ABW workspace, `observability/kql/AbwFullChainCore.kql:1#AbwFullChainCore`) and `AbwFullChain`, which adds the Entra rows (`observability/kql/AbwFullChain.kql:1#AbwFullChain`).

#### 10.3.1 Resolving the input to a set of ids

`AbwFullChainCore(anyId, lookback)` accepts any one id (the default `lookback` is 7 days) and first expands it into a set of request ids and trace ids. **Implemented**:

1. Normalise the input to lower case without whitespace (`qid`), and materialise the gateway view `gw = AbwGateway(lookback)` and the audit view `aud = AbwMcpAudit(lookback)` (`observability/kql/AbwFullChainCore.kql:4-6#qid`).
2. Build `gwTrace`: join each gateway row to the APIM `AppRequests` row with the same `TimeGenerated` (APIM role names starting `apim`) to learn the W3C trace id (`OperationId`) of each request id. This is a heuristic join on identical timestamps, not on a shared key (`observability/kql/AbwFullChainCore.kql:10-18#gwTrace`).
3. Build `toolRid`: from Foundry `execute_tool` spans, pull the `request_id` out of the tool result text with a regular expression, giving a request id to trace id pair for agent runs (`observability/kql/AbwFullChainCore.kql:19-25#toolRid`).
4. Build `tr`, the trace ids reachable from the input: gateway rows whose request id equals the input, audit rows whose request id or trace id equals the input, tool spans whose extracted request id equals the input, and the input itself when it looks like a 32-hex trace id (`observability/kql/AbwFullChainCore.kql:26-34#tr`).
5. Build `rids`: the request ids that share any of those traces, then `rk` (request ids) and `trk` (trace ids), and `ak = array_concat(rk, trk)` for the alert search (`observability/kql/AbwFullChainCore.kql:35-44#rids`).

Every row builder below then filters on `rk` or `trk`, so entering with a request id, a trace id, or the id found inside a tool result all reach the same chain.

#### 10.3.3 The Entra rows and the optional export workspace

`AbwFullChain` calls the core function and adds step 0 rows (`observability/kql/AbwFullChain.kql:5-7#toks`). It reads two Entra tables, written on lines of their own so deployment can rewrite them: `let entraNonInteractive = AADNonInteractiveUserSignInLogs;` and `let entraInteractive = SigninLogs;` (`observability/kql/AbwFullChain.kql:9-10#entraNonInteractive`).

- **With an export workspace (Configured).** The Bicep parameter `entraWorkspaceId` (the resource id of a workspace that the tenant already uses to receive Entra sign-in logs; this repo neither creates it nor writes to it) turns each of those two lines into `workspace('<id>').<table>`; the local pack builder does the same rewrite (`infra/06b-observability.bicep:34#entraPrefix`, `infra/06b-observability.bicep:50-55#functionAlias`, `observability/kql/pack.py:102-115#deploy_body`). Platform behaviour: `workspace()` takes a workspace id or ARM resource id and permissions are checked per workspace (https://learn.microsoft.com/azure/azure-monitor/logs/cross-workspace-query).
- **Without it (Configured).** `fn.fallback` (the `@fallback` line of the file) is used: `AbwFullChain` is deployed as a copy of `AbwFullChainCore`, so the Entra rows silently vanish; nothing in the output says they are missing (`observability/kql/AbwFullChain.kql:4#fallback`, `observability/kql/pack.py:102-110#fallback`).
- **The shape of the rows.** `shape` reads Entra columns with `column_ifexists` so a missing column does not break the query; `explain` lists a Conditional Access policy as `<policy name> = <result>` only when its result is something other than empty, `notApplied`, `notEnabled` or `reportOnlyNotApplied`, and keeps only city and country from the location (`observability/kql/AbwFullChain.kql:13-47#shape`, `observability/kql/AbwFullChain.kql:31-46#explain`).
- **The third argument.** `tokenIds` is a comma-separated list of `uti` values. A call refused at the gateway never reaches an MCP server, so no audit row carries its token id; the console passes the ids of the tokens it sent so those runs still show "Entra issued the token, the gateway refused it" (`observability/kql/AbwFullChain.kql:6-7#sent`, `console/e2e.py:138-140#_sent_tokens`, `DESIGN.md:170#tokenIds`).
- **Console fallback.** When the cross-workspace read fails, the console reruns the query as `AbwFullChainCore` (`console/e2e.py:84-85#Q_FULL_CORE`).

Edges stated in DESIGN.md: Entra exports a token row about 4-8 minutes after issue (non-interactive sign-ins can lag longer), and agent runs refused at the front door carry no known token id (**Designed**, `DESIGN.md:170#tokenIds`). Platform behaviour: routing Entra logs to Log Analytics can take up to three days at first-time setup, and in Log Analytics `TimeGenerated` is the receive time, not the sign-in time, so Entra's own `CreatedDateTime` is the time to trust (https://learn.microsoft.com/entra/identity/monitoring-health/reference-log-latency, https://learn.microsoft.com/entra/identity/monitoring-health/reports-faq). That is why the Entra windows above are on `CreatedDateTime`.

### 10.4 Ingestion latency and why the console polls and retries

What this section proves: every log hop in the chain arrives on its own schedule, and the Demo Console is built around that fact. It states a lag per hop, never blocks the live part of a scenario on logs, re-reads on demand through a separate read-only job, words each answer by the age of the run, and refuses to present an unfinished chain as finished. The numbers live in two places: the lag banner (`console/e2e.py:1288#LAG`) and the per-hop wording of the full-chain card (`console/e2e.py:1634-1651#_fc_waiting`).

#### 10.4.1 What the platform does and does not promise

**Platform behaviour** (each point comes from the Learn page named):

- Ingestion time. Once a record reaches the collection endpoint, Log Analytics ingests it in under 10 seconds on average. Azure resource logs take longer end to end: 30 seconds to 20 minutes, usually 3 to 10 minutes (https://learn.microsoft.com/azure/azure-monitor/logs/data-ingestion-time).
- `TimeGenerated` is the time the source stamped on the record. The workspace replaces it with the received time when it is more than two days in the past or more than one day in the future; `_TimeReceived` and `ingestion_time()` expose when the workspace received the record (same page). A query cannot see a record that is not ingested yet, so the only remedy is to ask again later.
- Sentinel delays every scheduled-rule run by five minutes to allow for ingestion latency (https://learn.microsoft.com/azure/sentinel/scheduled-rules-overview). An alert on a log row therefore needs the row's own ingestion time, plus that delay, plus up to one rule interval.
- Entra: Learn gives no steady-state figure. It says to expect about 24 hours before data appears in a newly set-up storage account or SIEM, and up to three days before activity logs routed for the first time to a Log Analytics workspace appear (https://learn.microsoft.com/entra/identity/monitoring-health/reference-log-latency). The 4-8 and 10-20 minute figures the repo quotes for Entra are the repo's own measurements, not a platform guarantee (`console/e2e.py:1634-1651#_fc_waiting` for 4-8, `console/e2e.py:1288#LAG` for 10-20).
- Query time range: the query API's `timespan` is applied in addition to any time filter written inside the query (https://learn.microsoft.com/javascript/api/@azure/monitor-query-logs/querybody?view=azure-node-latest). Learn's query-optimization guidance counts a time span over 15 days as a query that consumes excessive resources, and one over 90 days as abusive and possibly throttled (https://learn.microsoft.com/azure/azure-monitor/logs/query-optimization#time-span-of-the-processed-query).

The repo never claims a single number. These are the figures that appear in console text (**Implemented**) and in DESIGN.md and the playbook (**Designed**), with the place that states each:

#### 10.4.3 How the console copes

1. **The live part never waits for logs (Implemented).** A scenario finishes its live calls first. Every log-backed layer is then marked with the label "LOGS 2-18 MIN" and the text "Refresh from logs, 2-18 minutes after the call" (`console/e2e.py:585#LOGS`). Background probes are awaited for at most 25 seconds (`PROBE_WAIT`), and a probe that fails or times out returns nothing instead of failing the scenario (`console/e2e.py:309-315#PROBE_WAIT`).
2. **Refresh is its own read-only job (Implemented).** The `e2e_logs` runner imports the E2E module lazily and calls `run_logs` (`console/jobs.py:1365-1368#run_e2e_logs`). `run_logs` recalls the run from an in-memory trace store and calls `_refresh`, which on its general path reads in a fixed order: Foundry spans, the request-id chain, the full chain, Sentinel, Defender; the Foundry spans and Defender are read only for agent scenarios (`console/e2e.py:1858-1872#run_logs`, `console/e2e.py:1833-1855#_refresh`). The job kind is in `READONLY`, so it never conflicts with another job, and it is not in the set of kinds that the manager refuses while the kill switch is engaged (`console/jobs.py:473-497#READONLY`, `console/jobs.py:503-531#start`). Each source is read through `_safe`, which returns either the result or a reason, so one unreadable source never hides the others (`console/e2e.py:1315-1321#_safe`).
3. **The trace store is small and volatile (Implemented).** It keeps the newest 40 runs in memory (`_TRACE_MAX = 40`). After a console restart, or after 40 newer runs, Refresh stops with "That trace is no longer in memory" instead of guessing (`console/e2e.py:249-267#_TRACE_MAX`, `console/e2e.py:1858-1872#run_logs`).
4. **Wording depends on the age of the run (Implemented).** `_age_min` measures minutes since the click (`console/e2e.py:1299-1303#_age_min`). Three thresholds apply:
   - The request-id chain says "no row for this layer even now" only when the run is at least 12 minutes old; younger runs get "not there yet" wording. A log row that contradicts what the live step saw raises a WARNING instead of being smoothed over (`console/e2e.py:1461-1508#_refresh_rid`).
   - The full-chain card uses 15 minutes (`_FC_MATURE_MIN = 15`). Younger than that, an amber line says the chain is still filling in and names the missing hops. At 15 minutes or older the line says "Still missing N minutes after the click" and tells the presenter not to present those hops as logged (`console/e2e.py:1521#_FC_MATURE_MIN`, `console/e2e.py:1634-1651#_fc_waiting`).
   - The Sentinel step says "no alert names this request id" only at 20 minutes or more, and then also tells the presenter to check the rule's last run and that its 30-minute look-back covered the log row. Younger runs get "the rule runs every 5 minutes and alerts typically appear 5-15 minutes after the log row" (`console/e2e.py:1750-1786#_refresh_sentinel`).
5. **A wide API time range, a narrow query look-back (Implemented, with an inference).** The full chain is called with a 3-day look-back argument, but the Log Analytics call is given `24.0 * _FC_SPAN_DAYS` hours, which is 840 and which `la_query` turns into the ISO duration `P35D` because the value is 48 hours or more (`console/e2e.py:1522#_FC_SPAN_DAYS`, `console/e2e.py:1654-1707#_refresh_fullchain`, `console/azure_probe.py:165-180#la_query`). The second argument of `la_query` is the query time range in hours, not a timeout. Why: the Entra rows are stamped when the token was issued, and a token is reused until it expires, so they can be days older than the call (`DESIGN.md:170#tokenIds`). The data-plane scenario replays a run that can be days old; it reads a 14-day window and keeps only the identity chain because "AbwFullChain over that window takes about 50 seconds" (`console/e2e.py:126-128#_replay`). **Inference** (not stated in the repo; from the Learn page on the query `timespan` above): because the API range is applied in addition to the query's own filter, the console reaches back at most 35 days, although the KQL looks for the interactive sign-in over 90 days (`observability/kql/AbwFullChain.kql:73-77#loginRaw`).
6. **Degrade instead of failing (Implemented).** If the full-chain call fails, which is typical when the cross-workspace Entra read is not permitted, the console reruns `AbwFullChainCore` over 72 hours and says so in the job's step line ("showing every other row") and in the card's scope line ("so this chain has no Entra rows"). Entra token rows that were expected (tokens seen by MCP servers plus tokens the console sent) but not found are reported as missing, not left blank (`console/e2e.py:1654-1707#_refresh_fullchain`, `console/e2e.py:84-85#Q_FULL_CORE`).
7. **Control-plane propagation is polled, not waited for (Implemented).** The kill switch and the client allow-list are APIM named values, and "Azure applies the change in about a minute". `_gw_poll` therefore asks the gateway up to 9 times, 10 seconds apart, until it answers the status the scene wants (`console/jobs.py:1243-1260#_gw_poll`). This is policy-propagation latency, not log ingestion latency.
8. **The browser polls; nothing is pushed (Implemented).** `pollOnce` reads `/api/jobs/<id>?since=<n>`, and `kick` re-polls every 600 ms while any job is live. The status lights refresh every 15 seconds in the browser and are cached for 15 seconds on the server, and the "age" labels on cards re-render every 15 seconds (`console/web/util.js:131-158#kick`, `console/web/app.js:164#refreshStatus`, `console/jobs.py:621-628#status_lights`, `console/web/render.js:313#AGES`). A search of the console's Python, JavaScript and HTML for WebSocket, EventSource and event-stream code found none.
9. **Retries and caches (Implemented).**

| Caller | Policy | Citation |
|---|---|---|
| Azure probes (ARM and Log Analytics calls) | 3 attempts. A transport error waits 0.6 s times the attempt number. HTTP 429, 502, 503 and 504 wait 1 s plus the attempt number. Then a `ProbeError` | `console/azure_probe.py:103-116#_retrying` |
| KQL helper of the demo scripts | 4 attempts, waiting 3 s times the attempt number; no retry on a 4xx other than 429 | `demo/kql.py:48-61#_with_retry` |
| Agent run client | `APIConnectionError` is retried up to 10 attempts; delay starts at 3 s, grows by 1.5 and is capped at 15 s; each retry prints a "network blip" line | `console/agent_run.py:105-120#delay` |
| Probe results | Cached for 120 s unless a refresh is forced | `console/azure_probe.py:828-850#TTL` |

Why this shape: a presenter in front of a customer must be able to press Refresh as often as they like and must never be told that an unfinished chain is complete. Every state is therefore one of waiting, still missing or not found. The playbook states the rule: "A row whose log has not arrived says so; it is never filled in." (`docs/PROOF-PLAYBOOK.md:501#lags`).

Trade-off / limitation: the numbers disagree between code sites (Sentinel 5-15 against 9-13 against 22 observed; logs 2-18 against 5-10; see Findings at the end of section 12). The 15-minute maturity line is a presentation rule, not a platform property: a hop that arrives at minute 22 shows as missing until the next Refresh. The 35-day range is above Learn's 15-day guidance for query time spans.

### 10.5 The exceptions: guardrail trace id, Entra token and session id, and the private server

What this section proves: the request id is the main thread of the chain, and there are three places where it does not reach. Each is handled by a specific, citable mechanism, and each leaves a visible mark on the card (for example the label "direct VNet path, no APIM", `observability/kql/AbwFullChainCore.kql:149-160#mcpRows`).

#### 10.5.1 The guardrail row carries the trace id, not a request id

- **Implemented.** The guardrail row is built from the `invoke_agent` span: the content-filter results are parsed from the span property `microsoft.foundry.content_filter.results`, one entry per intervention point, and each point becomes "ok" or "BLOCKED" with the flagged categories. The row sets `RequestId = ''` and `TraceId = OperationId` (`observability/kql/AbwFullChainCore.kql:83-113#guardPoints`).
- Why no request id: the verdict is recorded on a Foundry span, and the only key a span has is the trace id. The APIM request id is minted by the gateway for a call that passes through it (`infra/apim/policies/mcp-jwt.policy.xml:82-84#x-abw-request-id`), and nothing copies it onto the Foundry span. The chain still reaches the guardrail row from a request id because `gwTrace` joins each gateway row to the APIM `AppRequests` row at the same timestamp and so learns the trace id (10.3.1). A run refused by the guardrail makes no tool call, so it has no tool-call request id at all.
- The row says what it could not see. Defender for AI and Purview run inside the Foundry content filter (comment in the KQL), so the function lists every provider whose result says `unavailable` as "no verdict from: ..." (`observability/kql/AbwFullChainCore.kql:92-100#guardUnavailable`).
- The denial view stores the trace id in the column named `RequestId` for layer 0 (`observability/kql/AbwDenials.kql:32-41#guardrail`). So the custom detail `RequestId` of rule ABW-008 holds a trace id, not an APIM request id (`observability/sentinel/abw-008-guardrail-intervention.kql:8-13#RequestId`). The console's Sentinel lookup searches the alert details for both the request id and the Foundry trace id, and starts the full chain from the trace id as the last resort (`console/e2e.py:1750-1760#_refresh_sentinel`, `console/e2e.py:131-135#_chain_ids`).
- **Platform behaviour.** Foundry guardrails have four intervention points and apply only to agents built in Foundry Agent Service (https://learn.microsoft.com/azure/foundry/guardrails/intervention-points).

#### 10.5.2 The Entra token id and the session id

Mechanics are in 10.3.3 and the token is explained in section 6; this note lists only what makes it an exception.

1. **Where the id comes from.** The `uti` claim is the token identifier and is equivalent to `jti` (https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference). The MCP server stores `uti`, falling back to `jti`, in `Caller.jti`, writes it as the audit field `jti`, and `AbwMcpAudit` exposes it as `TokenId` (`src/mcp/abw_mcp/auth.py:160-170#jti`, `src/mcp/abw_mcp/audit.py:178-216#build_event`, `observability/kql/AbwMcpAudit.kql:28-34#TokenId`). Entra logs the same value as `UniqueTokenIdentifier`, described by Learn as the unique token identifier for the request (https://learn.microsoft.com/azure/azure-monitor/reference/tables/aadnoninteractiveusersigninlogs), so the join finds the token-issue row (`observability/kql/AbwFullChain.kql:49-54#tokenRaw`).
2. **Why a third argument exists.** A call the gateway refuses never reaches an MCP server, so no audit row holds its token id. `AbwFullChain` therefore takes `tokenIds` as a third parameter (`observability/kql/AbwFullChain.kql:1-7#tokenIds`). The console fills it from the tokens it sends: it decodes each token's payload locally and without checking the signature (`demo/mcpclient.py:51-54#claims`), keeps `uti` in the run record, checks it against `^[A-Za-z0-9_-]{16,32}$` and keeps at most three (`console/e2e.py:101#_UTI`, `console/e2e.py:138-140#_sent_tokens`, `console/e2e.py:364-368#_note_token`). It is recorded when the console signs a persona in, when it makes a gateway call, and in the scenario that presents a token minted for a different API (`console/e2e.py:415#uti`, `console/e2e.py:686#_note_token`). The scenario summary keeps only a short list of claims, never the token (`demo/mcpclient.py:57-59#summarize`).
3. **The session id.** The token row carries `SessionId`. The function collects those ids (`sess`) and reads the interactive `SigninLogs` with `SessionId in (sess)` over 90 days, because the sign-in that started a session can be days older than the call (`observability/kql/AbwFullChain.kql:71-77#loginRaw`). The card shows only the first 8 characters of the session id (`observability/kql/AbwFullChain.kql:55-70#tokenRows`, `observability/kql/AbwFullChain.kql:79-100#loginRows`).
4. **No request id, no trace id.** Both Entra row types set `RequestId = ''` and `TraceId = ''`; they join only through the token id and the session id, and they are the only rows that come from outside the ABW workspace (the optional export workspace, 10.3.3).
5. **Platform behaviour.** `SessionId` is the id of the session generated during the sign-in; `CreatedDateTime` is the time of the sign-in activity; `TimeGenerated` is the time the request was received (same table reference as above).

Trade-off / limitation: calls made outside the console carry no known token id (**Designed**, `DESIGN.md:170#tokenIds`), and the console's record of the tokens it sent lives in the trace store of 10.4.3, so it disappears on restart.

#### 10.5.3 The private MCP server bypasses APIM

- **Configured.** The private server runs in the internal-only Container Apps Environment (resource `caePriv`, `internal: true`), so it has no public ingress. Its FQDN is a variable and its app is `privateMcp` (`infra/03-platform.bicep:377-397#caePriv`, `infra/04-apps.bicep:75#privateFqdn`, `infra/04-apps.bicep:131-142#privateMcp`). The Foundry connection `mcp-private-oauth` targets the app's own URL directly, over the delegated agent subnet (`scripts/foundry-connections.ps1:12#mcp-private-oauth`, `scripts/foundry-connections.ps1:64#private`). **Designed**: "This path never touches APIM" (`DESIGN.md:107#APIM`).
- **Implemented.** The server validates the user's token itself like every other server (`src/mcp/abw_mcp/auth.py:108-150#verify_token`) and takes its request id from the request: `x-abw-request-id`, else `x-request-id`, else `x-ms-request-id`, else `traceparent`, else a value built from the clock (`src/mcp/abw_mcp/auth.py:173-188#RequestContextMiddleware`). The APIM policy that overwrites the header is not on this path. What Foundry sends on this path is not in this repo.
- What changes in the data flow:
  1. No `ApiManagementGatewayLogs` row exists: `AbwGateway(1d)` filtered to `Server == 'private'` returns 0 while `AbwMcpAudit(1d)` for the same server shows rows (`docs/PROOF-PLAYBOOK.md:1444-1447#AbwGateway`).
  2. No APIM trace, no gateway metric, no per-user rate limit, and no kill switch, because the deny list lives in the APIM policy. A revoked user keeps access until the token expires; the repo says this is "read from the code, not exercised live" (`DESIGN.md:107#APIM`).
  3. The audit row still exists. The full-chain card labels the server's rows "direct VNet path, no APIM" (`observability/kql/AbwFullChainCore.kql:149-160#mcpRows`). The console's role tab labels the gateway row "NOT BEHIND APIM" and the data row "COSMOS AS USER", because the data call uses the user's own on-behalf-of token (`console/role_tabs.py:332-348#_private_rows`).
  4. The console never calls this server from the operator's machine: `validate` rejects a gateway call to `private`, because only the VNet-injected agent runtime can reach it (`console/jobs.py:563-575#validate`).
- Why: some systems of record should not sit behind a public gateway at all, and the model still works there because the server checks the user itself (**Designed**, `docs/PROOF-PLAYBOOK.md:1444-1447#AbwGateway`).
- Trade-off / limitation: the request id on this path is whatever the caller sends, and the kill switch does not cover it. The production fixes named in DESIGN.md are an internal APIM in front of the server, or a deny list read by the server (`DESIGN.md:107#APIM`). Sections 6, 7 and 8 explain the token checks, the role rules and the server internals.

What this section proves: what is kept, for how long and where, and what is never kept. Every retention number below is traced to a Bicep property or to a Learn page, for example the 1-day immutability period of the audit container (`infra/03-platform.bicep:186-201#wormPolicy`).

#### 10.6.1 Retention, immutability and TTLs

Not in this repo: a lifecycle-management policy, blob versioning, or a protected-table setting for `AppGenAIContent` (a search of `infra`, `scripts` and `docs` found none).

**WORM audit blob in detail.**

- **Implemented.** The sink writes `canonical_json(event)` plus a newline as one `append_block` to an append blob it creates on first use, authenticating with the server's managed identity (`src/mcp/abw_mcp/audit.py:88-118#_append_line`). By default the append is asynchronous and fail-open: a background thread drains a queue, and a failed append only prints `append_audit_failed` and logs it. With `AUDIT_FAIL_CLOSED` true the append happens inline and its error reaches the tool call (`src/mcp/abw_mcp/audit.py:88-118#emit`, `src/mcp/abw_mcp/config.py:149-150#audit_fail_closed`). The default is false.
- **Configured.** Every server identity except the vendor mock holds Storage Blob Data Contributor, scoped to the `worm-audit` container only (`infra/03-platform.bicep:546-556#raAuditAppend`).
- **Platform behaviour.** With `allowProtectedAppendWrites` an append blob can keep growing under the policy, and its effective retention is the time of its last append plus the interval; an unlocked time-based policy lets the property be switched on and off at any time (https://learn.microsoft.com/azure/storage/blobs/immutable-container-level-worm-policies). An unlocked time-based policy can be modified or deleted (https://learn.microsoft.com/azure/storage/blobs/immutable-policy-configure-container-scope). The role description is "Read, write, and delete Azure Storage containers and blobs" (https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/storage#storage-blob-data-contributor).
- **Designed.** "Demonstrates the pattern, not a compliance attestation": a compliance-grade deployment needs a locked policy and legal advice (`DESIGN.md:239#WORM`).
- Trade-off / limitation (**Inference** from the three Learn points above): the identity that writes the audit blob can also delete it, and the only protection is a 1-day policy that can be changed or deleted. The immutability therefore matters only inside that window and only against callers who hold the role; it gives no protection against anyone who controls the storage account.

**Cosmos.** **Platform behaviour:** when a container has no TTL property, items never expire (https://learn.microsoft.com/azure/cosmos-db/time-to-live). Orders written by the demo therefore stay until someone deletes them.

**Foundry trace content.** **Platform behaviour:** the `genAIContent` table appears as `AppGenAIContent` and carries seven attributes, among them `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result`. It can be made a protected table that only holders of Privileged Monitoring Data Reader can read (https://learn.microsoft.com/azure/azure-monitor/app/data-model-complete#generative-ai-telemetry, https://learn.microsoft.com/azure/azure-monitor/reference/tables/appgenaicontent, https://learn.microsoft.com/azure/azure-monitor/logs/protected-tables-configure). **Configured:** the Foundry template grants the project's managed identity Log Analytics Reader and Privileged Monitoring Data Reader on the App Insights component, with the description that the second role is needed to query GenAI content (`infra/foundry/modules-network-secured/application-insights-role-assignment.bicep:1-30#roleDefinitionGuids`, `infra/foundry/main.bicep:602-610#applicationInsightsRoleAssignment`).

#### 10.6.3 What is and is not persisted

| Item | Persisted? | Form | Citation |
|---|---|---|---|
| The bearer token | No. Only its identifier | `jti` holds the `uti` value. `Caller.token` is excluded from `repr`, so it cannot leak through a log line that prints the object | `src/mcp/abw_mcp/auth.py:30-41#Caller` |
| Tool arguments | No. Only a hash | `args_sha256`, a SHA-256 of the arguments' canonical JSON. DESIGN.md: "Never log tool arguments or document content" | `src/mcp/abw_mcp/audit.py:178-216#build_event`, `DESIGN.md:141#hash` |
| Tool results and document content | No. Only a size | `result_bytes` | `src/mcp/abw_mcp/audit.py:178-216#result_bytes` |
| Caller identity | Yes | `user_oid`, `user_upn`, `tid`, `roles`, `scp`, `azp`, `aud`, `jti` in every audit row that has a caller: personal data. `auth_failed` rows, and every row from the legacy and vendor servers (which never set a caller), carry no user fields | `src/mcp/abw_mcp/audit.py:178-216#user_upn`, `src/mcp/abw_mcp/auth.py:244-248#current_caller` |
| Client IP | Yes, at the gateway only | APIM logs the client IP (`logClientIp`); `AbwGateway` exposes it and rules ABW-004 and ABW-009 map it to an IP entity. Entra rows in the chain keep city and country, never the IP | `infra/05-apim.bicep:92-137#logClientIp`, `DESIGN.md:170#tokenIds` |
| HTTP bodies at the gateway | No | Body capture is 0 bytes on all four legs | `infra/05-apim.bicep:92-137#diagAppi` |
| Foundry agent content | Yes, outside the MCP server's control | Tool-call arguments and results as span attributes, in App Insights. The KQL reads results (to find the request id) and the first 100 characters of arguments from `AppDependencies` properties | `observability/kql/AbwFullChainCore.kql:19-25#toolRid`, `observability/kql/AbwFullChainCore.kql:137-148#tools` |
| Demo Console run records | In memory; non-secret facts on disk | Trace store (40 runs), `.state.json` with request ids and the last violation run | `console/e2e.py:249-267#_TRACE_MAX`, `console/jobs.py:81-90#save_state` |

**Why hash and size.** Hashing lets an auditor prove that a stored argument set matches a call without the log ever holding the argument. Trade-off / limitation: a SHA-256 of a low-entropy argument (a ticker, a quantity) can be reversed by guessing, so the hash is evidence of integrity, not anonymisation; and the identity fields make the audit trail itself personal data that inherits the workspace retention (30 days by default, see the first row of the table in 10.6.1) and the blob rules above.

**Moving target.** **Platform behaviour:** before October 31, 2026 the seven GenAI attributes go to both the existing tables and `AppGenAIContent`; from that date new data in `AppDependencies`, `AppTraces` and `AppEvents` keeps the keys but the values become a short pointer to `AppGenAIContent` (https://learn.microsoft.com/azure/azure-monitor/app/data-model-complete#generative-ai-telemetry). `AbwAgentActivity` and `AbwIdentityChain` already read `AppGenAIContent` (`observability/kql/AbwAgentActivity.kql:7#AppGenAIContent`, `observability/kql/AbwIdentityChain.kql:5#AppGenAIContent`); `AbwFullChainCore` still reads the tool result and arguments from `AppDependencies` (`observability/kql/AbwFullChainCore.kql:23#gen_ai.tool.call.result`, `observability/kql/AbwFullChainCore.kql:146#gen_ai.tool.call.arguments`), so its request-id bridge and its "args ..." detail would stop working after that date (Findings).

**Key takeaways**

- Logs arrive in stages and the repo states a lag per hop. The console never blocks on them, never fills a gap, and words every unfinished row by the age of the run: waiting, still missing, or not found.
- The Refresh job is read-only, so it can be pressed freely; its trace store is 40 runs in memory and is lost on restart.
- Three exceptions break the request-id thread: the guardrail row (trace id only, as with the tool discovery, Foundry agent and Foundry model rows, whose request id column is also empty), the Entra rows (token id and session id only, from an optional export workspace) and the private server (no APIM, so no gateway row, no kill switch and a caller-chosen id).
- The 35-day API time range is a trade made so Entra rows that are days old stay visible; it is above Learn's 15-day guidance and caps the KQL's 90-day sign-in look-back.
- Retention is one workspace default of 30 days for the logs (Learn gives the Application Insights tables 90 days by default, so those may keep longer), 7-day soft delete for blobs and Key Vault, and no TTL on Cosmos. The audit container's 1-day policy is unlocked: it shows the pattern and is not a compliance control.
- The MCP server never stores a token, an argument or a result. It stores the token id, an argument hash, a result size and the caller's identity claims, which are personal data. Foundry's own traces can hold arguments and results outside the server's control.
