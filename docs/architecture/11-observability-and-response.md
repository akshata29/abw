## 11. Observability, detection and response

ABW's observability is a pack rather than a product: ten KQL functions saved in the Log Analytics workspace, nine scheduled Microsoft Sentinel analytics rules that call those functions, three operational alert rules and one workbook. One Bicep stage deploys all four (`infra/06b-observability.bicep:1-14`, `README.md:82#observability`). This section lists what is recorded and where (11.1), the ten functions (11.2), the nine rules and how they become incidents (11.3), the cockpit workbook (11.4), the three alert rules (11.5), the optional tenant-level portal features that sit beside the pack (11.6) and how one decision is proven from logs alone (11.7). Which key joins which record, and how `AbwFullChain` stitches the rows, is section 10 (10.2 and 10.3) and is only cited here. The controls whose refusals the rules watch are sections 6 and 7, the MCP audit event is section 8, and the console that queries the pack is section 12.

Provenance labels as in section 10: **Implemented** (code), **Configured** (Bicep, policy XML, JSON), **Designed** (DESIGN.md or docs), **Platform behaviour** (a Microsoft Learn page, linked in the text), **Inference** (my own deduction, labelled as such).

### 11.1 Telemetry sources and tables

What this section proves: every ABW query reads from one workspace, but only some of the logs that workspace receives are queried. The map below shows which, and the couplings after it show the two places where a quiet configuration change would blind detection (`infra/05-apim.bicep:154-173#apimDiag`, `observability/kql/AbwMcpAudit.kql:4-9#ContainerAppConsoleLogs`).

#### 11.1.1 One workspace, one Application Insights component

The platform stages do not create a workspace. The Foundry stage receives the workspace and component names from `deploy.ps1` (`scripts/deploy.ps1:268-269#logAnalyticsName`) and the vendored Foundry template creates both: a `PerGB2018` workspace with 30-day retention and a workspace-based Application Insights component linked to it (`infra/foundry/modules-network-secured/application-insights.bicep:33-42#PerGB2018`, `infra/foundry/modules-network-secured/application-insights.bicep:44-55#appInsights`). The platform, governance and observability templates then reference both as `existing` (`infra/03-platform.bicep:65-70#appi`, `infra/06-governance.bicep:34#existing`, `infra/06b-observability.bicep:36#existing`). **Configured.**

Four consequences follow.

- **One query surface.** Every table in 11.1.2 sits in the same workspace, so the ABW functions join them with no cross-workspace expression. Only the optional Entra sign-in export is read from a second workspace. Platform behaviour: querying several workspace-based Application Insights components that share a workspace needs no cross-workspace query (https://learn.microsoft.com/azure/azure-monitor/logs/cross-workspace-query).
- **One workspace default.** The 30 days set in the vendored file are the workspace default, and no table-level retention exists anywhere in `infra/` (**Configured**, `infra/foundry/modules-network-secured/application-insights.bicep:40#retentionInDays`; **Inference** for the absence of overrides, from a search of every Bicep file). Platform behaviour: a table can carry its own retention, otherwise the workspace value applies; Learn lists the Application Insights tables, `AppTraces` and `AppDependencies` among them, as keeping 90 days by default and adjustable per table, so those tables may keep longer than 30 days (https://learn.microsoft.com/azure/azure-monitor/logs/data-retention-configure). Changing retention therefore means editing a vendored module or changing the workspace after deployment (see Findings).
- **One component, three producers.** The same component receives APIM telemetry, the MCP servers' SDK telemetry and Foundry's agent traces, which is why `AbwFullChainCore` separates the APIM rows by `AppRoleName` (`observability/kql/AbwFullChainCore.kql:11-19#AppRoleName`).
- **Ingestion is not private-only.** `deploy.ps1` passes ingestion access mode `Open` and public ingestion enabled to the Foundry stage, and the component accepts public queries (`scripts/deploy.ps1:270-272#amplsIngestionAccessMode`, `infra/foundry/modules-network-secured/application-insights.bicep:51-52#publicNetworkAccessForQuery`). The Foundry connection that carries the traces is keyed (auth type `ApiKey`); the governance template exempts it from the "no keyed connections" policy as Mitigated, stating that the key is write-only and the workspace is queried with Entra ID (`infra/foundry/modules-network-secured/application-insights.bicep:57-64#authType`, `infra/06-governance.bicep:258-271#appiReason`). **Configured.**

#### 11.1.3 Four couplings that decide what the pack can see

1. **Detection reads the stdout copy of the audit event, not the SDK copy.** The default audit service has two sinks: stdout (which also logs through the `abw.audit` logger) and the append blob (`src/mcp/abw_mcp/audit.py:219-223#build_default_audit_service`). Every ABW function and rule that needs the MCP audit event reads it through `AbwMcpAudit`, which reads the console path (`observability/kql/AbwMcpAudit.kql:4-9#ContainerAppConsoleLogs`); none reads `AppTraces`. Trade-off / limitation: if the Container Apps diagnostic settings (`diagCaePriv`, `diagCaePub`) were removed, `AbwMcpAudit` would return nothing and every function or rule that reads it, directly or through another function, would lose those rows, while the SDK copy kept arriving in Application Insights (**Inference**). `DESIGN.md:134` describes the audit event but not this dependency.
2. **Gateway decisions live in the `trace` record and depend on severity.** Platform behaviour (https://learn.microsoft.com/azure/api-management/trace-policy): a `trace` policy writes telemetry only when its severity is at or above the diagnostic setting's verbosity, and Application Insights sampling does not affect it. All three trace elements use `information` (`infra/apim/policies/mcp-jwt.policy.xml:57-63#abw-gateway`, `infra/apim/policies/agent-frontdoor.policy.xml:62-70#abw-gateway`, `infra/apim/policies/agent-frontdoor.policy.xml:145-159#abw-gateway`) and both diagnostics use verbosity `information` (`infra/05-apim.bicep:102#verbosity`, `infra/05-apim.bicep:149#verbosity`), so they are recorded (**Configured**). `AbwGateway` reads the decision, reason and user object id from the first record of `TraceRecords`; on the agent front door, a second record (`decision=deny:<reason>`) overrides the decision and reason for a late refusal, a 403 token quota or a 429 rate limit (`observability/kql/AbwGateway.kql:7-10#TraceRecords`, `infra/apim/policies/agent-frontdoor.policy.xml:142-157#abw-gateway`). **Inference:** raising the verbosity to `warning` or `error` would leave those columns empty, and ABW-004 and ABW-005, which filter on `Reason`, would never fire.
3. **Two custom metrics, one of them unused.** The decision metric `abw-gateway-decisions` (dimensions server, decision, reason, oid) is emitted by both gateway policies (`infra/apim/policies/mcp-jwt.policy.xml:51-56#abw-gateway-decisions`, `infra/apim/policies/agent-frontdoor.policy.xml:56-61#abw-gateway-decisions`). No function, rule or workbook tile reads it; a search of `observability/`, `console/`, `demo/`, `docs/` and `infra/` finds the name only in a diagram generator. The token metric is read: `llm-emit-token-metric` in namespace `abw-agent` with dimensions oid, upn and agent feeds `AbwTokenUsage` (`infra/apim/policies/agent-frontdoor.policy.xml:97-101#llm-emit-token-metric`, `observability/kql/AbwTokenUsage.kql:4-6#azure.ai_gateway.client.token.usage`). Platform behaviour (https://learn.microsoft.com/azure/api-management/emit-metric-policy): custom metrics with dimensions must be enabled in Application Insights (the diagnostic sets `metrics: true`, `infra/05-apim.bicep:105#metrics`); a policy may have at most five custom dimensions; each dimension is limited to 100 unique values and each namespace to 1,000 active time series, and beyond that new values are silently discarded. **Inference:** the same limits apply to `llm-emit-token-metric` (the Learn page names its sibling `azure-openai-emit-token-metric`), so the per-user cost view would stop counting new users once the cap is reached (see Findings).
4. **GenAI content can be made a protected table; this repo does not do so.** Platform behaviour (https://learn.microsoft.com/azure/azure-monitor/app/data-model-complete#generative-ai-telemetry, https://learn.microsoft.com/azure/azure-monitor/logs/protected-tables-configure, https://learn.microsoft.com/azure/azure-monitor/reference/tables/appgenaicontent): `AppGenAIContent` can be set as a protected table, which makes it visible only to holders of Privileged Monitoring Data Reader, and from 2026-10-31 new content in `AppDependencies`, `AppTraces` and `AppEvents` keeps its attribute keys but the values become a pointer. A search of `infra/`, `scripts/` and `docs/` finds no protection-level setting (**Inference**). The Foundry template grants Log Analytics Reader and Privileged Monitoring Data Reader to the Foundry project identity, with the description that the second role is needed to query GenAI content (`infra/foundry/modules-network-secured/application-insights-role-assignment.bicep:14-31#roleDefinitionGuids`). The same search finds the Privileged Monitoring Data Reader role only in that module, so if the table is protected in a deployed workspace (none was read), whoever runs `AbwAgentActivity` or `AbwIdentityChain` needs the role granted outside this repo (**Inference**). `AbwFullChainCore` still reads tool arguments and results from `AppDependencies` (`observability/kql/AbwFullChainCore.kql:20-25#toolRid`), which is the part that the 2026-10-31 change affects (see Findings).

### 11.2 The ten KQL functions

What this section proves: the pack is ten functions with one header contract, deployed as saved functions in the workspace, and most other consumers (rules, workbook, console, CLI) call those functions rather than repeating the logic; a few console probes and one workbook tile query tables directly (`observability/kql/pack.py:32-35#_META`, `infra/06b-observability.bicep:40-57#savedSearches`, `DESIGN.md:169-172`, `console/e2e.py:87-95#Q_SPANS`, `observability/workbook/build_workbook.py:382-390#SecurityIncident`).

#### 11.2.1 How the pack is built and deployed

- **File contract (Implemented).** Each `.kql` file starts with `// @function`, `// @params` and `// @description` on lines 1 to 3; only `AbwFullChain` adds `// @fallback` on line 4. `pack.py` reads these keys with one regular expression, only before the body starts (`observability/kql/pack.py:32-35#_META`, `observability/kql/pack.py:52-75#load_pack`, `observability/kql/AbwFullChain.kql:1-4#fallback`).
- **Ordering (Implemented).** `_dependency_order` places a function after every other function whose name appears followed by `(` in its body, and stops with "circular function dependency" if none can be placed (`observability/kql/pack.py:78-94#_dependency_order`). `cmd_build` writes the result to `pack.json` (`observability/kql/pack.py:125-131#cmd_build`).
- **Deployment (Configured).** Bicep loads `pack.json` and creates one workspace saved search per function: name `abw-<name>` in lower case, category `ABW Agent Wall`, `functionAlias` equal to the function name, `functionParameters` from `@params`, `version: 2`, and `etag: '*'` so a redeployment overwrites an existing function. `@batchSize(1)` deploys them one at a time because the workspace validates each query when it is saved, so a dependent function needs its dependencies to exist already (`infra/06b-observability.bicep:40-57#savedSearches`).
- **Entra rows (Configured).** With an export workspace id, Bicep replaces the two lines `= AADNonInteractiveUserSignInLogs;` and `= SigninLogs;` in `AbwFullChain` with `workspace('<id>')`-prefixed forms. With no id, the deployed `AbwFullChain` is its `@fallback`, the core function with the token column dropped (`infra/06b-observability.bicep:33-34#entraPrefix`, `infra/06b-observability.bicep:52#replace`, `observability/kql/pack.py:102-113#deploy_body`). A deployment without the export therefore returns the same rows without any marker that Entra rows are missing (see Findings).
- **Local runs (Implemented).** `let_prelude` turns every function into a local `<Name>_L` copy and `_localize` points calls at those copies, so a developer can test an edit without overwriting the deployed function; `check` runs one probe call per function (`observability/kql/pack.py:97-99#_localize`, `observability/kql/pack.py:116-122#let_prelude`, `observability/kql/pack.py:38-49#_CHECK_CALLS`).
- **Platform behaviour.** Learn notes that cross-resource queries do not support parameterized functions or functions whose definition includes `workspace()`-style expressions (https://learn.microsoft.com/azure/azure-monitor/logs/cross-workspace-query). `AbwFullChain` is parameterized and, with an export workspace, contains such an expression; ABW calls it from its own workspace, which is not the documented cross-resource case (**Inference**), but it is the first thing to check if the Entra rows stay empty.

#### 11.3.2 From query result to incident

1. **Author and check (Implemented).** One file per rule. Header keys are `@id`, `@name`, `@severity`, `@tactics`, `@frequency`, `@period`, `@group`, `@entity`, `@details` and `@description`; the query starts on line 11. `@id` is the stable key from which the rule's resource GUID is derived. `load_rules` splits `@entity` into `Type.identifier=column` mappings, builds the `@details` dictionary and defaults `@group` to `AnyAlert`; `cmd_build` writes `rules.json`; `cmd_check` runs every query against the workspace for 24 hours, or for 720 hours with `--wide`, which rewrites each `(Nm)` or `(Nh)` window to `(30d)` (`observability/sentinel/build_rules.py:1-18#GUID`, `observability/sentinel/build_rules.py:36-72#load_rules`, `observability/sentinel/build_rules.py:75-80#cmd_build`, `observability/sentinel/build_rules.py:82-98#cmd_check`).
2. **Deploy (Configured).** Bicep creates one `Microsoft.SecurityInsights/alertRules` resource of kind `Scheduled` per entry, named by a GUID of the workspace id and the rule id, so a redeployment updates in place. It depends on the Sentinel onboarding and on the functions, because every rule calls a function (`infra/06b-observability.bicep:60-70#onboardingStates`, `infra/06b-observability.bicep:102-105#dependsOn`).
3. **Run (Configured).** `queryFrequency` and `queryPeriod` come from the rule, `triggerOperator` is `GreaterThan` and `triggerThreshold` is 0, so any result row triggers (`infra/06b-observability.bicep:77-82#queryFrequency`).
4. **Alert (Configured).** `eventGroupingSettings.aggregationKind` is `AlertPerResult`: each result row becomes its own alert, carrying the entity mappings and the custom details (`infra/06b-observability.bicep:84-88#AlertPerResult`). Platform behaviour: custom details are stored on the alert's `ExtendedProperties`, up to 20 per rule, and a scheduled rule produces at most 150 alerts per run (https://learn.microsoft.com/azure/sentinel/surface-custom-details-in-alerts, https://learn.microsoft.com/azure/sentinel/scheduled-rules-overview).
5. **Incident (Configured).** `createIncident` is true, with grouping enabled, a five-hour grouping window and `reopenClosedIncident` false. For rules with `@group Account` the matching method is `Selected` on the `Account` entity, so alerts for the same person fold into one incident; otherwise it is `AnyAlert`, so every alert of that rule inside the window folds into one incident (`infra/06b-observability.bicep:89-101#createIncident`, `observability/sentinel/build_rules.py:1-18#GUID`). Platform behaviour: `Selected` groups alerts that share the selected entities and details, `AnyAlert` groups all alerts of the rule, and the reopen switch decides whether a late alert reopens a closed incident or opens a new one (https://learn.microsoft.com/azure/sentinel/create-analytics-rules).
6. **Title prefix (Configured, Inference).** The deployed display name is `ABW - ` followed by the rule name, and the rule names already begin with `ABW-00N`, so the alert and the incident in the Azure portal read "ABW - ABW-001 Information-barrier violation attempt (Wall MCP)". No alert-details override exists in the template, so the alert name is the display name (`infra/06b-observability.bicep:72#displayName`, https://learn.microsoft.com/azure/sentinel/customize-alert-details). The Defender portal shows the incident without the `ABW - ` prefix in the repo's own playbook (`docs/PROOF-PLAYBOOK.md:1194#Defender`); the workbook finds incidents with a title that starts with `ABW` (`observability/workbook/build_workbook.py:381-391#SecurityIncident`), and `AbwFullChainCore` matches incidents by alert id and not by title (`observability/kql/AbwFullChainCore.kql:264-272#alertIds`). Do not build automation on the title text.

#### 11.3.3 Timing, limits and trade-offs

- **Latency.** Platform behaviour: Learn describes a five-minute delay that Sentinel applies to scheduled queries to allow for ingestion latency (https://learn.microsoft.com/azure/sentinel/scheduled-rules-overview, https://learn.microsoft.com/azure/sentinel/ingestion-delay). Designed and observed: the docs give about 5 minutes of rule lag, about 8 minutes from refusal to incident and about 13 minutes for ABW-007 (`DESIGN.md:171`, `DESIGN.md:247`, `docs/RUNBOOK.md:345`); the playbook records Sentinel alerts after 5 to 15 minutes and, for one ABW-001 run, only at 22 minutes (`docs/PROOF-PLAYBOOK.md:605#Sentinel`, `docs/PROOF-PLAYBOOK.md:730#ABW-001`). The numbers differ between documents (see Findings).
- **Look-back versus ingestion delay (Inference).** The rule functions filter on `TimeGenerated` inside the look-back, so an event that arrives later than the window allows is never evaluated. ABW-007 alone uses a one-hour window; its source is the Storage resource log, which Learn places at the slow end of resource-log latency (see 11.1.2), so the longer window is the plausible reason (the code does not say).
- **Inert suppression.** `suppressionEnabled` is false while `suppressionDuration` is `PT1H`, so the duration has no effect (`infra/06b-observability.bicep:81-82#suppressionEnabled`).
- **Bounded noise.** ABW-006 drops anonymous data-plane denials and needs three denials in the window, and ABW-009 needs five throttled calls, so single events from those layers do not open incidents (`observability/sentinel/abw-006-repeated-denials.kql:1-16#3-data-plane`, `observability/sentinel/abw-009-throttled-burst.kql:1-15#Throttled`).
- **Defender-raised alerts.** Alerts from connected Defender products enter the same incident queue and appear in step 11 of the full-chain card only if an id of the run appears in their extended properties; 11.6 covers that path.

#### 11.4.3 Behaviour notes

- **Time range.** The global `TimeRange` defaults to 7 days and offers 1 hour, 6 hours, 24 hours, 3, 7, 14 and 30 days plus a custom range (`observability/workbook/build_workbook.py:657-700#allowCustom`). Four charts bin on `{TimeRange:grain}` (`observability/workbook/build_workbook.py:159-174#grain`, `observability/workbook/build_workbook.py:393-403#grain`, `observability/workbook/build_workbook.py:443-452#grain`, `observability/workbook/build_workbook.py:521-530#grain`). Platform behaviour: choosing a time-range parameter in a query's Time Range selector binds the chart to it, and it expands as `{TimeRange}` in the query text (https://learn.microsoft.com/azure/azure-monitor/visualize/workbooks-parameters). **Inference:** for a tile that calls a function, the data shown is the intersection of the picked range and the function's own 30-day look-back, so a custom range wider than 30 days cannot reach further back; `th-incidents` calls no function, so only the picked range bounds it (`observability/workbook/build_workbook.py:382-390#SecurityIncident`).
- **One parameter drives the tabs.** The link bar writes the hidden parameter `tab`, and each group is visible only for its value (`observability/workbook/build_workbook.py:700-728#LinkItem`, `observability/workbook/build_workbook.py:117-124#conditionalVisibility`). Platform behaviour: a links step outputs a parameter for the selected tab, and a parameter is usable only downstream of where it is set (https://learn.microsoft.com/azure/azure-monitor/visualize/workbooks-parameters). That is why the global parameters item is the first item after the title.
- **One drill-down.** `id-recent` exports the clicked row's `RequestId`; `id-chain` stays hidden while it is "none" and then runs `AbwFullChain('{RequestId}', 30d)` (`observability/workbook/build_workbook.py:238-270#RequestId`). The call has two arguments, so it carries no token ids: for a call refused at the gateway before any MCP server logged a token, the Entra rows cannot be reached from the workbook, which is what the third argument is for in the console (`console/e2e.py:138-140#_sent_tokens`). **Inference.**
- **Resource Graph tiles are live.** They have no time context, so governance, key posture and changes show the state at refresh time. The changes tab says "last 14 days" in its own text, and the query has no time filter of its own, so the window comes from the Resource Graph change store (`observability/workbook/build_workbook.py:625-640#ch-text`). **Inference.**
- **The incident tile is a title filter.** `th-incidents` lists only incidents whose title starts with `ABW` (`observability/workbook/build_workbook.py:382-390#startswith`). The rules produce titles of that shape (11.3), so they match. An incident created from another source, for example from Defender for Cloud alerts (11.6), appears only if its title starts with `ABW`, which this repo does not arrange. **Inference.**

### 11.5 The three operational alert rules

What this section proves: platform-health alerts are a separate, deliberately small set. They page on MCP server errors, gateway or backend failures and agent-run failures that are not guardrail stops, and they share one action group and one schedule (`infra/06b-observability.bicep:109-122#opsActionGroup`, `infra/06b-observability.bicep:126-151#opsAlerts`, `infra/06b-observability.bicep:153-187#opsAlertRules`). They are not security detections: those are the nine Sentinel rules (11.3).

#### 11.5.1 The action group

One action group named `ag-abw-ops-eus2-001` (location `global`, short name `abw-ops`, enabled, common alert schema) carries the notifications. The deployment script passes `alertEmail` only when it is present in the generated configuration (`scripts/deploy.ps1:164#alertEmail`). **Configured.** **Inference:** with no address configured the three alerts still fire in the portal but notify nobody.

#### 11.5.3 Shared schedule and behaviour

Each rule is a `Microsoft.Insights/scheduledQueryRules` resource of kind `LogAlert`, named `alrt-abw-<key>-eus2-001`, scoped to the workspace, evaluated every 5 minutes (`PT5M`) over a 15-minute window (`PT15M`). The condition counts rows (`Count`, `GreaterThan` the threshold) with one failing period out of one, `autoMitigate` is true and every rule notifies the same action group. The rules declare `dependsOn` on the function deployment (`infra/06b-observability.bicep:185-187#dependsOn`); **Inference:** this orders them after the saved functions that two of their queries call (`infra/06b-observability.bicep:153-187#opsAlertRules`). **Configured.** The deployment script treats a failed observability stage as possibly caused by functions that are not yet resolvable: unless `-WhatIf` or `-NoWait` is given, it waits 120 seconds and retries the stage once (`scripts/deploy.ps1:168-174#waiting`). It passes `alertEmail` and `entraWorkspaceId` to the stage only when they are present and non-empty in the generated configuration (`scripts/deploy.ps1:164-166#entraWorkspaceId`). **Implemented.**

- Platform behaviour: an alert that resolves automatically is stateful, and for rules evaluated every 5 to 15 minutes it resolves after the condition has been unmet for three evaluation periods (https://learn.microsoft.com/azure/azure-monitor/alerts/alerts-create-log-alert-rule). **Inference:** `autoMitigate` is the template property behind that option, so one episode produces one notification and a 15-minute window evaluated every 5 minutes keeps a single bad row in scope for three evaluations.
- Platform behaviour: ingestion delay can make log alerts fire late (https://learn.microsoft.com/azure/azure-monitor/alerts/alerts-troubleshoot-log). The same latency as in 10.4 therefore applies: a fault is detected minutes after it happens, not at once.

Trade-off / limitation: all three rules count rows. If the Container Apps diagnostic setting or the APIM diagnostic stops, the counts stay at zero and no alert fires; this repo has no rule that fires on missing data (not in this repo; see Findings).

#### 11.6.2 Agent 365 and the APIM gateway

Platform behaviour (https://learn.microsoft.com/azure/api-management/agent-365): Agent 365 discovers API Management gateways and their MCP servers, shows a central inventory, can block and unblock MCP servers, and on supported tiers controls individual tools and shows runtime signals. Consent grants the "A365 MCP Gateway Policy Operator" Azure role at tenant level (read API Management resources, read and write API-scoped policies, discover subscriptions). A server block inserts a managed `return-response` policy at the beginning of the API's inbound policy and the gateway answers HTTP 403 `AccessBlockedByGateway`; a tool-level block returns HTTP 200 with a JSON-RPC `isError=true` result and exists only on the AI Gateway tier (preview). The v2 tiers support inventory and block or unblock only, v1 tiers are not supported, and dynamic allowed-tool lists are not supported for tool governance. Agent 365 does not route agents through a customer gateway on its own: the agent developer configures the gateway endpoint, and connectivity to the MCP server should be restricted so the gateway is the only permitted caller.

What this means for ABW:

- **The repo grants the role but cannot consent.** The script tries both role-name spellings and records the documented name; its header names only the shorter spelling, so the two sources disagree (see Findings). Status is set to `CONFIGURED-NOT-YET-OBSERVED` whenever the role assignment reads back; whether the role is also held at a root scope is recorded separately in `tenantLevelConsentObserved` (`scripts/extras-agent-identity.ps1:143-148#A365`, `scripts/extras-agent-identity.ps1:187#CONFIGURED-NOT-YET-OBSERVED`, `scripts/extras-agent-identity.ps1:200#tenantLevelConsentObserved`). **Implemented.**
- **The tier limits are written into the output.** The script notes that on the APIM Standard v2 tier only inventory and server block or unblock apply, and that the role includes write access to API policies and tool servers, which is how block policy reaches the gateway and why the grant is inert until the tenant-level setting is on (`scripts/extras-agent-identity.ps1:204-205#tierNote`). **Implemented.**
- **Proven live.** A block on the legacy server took effect at APIM within about 15 seconds and was reverted (`README.md:144#proven`, `DESIGN.md:240#Live`). **Designed** (recorded result, not re-run for this document).
- **A redeploy may undo a block.** `infra/05-apim-apis.bicep` writes each API policy from the policy XML as raw XML (`infra/05-apim-apis.bicep:149-155#rawxml`, `infra/05-apim-apis.bicep:195-200#rawxml`). **Inference:** re-running that stage replaces the policy document, so a managed block that Agent 365 inserted could be removed; the repo does not test this.
- **The private server is outside it.** The private MCP server is not behind APIM (10.5), so a gateway-level block cannot reach it, and Learn's advice to restrict connectivity to the gateway does not hold for it (`DESIGN.md:107`). **Inference.**
- **Not a replacement for ABW's own controls.** The kill-switch controls are the APIM named values and the persona or group removal described in 12.5 and sections 6 and 7; a static note in the script (one manual observation from the build session, n=1, which the script does not run again) concludes that disabling the agent identity is not a kill switch for the demo path, at most a soft lever, because tool calls reach APIM with the user's token (`scripts/extras-agent-identity.ps1:336-337#static`, `scripts/extras-agent-identity.ps1:343-347#identityLeverTest`).

Platform behaviour: Defender for Cloud's AI threat protection is generally available, works with Prompt Shields and Microsoft threat intelligence, supports Azure OpenAI models (text tokens only), needs the Owner role at subscription scope to enable and integrates with Defender XDR (https://learn.microsoft.com/azure/defender-for-cloud/ai-threat-protection). With `-ResimulateIfNotIngested` it creates them once more if samples exist in Defender but no Defender for Cloud row has been seen in `SecurityAlert` after `-ResimulateAfterMinutes` (default 5); this branch sits inside the polling loop, so it needs `-PollMinutes` greater than `-ResimulateAfterMinutes` (the default is 0) and runs at most once (`scripts/extras-defender-sentinel.ps1:49#PollMinutes`, `scripts/extras-defender-sentinel.ps1:448-453#resimulated`). **Implemented.**

### 11.7 Proving a decision with only logs

What this section proves: one allowed or refused call can be shown, hop by hop, from Azure's own logs, by one function call, and the console's card applies explicit rules about what it will and will not claim from a chain (`console/e2e.py:1654-1707#_refresh_fullchain`, `console/e2e.py:1434-1455#_chain_notes`). The join keys and the row-by-row walk are 10.2 and 10.3 and are only cited here.

#### 11.7.1 The recipe

1. **Pick a run that is at least 15 minutes old.** The card treats 15 minutes as maturity (`console/e2e.py:1521#_FC_MATURE_MIN`). The playbook tells the presenter to press Refresh from logs 12 or more minutes after the click and records Log Analytics at 2 to 18 minutes, the Entra rows usually 4 to 8 minutes after a fresh token and Sentinel incidents 5 to 22 (`docs/PROOF-PLAYBOOK.md:936#Refresh`).
2. **Copy the request id** from the result card; the card shows the request id and the trace id with Copy buttons (`docs/PROOF-PLAYBOOK.md:937#AbwFullChain`). The MCP request id echoed in the tool result (the "tool-call request_id" on the board), the front door request id or the W3C trace id returns the same run; Foundry's own `gen_ai.tool.call.id` is not accepted (`docs/PROOF-PLAYBOOK.md:937#AbwFullChain`, `observability/kql/AbwFullChainCore.kql:3#tool-call`, `observability/kql/AbwFullChainCore.kql:19-34#toolRid`); the function's first parameter is a single "any id" value (`observability/kql/AbwFullChainCore.kql:4#anyId`). The console accepts ids of 8 to 64 hex digits or hyphens (`console/e2e.py:97#_ID`).
3. **Set the Log Analytics time range to Last 30 days and run `AbwFullChain('<rid>', 3d)`.** The second argument is the look-back for the core rows; the Entra rows reach back further, which is why the portal range matters (`console/e2e.py:1526-1528#_FC_SCOPE`, `docs/PROOF-PLAYBOOK.md:35#AbwFullChain`).
4. **For a call the gateway refused, add the token id as a third argument.** The third parameter takes the `uti` claim values of the tokens that were sent, so the Entra rows appear even when no MCP server logged a token (`observability/kql/AbwFullChain.kql:5-7#tokenIds`, `console/e2e.py:138-140#_sent_tokens`). The card's "Show the query" text is built the same way and joins one call per id when the run made several (`console/e2e.py:147-151#_full_query`).
5. **Read the rows by layer** (below) and apply the wording rules in 11.7.3.

An approval run makes two front-door calls, so it has two request ids and two trace ids; the console merges up to three chains into one time-ordered list, each row once (`console/e2e.py:131-135#_chain_ids`, `console/e2e.py:1564-1576#_fc_merge`, `docs/PROOF-PLAYBOOK.md:937#AbwFullChain`). Rows to expect: a person's run 3 to 6, an operator's agent run 15 to 30 (`docs/PROOF-PLAYBOOK.md:937#AbwFullChain`). The same chain is reachable in the cockpit through the Identity chain tab (11.4.2).

| The server read first, then refused on what it found | The MCP deny row itself records a successful downstream read before the refusal (no separate read row) | The note that a rule applied to what it found, not a missing role | `console/e2e.py:1434-1455#_chain_notes`, `console/e2e.py:1428#_READ_OK` |
| No model was involved | No "Foundry agent" row, in a non-agent scenario | The note "No Foundry hop" is added only for a direct, non-agent call | `console/e2e.py:1434-1455#_chain_notes` |
| Sentinel raised an incident | "Sentinel alert" and "Sentinel incident" | Badges ALERT and INCIDENT; due 9 to 13 minutes after the click | `console/e2e.py:1578-1606#_fc_verdict`, `console/e2e.py:1634-1651#_fc_waiting` |

The row sources and join keys behind these layers: front door `observability/kql/AbwFullChainCore.kql:55-66#frontdoor`, gateway tool call `observability/kql/AbwFullChainCore.kql:67-78#apimTool`, guardrail `observability/kql/AbwFullChainCore.kql:83-113#guardPoints`, agent `observability/kql/AbwFullChainCore.kql:114-125#agent`, model `observability/kql/AbwFullChainCore.kql:126-136#model`, Foundry tool call `observability/kql/AbwFullChainCore.kql:137-148#tools`, MCP audit `observability/kql/AbwFullChainCore.kql:149-160#mcpRows`, Storage `observability/kql/AbwFullChainCore.kql:175-187#storage`, Search `observability/kql/AbwFullChainCore.kql:196-217#searchRows`, Cosmos DB `observability/kql/AbwFullChainCore.kql:218-237#cosmosRows`, policy error `observability/kql/AbwFullChainCore.kql:238-248#policy`, Sentinel `observability/kql/AbwFullChainCore.kql:249-281#incidents`, Entra `observability/kql/AbwFullChain.kql:55-100#loginRows`. **Implemented.**

#### 11.7.3 What the card claims, what it refuses to claim

- **It claims only what a row says.** Badges are read from each row's own words (outcome, decision, status code, guardrail verdict) and never guessed (`console/e2e.py:1578-1606#_fc_verdict`).
- **It will not call a missing hop "not logged" too early.** `_fc_waiting` lists the hops the click says should exist and the logs have not delivered. Before 15 minutes the message says logs land in stages and to press Refresh or present an older run; after 15 minutes it says "Still missing ... Do not present those hops as logged for this run" (`console/e2e.py:1634-1651#_fc_waiting`).
- **It states its own limits, and only where they apply.** The scope text is built from the rows present. When Entra rows are present, or a token id has no Entra row yet, it explains that Entra exports a token row 4 to 8 minutes after issue and that a token is reused until it expires (so the sign-in can be days older than the run); when no token id is known it says so instead, and when the Entra export could not be read it says that. It adds that Search and Cosmos DB rows are matched to the MCP call by time because their logs carry no caller id (Storage is matched by request id) only when such a row exists, and that the MCP audit row is written when a call finishes (so it can sit after the data-plane row it caused) only when a data-plane row is listed before the MCP server row (`console/e2e.py:1526-1532#_FC_MATCHED`, `console/e2e.py:1698-1703#_fc_audit_after_data`).
- **It does not hide a failed Entra read.** When the Entra export cannot be read it falls back and says the chain has no Entra rows, with a short reason scrubbed of subscription paths and GUIDs (`console/e2e.py:1525#_FC_RESOURCE`, `console/e2e.py:1629-1632#_fc_why`).
- **Presenter wording.** The playbook says never to claim a Defender alert for a blocked prompt and to say "it stopped this prompt every time we tried it", never "always", because Prompt Shields is a classifier (`docs/PROOF-PLAYBOOK.md:504#Defender`, `docs/PROOF-PLAYBOOK.md:822#always`). It also says Sentinel and Defender silence is the healthy answer for an in-policy run (`docs/PROOF-PLAYBOOK.md:869#GOOD`). **Designed.**

What the card claims and does not is also written down for the presenter (`docs/PROOF-PLAYBOOK.md:939#reportOnlyInterrupted`).

#### 11.7.4 Landing order and the fallback ladder

The stages the card waits for, in the order it checks them (`console/e2e.py:1634-1651#_fc_waiting`):

| Hop | Expected after the click or token | When the card treats it as due |
|---|---|---|
| Entra token row | usually 4 to 8 minutes after the token is issued | The Entra read did not fail, and a token id known from the MCP row or sent by the console has no Entra token row (`entra_missing`) |
| APIM gateway row | about 1 minute | The gateway light is pass or block, and neither an "APIM front door" nor an "APIM gateway" row is present |
| Foundry spans | 1 to 5 minutes | The scenario is an agent run, the guardrail light is neither skipped nor not applicable, and no Foundry row is present |
| MCP server audit row | 6 to 10 minutes | The MCP light is pass or block and no "MCP server" row is present |
| Data-plane row | 2 to 8 minutes | The data light is pass or block, the traced call is one that reads Azure Storage (or no tool is known), and no data-plane row is present |
| Sentinel alert and incident | 9 to 13 minutes | The Sentinel light is "due" and no alert or incident row is present |

The Storage condition exists because only Storage reads leave a row under the request id; Search, Cosmos DB and the vendor feed do not, so a missing data-plane row is not called missing for them (`console/e2e.py:761-767#_storage_hop`). The message depends on the age of the click: under 15 minutes it says "Logs land in stages, so this chain is still filling in" and lists what has not arrived, and from 15 minutes it says "Still missing ... Do not present those hops as logged for this run" (`console/e2e.py:1521#_FC_MATURE_MIN`, `console/e2e.py:1648-1651#_FC_MATURE_MIN`). **Implemented.**

Ladder (`console/e2e.py:1654-1707#_refresh_fullchain`): the console asks `AbwFullChain` for each front-door id (up to three) through its pool of three workers, over a time span of 35 days (`console/e2e.py:1522#_FC_SPAN_DAYS`, `console/e2e.py:1663#_FC_SPAN_DAYS`). If a call errors it asks `AbwFullChainCore` over 3 days, which has every row except the Entra ones, and tells the viewer the Entra read failed (`console/e2e.py:1661-1675#Q_FULL_CORE`). If both return nothing it shows the identity chain card instead (`console/e2e.py:1675-1683#_emit_identity_chain`). The data-plane replay always uses the identity chain, because 14 days of full chain takes about 50 seconds (`console/e2e.py:126-128#_replay`). The call-count and the identity chain function are 10.3 and 11.2. **Implemented.**

The latency figures are not consistent across the repo: for Sentinel, the playbook gives 5 to 15 minutes in one place (with one run recorded at 22) and 9 to 13 in the stage list that the card's waiting line also uses; for Log Analytics, the playbook and the console give "5 to 10" in some places and "2 to 18" in others. See Findings and the platform figures in 10.4 (`docs/PROOF-PLAYBOOK.md:605#Sentinel`, `docs/PROOF-PLAYBOOK.md:938#Sentinel`, `console/e2e.py:782#usually`, `console/e2e.py:1643#Sentinel`).

#### 11.7.5 The two-minute portal path, and what logs alone cannot prove

The portal path the presenter uses: summarise `AbwDenials(24h)` by layer, then run `AbwIdentityChain('<rid>', 3d)` for one allowed and one refused id, then show the full chain on a run at least 15 minutes old with the portal range on Last 30 days (`docs/PROOF-PLAYBOOK.md:964#AbwDenials`, `docs/PROOF-PLAYBOOK.md:124#Azure`).

Limits of a logs-only proof:

- **Latency.** A missing row is evidence of absence only once the stage's delay has passed (11.7.4, and Learn's figures in 10.4).
- **Entra rows depend on an optional workspace.** With no export workspace configured, `AbwFullChain` is a copy of the core function, so the Entra rows can never appear; the console would then keep listing "the Entra token row" as still missing after 15 minutes (**Inference** from `console/e2e.py:1634-1651#_fc_waiting` and `console/e2e.py:1698#entra_missing`; deployment choice at `infra/06b-observability.bicep:52#entraWorkspaceId`).
- **A failed sign-in has no token,** so it has no Entra row in the chain; Sentinel does not see Entra sign-ins in this build because the Entra data connector is a tenant-level setting that was left alone, and the board reads Entra's own log through Graph instead (`docs/PROOF-PLAYBOOK.md:500#SigninLogs`).
- **Arguments are hashed.** The audit row proves which tool and which decision, not the argument values (10.1).
- **Search and Cosmos DB rows are time-matched,** so a busy minute can attach a neighbour's row (10.3).
- **No alert is guaranteed.** Neither Defender nor the rules are promised for every refusal. The playbook's example, a gateway 403 for a missing role, is below the ABW-006 threshold of three denials per identity in 30 minutes, and no other rule keys on that reason; ABW-001, ABW-002, ABW-003, ABW-004, ABW-005, ABW-007 and ABW-008 each fire on one matching event (every rule alerts on any row it returns), and ABW-009 needs five throttled calls (`docs/PROOF-PLAYBOOK.md:1104#BELOW`, `observability/sentinel/abw-006-repeated-denials.kql:11-15#Denials`, `infra/06b-observability.bicep:79-80#triggerThreshold`).

**Key takeaways**

- The cockpit workbook is generated from `build_workbook.py` (31 queries: 24 Log Analytics, 7 Resource Graph), calls eight of the ten pack functions directly (all but `AbwFullChainCore` and `AbwIdentityChain`; the nine rules call three of them: `AbwMcpAudit`, `AbwGateway` and `AbwDenials`), and is deployed as a shared workbook with three deploy-time placeholders; it has eight tabs and one drill-down that opens the full chain for a clicked request id.
- Resource Graph tiles show live state, not a time range; the incident tile filters on the `ABW` title prefix.
- Three platform-health alert rules (severity 2, 2 and 3) run every 5 minutes over a 15-minute window and notify one action group, which has a receiver only if an address was configured. They count rows, so a stopped feed means silence.
- Agent 365, Defender XDR Security for AI agents and Purview DSPM for AI are optional tenant-level features. The repo automates the Agent 365 access-control half, the Defender for Cloud to Sentinel wiring and read-only Purview checks; consent, the XDR switch and the Purview switch stay manual, and teardown does not reverse them.
- Defender XDR detection covers published Foundry agents only, and a Defender alert is never promised for a blocked prompt: the guardrail refusal is evidenced by ABW-008 and the guardrail rows.
- A decision is proven from logs by one call, `AbwFullChain('<rid>', 3d)`, on a run at least 15 minutes old with the portal range on Last 30 days; the card claims only what a row says, shows a hop as missing only when the click said it should exist, and never says "always".
- Logs-only proof has limits: latency, hashed arguments, time-matched Search and Cosmos DB rows, and Entra rows that exist only when an export workspace is configured.
