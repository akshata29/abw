**Console behaviour and safety rails (12.1 to 12.5)**

- **C1. Stop kills a restore script that is already running.** **Implemented.** Cancelling a job sets its cancel event and then kills the process tree of every child recorded on the job (`console/jobs.py:345-348#cancel`). Each child is added to that list as soon as it starts (`console/jobs.py:365-366#procs`) and removed after it exits (`console/jobs.py:399-402#procs`), and the HTTP route runs the cancel on a worker thread (`console/server.py:164-168#api_job_cancel`). The `ignore_cancel` flag only changes what the stream loop does afterwards: it does not break out on a cancel (`console/jobs.py:385#ignore_cancel`) and does not raise `Cancelled` (`console/jobs.py:403-404#ignore_cancel`). The restore calls in the allow-list and kill jobs set it (`console/jobs.py:1292-1299#ignore_cancel`, `console/jobs.py:1337-1343#ignore_cancel`), so the restore block still runs after a Stop, but the script running at that moment has already been killed. Why it matters: 12.5.4 says Stop does not skip the restore; the nuance is that Stop can end a restore script half-way, and the next poll of the status lights (12.1.7) shows what state that left.
- **C2. Reset demo is stoppable, and it changes more than local state.** **Implemented.** `run_restore` starts the restore script without `ignore_cancel` (`console/jobs.py:1055-1057#run_restore`), so a Stop kills it, raises `Cancelled`, and the state read-back and the front-door restore after it never run. The script has four independent steps (`demo/prove.py:339-353#restore_all`): clear the kill switch, reset the client allow-list, re-add the operator to the Falcon group (`demo/prove.py:168-176#set_falcon_membership`) and flip the identity back to the baseline persona roles, with up to three attempts (`demo/prove.py:323-336#become`). The section comment above the persona helpers says the operator mirrors a persona's app roles (`demo/prove.py:303#persona`). **Inference:** Reset demo therefore changes group membership and the operator's app-role assignments in the tenant, which needs the operator's directory permissions and should not be pressed in the middle of a live proof run.
- **C3. The Reset demo verdict ignores a failed persona flip or group re-add.** **Implemented.** `restore_all` runs four steps, catches every step failure, prints a failure line and carries on, and the `--restore` mode returns 0 whatever happened (`demo/prove.py:347-352#RESTORE`, `demo/prove.py:1182-1184#restore_all`). The first two steps call `run_ps`, which hands back the exit code and the output instead of raising on a non-zero exit (`demo/prove.py:179-182#run_ps`), so the kill-switch reset and the allow-list reset print "restored" even when their script exited with an error; the console covers those two with its own read-back of the gateway state (`console/jobs.py:1059-1061#gateway_state`). The other two steps, the group re-add and the persona flip, raise on failure and print "RESTORE FAILED", and nothing in the job reads them back. The job's verdict is "return code 0, kill switch off, allow-list at baseline and front door open" (`console/jobs.py:1075#good`), none of which looks at the group or persona steps. Why it matters: "Baseline restored." can be shown while the operator is still outside the Falcon group or the persona flip failed; the failure line is only in the raw output stream, so read it when the next scenario depends on identity.
- **C4. The Act 7 restore runs only if the change was recorded.** **Implemented.** `changed` starts false (`console/act7.py:720#changed`) and is set only after the helper that writes a named value returns (`console/act7.py:729-731#_set_named_value`, `console/act7.py:755-757#_set_named_value`); the `finally` block restores only when it is true (`console/act7.py:780-781#changed`), settles with `ignore_cancel` (`console/act7.py:788#ignore_cancel`) and, if the restore fails, tells the presenter to click Reset demo (`console/act7.py:793-794#Reset`). **Inference (low):** if the helper raises after APIM has applied the new value, for example a timeout on the reply, `changed` is still false and the lowered limit stays until Reset demo is clicked.
- **C5. The agent approval default is "yes" in the job and "ask" in the runner.** **Implemented.** The `agent` job takes `approve` from its parameters and defaults it to yes (`console/jobs.py:834#approve`), while the runner it launches defaults to ask (`console/agent_run.py:76#approve`). The catalog sets the value explicitly: ask for the order beat and yes for the pre-approved alternative (`console/catalog.py:438#approve`, `console/catalog.py:443#approve`). Why it matters: a caller that leaves the field out, such as an API client or the headless driver (C6), has any order-tool call approved without asking. Whether an order is then written is decided by the MCP server's own checks, in this order: the `Tools.Execute` scope and `Trade.Execute` role (`src/mcp/abw_mcp/servers/actions.py:145#require_scope_and_role`), the argument checks on ticker, side and quantity (`src/mcp/abw_mcp/servers/actions.py:20-23#quantity`), the restricted-list check, which refuses a restricted ticker for any caller and gives a separation-of-duties reason when the caller holds a wall role (`src/mcp/abw_mcp/servers/actions.py:58-75#separation_of_duties`), and the write to Cosmos DB, which by default runs with the user's own token, so the user's own Cosmos DB permission applies (`src/mcp/abw_mcp/servers/actions.py:91-98#use_user_token`) (12.5.5).

**Jump-box installation (12.6)**

- **J1. The VM's verify verdict ignores the APIM check and the persona sign-ins.** **Implemented.** The verdict covers the tools, the package stamp, the missing files, the virtual env, the shortcut and the console's health, page and catalog endpoints (`scripts/jumpbox-console-setup.ps1:558-559#shortcut`); it ignores the APIM result, the scoreboard, policy and persona endpoints and the persona sign-ins. The laptop prints the APIM result and each persona row as their own lines (`scripts/jumpbox-console.ps1:565#APIM`, `scripts/jumpbox-console.ps1:566-576#persona`), but the verdict it returns is the VM's (`scripts/jumpbox-console.ps1:580#V.ok`), the closing line is chosen from the same flag (`scripts/jumpbox-console.ps1:756#res.ok`), and the state file records it (`scripts/jumpbox-console.ps1:758#consoleOnVmVerify`). Why it matters: "verification passed" can appear under a failed APIM line; read the individual lines.
- **J2. A failed secrets lock-down or a leftover script copy does not fail the phase.** **Implemented.** The shortcut phase records an error text for the lock-down but its verdict is only the shortcut (`scripts/jumpbox-console-setup.ps1:445-447#secretsError`); the persona phase's verdict is "folder locked and upload deleted" and ignores the count of script copies it could not empty (`scripts/jumpbox-console-setup.ps1:608-612#scriptCopiesLeft`). The laptop prints a warning for each (`scripts/jumpbox-console.ps1:536#secretsError`, `scripts/jumpbox-console.ps1:543#scriptCopiesLeft`, `scripts/jumpbox-console.ps1:547#scriptCopiesLeft`). Why it matters: the phase still reports success, so the warning is the only signal; watch for it in the install output.
- **J3. The package copy never deletes, and the verify cannot see leftovers.** **Implemented**, effect **Inference (low)**. The first copy includes sub-folders, leaves out the evidence folder and has no purge or mirror option (`scripts/jumpbox-console-setup.ps1:366#robocopy`), so a file that a newer package no longer ships stays on the VM. The VM's own evidence is never overwritten: the second copy skips every file that already exists (`scripts/jumpbox-console-setup.ps1:368-372#robocopy`). The verify compares the recorded package stamp and a list of required files, not the folder's content (`scripts/jumpbox-console-setup.ps1:490-491#contentSha`). Why it matters: a stale or modified file on the VM is not reported.
- **J4. The installer signature check is a substring test.** **Implemented**, weakness **Inference (low)**. The installer is accepted when its Authenticode status is Valid and the expected signer text appears anywhere in the certificate subject (`scripts/jumpbox-console-setup.ps1:227-230#Signer`). A pin to the thumbprint or the exact subject would be stricter. The downloads come from pinned vendor addresses and versions (`scripts/jumpbox-console.ps1:72-77#tools`), which bounds the risk.
- **J5. The retry wrapper holds back a permanent failure for about four minutes.** **Implemented.** `Invoke-VmScript` wraps only the `az vm run-command invoke` call in `Invoke-Retry` with 8 attempts and a delay of 8 seconds times the attempt number (`scripts/jumpbox-console.ps1:410-414#Invoke-Retry`); the helper retries every exception with a bare catch and rethrows on the last attempt (`scripts/common.ps1:115-123#Invoke-Retry`), and the throw is conditioned only on the `az` exit code (`scripts/jumpbox-console.ps1:412#LASTEXITCODE`). The waits add up to 224 seconds (8+16+24+32+40+48+56). The comment above the function says it retries while the extension is busy or the agent is not ready (`scripts/jumpbox-console.ps1:405#Retries`), which understates it. Why it matters: a permanent `az` failure, such as a wrong subscription or a missing permission, surfaces only after about 224 seconds of "not ready" lines. **Inference (low):** a phase that returns an `ok` of false inside a successful run-command is not retried.
- **J6. The launcher accepts any account of the right tenant.** **Implemented**, effect **Inference**. The launcher compares only the tenant id of the Azure CLI sign-in (`scripts/jumpbox-console-start.ps1:33-39#Get-AzTenant`, `scripts/jumpbox-console-start.ps1:66#Get-AzTenant`, `scripts/jumpbox-console-start.ps1:80#Get-AzTenant`), switches the CLI to the plain token cache (`scripts/jumpbox-console-start.ps1:61-64#enable_broker_on_windows`) and starts the server with the switch that skips the server's own check (`scripts/jumpbox-console-start.ps1:85#skip-az-check`), so even the note in C17 is never printed. Why it matters: a different account of the same tenant is accepted silently, and the console's operator actions target the configured operator (C8), so they can act on an identity other than the token in use.
- **J7. The launcher polls only the requested port.** **Implemented**, effect **Inference (low)**. The health probe and the start loop poll the requested port, 60 times at one-second intervals (`scripts/jumpbox-console-start.ps1:20-25#Test-Console`, `scripts/jumpbox-console-start.ps1:86-91#Test-Console`), while the server moves on to the next free port, up to 24 ports along (`console/server.py:348-356#free_port`). If the preferred port is busy, the launcher either times out with "did not start" or accepts whatever else answers the health path with HTTP 200, and Edge opens the address built from the requested port (`scripts/jumpbox-console-start.ps1:47#url`, `scripts/jumpbox-console-start.ps1:93#Open-Edge`), not the one the server chose.
- **J8. The dry-run switch is honoured by three modes only.** **Implemented.** `-WhatIf` is read only by the install path, `-Remove` and `-RemovePersonaFiles` (`scripts/jumpbox-console.ps1:606#WhatIf`, `scripts/jumpbox-console.ps1:771#WhatIf`, `scripts/jumpbox-console.ps1:790#WhatIf`); the status mode (`scripts/jumpbox-console.ps1:727-743#Invoke-StatusMode`) and the verify mode (`scripts/jumpbox-console.ps1:745-762#Invoke-VerifyMode`) ignore it, and the verify mode still starts a throw-away console on the VM and makes an unauthenticated call to the gateway (`scripts/jumpbox-console.ps1:753-754#throw-away`). **Inference (low):** the extra work changes no tenant configuration, so the effect is low: the in-VM check resolves a private name, makes one call with no token and redeems cached persona sign-ins silently, never starting a device code (`scripts/jumpbox-console-setup.ps1:451-453#redeems`). It still leaves traces, a refused gateway request in the logs and, for each persona cached on the VM, token requests that can rewrite that persona's cache file on the VM (12.6.5, 12.6.7). Why it matters: a dry run of the verify mode is not a dry run (12.6.8).
- **J9. The state file's message understates what it holds.** **Implemented**, content **Inference (low)**. The laptop prints that the state file holds no secrets and only persona file names (`scripts/jumpbox-console.ps1:720#recorded`), but it also stores the VM's console block and APIM block (`scripts/jumpbox-console.ps1:714-715#apim`, `scripts/jumpbox-console.ps1:758#consoleOnVmVerify`). Those blocks include the persona sign-in rows (user names and role names), the gateway host name and its resolved addresses. They are not credentials, but they are tenant identifiers, so treat the file as sensitive; it stays in the generated-output folder on the laptop.
- **J10. Script-block logging on the VM was not checked.** **Implemented** (the record) and **Inference** (the effect). The runbook records that PowerShell script-block logging on the VM was not checked (`docs/RUNBOOK.md:127#logging`), and no PowerShell script in the scripts folder and no Bicep template in the infra folder sets or checks that policy (a search for the logging setting names found nothing). The clean-up empties only the run-command agent's script copies that carry the marker comment, which the code itself notes are readable by every local user (`scripts/jumpbox-console-setup.ps1:151-152#Everyone`, `scripts/jumpbox-console-setup.ps1:153-166#Clear-PayloadCopies`). **Platform behaviour:** when script-block logging is enabled, PowerShell records the content of the script blocks it processes in an event log (https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_logging_windows). That page describes PowerShell 7 and points to a separate page for Windows PowerShell 5.1. Why it matters: **Inference:** if the logging is on, the payload text could persist in a place the clean-up does not reach; check it before the personas phase on a machine you do not control.
