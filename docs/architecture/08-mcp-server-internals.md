### 8.1 Process and image

**What this section proves.** The six MCP servers are not six programs. There is one Python package and one container image. A single setting, `MCP_SERVER`, decides which tool set, which inbound authentication and which downstream credentials a container assembles at start-up. That keeps one code path for token validation, denial shapes and the audit event, at the price that every container carries the code and the settings of all six (Implemented: `src/mcp/abw_mcp/app.py:49-60#_build_registry`; Designed: `DESIGN.md:116#abw-mcp`).

#### 8.1.1 One image, six personalities

**Implemented.** `create_app` reads the settings, builds the runtime (settings, audit service, data-plane clients and, for four servers, an on-behalf-of broker), builds the tool registry for the chosen server, and attaches exactly one of three inbound behaviours: bearer-token validation, a shared vendor key, or nothing (`src/mcp/abw_mcp/app.py:188-194#create_app`). The table shows which registry, middleware and broker each server gets.

| Server | Tool registry | Tools | Inbound authentication | OBO broker built |
|---|---|---|---|---|
| research | `src/mcp/abw_mcp/app.py:50-51#research` | 2 | Entra token (`BearerAuthMiddleware`) | yes |
| wall | `src/mcp/abw_mcp/app.py:52-53#wall` | 3 | Entra token | yes |
| actions | `src/mcp/abw_mcp/app.py:54-55#actions` | 3 | Entra token | yes |
| private | `src/mcp/abw_mcp/app.py:56-57#private` | 2 | Entra token | yes |
| vendor (mock) | `src/mcp/abw_mcp/app.py:58-59#vendor` | 2 | shared key in the `x-vendor-key` header (`VendorKeyMiddleware`); the gateway injects it | no |
| legacy (POC) | `src/mcp/abw_mcp/app.py:60#legacy` | 5 | none | no |

The middleware choice is made at `src/mcp/abw_mcp/app.py:241-249#VendorKeyMiddleware`. The broker rule is "built unless the server is vendor or legacy" (`src/mcp/abw_mcp/app.py:75-77#obo`). The tool counts are the length of each server's `build_tools` list (section 8.3). The legacy registry is also the only one built with a default audit reason, `no_user_context` (`src/mcp/abw_mcp/app.py:60#no_user_context`).

Each personality needs its own settings; a missing one makes the server fail on the first request and then return HTTP 500 on every request (8.1.3). Every server needs the tenant id, its user-assigned managed identity client id and the audit storage account. The token-validating servers also need the MCP app registration's client id (`src/mcp/abw_mcp/config.py:95-108#validates_tokens`). On top of that:

| Server | Further required settings | Container Apps environment | Public base URL given to the server |
|---|---|---|---|

| wall | `STORAGE_ACCOUNT`, `SEARCH_ENDPOINT` (`src/mcp/abw_mcp/config.py:119#wall`) | private (`infra/04-apps.bicep:107#caePriv`) | gateway URL plus `/wall` (`infra/04-apps.bicep:111#serverEnv`) |

| private | `COSMOS_ENDPOINT` (`src/mcp/abw_mcp/config.py:121#private`) | private (`infra/04-apps.bicep:137#caePriv`) | the server's own internal URL (`infra/04-apps.bicep:141#privateFqdn`) |
| vendor | `VENDOR_API_KEY` (`src/mcp/abw_mcp/config.py:122#vendor`) | the public environment (`infra/04-apps.bicep:172#caePub`) | none is set, so the PRM URL is derived from request headers (`src/mcp/abw_mcp/app.py:91-98#derive_public_base_url`) |

**Why one image (Inference).** `DESIGN.md:116#abw-mcp` states the fact (one image, all servers, selected by `MCP_SERVER`) without giving a reason. The practical effect is that the token check, the denial shapes and the audit event exist once, so a fix reaches all six servers with one build and the audit schema cannot drift between servers.

**Trade-off / limitation (Configured).** The deployment gives every one of the six container apps every data-plane endpoint: the storage account, the Cosmos DB endpoint, the Search endpoint and the index name are in the common settings list (`infra/04-apps.bicep:53-66#commonEnv`). What stops the research server from reading a wall container is therefore not configuration. It is the identities and role assignments behind the call (section 7.5). The legacy server, the deliberately leaky proof of concept, ships in the same image as the governed servers (`src/mcp/abw_mcp/app.py:60#legacy`).

#### 8.1.3 The ASGI structure

**Implemented.** uvicorn is pointed at `abw_mcp.app:app`. That object is not a Starlette application but a small wrapper, `LazyApp`. On the first ASGI scope it receives, `LazyApp` calls `create_app()`, which reads the settings and builds everything. Every later scope goes straight to the built application (`src/mcp/abw_mcp/app.py:176-185#LazyApp`; `src/mcp/abw_mcp/app.py:257#LazyApp`). The docstring gives the reason: settings can then be supplied at run time. A consequence is that a missing required setting raises a `ValueError` naming the missing settings (`src/mcp/abw_mcp/config.py:133-134#missing`) when the first scope arrives, not when the module is imported. Inference, from uvicorn's lifespan handling (not run here): the start command passes no lifespan flag, so uvicorn ignores an exception from the first scope; the process stays up, every later request, including `/healthz`, calls `create_app()` again and fails with HTTP 500, and the platform restarts the container only when its probes fail (`src/mcp/Dockerfile:15#CMD`; `src/mcp/abw_mcp/app.py:176-185#LazyApp`; the probes are in the 8.1.2 table).

```text
uvicorn (all interfaces, port 8080, proxy headers)
  LazyApp                           builds the app on the first ASGI scope
    OpenTelemetryMiddleware         one span per request; /healthz is excluded
      RequestContextMiddleware      request id into a context variable
        BearerAuthMiddleware        research, wall, actions, private
        VendorKeyMiddleware         vendor only
        (nothing)                   legacy
          Starlette router
            /mcp          GET, POST, DELETE -> AutoStartingSessionApp -> MCP SDK -> ToolRegistry
            /healthz      GET -> {"status":"ok","server":"<name>"}
            /.well-known/oauth-protected-resource   GET -> PRM document
```

**Why this order (Implemented, from the code comment).** Starlette wraps middleware in reverse order of registration. OpenTelemetry is registered last and so is outermost, which means its spans cover authentication failures. The request-context middleware is next, so the request id is already available when the auth middleware writes its `auth_failed` event. The auth middleware is innermost (`src/mcp/abw_mcp/app.py:250-253#OpenTelemetryMiddleware`).

**The SDK wrapper.** `AutoStartingSessionApp` wraps the SDK's ASGI app and makes sure the session manager's run context is started before a request is handled. The start is idempotent behind an `anyio` lock. The application lifespan starts the audit service and the session manager and stops them in reverse order on shutdown (`src/mcp/abw_mcp/app.py:145-173#AutoStartingSessionApp`; `src/mcp/abw_mcp/app.py:230-237#lifespan`).

**Server identity.** The SDK server object is named `abw-<server>`, version 0.1.0, with the title `ABW <server> MCP` (`src/mcp/abw_mcp/app.py:202-209#Server`). The package version is declared separately (`src/mcp/pyproject.toml:7#version`).

#### 8.1.4 Endpoints

**Implemented.** Three routes exist on every server (`src/mcp/abw_mcp/app.py:224-228#routes`).

| Path | Methods | Authentication | Returns | Code |
|---|---|---|---|---|
| `/mcp` | GET, POST, DELETE | bearer token (research, wall, actions, private); `x-vendor-key` (vendor); none (legacy) | the MCP streamable HTTP endpoint; a POST carries a JSON-RPC request or notification | `src/mcp/abw_mcp/app.py:225#streamable_app` |
| `/healthz` | GET | none | `{"status":"ok","server":"<name>"}` | `src/mcp/abw_mcp/app.py:218-219#healthz` |
| `/.well-known/oauth-protected-resource` | GET | none | the PRM document | `src/mcp/abw_mcp/app.py:227#oauth-protected-resource` |

Only `/mcp` is authenticated: both middlewares pass every other path and every non-HTTP scope straight through (`src/mcp/abw_mcp/auth.py:209-212#__call__`; `src/mcp/abw_mcp/app.py:124-127#__call__`). The vendor and legacy servers still serve the PRM route, because the route list does not depend on the server (`src/mcp/abw_mcp/app.py:224-228#routes`).

The PRM document, the same on every server except for its values (`src/mcp/abw_mcp/app.py:101-112#_build_prm_payload`):

| Field | Value | Code |
|---|---|---|
| `resource` | the public base URL plus `/mcp` | `src/mcp/abw_mcp/app.py:102#resource` |
| `authorization_servers` | one entry: the tenant's v2.0 issuer | `src/mcp/abw_mcp/app.py:105#authorization_servers` |
| `scopes_supported` | `api://<mcp-app-client-id>/<scope>` for each scope in the server's list (`Tools.Read`, plus `Tools.Execute` for actions); an empty list when the server has no app registration | `src/mcp/abw_mcp/app.py:106-110#scopes_supported` |
| `bearer_methods_supported` | `["header"]` | `src/mcp/abw_mcp/app.py:111#bearer_methods_supported` |

The public base URL is the `PUBLIC_BASE_URL` setting when set. Otherwise it is rebuilt from `x-forwarded-host` (or `host`), `x-forwarded-proto` and `x-forwarded-prefix` (`src/mcp/abw_mcp/app.py:91-98#derive_public_base_url`). The same function builds the URL that the 401 challenge points to (`src/mcp/abw_mcp/app.py:244-249#prm_url_builder`).

**Trade-off / limitation (Inference).** The image's proxy flags make uvicorn trust the forwarded client address and scheme from any peer (`src/mcp/Dockerfile:15#CMD`), and the application reads the `X-Forwarded-*` headers itself from any caller, whatever those flags say, when `PUBLIC_BASE_URL` is unset (`src/mcp/abw_mcp/app.py:91-98#derive_public_base_url`). A caller that can reach such a server directly can therefore choose the `resource` URL it advertises. Only the vendor server leaves `PUBLIC_BASE_URL` unset (`infra/04-apps.bicep:176-181#vendor`), and the document carries no secret, so the impact is low.

#### 8.1.5 Transport and JSON-RPC

**Implemented.** The SDK's streamable HTTP session manager is built with `json_response=True` and `stateless=True` (`src/mcp/abw_mcp/app.py:210-215#StreamableHTTPSessionManager`). In practice, each POST is an independent request that is answered with one JSON body (no event stream), and the server keeps no session between calls. There is no `/sse` route (`src/mcp/abw_mcp/app.py:224-228#routes`), and the replicas are interchangeable because no session needs a sticky route (`infra/modules/mcp-app.bicep:19-20#minReplicas`).

`DESIGN.md:114#stateless_http=True` names the same two options as `stateless_http=True` and `json_response=True`, while the code sets `stateless=True` and `json_response=True` on the session manager. Inference: this is a naming difference between the SDK's server classes, not a behavioural one. Learn documents the transport (https://learn.microsoft.com/azure/container-apps/mcp-overview) and describes the equivalent stateless setting of the TypeScript SDK (https://learn.microsoft.com/azure/container-apps/tutorial-mcp-server-nodejs#define-the-mcp-tools). How the Python SDK treats `GET` and `DELETE` on `/mcp` in stateless mode, and whether it issues any session id, is SDK behaviour that this repo does not define and I did not verify.

**Why stateless (Inference).** Authorization is decided per request from the token (section 7.4), so a session would add nothing to the security model and would force session affinity or shared state across replicas. The repo states no reason.

**DNS-rebinding protection is switched off.** The transport is built with `enable_dns_rebinding_protection=False` (`src/mcp/abw_mcp/app.py:214#enable_dns_rebinding_protection`). The repo gives no reason; it is listed in the Findings. Inference, not stated in the repo: the host name arrives as the gateway's or the container app's name and not as localhost, so a host allow-list would need maintaining per deployment; and a rebinding defence matters most for a server bound to localhost and reachable from a browser, whereas this server validates a bearer token on `/mcp` (except vendor and legacy), so the practical exposure is small.

The JSON-RPC methods and who answers them:

| Method | Answered by | Behaviour | Code |
|---|---|---|---|
| `initialize` | SDK | the handshake; the server reports its name and version | `src/mcp/abw_mcp/app.py:202-209#Server` |
| `notifications/*` (for example `notifications/initialized`) | SDK | accepted without a reply | `src/mcp/tests/conftest.py:262#notifications/initialized` |
| `ping` | SDK | liveness at protocol level | `infra/apim/policies/mcp-jwt.policy.xml:42#ping` |
| `tools/list` | this repo: `on_list_tools` | role-filtered list; one `tool_listed` audit event per visible tool | `src/mcp/abw_mcp/app.py:196-197#on_list_tools` |
| `tools/call` | this repo: `on_call_tool` | the lifecycle in section 8.2 | `src/mcp/abw_mcp/app.py:199-200#on_call_tool` |
| anything else (`resources/*`, `prompts/*` and so on) | SDK, no handler registered | the SDK's own answer (not verified here) | `src/mcp/abw_mcp/app.py:202-209#Server` |

The rows answered by the SDK are SDK behaviour: this repo registers no handler for them and I did not verify them. Only two handlers are registered, so the servers expose tools and nothing else. The gateway is stricter than the server for the other methods: outside the discovery set it demands one of the API's roles (`infra/apim/policies/mcp-jwt.policy.xml:42-44#discovery`; section 7.3). The tests send an `initialize` request and then the `initialized` notification, with the protocol version `2025-03-26` and an `Accept` header that offers both JSON and event streams (`src/mcp/tests/conftest.py:236-262#PROTOCOL_VERSION`). Which protocol versions the SDK accepts is not defined in this repo.

### 8.2 Request lifecycle for tools/call

**What this section proves.** A tool call passes through eleven stages, and almost every stage can end the request. Stages 1 to 6 are generic and identical for all tools. Stages 7 to 9 are per tool and are catalogued in section 8.3. Authentication is middleware, so it runs before the SDK parses the JSON-RPC body: the order "parse then authenticate" that one might expect is reversed here (`src/mcp/abw_mcp/app.py:250-253#OpenTelemetryMiddleware`; `src/mcp/abw_mcp/auth.py:209-223#__call__`). Token mechanics are in section 6.

```text
Authorization: Bearer <token>   (from the client, through the gateway of section 7.3)
  |
  v 1  OpenTelemetryMiddleware       span per request, /healthz excluded
  v 2  RequestContextMiddleware      request id -> context variable
  v 3  BearerAuthMiddleware          verify_token -> Caller
  |                                  fail: auth_failed event + HTTP 401 or 403
  v 4  router /mcp -> AutoStartingSessionApp -> MCP SDK   JSON-RPC parse, tools/call
  v    on_call_tool -> ToolRegistry.call_tool
  v 5    unknown tool?               NOT_FOUND          (unknown_tool)
  v 6    requirement fails?          DENIED FORBIDDEN   (missing_role, missing_scope)
  v 7    argument model fails?       ERROR INVALID_ARGUMENT
  v 8    handler: tool rule          DENIED FORBIDDEN or WALL_VIOLATION
  v 9    OBO + data call             DENIED obo_failed:<code> | storage_rbac_denied (Storage only)
  v 10   AuditService.emit           stdout line + append blob (after the data call)
  v 11   CallToolResult              HTTP 200 JSON, structuredContent, isError per MCP_DENIAL_MODE
```

**1. Ingress, gateway headers and the span.** The request normally arrives from the gateway, which has already validated the token, applied its own rules and added two headers: `x-abw-request-id` (the gateway's request id) and `x-abw-gateway: apim` (`infra/apim/policies/mcp-jwt.policy.xml:82-87#x-abw-request-id`). A search of `src` finds no code that reads `x-abw-gateway`, so that header is evidence for people reading logs and not an input to any decision here. The vendor API goes through the same policy and then also deletes the inbound `Authorization` header and injects the vendor key from a Key Vault-backed named value, so the vendor container never sees the user's token (`infra/05-apim-apis.bicep:75-78#vendorSection`; `infra/05-apim-apis.bicep:160#__VENDOR_SECTION__`). The OpenTelemetry middleware opens a server span for the request and skips `/healthz` (`src/mcp/abw_mcp/app.py:253#excluded_urls`). Two paths do not come through this policy: the private server's direct path, and the legacy API, which uses the separate subscription-key policy (sections 7.3 and 7.9).

**2. Request id.** `RequestContextMiddleware` sets a context variable to the first present of `x-abw-request-id`, `x-request-id`, `x-ms-request-id` and `traceparent`, else `req-` plus epoch milliseconds, and resets it when the request ends (`src/mcp/abw_mcp/auth.py:173-188#RequestContextMiddleware`). That one id appears in the audit event, in the response payload and on the downstream storage and search calls (stages 9 to 11).

**3. Authenticate.** `BearerAuthMiddleware` acts only on `/mcp`. It takes the text after `Bearer ` (the scheme is matched case-insensitively), calls `verify_token`, and gets back a `Caller` (`src/mcp/abw_mcp/auth.py:209-219#verify_token`). Section 7.4.1 lists the nine ordered checks and the reason code each produces. On failure the middleware writes one `auth_failed` audit event and returns a JSON 401 or 403 with a challenge header that points at the PRM document (`src/mcp/abw_mcp/auth.py:224-242#auth_failed`; `src/mcp/abw_mcp/auth.py:250-260#_auth_error_response`). On success the caller is published on a context variable for the rest of the request and reset in a `finally` block (`src/mcp/abw_mcp/auth.py:244-248#current_caller`). The context variable defaults to no caller (`src/mcp/abw_mcp/auth.py:25#current_caller`).

**4. Dispatch and JSON-RPC parse.** The router sends the request to `AutoStartingSessionApp`, which starts the session manager if needed and hands the request to the SDK (`src/mcp/abw_mcp/app.py:171-173#__call__`). The SDK parses the JSON-RPC envelope and answers `initialize`, `ping` and notifications itself. For `tools/call` it invokes the registered handler, which passes the current caller, the tool name and the arguments to the registry (`src/mcp/abw_mcp/app.py:199-200#on_call_tool`). Malformed JSON-RPC and unknown methods are the SDK's responsibility and are not defined in this repo. Tested in process: the caller set in the middleware is visible to the handler (`src/mcp/tests/test_servers.py:33-63#test_role_filtered_tools_list`).

**5. Unknown tool.** A name that is not in the server's registry returns `NOT_FOUND` with the reason `unknown_tool`. The audit event for it carries no caller and no tool name (`src/mcp/abw_mcp/registry.py:159-161#unknown_tool`; `src/mcp/abw_mcp/registry.py:222-236#_error_result`). The check runs before the role check, so "unknown tool" and "tool unavailable for you" are different answers (Findings).

**6. Requirement (the role filter).** Each tool carries a requirement that returns a decision and a reason. `require_any_role` fails with `missing_role` when the caller has none of the listed roles. `require_scope_and_role` fails with `missing_scope` when the scope is absent and then applies the role test (`src/mcp/abw_mcp/registry.py:98-121#require_any_role`). A failure becomes `FORBIDDEN` with the message "Tool unavailable for this caller." and is audited as `tool_denied`; the arguments are hashed as an empty object (`src/mcp/abw_mcp/registry.py:163-165#FORBIDDEN`). `tools/list` applies the same predicate, so a tool that would not be listed is also refused if called (`src/mcp/abw_mcp/registry.py:132-156#list_tools`). Why: one predicate per tool means the list and the call cannot disagree.

**7. Argument validation.** The arguments are validated against the tool's Pydantic model, which forbids unknown fields (`src/mcp/abw_mcp/registry.py:24-27#ArgsModel`). A failure becomes `INVALID_ARGUMENT` with the reason `invalid_arguments`, a message made only of each field's location and the validator's text (the supplied value is not echoed), an audit event `tool_denied` with decision `deny`, and `obo` false. For this one denial the audit hash covers the real arguments (`src/mcp/abw_mcp/registry.py:167-175#invalid_arguments`; `src/mcp/abw_mcp/registry.py:45-51#validation_message`). Validation follows the role check, so an unentitled caller cannot learn a tool's argument rules from its error messages (Inference from the order).

**8. The tool rule.** The handler runs (`src/mcp/abw_mcp/registry.py:177-178#handler`). Each tool applies its own rules before touching data: the wall server checks the caller's project role, the actions server checks the restricted list and separation of duties, and so on (section 8.3). A rule failure raises `ToolError` with a code (`FORBIDDEN` or `WALL_VIOLATION`), a reason, an audit event name (`tool_denied`, `wall_violation_attempt` or `order_blocked`) and a `downstream` hint (`src/mcp/abw_mcp/registry.py:54-76#ToolError`). A `ToolError` is turned into a result and audited (`src/mcp/abw_mcp/registry.py:192-193#ToolError`).

**9. OBO and the data call.** Inside the handler, a user-attributed read calls the data-plane wrapper with `use_user_token` true. The wrapper asks the broker for a downstream token for this caller, builds a new Azure SDK client around it, and makes the call (`src/mcp/abw_mcp/data.py:57-65#read_blob_text`; `src/mcp/abw_mcp/obo.py:60-75#acquire_token_on_behalf_of`). Section 6 explains the exchange. Four facts matter for authorization:

- A fresh client is built for each call from that caller's token, so no credential is shared between users (`src/mcp/abw_mcp/data.py:152-157#_build_blob_service`; Inference on intent).
- If the exchange fails there is no fall-back to the server's managed identity: the call ends as `FORBIDDEN` with the reason `obo_failed:<code>` (`src/mcp/abw_mcp/registry.py:179-191#obo_failed`; `src/mcp/abw_mcp/data.py:191-194#_obo_credential`). Tested: a test pins that a failed exchange is returned as `FORBIDDEN` with the reason `obo_failed:invalid_grant` and is audited; it uses the fake data plane, so the credential choice inside the real data plane client is not exercised (`src/mcp/tests/test_servers.py:141-156#test_obo_failure_does_not_fallback`).
- A Storage refusal is translated: an HTTP 403 from Blob Storage becomes `FORBIDDEN` with the reason `storage_rbac_denied`, and the wall server then audits it as `wall_violation_attempt` (`src/mcp/abw_mcp/data.py:68-71#storage_rbac_denied`; `src/mcp/abw_mcp/servers/wall.py:94-96#wall_violation_attempt`). Platform behaviour: Storage returns 403 when the token's principal lacks a data role on the container (https://learn.microsoft.com/troubleshoot/azure/azure-storage/blobs/authentication/storage-troubleshoot-403-errors). The mapping keys on the status code alone, so any 403 is reported with that reason (Findings).
- Search and Cosmos DB errors are not translated anywhere in the wrapper (`src/mcp/abw_mcp/data.py:73-97#search_documents`). Such an exception is neither an OBO error nor a tool error, so it propagates out of the registry past both audit calls (`src/mcp/abw_mcp/registry.py:177-193#OboError`). How the SDK renders it, and whether any audit line exists for it, is not defined in this repo and not tested (Findings).

The gateway request id is stamped on the downstream call when it matches a safe pattern of 1 to 64 letters, digits and `._:-` (`src/mcp/abw_mcp/data.py:21-28#downstream_request_id`). Blob reads pass it as `client_request_id` and Search queries as `request_id` (`src/mcp/abw_mcp/data.py:201-204#client_request_id`; `src/mcp/abw_mcp/data.py:207-217#request_id`). Platform behaviour: Storage records `x-ms-client-request-id` in its analytics logs and in the Azure Monitor `clientRequestId` column (https://learn.microsoft.com/rest/api/storageservices/get-blob#request; https://learn.microsoft.com/azure/storage/blobs/monitor-blob-storage-reference#azure-monitor-logs-tables). That is what lets the layer-3 query join a Storage refusal to a gateway decision (section 7.5).

**10. Audit.** After the handler returns, or after a `ToolError` or `OboError` has been converted, the registry builds one audit event and passes it to the audit service, which writes it to every sink: a JSON line on stdout and an append-blob line in the WORM container (`src/mcp/abw_mcp/registry.py:201-218#emit`; `src/mcp/abw_mcp/audit.py:155-216#AuditService`). The event is written after the data call, not before it, so the audit trail is not write-ahead (Findings). Section 8.4 lists every field.

**11. Response.** The registry adds the request id to the payload when the tool did not set one, serialises the payload once as compact JSON, and returns it twice: as a text content item and as `structuredContent`. It sets no `isError` on an allowed call (`src/mcp/abw_mcp/registry.py:195-222#CallToolResult`). A denial or error uses the same two carriers. By default the HTTP status is 200 and `isError` is false. The code comment gives the reason: the Foundry Agent Service aborts the whole run with an HTTP 400 `tool_user_error` when a tool returns `isError` true (a claim I did not verify on Learn). Setting `MCP_DENIAL_MODE` to `strict` makes `isError` true (`src/mcp/abw_mcp/registry.py:263-270#isError`; `src/mcp/abw_mcp/config.py:21-26#_parse_denial_mode`). Why: a normal result lets the model explain the refusal to the user, and the refusal is still audited. Section 8.5 lists every payload shape.

**Variations by server.**

| Server | Difference from the lifecycle above | Code |
|---|---|---|
| research, wall, actions, private | none: stages 1 to 11 as described | `src/mcp/abw_mcp/app.py:243-249#BearerAuthMiddleware` |
| vendor | stage 3 is the vendor-key check: the `x-vendor-key` header is compared in constant time with the configured key, and a mismatch returns HTTP 401 `{"error":"invalid_vendor_key"}`. The generic stages guarantee identity, role, argument shape and an audit line; they do not guarantee that a handler applied its data rule (section 8.8).

### 8.3 Server catalogue

**What this section proves.** The six servers are one code base with six tool lists. Each server's `build_tools()` list is handed to the same registry, so the generic stages of a call (token check, role filter, argument validation, token exchange, audit) are identical for all of them (`src/mcp/abw_mcp/app.py:49-60#_build_registry`). What differs is only which tools exist, which requirement each tool carries, which data store its handler touches, which credential the handler uses, and which extra rule it applies before it touches data. The four governed servers (research, wall, actions, private) carry the caller's identity down to the data plane. The vendor mock and the legacy server deliberately do not.

**How to read the tables.** "Wire shape" is the HTTP 200 `structuredContent` object described in 8.5. `downstream` is the service, target and status triple that a handler puts in the audit event (`src/mcp/abw_mcp/servers/research.py:43#downstream`). The audit flag `obo` says whether the handler was written to use the caller's token downstream; it is not proof that an exchange happened (see Findings). Statements are **Implemented** (read from the code) unless labelled **Configured** (Bicep, policy XML, scripts) or **Tested** (section 8.7). Live proofs are cited as `P<nn>` from `demo/prove.py`; they ran as the deploying operator mirroring a persona's roles and groups, not as persona sign-ins (`demo/prove.py:303-304#persona`, section 7.5).

**Tool counts.** research 2, wall 3, actions 3, private 2, vendor 2, legacy 5: 17 tools in all. The governed agent's allow-list names every tool of the five non-legacy servers (12 tools) and puts `place_order` behind human approval (`src/agent/abw_agents.py:42-49#WALL_DESK_TOOLS`).

#### 8.3.1 What every registry server inherits

All six servers use the same `ToolRegistry`. The registry can refuse a call for four reasons that no tool author writes (three before the handler runs, one while it runs). After the handler runs, it writes the audit event and builds the result. A tool's own rules (the following sections) run inside the handler and can only add refusals (`src/mcp/abw_mcp/registry.py:158-220#call_tool`).

| Situation | `reason` | Error code | Payload `decision` | Audit event and decision | Code |
|---|---|---|---|---|---|
| Tool name not in the registry | `unknown_tool` | `NOT_FOUND` | `ERROR` | `tool_denied`, `deny`; no `tool`, no caller fields, `data_class` null, `args_sha256` of `{}`; `obo` true on the four governed servers | `src/mcp/abw_mcp/registry.py:159-161#unknown_tool`; `src/mcp/abw_mcp/registry.py:222-236#_error_result` |
| Requirement not met on a call | `missing_role` or `missing_scope`; `forbidden` if the requirement returns no reason | `FORBIDDEN` | `DENIED` | `tool_denied`, `deny`; caller, tool and `data_class` recorded; `args_sha256` of `{}` | `src/mcp/abw_mcp/registry.py:163-165#forbidden` |
| Arguments fail the model (unknown field, type, range, pattern) | `invalid_arguments` | `INVALID_ARGUMENT` | `ERROR` | `tool_denied`, `deny`; the real arguments are hashed; `obo` false | `src/mcp/abw_mcp/registry.py:167-175#invalid_arguments`; `src/mcp/abw_mcp/registry.py:24-27#ArgsModel` |
| Downstream token exchange fails | `obo_failed:<code>` | `FORBIDDEN` | `DENIED` | `tool_denied`, `deny`; `obo` stays true; no `downstream` | `src/mcp/abw_mcp/registry.py:179-191#obo_failed` |
| Handler raises `ToolError` | the handler's reason | the handler's code | `DENIED` for `FORBIDDEN` and `WALL_VIOLATION`, else `ERROR` | the handler's event and decision | `src/mcp/abw_mcp/registry.py:192-193#ToolError`; `src/mcp/abw_mcp/registry.py:273-292#_error_payload` |
| Handler succeeds | none (legacy: `no_user_context`) | none | none | `tool_call` (actions: `order_placed`), `allow` | `src/mcp/abw_mcp/registry.py:195-220#structuredContent` |
| Handler raises any other exception (for example a Search or Cosmos HTTP error) | none | none | none | no event from the registry | `src/mcp/abw_mcp/registry.py:177-193#except` |

Two rules apply to every row. Role-less callers never see the tool in `tools/list` (`src/mcp/abw_mcp/registry.py:132-137#requirement`). The reason `missing_role` seen at the MCP server is an HTTP 200 `DENIED`, not the HTTP 403 that the gateway returns for the same case (section 7.3, `src/mcp/tests/test_servers.py:250-266#test_entitled_to_nothing_sees_no_tools_and_cannot_call`).

**Why.** Putting these refusals in the registry means a new tool cannot forget the role gate, the validation or the audit event. **Trade-off / limitation.** The registry cannot know a tool's data rule, so a handler that skips its own check is unprotected at Layer 2 (section 8.8). The last row is **Inference** from the code: there is no catch-all clause, so an unmapped exception leaves `call_tool` before any audit emit; how the MCP SDK renders it is not tested in this repo (Findings).

**Narrative.**

- **Two independent walls.** Layer 2 is the role-to-project map. Layer 3 is the group grant on the container. P03 shows the Falcon document returned and the Orion document and Orion search refused for a Falcon-crossed caller, with a `request_id` on the refusal (`demo/prove.py:639-655#p03`). P16 provides the Storage-side check: it removes the caller's Falcon group membership while the Entra role claim is unchanged, so Layer 2 still passes and Storage refuses with `storage_rbac_denied` (`demo/prove.py:963-989#p16`).
- **The event name does not say which wall refused.** `wall_violation_attempt` is used for both the pre-check refusal and a Storage 403. Tell them apart by `reason` (`project_not_in_token_roles` versus `storage_rbac_denied`) and by `downstream.service` (search versus storage).

- **What search returns.** Wall documents carry a roughly 240-character summary and no snippet or content in the index, so the search tool can only ever return summaries (`src/seed/seed.py:131-172#build_search_documents`). Full text needs `get_deal_document`, which Storage then evaluates.
- **Trade-off / limitation.** Adding a deal touches an app role, the gateway's role list, this file in several places and a Storage container with a grant (section 8.8). There is no entitlement store (section 7.9).

- **Proof.** P04 shows ZYNX on the list, ACME not, a ZYNX buy refused, an ACME buy accepted with an order id, and the order visible in the caller's own list (`demo/prove.py:660-681#p04`). P05 shows the human approval gate on the agent side (`demo/prove.py:689-702#p05`).
- **`separation_of_duties` cannot fire with real tokens.** Roles are issued per API, so a token for the actions API cannot carry `Wall.*` roles. ### 8.4 The audit event

**What this section proves.** Every refused bearer token, every `tools/call` and every `tools/list` call (one event per visible tool) becomes one structured JSON event of 21 keys; vendor key failures and unexpected handler exceptions write no audit event (`src/mcp/abw_mcp/auth.py:224-239#auth_failed`; `src/mcp/abw_mcp/registry.py:177-193#OboError`; `src/mcp/abw_mcp/app.py:115-141#VendorKeyMiddleware`). The event is built in one function and handed unchanged to every sink (`src/mcp/abw_mcp/audit.py:178-216#build_event`). The identity fields are copied from the verified token, never from the request body (`src/mcp/abw_mcp/audit.py:201-208#getattr`). Tool arguments and results are never stored, only a SHA-256 of the arguments and a byte count of the answer (`src/mcp/abw_mcp/audit.py:212-213#args_sha256`). The section is also candid about the limits: how durable the trail is depends on platform settings more than on code. The retention policy on the audit container is unlocked, a failed blob write is silent by default, and the Application Insights copy may not be delivered at all (Inference, below; Findings).

**How to read the tables.** Statements are **Implemented** (read from code) unless labelled **Configured** (Bicep, policy XML, scripts), **Designed** (`DESIGN.md`), **Tested** (section 8.7) or **Platform behaviour** (a Microsoft Learn URL in plain text). A value in angle brackets is an identifier or digest that this document never prints. How `request_id` joins the layers is section 10, and how the detections read these events is section 11. This section covers the producer.

**Notes on the fields.**

1. **Identity comes only from the token.** No tool accepts a user, role or group parameter, so nothing in the arguments can change who the event names (**Designed**: `DESIGN.md:131#identity`; **Implemented**: `src/mcp/abw_mcp/registry.py:158-165#call_tool`). The event has no group list: the frozen `Caller` has no groups field, because the groups that decide Layer 3 are evaluated by the data plane on the user's own token (`src/mcp/abw_mcp/auth.py:29-41#Caller`, section 7.5).
2. **`user_upn` is a label, `user_oid` is the key.** Learn describes `preferred_username` as mutable and says it cannot be used for authorization decisions, and the claims-validation guidance says the same for `email` and `unique_name` (Platform behaviour: https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference and https://learn.microsoft.com/entra/identity-platform/claims-validation). The claim also needs the `profile` scope and exists only in v2.0 tokens. The code accepts only v2.0 tokens (`src/mcp/abw_mcp/auth.py:144-145#bad_issuer`). Whether the deployed tokens carry the claim is not checked in this repo, yet `AbwDenials.kql` shows it as the principal name for Layer 2 rows (`observability/kql/AbwDenials.kql:63#Principal`).
3. **`jti`.** Learn documents `uti` as the token identifier claim, "equivalent to `jti` in the JWT specification", unique per token and case-sensitive (Platform behaviour: https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference). The code falls back to an empty string, not null, when neither claim exists (`src/mcp/abw_mcp/auth.py:168#uti`). Section 6 covers the token itself.
4. **`obo` is set by the code path.** It defaults to true for successful outcomes and for handler errors, is false for `auth_failed` and for an argument-validation failure, and is computed as "the server is neither legacy nor vendor" for list events, unknown-tool events and requirement failures (`src/mcp/abw_mcp/registry.py:151#legacy`, `src/mcp/abw_mcp/registry.py:222-236#_error_result`, `src/mcp/abw_mcp/registry.py:167-175#invalid_arguments`, `src/mcp/abw_mcp/auth.py:235#obo`). On the four governed servers it is therefore true on a refusal that happens before any exchange, so it cannot be read as "an exchange took place" (Findings).
5. **`trace_id` can be null.** It is read from the active OpenTelemetry span. If the observability setup returned early because there is no connection string, no span context with a valid id exists and the field is null (**Inference** from `src/mcp/abw_mcp/app.py:63-65#connection_string`, `src/mcp/abw_mcp/audit.py:149-151#is_valid`).
6. **Who is not in the event.** For an unknown tool the registry builds the event without the caller and without the tool name, so a verified user whose request names a non-existent tool appears with null identity (`src/mcp/abw_mcp/registry.py:159-161#unknown_tool`, `src/mcp/abw_mcp/registry.py:222-236#_error_result`). An `auth_failed` event never carries identity either, even when the token was fully parsed before a later check failed (`src/mcp/abw_mcp/auth.py:224-239#auth_failed`).

One more kind of record is not an audit event. #### 8.4.3 Where each event goes: two sinks, three destinations

The production service is built with two sink objects: the first writes two destinations, the `abw.audit` logger record and then the console line, and the second appends the event to the per-server, per-day blob (`src/mcp/abw_mcp/audit.py:222#StdoutLoggerAuditSink`). The vendor server gets the same two sinks as every other server (`src/mcp/abw_mcp/audit.py:219-223#build_default_audit_service`). `AuditService.emit` calls each sink in order with no `try` block, so an exception in the first sink would stop the second and would surface in the request (`src/mcp/abw_mcp/audit.py:174-176#sink`).

**Platform behaviour behind the table.**

1. **Which copy does the repo itself read?** The console copy. #### 8.4.4 The WORM blob in detail

The append-blob sink is the one that is supposed to make the trail tamper-evident. Its behaviour has several details that matter to an auditor.

1. **Name.** The blob is `<server>/<YYYY>/<MM>/<DD>/<server>.jsonl`, derived from the event's own `ts`. That is one append blob per server per UTC day (`src/mcp/abw_mcp/audit.py:130-133#jsonl`). The container is `worm-audit` by default, and the account is the same account that holds the research and wall data (`src/mcp/abw_mcp/config.py:149#AUDIT_CONTAINER`, `infra/04-apps.bicep:57-59#AUDIT_STORAGE_ACCOUNT`).
2. **Credential.** The sink uses the server's own managed identity (`ManagedIdentityCredential` with the settings' identity client id), never the user's token, so a write does not depend on the user's rights (`src/mcp/abw_mcp/audit.py:129#ManagedIdentityCredential`).
3. **Create-if-missing.** The first write of a day per process reads the blob's properties. If that fails for any reason, it calls create, and if create fails it reads the properties again (`src/mcp/abw_mcp/audit.py:105-117#create_append_blob`). The Python SDK documents `create_append_blob` as overwriting the content of any existing blob (https://learn.microsoft.com/python/api/azure-storage-blob/azure.storage.blob.blobclient). So a transient failure of the properties call, on a blob that exists, would lead to an overwrite attempt. Both locked and unlocked time-based policies protect blobs against overwrites (https://learn.microsoft.com/azure/storage/blobs/immutable-time-based-retention-policy-overview), so it is the container policy, not this code, that stops a truncation. Two replicas may race on the first write of a day (`infra/modules/mcp-app.bicep:19-20#maxReplicas`). This is an **Inference** from the code and the Learn text, untested.
4. **Append.** Each event is one `append_block` of `canonical_json(event) + newline` encoded as UTF-8 (`src/mcp/abw_mcp/audit.py:118#append_block`). Under a lock, so only one thread writes at a time within a process (`src/mcp/abw_mcp/audit.py:106#_lock`).
5. **Fail-open by default.** `emit` puts the event on a queue and returns. A daemon thread named `abw-audit-blob` writes it later (`src/mcp/abw_mcp/audit.py:72-76#abw-audit-blob`, `src/mcp/abw_mcp/audit.py:88-92#emit`). If a write raises, the thread prints `append_audit_failed` to standard error, logs the exception and goes on to the next event. The failed event is dropped (`src/mcp/abw_mcp/audit.py:94-103#append_audit_failed`). At shutdown, `stop` queues an end marker and waits at most five seconds for the thread (`src/mcp/abw_mcp/audit.py:78-86#join`).
6. **Fail-closed, optional.** With `AUDIT_FAIL_CLOSED` true there is no thread. `emit` appends synchronously and any exception propagates to the caller (`src/mcp/abw_mcp/audit.py:88-91#audit_fail_closed`). The setting defaults to false and Bicep does not set it, so the deployment runs fail-open (`src/mcp/abw_mcp/config.py:150#AUDIT_FAIL_CLOSED`; `infra/04-apps.bicep:53-66#commonEnv` has no such entry). Fail-closed is also not "audit before act": the registry emits after the data call returned, on the event-loop thread (`src/mcp/abw_mcp/registry.py:177-218#emit`).
7. **The retention policy.** The container has a time-based retention policy of one day with protected append writes allowed. Bicep leaves it unlocked and says it is a demonstration of the pattern, not a compliance attestation (**Configured**: `infra/03-platform.bicep:195-202#wormPolicy`; **Designed**: `DESIGN.md:239#unlocked`).
8. **The role.** Every server identity except the vendor's gets Storage Blob Data Contributor, scoped to the `worm-audit` container only (**Configured**: `infra/03-platform.bicep:548-556#raAuditAppend`). That role reads, writes and deletes containers and blobs (https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/storage#storage-blob-data-contributor). The policy, not the role name, is what makes the blobs append-only.

**Platform behaviour for the policy** (https://learn.microsoft.com/azure/storage/blobs/immutable-container-level-worm-policies#allow-protected-append-blobs-writes and https://learn.microsoft.com/azure/storage/blobs/immutable-time-based-retention-policy-overview):

- With an active time-based policy, appending to an append blob is prohibited unless protected append writes are allowed. With the property on, a blob can be created in the protected container and new blocks appended, while existing blocks cannot be modified or deleted. The effective retention of an append blob is the time of the last append plus the interval.
- The minimum interval is one day. A new policy is unlocked, "for testing purposes". An unlocked policy can be shortened or deleted and the append property can be toggled; a locked policy cannot be deleted and its interval can only be extended. SEC 17a-4(f) compliance needs a locked policy, and Microsoft recommends locking within about 24 hours.
- An unlocked policy gives no protection against deletion of the container or the account.

**Why.** Append-only semantics with a platform-enforced retention gives a tamper-evident trail without a custom hash chain, and the managed identity keeps the write independent of the user. **Trade-off / limitation.**

- **Durability is configuration, not code.** One day of retention, unlocked: after a blob's last append plus one day, a holder of the contributor role can delete it, and a holder of the management-plane rights can shorten or remove the policy (Findings).
- **Fail-open.** A failed append loses the event and writes only a stderr line (`src/mcp/abw_mcp/audit.py:101-103#Exception`).
- **Five-second flush.** Events still queued after the five-second join at shutdown can be lost. The queue has no size limit (`src/mcp/abw_mcp/audit.py:64#Queue`).
- **Any server can write into any server's blob.** The role is container-wide, so a compromised server identity can append lines to another server's day-blob, and can read the lot. The lines are not signed and carry no sequence number or hash chain, so an inserted line cannot be told from a real one inside the file (**Inference** from `infra/03-platform.bicep:548-556#raAuditAppend` and `src/mcp/abw_mcp/audit.py:118#append_block`).
- **A cap of 50,000 blocks.** The blob name has no counter, so there is no roll-over (`src/mcp/abw_mcp/audit.py:131-133#jsonl`). Learn gives the limit as 50,000 appends per append blob (https://learn.microsoft.com/rest/api/storageservices/append-block#remarks and https://learn.microsoft.com/azure/storage/blobs/scalability-targets#scale-targets-for-blob-storage). Once a day-blob is full, further appends fail, which is silent in fail-open mode and a failed call in fail-closed mode. This is an **Inference** from the cited limits and the blob naming.
- **The vendor identity is not in the role assignment**, although the vendor server builds the sink (`infra/03-platform.bicep:548#vendor`, `src/mcp/abw_mcp/audit.py:222#AppendBlobAuditSink`). Its blob writes should therefore fail and be dropped silently, leaving the console line as the only record for the vendor server (**Inference**, untested).

#### 8.4.5 Why arguments are hashed, and what `data_class` is

**Arguments are hashed so the trail proves which arguments were used without becoming a second copy of what the user asked for.** The design says never to log tool arguments or document content, only a hash and a size (**Designed**: `DESIGN.md:141#Never`). The reason is a governance one (**Inference** from that rule and the wall design): the audit trail has a wider readership than the wall, so it must not hold wall content or free-text queries. A test plants a canary string in the arguments and checks that it is absent from the serialised event while `args_sha256` is present (**Tested**: `src/mcp/tests/test_servers.py:160-175#test_audit_redacts_arguments_and_content`).

The hash is the SHA-256 of the UTF-8 bytes of the arguments as JSON with sorted keys, compact separators, non-ASCII characters left as they are, and unknown types turned into strings (`src/mcp/abw_mcp/util.py:14-24#sha256_json`). Anyone holding a candidate argument object can recompute it and compare. Which arguments are hashed depends on the path:

| Situation | `args_sha256` is the hash of | Code |
|---|---|---|
| `tool_listed` | nothing (null) | `src/mcp/abw_mcp/registry.py:132-156#args` |
| `auth_failed` | nothing (null) | `src/mcp/abw_mcp/auth.py:233#args` |
| Unknown tool | an empty object | `src/mcp/abw_mcp/registry.py:222-236#_error_result` |
| Requirement failure (`missing_role`, `missing_scope`) | an empty object, not the real arguments | `src/mcp/abw_mcp/registry.py:163-165#forbidden` |
| Argument validation failure | the arguments as sent | `src/mcp/abw_mcp/registry.py:167-175#invalid_arguments` |
| Handler refusal or error | the arguments as sent (an empty object when there are none) | `src/mcp/abw_mcp/registry.py:256#arguments` |
| Success | the arguments as sent (an empty object when there are none) | `src/mcp/abw_mcp/registry.py:202-216#args` |

**Trade-off / limitation.** A hash is a fingerprint, not redaction. For a low-entropy argument such as a ticker, a note id or a project name, anyone with the log can hash candidates and find the match. It protects free text and large content, not small identifiers. The hash also does not tell an auditor which document was read unless a candidate id is already known. For blob reads the event names the container and status, not the object. The object name is in the Storage diagnostic log, which records the requested URI, the requester's object id and the client request id, and the MCP stamps its request id on the downstream call as that client request id (Platform behaviour: https://learn.microsoft.com/azure/azure-monitor/reference/tables/storagebloblogs; **Implemented**: `src/mcp/abw_mcp/data.py:24-28#downstream_request_id`; **Configured**: `observability/kql/AbwDenials.kql:77#ClientRequestId`). So the MCP event answers who, what kind of call, and which decision, and the Storage log answers which object.

**`data_class` is a constant per tool, not a property of the data returned.** It is set once on each tool definition (`src/mcp/abw_mcp/registry.py:78-91#ToolDefinition`):

| `data_class` | Tools | Code |
|---|---|---|
| `public` | research: `search_research`, `get_research_note` | `src/mcp/abw_mcp/servers/research.py:75#public`; `src/mcp/abw_mcp/servers/research.py:83#public` |
| `wall` | wall: `list_my_wall_crossings`, `search_deal_documents`, `get_deal_document` | `src/mcp/abw_mcp/servers/wall.py:120#wall`; `src/mcp/abw_mcp/servers/wall.py:128#wall`; `src/mcp/abw_mcp/servers/wall.py:136#wall` |
| `internal` | actions (3 tools) and private (2 tools) | `src/mcp/abw_mcp/servers/actions.py:138#internal`; `src/mcp/abw_mcp/servers/private.py:67#internal` |
| `external` | vendor mock (2 tools) | `src/mcp/abw_mcp/servers/vendor.py:70#external` |
| `mixed` | legacy `search_research`, `search_deal_documents`, `get_deal_document`, `place_order` | `src/mcp/abw_mcp/servers/legacy.py:116-119#mixed` |
| `internal` | legacy `get_firm_positions` | `src/mcp/abw_mcp/servers/legacy.py:120#internal` |

The design text lists `public`, `wall:falcon`, `wall:orion` and `internal` (**Designed**: `DESIGN.md:138#data_class`). The code has no per-project class, and adds `external` and `mixed`. The consequence is that the project a user touched is not a field. It can be read from `downstream.target` only on some paths: the container name on a successful `get_deal_document`, and the project name on a pre-check refusal. A successful `search_deal_documents` records the index name (`src/mcp/abw_mcp/servers/wall.py:84#search_index`), so its project is recoverable only through the argument hash (Findings).

#### 8.4.6 What the trail answers, and what it does not

**What this section proves.** The event answers who, which tool, which decision and when from the verified token and the code path (`src/mcp/abw_mcp/audit.py:178-216#build_event`). It does not by itself answer which object was read, which group admitted the user, or whether the record is complete. Those answers sit in the data plane's own logs and in the retention policy of the container.

| Question an auditor asks | Where the answer is | Caveat |
|---|---|---|
| Who called which tool, when, with which decision? | `user_oid`, `user_upn`, `azp`, `server`, `tool`, `ts`, `decision` (8.4.1) | `user_upn` is display only. Unknown-tool and `auth_failed` rows have no identity. |
| Which arguments? | `args_sha256`: recompute from a candidate | Not reversible. Requirement failures hash an empty object. |
| Which document? | The Storage diagnostic log, joined on the request id | The MCP event has the container only |
| Which group let the user in? | The data plane's own logs and the user's group membership | Not in the MCP event: there is no groups field |
| Was this the same token as another call? | `jti` | Can be an empty string |
| Was the refusal a policy or an error? | `reason`, and the wire `decision` (section 8.5) | The audit `decision` is only `deny`, even for "not found" |
| Is the record complete and unaltered? | The retention policy of the audit container | One day, unlocked; fail-open writes; no hash chain (8.4.4) |

### 8.5 Error and denial taxonomy

**What this section proves.** Every refusal that ABW code or gateway policy writes itself arrives in one of six wire shapes, and the shape depends on the layer that refused as much as on the cause. Two cases fall outside the six: a call to the legacy API without its subscription key is refused by APIM itself with a 401 (**Configured**: `infra/05-apim-apis.bicep:176#subscriptionRequired`; Platform behaviour: https://learn.microsoft.com/azure/api-management/api-management-subscriptions), and an unmapped exception reaches the client as whatever the MCP SDK makes of it (8.5.6). Tool-level refusals are built in one place (`src/mcp/abw_mcp/registry.py:273-292#_error_payload`), and only two error codes count as a policy denial (`src/mcp/abw_mcp/registry.py:42#DENIED_CODES`). Other failures, such as "not found" and "invalid argument", come back as errors but are still audited as `deny`. The same cause (a client that is not allowed, a missing scope, a caller with no role) is refused with a different body at the gateway and at the server (8.5.7). This section lists each reason once: where it is raised, what the caller sees and what the audit trail records. The audit fields are in 8.4, the gateway decision order is in 7.3 and the rules behind the tool-level refusals are in 7.4.

**How to read the tables.** Statements are **Implemented** (read from code) unless labelled **Configured** (Bicep, policy XML), **Designed** (`DESIGN.md`), **Tested** (8.7), **Inference** or **Platform behaviour** (a Microsoft Learn URL in plain text). The wire-shape column uses the identifiers S1 to S6 from 8.5.1. The audit column gives the event name and the decision exactly as 8.4 describes them; refusals at the gateway are not in the MCP audit trail at all. Reason strings are the values of the `reason` field. The reason for a wrong target API is written `bad_aud` + `ience`, following the spelling note in 7.4.

#### 8.5.1 Six wire shapes, three vocabularies, soft versus strict

The registry builds shape S6 in one function (`src/mcp/abw_mcp/registry.py:238-270#_tool_error_result`). The other five shapes are produced before any tool code runs, by the gateway or by one of the two middleware classes that sit in front of the registry.

| Id | Produced by | HTTP | Body | Challenge header | Code |
|---|---|---|---|---|---|
| S1 | APIM, token validation failed | 401 | JSON: `error` is `unauthorized`, plus `server` and a fixed sentence in `reason` (a sentence, not a code) | Yes: `error` is `invalid_token`, plus a parameter that points at the PRM document URL | `infra/apim/policies/mcp-jwt.policy.xml:96-112#invalid_token` |
| S2 | APIM, deny decision | 403 | JSON: `error` is `forbidden`, plus `reason` (a code), `server` and `request_id` | None | `infra/apim/policies/mcp-jwt.policy.xml:64-80#forbidden` |
| S3 | APIM, rate limit | 429 | Native APIM answer; the policy sets no custom body | Not set by the policy | `infra/apim/policies/mcp-jwt.policy.xml:81#rate-limit-by-key` |
| S4 | Vendor mock, wrong or missing vendor key | 401 | JSON: `error` is `invalid_vendor_key` | None set in code | `src/mcp/abw_mcp/app.py:139-141#invalid_vendor_key` |
| S5 | MCP bearer middleware, `/mcp` only | 401 or 403 | JSON: `error` is `invalid_token` (401) or `insufficient_scope` (403), plus `error_description` holding the reason code | Yes: `error`, `error_description` and the same PRM parameter | `src/mcp/abw_mcp/auth.py:250-260#_auth_error_response` |
| S6 | Registry, tool-level | 200 | A tool result whose text content and `structuredContent` both hold the JSON shown below; `decision` is `DENIED` or `ERROR` | None | `src/mcp/abw_mcp/registry.py:238-270#_tool_error_result` |

No refusal in this code is a JSON-RPC `error` object. S6 is a normal JSON-RPC result, and the S1 to S5 shapes are plain HTTP answers. Any JSON-RPC error that exists would come from the MCP SDK for a protocol problem (SDK behaviour, not verified here).

**Three vocabularies.** The same event is described by three different word lists, and they do not map one to one.

| Vocabulary | Values | Defined at |
|---|---|---|
| Wire `error` string at the HTTP level | `unauthorized` (S1), `forbidden` (S2), `invalid_vendor_key` (S4), `invalid_token` or `insufficient_scope` (S5) | `infra/apim/policies/mcp-jwt.policy.xml:64-80#forbidden`; `src/mcp/abw_mcp/auth.py:44-57#AuthError` |
| Tool error `code` and payload `decision` | `FORBIDDEN` and `WALL_VIOLATION` give `DENIED`. `NOT_FOUND` and `INVALID_ARGUMENT` give `ERROR`. | `src/mcp/abw_mcp/registry.py:42#DENIED_CODES`; `src/mcp/abw_mcp/registry.py:273-279#_error_payload` |
| Audit `event` and `decision` | `decision` is only `allow` or `deny`. A `ToolError` defaults to event `tool_denied` and decision `deny`; handlers override the event (`wall_violation_attempt`, `order_blocked`). | `src/mcp/abw_mcp/registry.py:54-75#ToolError`; `src/mcp/abw_mcp/registry.py:63-65#tool_denied` |

So a "not found" is payload `ERROR` and audit `deny`, and an operator who filters the audit trail on `deny` sees it next to real denials (Findings).

**Soft versus strict.**

1. **Default (`soft`).** A refusal is an ordinary tool result: HTTP 200, `isError` false. The same compact JSON is the text content item and the `structuredContent` (`src/mcp/abw_mcp/registry.py:247#compact_json`; `src/mcp/abw_mcp/registry.py:266-270#structuredContent`).
2. **`strict`.** `isError` is set true on every error result, not only on denials. The expression at `src/mcp/abw_mcp/registry.py:269#strict` sits in the one function that every error result passes through, so `NOT_FOUND` and `INVALID_ARGUMENT` results are flagged too.
3. **Setting.** `MCP_DENIAL_MODE` defaults to `soft` (`src/mcp/abw_mcp/config.py:157#MCP_DENIAL_MODE`). The Bicep settings list does not set it (`infra/04-apps.bicep:53-66#commonEnv`), so every deployed server runs soft. Any other value than `soft` or `strict`, in any letter case, makes `Settings.from_env` raise (`src/mcp/abw_mcp/config.py:21-26#_parse_denial_mode`). The settings are read when the app first handles a scope, not in the start command, so the process stays up and answers HTTP 500 to every request instead of exiting (Inference, 8.1.3).
4. **Why.** The code comment states that Foundry Agent Service aborts the whole run with HTTP 400 `tool_user_error` when a tool returns `isError` true, so a denial is returned as a normal result that the model can explain, while the audit event is still written first (`src/mcp/abw_mcp/registry.py:263-265#isError`). I searched Microsoft Learn for this behaviour and did not find it documented, so treat it as the code's own statement. `DESIGN.md` gives the user-facing reason (`DESIGN.md:227#Soft`) and notes that a denial therefore prints as status `ok` and must be detected from the body (`DESIGN.md:228#content-based`).
5. **Tested.** Soft: `src/mcp/tests/test_servers.py:67-86#test_wall_isolation_and_audit` asserts that `isError` is false (line 79). Strict: `src/mcp/tests/test_servers.py:234-247#test_strict_denial_mode_uses_mcp_is_error`.

**Illustrative example of S6** (a soft denial; the values in angle brackets are placeholders; the key order is the code order, and the `request_id` key is present only when the request carried one):

```json
{
  "decision": "DENIED",
  "error": "FORBIDDEN",
  "message": "Caller is not crossed on that project.",
  "reason": "project_not_in_token_roles",
  "request_id": "<request-id>",
  "note": "<fixed instruction to the model: blocked by policy and logged; tell the user what was blocked and the reason code; do not retry, rephrase or look for a workaround>"
}
```

The key order and the optional keys come from `src/mcp/abw_mcp/registry.py:273-292#_error_payload`. The `note` is a fixed instruction aimed at the model, not at the user (`src/mcp/abw_mcp/registry.py:286-289#note`); the note for `INVALID_ARGUMENT` tells the model to fix the arguments and retry once (`src/mcp/abw_mcp/registry.py:290-291#INVALID_ARGUMENT`). `request_id` is read from the request context (`src/mcp/abw_mcp/registry.py:282-284#request_id`), and successful results carry it too (`src/mcp/abw_mcp/registry.py:197-200#request_id`).

**Trade-off / limitation.** In soft mode a client that checks only the HTTP status or `isError` sees a success. It has to read `structuredContent.decision`. The gateway has no outbound processing (`infra/apim/policies/mcp-jwt.policy.xml:93-95#outbound`), so APIM records these answers as ordinary successful calls (Inference). Tool-level denials are therefore visible only in the MCP audit event (8.4) and its detections (section 11).

#### 8.5.2 Gateway refusals (S1 to S3)

The gateway runs these checks before a request reaches a server. The full decision order and the per-API parameters are in 7.3. The deny reason is computed once, by a chain of `if` statements that returns at the first match, so the order of the checks decides which reason the caller sees (`infra/apim/policies/mcp-jwt.policy.xml:31-46#abw-deny`). A refusal at this layer never reaches the MCP server, so it has no MCP audit event.

| Reason | Where raised | Wire shape | Recorded |
|---|---|---|---|
| Token invalid; body `error` is `unauthorized` (no code) | `validate-jwt` fails at `infra/apim/policies/mcp-jwt.policy.xml:17-30#validate-jwt`; `on-error` answers at `infra/apim/policies/mcp-jwt.policy.xml:96-112#invalid_token` | S1 | Inference: only in the APIM gateway log. The decision metric and trace run later in the pipeline and are skipped on this path. |
| `revoked` | `infra/apim/policies/mcp-jwt.policy.xml:37#revoked` | S2 | Metric and trace, then the 403 |
| `client_not_allowed` | `infra/apim/policies/mcp-jwt.policy.xml:38#client_not_allowed` | S2 | Metric and trace, then the 403 |
| `missing_scope` | `infra/apim/policies/mcp-jwt.policy.xml:39#missing_scope` | S2 | Metric and trace, then the 403 |
| `missing_role` | `infra/apim/policies/mcp-jwt.policy.xml:44#missing_role` | S2 | Metric and trace, then the 403 |
| Rate limit exceeded (120 calls per 60 s per user) | `infra/apim/policies/mcp-jwt.policy.xml:81#rate-limit-by-key` | S3 | The metric already counted an allow for this call (Inference from the order) |

- **What `validate-jwt` pins.** The bearer scheme, an expiry, a signature, a 60 second clock skew, the issuer, the target API (`aud`) and the `tid` claim must all be present and right. Any failure gets the same S1 body with no machine-readable reason (`infra/apim/policies/mcp-jwt.policy.xml:17-30#validate-jwt`). The specific reason code exists only in the server's own S5 answer (8.5.3), which the gateway never reaches. Platform behaviour: when an error occurs, the remaining steps of the `inbound`, `backend` and `outbound` sections are skipped and execution jumps to `on-error` (https://learn.microsoft.com/azure/api-management/api-management-error-handling-policies#error-handling-in-api-management). By that rule the metric and trace are not emitted for S1 (Inference).
- **Telemetry for S2.** The metric `abw-gateway-decisions` and the trace record both allows and denies, and both run before the `choose` that returns the 403 and before the limiter (`infra/apim/policies/mcp-jwt.policy.xml:51-56#abw-gateway-decisions`; `infra/apim/policies/mcp-jwt.policy.xml:57-63#request_id`). The 403 body repeats the same request id (`infra/apim/policies/mcp-jwt.policy.xml:64-80#forbidden`).
- **`discovery` is not a refusal and not a reason code.** It is a policy variable that waives the role check for `initialize`, `ping`, `tools/list` and `notifications/*` when the list-open placeholder is true (`infra/apim/policies/mcp-jwt.policy.xml:42#discovery`); the reason logged for an allowed call is `ok` (`infra/apim/policies/mcp-jwt.policy.xml:54#reason`). A caller with no role can therefore list tools through the gateway, and the server answers with an empty list (7.4).
- **S3.** Platform behaviour: `rate-limit-by-key` answers 429 when the limit is exceeded (https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy). Which APIs share one counter is an open question (7.3).

#### 8.5.3 Container-edge refusals (S4 and S5)

Two checks sit in front of the registry inside the container. Both return before any tool code runs, and the choice between them depends on the server (`src/mcp/abw_mcp/app.py:241-253#BearerAuthMiddleware`).

**S4, the vendor mock.** The vendor server has no bearer check. Its middleware compares the `x-vendor-key` header with the configured key in constant time and answers 401 `invalid_vendor_key` on a mismatch (`src/mcp/abw_mcp/app.py:115-142#VendorKeyMiddleware`; `src/mcp/abw_mcp/app.py:138#compare_digest`; `src/mcp/abw_mcp/app.py:139-141#invalid_vendor_key`). The refusal returns before the registry, so no MCP audit event is written. Before the comparison, a log line named `vendor_request` goes to the logger `abw.vendor`. It records whether an authorization header and a vendor key were present, and the client address, not their values (`src/mcp/abw_mcp/app.py:129-138#vendor_request`). The gateway adds the key for the vendor API, so an agent or user never holds it (7.3).

**S5, the bearer middleware.** Every other server except legacy wraps the exact path `/mcp` in token validation (`src/mcp/abw_mcp/auth.py:209-212#/mcp`). Section 6 covers how the token is checked; this table covers what the caller sees.

| Reason (`error_description`) | HTTP and `error` | Condition | Code |
|---|---|---|---|
| `missing_token` | 401 `invalid_token` | No bearer value in the `Authorization` header | `src/mcp/abw_mcp/auth.py:111-112#missing_token` |
| `bad_signature` | 401 `invalid_token` | The header cannot be parsed, no key matches the `kid`, the signature does not verify, or any other decode failure | `src/mcp/abw_mcp/auth.py:113-116#bad_signature`; `src/mcp/abw_mcp/auth.py:129-130#bad_signature`; `src/mcp/abw_mcp/auth.py:141-142#bad_signature` |
| `bad_aud` + `ience` | 401 `invalid_token` | `aud` is neither the bare client id nor its `api://` form | `src/mcp/abw_mcp/auth.py:131-132#bad_aud`; `src/mcp/abw_mcp/config.py:73-75#mcp_app_client_id` |
| `bad_issuer` | 401 `invalid_token` | `iss` is wrong, or the token is not a v2.0 token | `src/mcp/abw_mcp/auth.py:133-134#bad_issuer`; `src/mcp/abw_mcp/auth.py:144-145#bad_issuer` |
| `expired` | 401 `invalid_token` | `exp` is in the past, after a 60 second leeway | `src/mcp/abw_mcp/auth.py:135-136#expired`; `src/mcp/abw_mcp/auth.py:118-128#leeway` |
| `not_yet_valid` | 401 `invalid_token` | `nbf` is in the future, after the same leeway | `src/mcp/abw_mcp/auth.py:137-138#not_yet_valid` |
| `bad_tenant` | 401 `invalid_token` | `tid` is not the configured tenant | `src/mcp/abw_mcp/auth.py:146-147#bad_tenant` |
| `app_only` | 401 `invalid_token` | The token is an app-only token, or has no `oid` | `src/mcp/abw_mcp/auth.py:148-149#app_only` |
| `bad_azp` | 401 `invalid_token` | `azp` is not in the configured list; checked only when the list is not empty | `src/mcp/abw_mcp/auth.py:151-153#bad_azp` |
| `missing_scope` | 403 `insufficient_scope` | `scp` lacks the required scope (default `Tools.Read`) | `src/mcp/abw_mcp/auth.py:156-157#missing_scope` |

- **Wire body and challenge.** The body is `error` plus `error_description`, and the `WWW-Authenticate` header repeats both and adds a parameter that points at the PRM document URL (`src/mcp/abw_mcp/auth.py:250-260#_auth_error_response`; `src/mcp/abw_mcp/auth.py:257#error_description`). The status is 403 only for `missing_scope` and `missing_role`, and 401 for every other reason (`src/mcp/abw_mcp/auth.py:44-57#AuthError`).
- **Audit.** Every S5 refusal writes one `auth_failed` event with decision `deny` and the reason code. The event has no caller identity, no argument hash, `result_bytes` 0 and `obo` false (`src/mcp/abw_mcp/auth.py:224-239#auth_failed`).
- **Open routes.** Only the exact path `/mcp` is protected. `/healthz` and the PRM route are reachable without a token by design (`src/mcp/abw_mcp/auth.py:209-212#/mcp`).
- **A hook that is never wired.** The middleware accepts an optional `authorization_check` function that would raise `missing_role` at this layer (`src/mcp/abw_mcp/auth.py:194-223#authorization_check`). The application does not pass one (`src/mcp/abw_mcp/app.py:243-249#BearerAuthMiddleware`), so role checks happen only in the registry (8.5.4).

**Trade-off / limitation.** An S5 answer carries the precise reason, which helps a developer but also tells a probing client which check failed. The gateway's S1 answer is deliberately vague. Because the gateway is in front of the research, wall, actions and vendor servers, a probe normally meets S1 first; the private server has no gateway.

#### 8.5.4 Registry refusals (S6)

All of these come back as HTTP 200 and go through one function that emits the audit event and builds the payload (`src/mcp/abw_mcp/registry.py:238-270#_tool_error_result`). The checks run in a fixed order: unknown tool, requirement, argument validation, then the handler (`src/mcp/abw_mcp/registry.py:158-193#call_tool`).

| Reason | Where raised | Payload `error` and `decision` | Audit event and decision | Notes |
|---|---|---|---|---|
| `unknown_tool` | `src/mcp/abw_mcp/registry.py:159-161#unknown_tool` | `NOT_FOUND`, `ERROR` | `tool_denied`, `deny` | No caller and no tool are passed, so the event has no identity fields, no tool name and no data class; the arguments are hashed as `{}` (`src/mcp/abw_mcp/registry.py:222-236#_error_result`) |

#### 8.5.6 What is not mapped

The mapping is partial. These cases are not turned into a denial or an error shape (Implemented, from the structure of the code).

1. **Search errors.** `search_documents` has no error mapping, and the OBO call that builds its credential runs outside any `try` (`src/mcp/abw_mcp/data.py:73-97#search_documents`). A Search 403 or 5xx leaves the handler as an exception.
2. **Cosmos errors.** A point read returns nothing on 404 and re-raises every other error (`src/mcp/abw_mcp/data.py:99-116#cosmos_read_item`). Query and upsert have no mapping at all (`src/mcp/abw_mcp/data.py:118-135#cosmos_query_items`; `src/mcp/abw_mcp/data.py:137-147#cosmos_upsert_item`). The Cosmos status codes for a data-plane RBAC refusal are not mapped in this repo.
3. **Storage errors other than 404 and 403.** They are re-raised (`src/mcp/abw_mcp/data.py:57-71#read_blob_text`).
4. **Exchange failures that are not an MSAL error result.** The broker converts only a returned error into `OboError` (`src/mcp/abw_mcp/obo.py:64-75#acquire_token_on_behalf_of`), so a network failure inside the call would propagate unchanged (Inference).
5. **Any other exception.** `call_tool` catches `OboError` and `ToolError` only (`src/mcp/abw_mcp/registry.py:177-193#OboError`). An unmapped exception therefore skips every audit emit, so **no MCP audit event is written** for that call (Inference from the code structure; there is no test). How the SDK renders the exception to the client is SDK behaviour, not verified here.
6. **Protocol errors.** A malformed JSON-RPC message, an unknown method or a bad session is handled inside the SDK. SDK behaviour, not verified here.
7. **A failing audit sink.** `AuditService.emit` has no `try` around its sinks (`src/mcp/abw_mcp/audit.py:174-176#sink`). A stdout failure, or a blob failure in fail-closed mode, would raise inside `call_tool` after the decision was made and turn a soft denial into an unhandled exception (8.4.4).

**Trade-off / limitation.** The result is a split: refusals the code anticipated are crisp, audited and explainable; failures it did not anticipate are neither, and the unmapped path leaves no MCP audit record. Closing it needs a catch-all in `call_tool` that emits a `tool_denied` or error event and returns an S6 `ERROR` (not implemented; 8.8).

**How to tell the shapes apart from a client log.**

- HTTP 429 and no JSON body: S3.
- HTTP 401, body `error` is `unauthorized`, with a `server` key: S1 (gateway).
- HTTP 403, body `error` is `forbidden`, with `reason`, `server` and `request_id`: S2 (gateway).
- HTTP 401, body `error` is `invalid_vendor_key`: S4 (vendor mock).
- HTTP 401 or 403, body `error` is `invalid_token` or `insufficient_scope`, with `error_description`: S5 (server edge).
- HTTP 200 and a `structuredContent` object whose `decision` is `DENIED` or `ERROR`: S6 (tool level). In strict mode the result also has `isError` true.

### 8.6 Configuration surface

**What this section proves.** What a server does is decided by one list of settings, read once when the application is built into a frozen object (`src/mcp/abw_mcp/config.py:35-59#Settings`). Each server has a short list of settings it cannot run without, and a missing one makes the settings load raise an error (`src/mcp/abw_mcp/config.py:87-110#from_env`, `src/mcp/abw_mcp/config.py:133-134#missing`). The load is lazy: the app is built when it first receives a scope, not in the start command, so the process stays up and answers HTTP 500 to every request instead of exiting (Inference, 8.1.3). The platform supplies most values from one list that all six apps share plus a short per-server list (`infra/04-apps.bicep:53-66#commonEnv`, `infra/04-apps.bicep:77-84#serverEnv`), and it leaves three safety-relevant settings to the code defaults. The synthetic data that the servers read is described at the end (8.6.5).

**How to read the tables.** "Default" is the value the code uses when the setting is absent. "Required for" follows the per-server list in `server_requirements` (`src/mcp/abw_mcp/config.py:117-128#server_requirements`). "Set in Bicep" gives the line of the entry in `infra/04-apps.bicep`, or "not set" when the code default applies. "Read at" gives the code that consumes the value. Statements are **Implemented** or **Configured** unless labelled **Inference** or **Platform behaviour** (a Microsoft Learn URL in plain text). Because the settings are read once, a changed value takes effect only in a new process (**Inference** from `src/mcp/abw_mcp/app.py:176-185#LazyApp`). How the identity and token settings are used at run time is section 6; this section only lists them.

**Why this shape.** Every server receives every data-plane endpoint, so the configuration is not a barrier: a research server that is given the Cosmos endpoint still cannot use it, because its identity has no Cosmos role and the user's token carries no Cosmos right (section 7.5). The barrier is RBAC and the on-behalf-of user, which is the point of the design, but it means that reading the settings alone says nothing about what a server can reach.

**The two secret-valued settings.** Container Apps secrets are defined at the app level and can hold either a value or a reference to a Key Vault secret that the platform retrieves with a managed identity that has been given access to the vault (Platform behaviour: https://learn.microsoft.com/azure/container-apps/manage-secrets#reference-secret-from-key-vault). In this repo both secrets are plain values: the connection-string secret takes the platform output (`infra/04-apps.bicep:68-73#appi-conn`) and the vendor secret takes the secure parameter (`infra/04-apps.bicep:182-187#vendor-api-key`). A search of `infra` and `scripts` found no Key Vault reference in any Container Apps secret.

**The vendor key, end to end (Configured).**

1. The deploy script generates a strong random value once and keeps it in the git-ignored `.secrets` folder under the repository root, outside version control but inside the working tree (`scripts/common.ps1:7#SecretsDir`, `scripts/deploy.ps1:182-186#Get-VendorKey`, `.gitignore:2#.secrets`).
2. It reaches Bicep as the secure parameter `vendorApiKey`; the copy of the parameter file kept for reference masks it (`scripts/deploy.ps1:48#SecretParamKeys`, `infra/04-apps.bicep:33-35#vendorApiKey`).
3. The apps stage writes it into Key Vault through the management plane, because the vault's data plane is firewalled, and also into the vendor container as a secret value (`infra/04-apps.bicep:37-50#vendorKeySecret`, `infra/04-apps.bicep:182-187#vendor-api-key`).
4. The apis stage creates a Key Vault-backed named value from the versionless secret URI, so a new secret version needs no redeployment of the gateway (`scripts/deploy.ps1:374-376#versionless`, `infra/05-apim-apis.bicep:81-91#nvVendorKey`).
5. The vendor API's policy section deletes the caller's `Authorization` header and sets the key header from that named value, so the vendor mock never sees a user token (`infra/05-apim-apis.bicep:75-78#vendorSection`).
6. At run time the vendor server compares the header with its own copy in constant time and answers 401 on a mismatch (`src/mcp/abw_mcp/app.py:124-142#compare_digest`; 8.5.3).

**Trade-off / limitation.** The vendor mock holds its own copy of the key while the gateway reads Key Vault, so a rotation made in Key Vault alone would leave the two out of step until the apps stage is run again (**Inference**; not tried). The vendor identity is granted the Key Vault secrets-user role under a comment that says the mock reads its key through a secret reference, but no such reference exists, so that grant looks unused (`infra/03-platform.bicep:558-567#raVendorKv`; Findings). The module README lists `MCP_APP_CLIENT_ID` as required for every server, although the code exempts vendor and legacy (`src/mcp/README.md:34`; `src/mcp/abw_mcp/config.py:101#validates_tokens`).

The index has ten fields: the key, `title`, `content`, `summary`, `snippet`, `ticker`, `classification`, `project`, `blob_path` and `updated`. It has no per-document access-control field (`src/seed/seed.py:113-128#SearchField`). The restricted tickers pair with the wall documents: the wall documents carry the first restricted ticker of their deal (`src/seed/seed.py:165#ZYNX`). The counterparty names in the limit rows are synthetic (`src/seed/seed.py:235-238#counterparty`).

**What the script does, in order.**

1. Resolves the three endpoints, with a command-line flag first, then the settings of the job, then a generated platform output file (`src/seed/seed.py:67-82#resolve_config`).
2. Loads the markdown files and builds the 24 search documents (`src/seed/seed.py:95-103#load_markdown_files`, `src/seed/seed.py:131-172#build_search_documents`).
3. Validates the shapes: every file must start with the synthetic banner, every wall file must carry the MNPI banner, and there must be exactly 24 documents, or the script exits (`src/seed/seed.py:256-266#validate_shapes`).
4. Under `--dry-run` it uses no credential and only counts (`src/seed/seed.py:49-57#dry-run`, `src/seed/seed.py:275-278#dry_run`).
5. Otherwise it picks a credential: the seed managed identity when `AZURE_CLIENT_ID` is set, else the operator's CLI credential chain (`src/seed/seed.py:85-92#get_credential`).
6. Uploads each blob with overwrite, creates or updates the index, merges or uploads the documents, and upserts the Cosmos items; it requires the three Cosmos containers to exist already and exits with an instruction otherwise (`src/seed/seed.py:175-185#upload_blobs`, `src/seed/seed.py:188-195#sync_search_index`, `src/seed/seed.py:198-206#ensure_container`).
7. Prints one summary line. A full run reports 24 blobs, 24 search documents, 4 restricted items, 22 positions and 0 orders (derived from `src/seed/seed.py:269-285#main`; not run).

**Why.** The upserts and the overwrite make a re-run safe. The wall documents are indexed with a summary only, at most 240 characters taken from two body lines, and no full text (`src/seed/seed.py:156-157#summary`), so a search can surface a wall document's existence and gist only to a caller the index lets in, and the full text needs the caller's own Storage role (section 7.5). Seeding as a separate identity keeps data creation out of the six servers' roles.

**Trade-off / limitation.**

- **No access-control field in the index.** Wall isolation in search rests on the `project` filter that the wall server adds (`src/mcp/abw_mcp/servers/wall.py:67#classification`). The only Search role assignment for people is the research group's reader role on the whole service (`infra/03-platform.bicep:640-648#raSearchResearch`), so role assignments do not separate the two deals, and the documents carry no access field of their own (section 7.5).
- **The seed identity stays powerful.** It holds write roles on the whole storage account, on the search service and on Cosmos, and nothing in the deploy script revokes them after the job succeeds; only deleting the resource group removes the identity (`infra/04b-seed-job.bicep:61-99#roleDefinitionId`, `scripts/deploy.ps1:406-437#seed`, `scripts/teardown.ps1:13`; Findings).
- **Seeded data skips the MCP checks.** The script writes as the seed identity, so no MCP audit event describes it and no wall or role rule applies to it. That is by design for a bootstrap, and it is why the seed identity belongs in a threat model (section 7.9).
- **A fixed shape.** The seed asserts an exact count of 24 documents, so adding a document means changing the script (8.8).

### 8.7 Tests under src/mcp/tests

**What this section proves.** The unit suite runs the real ASGI application, the real bearer middleware, JWT verification against a locally signed key, the real registry and tool handlers, and the real audit event builder. #### 8.7.4 How to run

From the repository root:

```
.\.venv\Scripts\python.exe -m pytest src\mcp\tests -q
```

- **Dependencies.** The `test` extra supplies pytest and pytest-asyncio (`src/mcp/pyproject.toml:28-32#pytest-asyncio`). There is no pytest section in the project file, so no asyncio mode, markers or paths are configured; the explicit markers in T01 to T12, T19 and T20 make that safe. Whether the extra is already installed in the repository's virtual environment is not verified here.
- **Imports.** `conftest.py` inserts the `src/mcp` directory at the front of `sys.path`, so `abw_mcp` imports without installing the package (`src/mcp/tests/conftest.py:18-20#sys.path`). It also imports from `cryptography`, which is not a direct dependency in `src/mcp/pyproject.toml:11-26#dependencies`; it presumably arrives transitively (Inference).
- **Manual script.** `smoke_local.py` is a manual in-process walk-through that builds a runtime with the same fakes, calls `tools/list` and `tools/call` for `search_research`, and prints the audit rows (`src/mcp/tests/smoke_local.py:80-104#main`). - **No network.** The suite needs no Azure access: the transport is in-process and the broker, data plane and key fetch are fakes (8.7.1).

### 8.8 Extension guide

**What this section proves.** The platform is extended by repeating a pattern, not by editing an entitlement store. A new tool is a few lines in one server file. A new server or a new deal is a vertical change across code, Bicep, Entra and scripts, and several of the lists it must join are hand-maintained. Each step below names the file and the line range to copy from. **Implemented pattern** means every step exists today as code, Bicep or script that can be mirrored. **Needs new design** means the repository has no mechanism. Nothing here was deployed or run. The building blocks are the registry types (`src/mcp/abw_mcp/registry.py:78-121#ToolDefinition`).

#### 8.8.1 Add a tool to an existing server (Implemented pattern)

1. **Arguments.** Subclass `ArgsModel`. Unknown fields are rejected and every constraint (length, range, pattern, literal) is enforced before the handler runs (`src/mcp/abw_mcp/registry.py:24-27#ArgsModel`). A model with a pattern and a literal is the worked example (`src/mcp/abw_mcp/servers/wall.py:19-26#GetDealDocumentArgs`); a tool without arguments uses an empty model (`src/mcp/abw_mcp/servers/wall.py:108-109#EmptyArgs`).
2. **Handler.** Write `async def handler(caller, args, runtime) -> ToolOutcome`. Apply the data rule first and raise `ToolError(code, message, reason=...)` to refuse (`src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`, `src/mcp/abw_mcp/registry.py:54-75#ToolError`). Use the `runtime.data` helpers with their default `use_user_token=True` so that the user's token goes down (section 6). Return a `ToolOutcome` whose `downstream` carries the service, target and status for the audit line (`src/mcp/abw_mcp/registry.py:30-39#ToolOutcome`, `src/mcp/abw_mcp/servers/wall.py:88-105#get_deal_document`).
3. **Registration.** Add a `ToolDefinition(name, description, args_model, handler, requirement, data_class)` to the server's `build_tools()` (`src/mcp/abw_mcp/servers/wall.py:112-138#build_tools`). The requirement decides both visibility in `tools/list` and permission on `tools/call`; choose `allow_all`, `require_any_role(...)` or `require_scope_and_role(scope, *roles)` (`src/mcp/abw_mcp/registry.py:94-121#require_scope_and_role`).
4. **Data class.** It is a free string used only in the audit event; the code uses public, wall, internal, external and mixed (`src/mcp/abw_mcp/registry.py:78-87#data_class`, 8.4.5).
5. **Data-plane grant.** If the tool reads a store or container that its callers cannot yet read, add the RBAC to the group in Bicep (`infra/03-platform.bicep:617-648#raResearchBlob`). The MCP code cannot grant access, because the user's own token decides (7.5).
6. **Agent allow-list.** Add the tool name to the desk's list and, for a state-changing tool, to the approval-required list (`src/agent/abw_agents.py:42-48#WALL_DESK_TOOLS`, `src/agent/abw_agents.py:49#APPROVAL_REQUIRED`).
7. **Tests and documents.** Add cases beside T02 (visible tools), T12 (role-less caller) and a rule test in the style of T03 or T05 (`src/mcp/tests/test_servers.py:32-63#test_role_filtered_tools_list`). Update the tables in 8.3 and the matrix in 7.6.

Not needed: a gateway change, because the policy checks the method, the fixed `Tools.Read` scope and the API's role list but never the tool name (`infra/apim/policies/mcp-jwt.policy.xml:39-44#Tools.Read`); an image change; an Entra change unless the tool needs a new role.

**Why.** Because the generic stages live in the registry, a new tool inherits the role filter, validation, the audit event and the soft denial without extra code. **Trade-off / limitation.** The registry cannot know a tool's data rule, so a handler that skips its own check is unprotected at Layer 2. The user's token still bounds the damage where the store enforces per-user RBAC, but Cosmos RBAC here is container-scoped, so the per-user and per-desk filters are Layer 2 rules (`src/mcp/abw_mcp/servers/actions.py:113-127#user_oid`, `src/mcp/abw_mcp/servers/private.py:19-34#desk`). **Trap.** `Tools.Execute` is enforced only through the requirement a tool declares (`src/mcp/abw_mcp/servers/actions.py:145#Tools.Execute`); a state-changing tool that uses `require_any_role` alone would never check it.

**Why.** One image and one registry keep the generic stages identical for every server, so the review effort for a new server is its tools and its grants. **Trade-off / limitation.** Every list above is hand-maintained and none is derived from another, so a missed list fails late: the gateway entry is missing, or the agent cannot find the tool, or the exchange is refused at run time. **Trap.** The identity output addresses each identity by its position in the key list (`uamis[0]` to `uamis[5]`), so a new key must be appended at the end of the list; inserting it earlier would make every later line point at the wrong identity (Inference from `infra/03-platform.bicep:767-774#uamis`).

#### 8.8.3 Add a deal (Implemented pattern; no entitlement store)

The example is a third project beside Falcon and Orion. A deal is not a row in a store: it is an Entra role, a group, a container, a grant, code constants and seed data.

1. **Entra.** Add an app role on the wall API, a security group for the deal, and the persona role and group assignments (`identity/Setup-Entra.ps1:33-35#Wall.Falcon`, `identity/Setup-Entra.ps1:48#$Groups`, `identity/Setup-Entra.ps1:50-61#$Users`; the assignment loops are `identity/Setup-Entra.ps1:224-235#group` and `identity/Setup-Entra.ps1:237-251#appRoleAssignments`).
2. **Gateway.** Add the role to the wall API's role list (`infra/05-apim-apis.bicep:45#roles`).
3. **MCP code.** In `wall.py`: the project title map (`src/mcp/abw_mcp/servers/wall.py:13-16#PROJECT_TITLES`), the `project` literal (`src/mcp/abw_mcp/servers/wall.py:21#Literal`), the document-id pattern (`src/mcp/abw_mcp/servers/wall.py:26#doc_id`), the role-to-project function, which is one `if` per role (`src/mcp/abw_mcp/servers/wall.py:29-36#caller_projects`), and the role list in the three tool requirements (`src/mcp/abw_mcp/servers/wall.py:119#require_any_role`, `src/mcp/abw_mcp/servers/wall.py:127#require_any_role`, `src/mcp/abw_mcp/servers/wall.py:135#require_any_role`) with their descriptions. The container name is derived as `wall-<project>` (`src/mcp/abw_mcp/servers/wall.py:91#container`).
4. **Legacy server.** It repeats the project literal and the document pattern; update it only if the legacy comparison should include the new deal (`src/mcp/abw_mcp/servers/legacy.py:28#Literal`, `src/mcp/abw_mcp/servers/legacy.py:32#doc_id`).
5. **Storage and Search.** Add a container and a reader assignment for the new group (`infra/03-platform.bicep:170-184#cFalcon`, `infra/03-platform.bicep:628-636#raFalconBlob`) and the group id in the `groupIds` parameter (`infra/03-platform.bicep:37-38#groupIds`, `scripts/deploy.ps1:311-318#groupIds`). The Orion container has no reader by design (`infra/03-platform.bicep:638#Orion`). The search index already carries `classification` and `project` as filterable fields (`src/seed/seed.py:113-128#classification`).
6. **Seed data.** The seed hard-codes the deal list (`src/seed/seed.py:97#wall-orion`), the project map (`src/seed/seed.py:153#falcon`), the container map (`src/seed/seed.py:180#wall-falcon`) and the restricted-list rows, which carry a `project` field (`src/seed/seed.py:211-214#ZYNX`). A two-way conditional picks one of two synthetic tickers, so a third deal would be mislabelled until it is edited (`src/seed/seed.py:165#VRDN`). `validate_shapes` asserts exactly 24 documents, so adding any document changes that count (`src/seed/seed.py:256-266#validate_shapes`). New Markdown files go under the data folders for research, Falcon and Orion.
7. **Agent.** Update the tool descriptions that name the deals (`src/agent/abw_agents.py:109-116#DESCRIPTIONS`).
8. **Separation of duties.** No change is needed: the rule tests the role prefix `Wall.`, so a new deal role is picked up (`src/mcp/abw_mcp/servers/actions.py:40-41#_has_wall_role`). The prefix match also means any unrelated role that starts with `Wall.` would trigger the rule (Findings).
9. **Tests and documents.** Extend T02, T03 and T12 and the entitlement matrix in 7.6.

Adding a **document** to an existing deal is smaller: add the Markdown file under the seed data folder and change the expected count in `validate_shapes`, then re-run the seed job (`src/seed/seed.py:256-266#validate_shapes`). Seeded data bypasses every MCP check and the MCP audit trail by design, because the seed identity writes directly (`infra/04b-seed-job.bicep:61-99#sqlRoleDefinitions`).

**Why.** Keeping the barrier in roles, groups and RBAC means a deal is decided by the platform's own services, not by a table in this application. **Trade-off / limitation.** There is no entitlement store, so a deal touches at least Entra, the gateway, the MCP code, Storage, the seed and the agent, and no approval, expiry or review step exists (section 7.9, `src/mcp/abw_mcp/servers/wall.py:13-16#PROJECT_TITLES`).

#### 8.8.4 Implemented pattern versus needs new design

| Capability | Status | Evidence |
|---|---|---|
| A new tool on an existing server | Implemented pattern | Registry types, requirement helpers and the agent allow-list (`src/mcp/abw_mcp/registry.py:94-121#allow_all`) |
| A new server over the same kinds of store | Implemented pattern, with hard-coded lists | `src/mcp/abw_mcp/app.py:39-60#SERVER_SCOPES`; `src/mcp/abw_mcp/config.py:117-128#server_requirements` |
| A new deal | Implemented pattern, at least six places | `src/mcp/abw_mcp/servers/wall.py:13-36#PROJECT_TITLES` |
| A central entitlement store with approval, expiry and review | Needs new design | Nothing derives the deal list from data (`src/mcp/abw_mcp/servers/wall.py:29-36#caller_projects`) |
| Per-tool or per-argument policy at the gateway | Needs new design | The gateway reads the method, a fixed scope and the role list (`infra/apim/policies/mcp-jwt.policy.xml:39-44#missing_role`) |
| Per-desk or per-row entitlements enforced by the data plane | Needs new design | Cosmos RBAC is container-scoped, so those filters are Layer 2 rules (`src/mcp/abw_mcp/servers/private.py:19-34#desk`) |
| A catch-all for unmapped handler exceptions with an error audit event | Needs new design (not implemented) | The registry catches two exception types only (`src/mcp/abw_mcp/registry.py:177-193#except`; 8.5.6) |
| Tamper-evident audit lines (sequence number, hash chain or signature) | Needs new design (not in this repo) | The event has no integrity field (`src/mcp/abw_mcp/audit.py:178-216#build_event`) |
| Audit written before the action | Needs new design | The event is emitted after the handler has run (`src/mcp/abw_mcp/registry.py:177-216#emit`) |

**Key takeaways**

- **One image, six servers.** The `MCP_SERVER` setting picks research, wall, actions, private, vendor or legacy; the same code builds that server's tool registry and chooses the middleware around it (Implemented: `src/mcp/abw_mcp/config.py:88-93#from_env`, `src/mcp/abw_mcp/app.py:49-60#_build_registry`, `src/mcp/abw_mcp/app.py:241-249#VendorKeyMiddleware`). The image starts one `uvicorn` command on port 8080 (`src/mcp/Dockerfile` line 15).
- **One stateless, JSON-only route carries the protocol.** `/mcp` accepts GET, POST and DELETE; `/healthz` and the discovery document sit beside it; the session manager runs in JSON-response, stateless mode with DNS-rebinding protection off (Implemented: `src/mcp/abw_mcp/app.py:210-215#StreamableHTTPSessionManager`, `src/mcp/abw_mcp/app.py:224-228#healthz`). What the SDK does with those flags is SDK behaviour, not verified here.
- **Only `/mcp` is authenticated, and legacy is not.** The bearer middleware guards the exact path `/mcp`, the vendor mock checks a shared key instead, and the legacy server installs neither (Implemented: `src/mcp/abw_mcp/auth.py:209-212#__call__`, `src/mcp/abw_mcp/app.py:241-249#BearerAuthMiddleware`).
- **Middleware order decides what the logs can say.** OpenTelemetry is outermost, then the request context, then authentication, so a failed token check still has a request id and a span, but its `auth_failed` event carries no caller identity (Implemented: `src/mcp/abw_mcp/app.py:250-253#OpenTelemetryMiddleware`, `src/mcp/abw_mcp/auth.py:224-239#auth_failed`). The wrapping order is stated in a code comment; the framework behaviour behind it is not verified here.
- **The call order is fixed and deny-first.** `call_tool` resolves the tool, checks its requirement, validates the arguments and runs the handler; the success event is written only after the handler returns, and a failed token exchange is refused and audited, not retried with the service identity (Implemented: `src/mcp/abw_mcp/registry.py:158-175#call_tool`, `src/mcp/abw_mcp/registry.py:177-193#OboError`, `src/mcp/abw_mcp/data.py:57-62#use_user_token`; Tested: a test pins the refusal and its audit event, but it uses the fake data plane, so the credential choice inside the real data plane client is not exercised, `src/mcp/tests/test_servers.py:141-156#test_obo_failure_does_not_fallback`).
- **Tool-level refusals are HTTP 200 by default, and every refusal that ABW code or gateway policy writes itself arrives in one of six wire shapes.** The gateway produces S1 to S3, the vendor key check S4 and the bearer middleware S5; the registry produces S6, the soft denial, a `DENIED` or `ERROR` payload in `structuredContent`, and strict mode adds `isError` to every error result (Implemented: `src/mcp/abw_mcp/registry.py:238-270#_tool_error_result`, `src/mcp/abw_mcp/registry.py:273-292#_error_payload`). Two cases fall outside the six: the legacy API's missing-key refusal is APIM's own 401 (Configured: `infra/05-apim-apis.bicep:176#subscriptionRequired`; Platform behaviour: https://learn.microsoft.com/azure/api-management/api-management-subscriptions), and an unmapped exception reaches the client as whatever the MCP SDK makes of it (8.5.6). The reason given for `isError`, that Foundry aborts the run, is a code comment (`src/mcp/abw_mcp/registry.py:263-265#Foundry`) that I did not find on Microsoft Learn.
- **The audit event has 21 keys, hashed arguments and two sinks.** It records who, what, which decision and why, and keeps only a hash of the arguments; the default service writes a stdout line and a per-server, per-day append blob (Implemented: `src/mcp/abw_mcp/audit.py:178-216#build_event`, `src/mcp/abw_mcp/audit.py:219-223#build_default_audit_service`). The blob container's retention policy is time-based, unlocked and one day long, so it shows the pattern but is not a compliance attestation (Configured: `infra/03-platform.bicep:193-202#immutabilityPeriodSinceCreationInDays`; Designed: `DESIGN.md:239#unlocked`; Platform behaviour: https://learn.microsoft.com/azure/storage/blobs/immutable-time-based-retention-policy-overview).
- **At least three audit holes are known; the Findings list more.** An unknown tool name is refused with no identity and no tool in the event; an exception that is neither a token-exchange failure nor a tool error writes no MCP audit event; and a failed blob append is only printed to standard error and logged on the replica, and nothing alerts on it, because fail-closed mode is off by default and the Bicep never sets it (Implemented: `src/mcp/abw_mcp/registry.py:159-161#unknown_tool`, `src/mcp/abw_mcp/registry.py:177-193#ToolError`, `src/mcp/abw_mcp/audit.py:94-103#append_audit_failed`; Configured: `src/mcp/abw_mcp/config.py:150#audit_fail_closed`, `infra/04-apps.bicep:53-66#commonEnv`).
- **`Tools.Execute` is enforced only at the tool.** The gateway hard-codes `Tools.Read`, every server's bearer check asks for `Tools.Read`, and only the `place_order` requirement asks for `Tools.Execute` plus a role; no test or live proof exercises that refusal (Configured: `infra/apim/policies/mcp-jwt.policy.xml:39#Tools.Read`, `infra/04-apps.bicep:64#MCP_REQUIRED_SCOPE`; Implemented: `src/mcp/abw_mcp/servers/actions.py:140-147#require_scope_and_role`; Tested: every live `place_order` call passes the execute scope, `demo/prove.py:618#Tools.Execute`).
- **Settings fail in different ways.** A mistyped denial mode makes the settings load raise, so the server answers HTTP 500 to every request instead of exiting (Inference, 8.1.3); a mistyped boolean silently becomes false; and `LOG_LEVEL` is parsed and never applied (Implemented: `src/mcp/abw_mcp/config.py:14-26#_parse_bool`, `src/mcp/abw_mcp/config.py:152#log_level`).
- **Data calls run as the user.** Blob, Search and, by default, Cosmos DB calls carry a token exchanged on behalf of the caller, so the data plane makes the final decision; section 6 covers the exchange (Implemented: `src/mcp/abw_mcp/data.py:57-71#read_blob_text`, `src/mcp/abw_mcp/obo.py:64-68#acquire_token_on_behalf_of`). The deliberate exception is the restricted-list read, which uses the server's own identity (`src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`).
- **The seed data is synthetic and hard-coded.** The deal list, the ticker mapping and the expected count of 24 indexed documents are fixed in the seed job, which writes below the MCP layer (Implemented: `src/seed/seed.py:256-266#validate_shapes`; Configured: `infra/04b-seed-job.bicep:61-99#raBlob`).
- **The tests prove Layer 2 with in-memory fakes; Layer 3 is proven live.** The storage-denial test injects the typed error, so the translation of a real Storage 403 is not unit-tested, and the suite was not run for this document (Tested: `src/mcp/tests/test_servers.py:90-105#test_storage_rbac_denial_audited`, `src/mcp/tests/conftest.py:92-97#DataAccessError`; Implemented: `src/mcp/abw_mcp/data.py:68-70#storage_rbac_denied`).
- **Extension relies on hand-kept lists, and there is no entitlement store.** A new server touches the settings literal, the registry builder, the scope map, the identity script, the platform identity list and the deploy stages; a new deal touches the seed, the wall rules, the groups and the role assignments (Implemented: `src/mcp/abw_mcp/config.py:117-128#server_requirements`, `src/mcp/abw_mcp/servers/wall.py:13-16#PROJECT_TITLES`; Configured: `identity/Setup-Entra.ps1:266-276#federatedIdentityCredentials`, `infra/03-platform.bicep:767-774#uamis`, `scripts/common.ps1:181#uamiKeys`). Section 8.8 lists the files and separates what is implemented from what needs new design.
- **Every open item is in the Findings below.** They are grouped by area, and the first one explains why the reason in a gateway refusal is not always the one the file header predicts (`infra/apim/policies/mcp-jwt.policy.xml:37-44#abw-deny`).


### 8.9 Findings

The 37 findings raised while writing sections 7 and 8 (documentation mismatches, defects and undocumented decisions) are collected in [Appendix B.5](appendix-b-findings-register.md#b5-raised-while-writing-sections-7-and-8). Where the text above says "Findings" or quotes a finding number, it means that list.


**MCP server behaviour**

- `src/mcp/abw_mcp/registry.py:158-165#unknown_tool` - An unknown tool name is refused before the role check and is written with no caller and no tool: `call_tool` holds the caller, but the helper is called without it (`src/mcp/abw_mcp/registry.py:222-236#_error_result`), so the event has no `user_oid`, no `tool` and an `args_sha256` over `{}`, and the attempted name appears only in the response message. A real tool that the caller lacks is refused later, with the caller's identity and the reason `missing_role` (`src/mcp/abw_mcp/registry.py:163-165#forbidden`). - A caller who holds some role for that API, or any caller on the private server, which has no gateway, can tell "does not exist" (payload `ERROR`, reason `unknown_tool`) from "not for me" (`DENIED`, `missing_role`), so that caller can probe tool names, and nothing records who probed or which name was tried. A caller with none of an API's roles is refused at the gateway first (`infra/apim/policies/mcp-jwt.policy.xml:43-44#missing_role`; section 8.5.7). The roll-up row would show an empty principal (`observability/kql/AbwDenials.kql:57-66#UserUpn`; Inference, the query was not run). Low severity, because the tool names are not secret; the real gap is attribution.
- `src/mcp/abw_mcp/registry.py:54-66#tool_denied` - The audit `obo` flag is a default or a guess, not a record of an exchange. A `ToolError` defaults to `obo=True`; the unknown-tool and failed-requirement refusals take the flag from the server name (`src/mcp/abw_mcp/registry.py:232#obo`); the wall pre-call refusal (`src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`) and both `order_blocked` refusals (`src/mcp/abw_mcp/servers/actions.py:58-75#order_blocked`) pass no `obo`, so they read `true`, although the restricted read before the order refusals used the server's own identity (`src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`) and the wall refusal made no data call at all. - A query that counts `OnBehalfOf == true` (`observability/kql/AbwMcpAudit.kql:23#OnBehalfOf`) over-counts exchanges, so it is not evidence that a user token reached a store (section 8.4).
- `src/mcp/abw_mcp/registry.py:42#DENIED_CODES` - Only `FORBIDDEN` and `WALL_VIOLATION` render as payload `DENIED` (`src/mcp/abw_mcp/registry.py:273-292#_error_payload`). `NOT_FOUND` and `INVALID_ARGUMENT` render as `ERROR`, yet the same results are audited with decision `deny` (`src/mcp/abw_mcp/registry.py:167-175#invalid_arguments`; `src/mcp/abw_mcp/servers/private.py:47#counterparty_not_found`). - The label the user sees and the label in the audit disagree, and the roll-up counts a mistyped ticker or an unknown counterparty as a refusal (`observability/kql/AbwDenials.kql:58#Decision`), so refusal counts include ordinary input errors.
- `src/mcp/abw_mcp/data.py:73-97#search_documents` - Search has no error mapping at all, a Cosmos point read maps only 404 (`src/mcp/abw_mcp/data.py:99-116#cosmos_read_item`), and the Cosmos query and upsert helpers map nothing (`src/mcp/abw_mcp/data.py:118-147#cosmos_query_items`). `call_tool` catches only `OboError` and `ToolError` (`src/mcp/abw_mcp/registry.py:177-193#ToolError`), so any other exception skips every audit emit and no MCP event exists for that call. - A Search or Cosmos refusal (the status codes for a data-plane RBAC refusal are not mapped in this repo) is invisible to the MCP trail, and neither roll-up stream covers it: the data-plane branch reads Storage logs only (`observability/kql/AbwDenials.kql:67-77#StorageBlobLogs`). How the MCP SDK renders the exception to the client is SDK behaviour, not verified here. No test injects a Search or Cosmos error; the only injected data error is a Storage 403 (`src/mcp/tests/conftest.py:96#DataAccessError`). Section 7.5 states the Layer 3 consequence and section 8.5.6 lists the unmapped cases.
- `src/mcp/abw_mcp/data.py:109-116#status_code` - A Cosmos point read treats any 404 as "item absent" and returns nothing. The restricted-list check reads through that helper (`src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`), and both `check_restricted_list` and `place_order` read an empty result as "not restricted" (`src/mcp/abw_mcp/servers/actions.py:44-55#check_restricted_list`, `src/mcp/abw_mcp/servers/actions.py:58-75#restricted`). - Learn describes a 404 as acting on a resource that no longer exists, without saying which kind (https://learn.microsoft.com/rest/api/cosmos-db/http-status-codes-for-cosmosdb), so a deleted or renamed `restricted` container would probably read as an empty list, and orders for restricted names would pass (Inference; SDK behaviour not verified; untested). A removed role assignment would give a 403 instead, which is unmapped (previous item). A fail-closed design would treat a missing container differently from a missing item (new design, not implemented).
- `src/mcp/abw_mcp/servers/actions.py:77-90#uuid4` - `place_order` writes a fresh `uuid4` id on every call, so a retried call places a second order, and the stored status is the literal `ACCEPTED` (`src/mcp/abw_mcp/servers/actions.py:84#ACCEPTED`); nothing in this repo sends the order anywhere. An order is bounded by the role and scope, the restricted-list rules, a quantity of 1 to 1,000,000 (`src/mcp/abw_mcp/servers/actions.py:20-23#PlaceOrderArgs`) and the gateway's per-user rate limit (`infra/apim/policies/mcp-jwt.policy.xml:81#rate-limit-by-key`). The tool description names human approval (`src/mcp/abw_mcp/servers/actions.py:140-147#synthetic`), which is an agent-side setting that the server does not enforce (`src/agent/abw_agents.py:49#APPROVAL_REQUIRED`; section 7.9). - It is a synthetic order record, not a trade, which is the right scope for a demo. A real order path would need new design: an idempotency key, an order state machine, an order-management integration and server-side approval evidence (not implemented).
- `src/mcp/abw_mcp/obo.py:60-65#acquire_token_on_behalf_of` - The OBO exchange is a synchronous call, and so is the managed-identity assertion callback behind it (`src/mcp/abw_mcp/obo.py:77-79#_get_client_assertion`). The data layer runs the exchange and builds the client on the event-loop thread, and only the final data call goes through `to_thread` (`src/mcp/abw_mcp/data.py:57-65#to_thread`, `src/mcp/abw_mcp/data.py:191-194#_obo_credential`, `src/mcp/abw_mcp/data.py:177-189#CosmosClient`). - A token-cache miss can block the loop for up to two network round trips (the assertion, then the exchange), which stalls other requests on that replica. Not measured (Inference). When MSAL calls the callback and how its cache answers a repeat exchange are SDK behaviour, not verified here (section 6 covers the exchange).
- `src/mcp/abw_mcp/registry.py:263-269#isError` - The default `soft` mode returns every refusal as a normal result (`isError` false) so that the model can explain it, and `strict` sets `isError` for every error shape, `NOT_FOUND` and `INVALID_ARGUMENT` included. Strict mode is tested (`src/mcp/tests/test_servers.py:234-247#test_strict_denial_mode_uses_mcp_is_error`). The reason for soft mode is a code comment: Foundry aborts the run when a tool returns `isError` (`src/mcp/abw_mcp/registry.py:263-265#Foundry`). I did not find that behaviour on Learn, so it is the code's claim only. - A client or evaluator that reads only the HTTP status or `isError` sees a policy denial as a success, and must read `structuredContent.decision` instead (section 8.5).
- `src/mcp/abw_mcp/app.py:210-215#enable_dns_rebinding_protection` - The session manager is built with DNS-rebinding protection off and no stated reason. Every governed server validates a bearer token on every `/mcp` request (`src/mcp/abw_mcp/app.py:241-249#BearerAuthMiddleware`) and the vendor checks a key, so a rebinding page would not hold a credential; the legacy server has neither check, by design (section 8.3.7). A possible reason is a Host-header mismatch behind the ingress, which is a guess. - Low severity; the setting should carry a comment that says why (Inference; SDK behaviour, not verified here).
- `src/mcp/abw_mcp/app.py:91-98#derive_public_base_url` - When `PUBLIC_BASE_URL` is unset, the base URL in the discovery document is built from `x-forwarded-host`, `host`, `x-forwarded-proto` and `x-forwarded-prefix`, and the route is added for every server and needs no token (`src/mcp/abw_mcp/app.py:101-112#_build_prm_payload`, `src/mcp/abw_mcp/app.py:221-227#oauth-protected-resource`). The Bicep sets the value for the four governed servers and legacy (`infra/04-apps.bicep:77-84#serverEnv`, `infra/04-apps.bicep:159#PUBLIC_BASE_URL`) but not for the vendor (`infra/04-apps.bicep:166-189#VENDOR_API_KEY`), and the application reads those headers from any caller, whatever the image's proxy settings (`src/mcp/abw_mcp/app.py:91-98#derive_public_base_url`). - On the vendor, a caller who controls those headers could make the document name another host. The document holds no secret, so the effect is a misleading URL, not disclosure (Inference; low severity).
- `src/mcp/abw_mcp/app.py:115-142#VendorKeyMiddleware` - The vendor audit has no person in it: the vendor takes no bearer token, the registry is called with no caller, and the gateway deletes the `Authorization` header and injects the Key-Vault-backed key (`infra/05-apim-apis.bicep:75-78#vendorSection`). The one log line that describes the request, `vendor_request` (`src/mcp/abw_mcp/app.py:130-137#vendor_request`), is written at INFO for every `/mcp` request before the key is checked. It carries two presence flags (an Authorization header was seen, a vendor key was seen) and the client address, but no request id, although the request-context middleware does set one on this path (`src/mcp/abw_mcp/app.py:250-253#RequestContextMiddleware`). A wrong key gets 401 `invalid_vendor_key` and no audit event. - Section 8.3.6 calls that line the evidence that the user's token does not reach the vendor. The line shows which headers arrived, not what the vendor did with them. The log exporter is limited to the `abw.audit` logger; traces and metrics are still exported (`src/mcp/abw_mcp/app.py:66-70#logger_name`; Learn describes `logger_name` as the logger under which telemetry is collected: https://learn.microsoft.com/python/api/overview/azure/monitor-opentelemetry-readme), so a record on the `abw.vendor` logger is not exported, and the line may not be emitted anywhere: the settings parse `LOG_LEVEL` but nothing applies it, and the Python default threshold is WARNING (https://learn.microsoft.com/troubleshoot/azure/azure-monitor/app-insights/telemetry/opentelemetry-troubleshooting-python), so an INFO record is probably dropped (Inference; uvicorn behaviour not verified here). The control is the gateway's header rewrite; the log line only shows what arrived.

**Audit event fidelity**

- `src/mcp/abw_mcp/registry.py:222-236#_error_result` - The unknown-tool and failed-requirement refusals go through a helper that always hashes an empty object (`src/mcp/abw_mcp/registry.py:158-165#_error_result`), so the caller's arguments are discarded, while a validation failure, a handler error and a success hash the arguments as received (`src/mcp/abw_mcp/registry.py:167-175#arguments`, `src/mcp/abw_mcp/registry.py:238-262#_tool_error_result`, `src/mcp/abw_mcp/registry.py:195-216#arguments`, `src/mcp/abw_mcp/audit.py:193#sha256_json`). **Audit sinks**

- `src/mcp/abw_mcp/config.py:150#audit_fail_closed` - Every server is fail-open, because the Container Apps template does not set `AUDIT_FAIL_CLOSED` (`infra/04-apps.bicep:53-66#commonEnv`). A failed append is printed to stderr and logged as `append_audit_failed` with no retry (`src/mcp/abw_mcp/audit.py:94-103#append_audit_failed`), and no query, alert, test, script or document refers to that string (grep over the repository's code, docs and observability files). - WORM events can be lost silently, and the console copy (and App Insights, if it is exported) is then the only record, and neither is immutable (section 8.4).
- `src/mcp/abw_mcp/audit.py:88-92#emit` - Fail-closed is not audit-before-act. The success emit runs after the handler (`src/mcp/abw_mcp/registry.py:195-216#emit`), the inline append uses the synchronous client on the event-loop thread (`src/mcp/abw_mcp/audit.py:124-125#AppendBlobClient`), the service loops over its sinks with no handler (`src/mcp/abw_mcp/audit.py:174-176#emit`), and the console sink runs first (`src/mcp/abw_mcp/audit.py:222#sinks`). So `place_order` has already persisted the order when a failed append raises (`src/mcp/abw_mcp/servers/actions.py:91-98#use_user_token`), and `src/mcp/README.md:40#AUDIT_FAIL_CLOSED` says such failures "deny calls". - Fail-closed turns an audit failure into a failed response, not a blocked action. How the SDK renders the raised error is not verified here (Inference; untested). A real audit-before-act design would write an intent record first and refuse on failure (new design, not implemented).
- `src/mcp/abw_mcp/audit.py:194-216#request_id` - Events carry no sequence number and no hash chain, and each event is one block (`src/mcp/abw_mcp/audit.py:105-118#_append_line`). Learn says the existing blocks of a protected append blob cannot be modified or deleted (https://learn.microsoft.com/azure/storage/blobs/immutable-container-level-worm-policies#allow-protected-append-blobs-writes), but an event that was never written cannot be detected from the blob alone. - Completeness cannot be proven from the trail. A per-server sequence number plus a periodic signed checkpoint would be new design (not implemented).
- `src/mcp/abw_mcp/audit.py:130-133#jsonl` - There is one append blob per server per UTC day, with one block per event (`src/mcp/abw_mcp/audit.py:118#append_block`) and no rollover. Learn gives 50,000 as the maximum number of appended blocks per append blob (https://learn.microsoft.com/rest/api/storageservices/append-block#remarks), which averages one event every 1.7 seconds over 24 hours (86,400 divided by 50,000). Every `tool_listed` costs a block, and the replicas of a server share the blob. - Past the limit, later appends fail and, fail-open, are dropped (Inference; untested; the real event rate was not measured). Rolling to a new blob by index would be new design.
- `src/mcp/abw_mcp/audit.py:105-118#create_append_blob` - The first write of each day's blob in each process checks for the blob and calls `create_append_blob` after any exception from the check, not only after "not found" (`src/mcp/abw_mcp/audit.py:109-117#_created`). Learn says `create_append_blob` overwrites an existing blob (https://learn.microsoft.com/python/api/azure-storage-blob/azure.storage.blob.blobclient) and that both locked and unlocked time-based policies protect against overwrites (https://learn.microsoft.com/azure/storage/blobs/immutable-time-based-retention-policy-overview). If the create is refused, the code reads the properties again and the append proceeds (`src/mcp/abw_mcp/audit.py:111-116#get_blob_properties`), so a refused overwrite is not a lost event. With the policy in place a first-write race between two replicas is benign; without any policy the second create would empty the day's blob (`infra/03-platform.bicep:193-202#immutabilityPeriodSinceCreationInDays`, `infra/modules/mcp-app.bicep:19-20#maxReplicas`). - The code adds no guard of its own, so the first block's integrity rests on the storage policy alone (Inference; untested). A create that is conditional on the blob not existing would be new design.
- `src/mcp/abw_mcp/audit.py:64-84#timeout` - The blob sink is fed by an unbounded queue (`src/mcp/abw_mcp/audit.py:64#Queue`) that a daemon thread drains, and shutdown waits at most five seconds (`src/mcp/abw_mcp/audit.py:84#timeout`). Queued events are lost on a crash or a slow shutdown, and the console is then the only other record. A slow Storage endpoint lets the queue grow without a bound. - Events can vanish in exactly the failure cases an investigator cares about (Inference; the container stop behaviour is not verified here).
- `infra/03-platform.bicep:548-556#raAuditAppend` - Five identities (research, wall, actions, private and legacy) hold Blob Data Contributor on the whole `worm-audit` container, because the loop condition excludes the vendor. The comment at the grant counts "five governed servers + legacy", which is six names and a set that includes the vendor (`infra/03-platform.bicep:547#governed`), so it does not match the grant. Learn lists read, write and delete for that role (https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/storage#storage-blob-data-contributor), so append-only comes from the retention policy and not from the role, and any of the five can append to any server's day blob (Inference). - A compromised research container could add forged events to another server's file but, within the policy's limits, could not erase existing ones (section 7.5).
- `infra/03-platform.bicep:548-556#vendor` - The vendor has no role on the audit container, yet every server must have `AUDIT_STORAGE_ACCOUNT` (`src/mcp/abw_mcp/config.py:103-110#AUDIT_STORAGE_ACCOUNT`), the shared settings supply it to the vendor (`infra/04-apps.bicep:57#AUDIT_STORAGE_ACCOUNT`, `infra/04-apps.bicep:53-66#commonEnv`, `infra/04-apps.bicep:176#concat`), and the lifespan starts the blob sink for every server (`src/mcp/abw_mcp/app.py:230-236#audit`). So the vendor's appends should be refused on every event and logged only on the replica, which leaves a console trail but no WORM trail for the vendor (Inference; not observed; section 8.4.4 states it). - The fail-open sink hides a missing role.
- `infra/03-platform.bicep:193-202#immutabilityPeriodSinceCreationInDays` - The retention policy is one day and unlocked (`infra/03-platform.bicep:193-202#allowProtectedAppendWrites`), and the Bicep comment and `DESIGN.md:239#unlocked` say that this is deliberate and not a compliance attestation. Learn says a new policy is unlocked for testing and must be locked for SEC 17a-4(f) (https://learn.microsoft.com/azure/storage/blobs/immutable-time-based-retention-policy-overview), and that with protected appends the effective retention is the last append plus the interval (https://learn.microsoft.com/azure/storage/blobs/immutable-container-level-worm-policies#allow-protected-append-blobs-writes), so each day blob is protected until one day after its last append. - Until the policy is locked, it is a test configuration (section 7.9).
- `infra/04-apps.bicep:57#AUDIT_STORAGE_ACCOUNT` - The audit trail and the data share one storage account (`infra/04-apps.bicep:59#STORAGE_ACCOUNT`), so account-scope roles also cover the audit container: the legacy identity's Blob Data Reader (`infra/03-platform.bicep:569-578#raLegacyBlob`) and the seed identity's Blob Data Contributor (`infra/04b-seed-job.bicep:61-69#raBlob`). No tool reaches the container today, because the legacy document tool builds only `research-public` or `wall-` names (`src/mcp/abw_mcp/servers/legacy.py:70-73#wall-`). - A future tool that takes a container name, or a wider legacy-style identity, would expose the trail, so the separation is by convention (Inference; section 7.5).

Proof P10 reads the console copy of the event, and no proof reads the audit blob. - The WORM trail, the part an auditor would ask about, has no automated check (checked by search here; this reference did not run the suite).
- `src/mcp/tests/test_servers.py:159-176#test_audit_redacts_arguments_and_content` - In the unit suite only `search_research` is completed by an entitled caller. The per-persona tests call `tools/list` only (`src/mcp/tests/test_servers.py:40-63#tools`), `place_order` is called only to be blocked or rejected (`src/mcp/tests/test_servers.py:109-137#test_restricted_list_and_separation_of_duties`, `src/mcp/tests/test_servers.py:207-231#test_argument_validation`), `get_deal_document` only to be refused by the project rule, by a simulated Storage 403 or by argument validation (`src/mcp/tests/test_servers.py:66-105#test_storage_rbac_denial_audited`), the role-less test calls one tool per server and expects a refusal (`src/mcp/tests/test_servers.py:250-266#test_entitled_to_nothing_sees_no_tools_and_cannot_call`), and `get_headlines` is called directly (`src/mcp/tests/test_downstream.py:71-75#get_headlines`). **Documentation mismatches**

- `DESIGN.md:128#missing_role` - The design lists "403 missing_role on tools/call" among the rules in code, but the MCP server answers a role-less call with HTTP 200 and a DENIED result whose reason is `missing_role` (`src/mcp/abw_mcp/registry.py:163-165#forbidden`, `src/mcp/tests/test_servers.py:250-266#test_entitled_to_nothing_sees_no_tools_and_cannot_call`); the 403 exists only at the gateway (`infra/apim/policies/mcp-jwt.policy.xml:43-44#missing_role`). - On the private path, which has no gateway, a client written from the design would wait for a 403 that never comes (S2 against S6 in section 8.5).
- `DESIGN.md:138#data_class` - The design lists the `data_class` values `public`, `wall:falcon`, `wall:orion` and `internal`, but the code writes `public`, `wall`, `internal`, `external` and `mixed` (`src/mcp/abw_mcp/servers/research.py:75#public`, `src/mcp/abw_mcp/servers/wall.py:120#wall`, `src/mcp/abw_mcp/servers/vendor.py:70#external`, `src/mcp/abw_mcp/servers/legacy.py:116-119#mixed`). - A filter on `wall:falcon` returns nothing (section 8.4).
- `DESIGN.md:145-147#VENDOR_API_KEY` - The settings list omits `AUDIT_FAIL_CLOSED` and `COSMOS_OBO_SCOPE` (`src/mcp/abw_mcp/config.py:150#audit_fail_closed`, `src/mcp/abw_mcp/config.py:155#COSMOS_OBO_SCOPE`) and says the vendor key is a Key Vault reference through the identity, whereas the Bicep passes a plain app secret value (`infra/04-apps.bicep:182-187#vendor-api-key`) and a Bicep comment repeats the reference claim (`infra/03-platform.bicep:558#vendor`). - A reader of the design would think the vendor key is not held in the app.
- `src/mcp/README.md:11#fallback` - The module README's diagram says Cosmos DB is reached by "OBO or UAMI fallback", but a failed exchange is a denial and never a switch to the server identity (`src/mcp/abw_mcp/registry.py:177-191#obo_failed`, `src/mcp/abw_mcp/data.py:177-182#use_user_token`); the test pins only that the failed exchange is returned as FORBIDDEN with reason `obo_failed:invalid_grant` and is audited, and it uses the fake data plane, so the credential choice inside the real data plane client is not exercised (`src/mcp/tests/test_servers.py:140-156#test_obo_failure_does_not_fallback`). For Cosmos DB the server's own identity is used only for the restricted list read and when `COSMOS_OBO` is off on the actions and private servers; the legacy server always uses its own identity (`src/mcp/abw_mcp/servers/legacy.py:98#use_user_token`). The README also lists `MCP_APP_CLIENT_ID` as required for every server although the vendor and legacy servers are exempt (`src/mcp/README.md:34#MCP_APP_CLIENT_ID`, `src/mcp/abw_mcp/config.py:101#validates_tokens`), and says `AUDIT_FAIL_CLOSED` makes blob-audit failures deny calls (`src/mcp/README.md:40#AUDIT_FAIL_CLOSED`) although the denial comes after the action has run (the audit-sink items above; section 8.4). - Small wording gaps, but readers take the README as the contract.
- `DESIGN.md:31` and `infra/05-apim-apis.bicep:43` - Two more mismatches sit in the Gateway and policy group at the start of these findings: the gateway check order described at `DESIGN.md:31`, and the API descriptions at `infra/05-apim-apis.bicep:43` and `infra/05-apim-apis.bicep:54`.

**Checked and found sound**

- `src/mcp/abw_mcp/servers/wall.py:62-70#classification` - The Search filter interpolates only the project, which is limited to two literals, and the free-text query goes to the query parameter, not into the filter (`src/mcp/abw_mcp/servers/wall.py:19-22#Literal`, `src/mcp/abw_mcp/servers/wall.py:66#query`). `get_deal_document` takes the project from a validated id prefix, refuses it unless the project is in the caller's roles, and only then forms the container name (`src/mcp/abw_mcp/servers/wall.py:25-26#pattern`, `src/mcp/abw_mcp/servers/wall.py:88-93#container`, `src/mcp/abw_mcp/servers/wall.py:39-47#project_not_in_token_roles`, `src/mcp/tests/test_servers.py:207-231#test_argument_validation`). - I found no injection path (Inference from reading the code; not tested adversarially).
- `src/mcp/abw_mcp/servers/private.py:11-12#PositionsArgs` - The positions query is parameterised on the desk, bound to the desk's partition key, and the desk name is limited by a pattern; the credit-limit id comes from a slug function over a bounded name (`src/mcp/abw_mcp/servers/private.py:19-28#partition_key`, `src/mcp/abw_mcp/servers/private.py:15-16#CreditLimitArgs`, `src/mcp/abw_mcp/data.py:149-150#credit_limit_id`). - Inference from the code.
- `src/mcp/abw_mcp/app.py:138#compare_digest` - The vendor key is compared with a constant-time function (standard-library behaviour, not verified here), and a wrong key gets 401 `invalid_vendor_key` (S4 in section 8.5). - Implemented and tested for a missing header, a wrong key and the right key (`src/mcp/tests/test_servers.py:178-191#test_vendor_key_enforcement`). A key made only of spaces is the one gap in the presence check and is listed under Configuration and deployment.
- `src/mcp/abw_mcp/registry.py:163-168#model_validate` - Arguments are validated after the role check and before the handler, and the argument models reject unknown fields, so a call with a surprise argument never reaches a data call (`src/mcp/abw_mcp/registry.py:27#forbid`, `src/mcp/tests/test_servers.py:207-231#test_argument_validation`). - Implemented and tested.
