### 9.7 Act 6: One request, every layer

**What this section proves.** Act 6 answers one question for every click: where in the platform did this request stop, and which layer said no? The console follows a single request through twelve layers: seven on the request path, in order (Entra sign-in, Conditional Access, the guardrail, the agent, the AI gateway, the MCP server, the data) and five watchers that record it (Azure Monitor, Sentinel, Defender, Azure Policy, Agent 365) (`console/e2e.py:44-45#PATH`, `console/catalog.py:599#story`). The first half of the act, beats 6.1 to 6.4, shows four refusals that stop at four different places for four different reasons. A wrong password stops at Entra: no token exists, so nothing reaches the gateway (6.1). A shared key is refused at the governed gateway and at Foundry, which both ignore keys (6.2). A genuine token without a role for the Wall server is refused at the gateway with HTTP 403 and reason `missing_role` (6.3). A genuine token with a Wall role passes the gateway, and the MCP server refuses the wrong deal with a soft DENIED and reason `project_not_in_token_roles`, so Storage is never asked (6.4) (`console/e2e.py:639-678#sc_auth_failed`, `console/e2e.py:729-760#sc_keys`, `infra/apim/policies/mcp-jwt.policy.xml:31-46#missing_role`, `src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`). Beats 6.5 to 6.8 (9.7.6 to 9.7.9) continue with the Storage refusal, the guardrail and the two requests that are allowed end to end (`console/catalog.py:682-739#data_plane`).

#### 9.7.1 Act overview

**Purpose.** Acts 1 to 5 each prove one control. Act 6 puts every control on one board, so that "which layer said no, and which layers never saw the request" has a visible answer for each of eight requests: six that should fail, then two that should work (`console/catalog.py:599#story`). The board is a feature of the demo console, not of the platform. The console builds it in its own process from the live call plus read-only reads of Azure, and the module header promises that nothing in it writes to Entra, changes a role or touches anything outside the demo resource group, and that no token, key or password is emitted or stored (`console/e2e.py:1-18#Nothing`). Provenance: Implemented (the board, the scenarios and the log read-back), Configured (the gateway policy and the Sentinel rules the beats read), Platform behaviour (Entra sign-in logging, Conditional Access and smart lockout, each marked where it is used).

**The twelve layers.** A board always has twelve rows. Seven are the layers a request can pass through, in this order; five are watchers that sit beside the path and record it (`console/e2e.py:44#PATH`, `console/e2e.py:45#WATCH`). Each row has a title, a one-line sub-title and a default "how to show this in Azure" click path (`console/e2e.py:49-62#LAYER_INFO`, `console/e2e.py:65-79#CLICK`). States and evidence tags are those of 9.1.3; the tables say what each row asserts and which source is allowed to move it.

**The evidence board.** Provenance: Implemented. The board is a small data structure the console builds in its own process. Five rules decide what it may show.

1. *A board is built at click time, from the live call or, in beat 6.5, from a saved earlier one.* Each scenario runs inside a `Ctx` that owns one `Board` and a three-thread pool. The scenario writes rows with `put`, whose default evidence tag is `live`. `finalize` then fills every row the scenario did not write: a path row becomes `na` "Not part of this scenario." and a watch row becomes `na` "Nothing to see here for this scenario." (`console/e2e.py:279-300#Ctx`, `console/e2e.py:193-200#put`, `console/e2e.py:215-221#finalize`). The configuration reads a row may quote (`PROBE_IDS`) start in the pool when the scenario starts and are waited for at most 25 seconds (`console/e2e.py:46-47#PROBE_IDS`, `console/e2e.py:271-277#_prefetch`).
2. *The headline is derived, not typed.* It is the scenario's own headline if it set one, else "STOPPED AT: " plus the title of the first blocked path row, else "ALLOWED END TO END". The same payload carries the actor, the one-sentence outcome, the request id, the per-click nonce, the click time, the twelve rows, the small status lamps (`pass` and `seen` light green, `block` red) and a trace reference that later refreshes use (`console/e2e.py:326-346#payload`, `console/e2e.py:235-247#lights`).
3. *A row can turn green only from a named source.* `pass` and `block` come from the live call, except in beat 6.5, which replays the newest saved data-plane denial and writes them with the evidence tag `replay` (`console/e2e.py:849-892#sc_data_plane`). In a live call `entra_pass` runs only after a token request returned a token, and `apply_gateway` reads the real HTTP status and tool decision of the reply (`console/e2e.py:371-378#entra_pass`, `console/e2e.py:462-504#apply_gateway`). A row whose source is a configuration read or a portal step can only be `info`, `na`, `due` or `portal` (`console/e2e.py:380-390#ca_row`, `console/e2e.py:944-948#_agent365_row`). `seen` is written only by a refresh reader that found a log row, or by a replay of an earlier real run (`console/e2e.py:1324-1330#_confirm`, `console/e2e.py:589-603#_violations_replay`).
4. *Rows whose evidence cannot exist yet are "waiting" until logs arrive.* At click the Monitor row is `due` with a lag label, and so is the Sentinel row when a rule is registered for the refusal; the other watcher rows are `quiet`, `info`, `na` or `portal`, as the table shows. Beat 6.5 is the exception: it replays saved logs, so it shows `seen` at click. A refresh turns a row into `seen` or `quiet` when it finds the evidence, or rewrites it as `due` with the same label when it does not (`console/e2e.py:1333-1335#_waiting`). A confirmation keeps the click-time sentence and appends the log's own words (`console/e2e.py:1324-1330#_confirm`). The lags the console states are repository observations, not platform guarantees: Log Analytics 2-18 minutes, Sentinel alerts 5-15, Entra's own sign-in log 10-20 (`console/e2e.py:1288#LAG`, `console/catalog.py:601#wait`). Platform behaviour: Microsoft documents Entra log delivery to Log Analytics as taking up to three days and gives no per-minute guarantee (https://learn.microsoft.com/entra/identity/monitoring-health/reference-log-latency). The full-chain card expects the hops in stages: the Entra token row 4-8 minutes after the token is issued, the gateway row about 1, Foundry spans 1-5, the MCP audit row 6-10, the data-plane row 2-8, the Sentinel alert and incident 9-13 (`console/e2e.py:1634-1651#_fc_waiting`). Section 11 holds the lag table.
5. *"Refresh from logs" reads Azure back for one saved board.* It is the job kind `e2e_logs`. It recalls the board from an in-memory store of at most 40 traces, so a console restart or 40 newer runs lose it, and the job then says so and asks for a fresh run (`console/e2e.py:250-270#_TRACE_MAX`, `console/e2e.py:1858-1875#run_logs`). Otherwise it runs `_refresh`, which picks a reader by scenario and lists, in its summary, every watcher row still `due` (`console/e2e.py:1833-1855#_refresh`, `console/e2e.py:1858-1875#run_logs`). The readers are in the table.

| Scenario | What the refresh searches for | What it reads | Rows it can change |
|----------|------------------------------|---------------|--------------------|
| `auth_failed` (6.1) | The Entra correlation id from the click; else the newest failed sign-in for that user name since two minutes before the click | Microsoft Graph `auditLogs/signIns` filtered by user name and time, top 20, one slow call with a 150 s timeout; and the `SigninLogs` table by correlation id, only when the workspace shows the Entra connector delivering (`console/e2e.py:1347-1356#_graph_signins`, `console/e2e.py:1359-1399#_refresh_auth_failed`) | `entra` and `ca` get a confirmation, `monitor` becomes `seen` "IN ENTRA'S LOG" (tag `graph`), `sentinel` becomes `seen` "IN SIGNINLOGS" only when connected and found |

The Sentinel reader looks for a SecurityAlert row naming the request id. While the click is under 20 minutes old a missing alert keeps the row `due` ("the rule runs every 5 minutes and alerts typically appear 5-15 minutes after the log row"); after that it becomes `quiet` "NOT FOUND" (`console/e2e.py:1750-1786#_refresh_sentinel`). The Defender reader reads `Microsoft.Security/alerts` through ARM twice and merges them, drops sample alerts, and shows `seen` "ALERT RAISED", `due` "ALERT NOT GUARANTEED" under 20 minutes, or `quiet` "NO ALERT RAISED" after (`console/e2e.py:1789-1803#_defender_alerts`, `console/e2e.py:1806-1830#_refresh_defender`).

*How a scenario function builds its board.* Every function follows one pattern: name the actor (`ctx.actor`); record what a later refresh will need in `ctx.ref` (scenario, click time, request id, nonce, user name and object id, server, persona); make one live call; write rows with `put`; mark everything the call could not reach with `skip_rest`; then add the watcher rows with `watch_rows` and emit the board (`console/e2e.py:279-300#Ctx`, `console/e2e.py:210-214#skip_rest`, `console/e2e.py:770-793#watch_rows`, `console/e2e.py:344-356#finish`). The three scenarios that call a tool through the gateway as a signed-in user share `direct_call`: it announces "Getting <actor>'s token for the wall API and calling get_deal_document", makes the one live call through `gateway_call`, writes the Conditional Access, no-model and Policy rows, then the Entra row (a "NO TOKEN" block if Entra would not issue the token), then `apply_gateway` and `watch_rows`. The document is FALCON-001 unless the scenario overrides it; the wrong-deal scenario asks for ORION-001 (`console/e2e.py:810-832#direct_call`, `console/e2e.py:833-847#sc_no_mcp_access`).

*Whose token is used.* `persona_for` resolves the persona: a "fixed" scenario uses its own person; a "pinned" one uses the persona its button sends if that is valid and otherwise its default (Priya for 6.3), without consulting the Acting-as picker; a "follows Acting as" one uses the persona the picker adds to the request if valid and otherwise the operator; every other mode ignores the picker (`console/e2e.py:1230-1240#persona_for`). `validate` runs when the job is submitted and refuses before any call is made: an unknown scenario, the wrong job kind, an unknown persona, and a pinned or followed persona who has not signed in once, with a message that points to "Acting as" (`console/e2e.py:1243-1262#validate`). `_execute` stores the resolved persona in the job parameters, so the card says whom the call was made as (`console/e2e.py:1265-1276#_execute`).

**Entra and Conditional Access rows.** Provenance: Implemented (the reads and the notes), Configured (one report-only policy), Platform behaviour (marked, with the Microsoft Learn page).

- *Read through the live call.* The `entra` row is `live`: it is written from the token request the scenario made itself, the refused password attempt in 6.1, or the token that `jobs.token_for` returned in 6.3, 6.4 and 6.7 (`console/e2e.py:371-378#entra_pass`, `console/e2e.py:407-421#gateway_call`, `console/jobs.py:428-437#token_for`).
- *Read through Microsoft Graph.* Only after a refresh, and only for a wrong password: Entra's sign-in log through `auditLogs/signIns` (`console/e2e.py:1347-1356#_graph_signins`). The Conditional Access configuration is read by a probe: Graph `/identity/conditionalAccess/policies`, counting the policies whose display name starts with "ABW" and how many of them are `enabledForReportingButNotEnforced` (`console/azure_probe.py:647-674#probe_conditional_access`).
- *Only a portal step.* The console gives a click path with placeholders (`{upn}` and the policy name) and tags it as not seen: the sign-in log path is "[path from docs, not seen]", and the Conditional Access path is "[policy list seen; Report-only tab path from docs]" (`console/e2e.py:65-67#CLICK`).
- *What the report-only policy is.* Configured: one policy in state `enabledForReportingButNotEnforced` for the members of `sg-abw-demo-all`, excluding the operator, every directory role whose name ends in "Administrator" and any break-glass-looking group, targeting the five MCP API app registrations, with the grant control "require MFA". The script records its status as `CONFIGURED-NOT-YET-OBSERVED` and `-Remove` rolls it back (`scripts/extras-agent-identity.ps1:17-23#enabledForReportingButNotEnforced`, `scripts/extras-agent-identity.ps1:236-262#CONFIGURED-NOT-YET-OBSERVED`).
- *What it does and does not do.* Platform behaviour: a report-only policy is evaluated at sign-in and not enforced, and its result appears in the Conditional Access and Report-only tabs of the sign-in log details (https://learn.microsoft.com/entra/identity/conditional-access/concept-conditional-access-report-only). So it records what it would require and blocks nothing. The `ca` row says the same, and adds that the policy is evaluated at sign-in, not on every call: a token that is already issued is not re-checked, so none of the Act 6 scenarios is a Conditional Access test (`console/e2e.py:380-384#ca_row`). In 6.1 the password fails first, so the row is `skip` "NOT EVALUATED" and, after a refresh, Entra's own `conditionalAccessStatus` is shown next to the prediction (`console/e2e.py:1359-1399#_refresh_auth_failed`).
- *The wrong-password flow.* The console asks Entra for a token with a username-and-password (ROPC) request. Platform behaviour: Microsoft recommends not using that flow, and it cannot satisfy multi-factor authentication (https://learn.microsoft.com/entra/identity-platform/v2-oauth-ropc). Here it is used only to prove a refusal, with a fresh made-up password, so it can only fail. Entra answers AADSTS50126 for a bad user name or password (https://learn.microsoft.com/entra/identity-platform/reference-error-codes). Smart lockout defaults to 10 failed attempts and a one-minute lockout that grows with repeats (https://learn.microsoft.com/entra/identity/authentication/howto-password-smart-lockout); the console allows itself five attempts in ten minutes, held in memory and shared by every user of the console (`console/e2e.py:512-525#_ropc_guard`, `console/e2e.py:639-678#sc_auth_failed`).

*The three admin-portal features, and what each is for this row.* The twelve rows have no row of their own for them; each reaches the board through a watcher.

1. *Agent 365 gateway (the `agent365` row).* Configured: the Azure role "A365 Gateway Policy Operator" is assigned to the first-party "Agent 365" service principal at the APIM scope. #### 9.7.2 Beat 6.1: Sign-in fails: a wrong password

**Purpose.** Show that Entra, the first layer, refuses someone who cannot prove who they are, and that a refusal there is a complete stop: no token exists, so the gateway, the MCP server and the data never see the request. The beat has one main button, "Try a wrong password", and two alternates that stop one layer later, at the gateway: "A real token, the wrong API" and "No token at all" (`console/catalog.py:604-613#auth_failed`). Provenance: Implemented. The spoken line is that Entra says no with an AADSTS code and a correlation id, and every row after it reads "never reached" (`docs/TALK-TRACK.md:199#AADSTS50126`).

**Actors and tokens.** Provenance: Implemented. The shared table in 9.7.1 lists all eight beats; the three variants of this beat are:

- *Main button.* Ian's user name with a made-up password (`console/e2e.py:641-644#actor`). No token is issued, so there is none to name. The console sends a username-and-password token request through MSAL from the test client, which is a public client, with an empty in-memory token cache and the research API's `Tools.Read` scope (`console/e2e.py:648-649#SerializableTokenCache`, `identity/Setup-Entra.ps1:171-177#isFallbackPublicClient`, `console/personas.py:126-129#_new_app`). The password is "wrong-" plus ten random hex characters, new on every click and never shown or stored (`console/e2e.py:649#hex`, `console/e2e.py:677#stored`). Platform behaviour: this is the resource owner password credentials flow, which Microsoft does not recommend and which cannot satisfy multifactor authentication (https://learn.microsoft.com/entra/identity-platform/v2-oauth-ropc).
- *"A real token, the wrong API".* The operator, with a genuine Entra token for Azure Resource Manager (audience `https://management.azure.com`) taken from the az CLI cache and sent to the Wall MCP API (`console/e2e.py:683-691#ARM`, `console/azure_probe.py:30#ARM`).

**Preconditions.** Provenance: Implemented. Beyond the act-wide list in 9.7.1:

- Nobody has to be signed in through Acting as. The three scenarios ignore the persona picker, and `validate` asks for a sign-in only for a persona the scenario really runs as (`console/e2e.py:1210-1212#persona`, `console/e2e.py:1243-1262#validate`).

**Sequence.** Main button, scenario `auth_failed`:

1. The button starts an `e2e` job. `_execute` resolves no persona for this scenario and runs its handler (`console/e2e.py:1265-1276#_execute`).
2. The handler starts a background check of whether Entra's sign-in logs reach the workspace: a `Usage` query for `SigninLogs` or `AADNonInteractiveUserSignInLogs` data over 30 days, where any failure means "unknown" (`console/e2e.py:546-552#SigninLogs`, `console/e2e.py:645#submit`).
3. It takes one place in the shared password budget. The timestamp is recorded before the attempt, and the sixth attempt inside ten minutes is refused with "That is five wrong-password attempts in ten minutes" and a request to wait or use the other two sign-in scenarios (`console/e2e.py:519-525#_ropc_guard`).
4. It asks Entra to sign Ian in with the made-up password; the job log reads "Asking Entra to sign <upn> in with a made-up password" (`console/e2e.py:647-649#acquire_token_by_username_password`).
5. If Entra ever returned a token, the handler would raise "Entra issued a token for a made-up password. Stop the demo and check the tenant's sign-in settings." (`console/e2e.py:650-651#RuntimeError`).
6. Otherwise it reads the first error code, the correlation id and a plain-words meaning, taken from a table of nine codes or else from the first line of Entra's own description cut at 140 characters (`console/e2e.py:652-657#correlation_id`, `console/e2e.py:506-511#_AADSTS`). Platform behaviour: AADSTS50126 is Entra's code for an invalid user name or password (https://learn.microsoft.com/entra/identity-platform/reference-error-codes).

8. It marks the five rows after Conditional Access `skip` with the default label "NEVER REACHED" (`console/e2e.py:661#skip_rest`, `console/e2e.py:210-213#skip_rest`).
9. It writes the watchers that do not apply, and the monitor row, which is `due` with the tag `graph` (`console/e2e.py:662-665#agent365`).
10. It waits up to 20 seconds for the background check and writes the Sentinel row from the answer (`console/e2e.py:666-675#connected`).
11. `finish` emits the board. The banner is "STOPPED AT: Entra login" because Entra is the first row in the `block` state (`console/e2e.py:329-338#headline`, `console/e2e.py:350-352#finish`).

- A1. "A real token, the wrong API" gets the operator's Azure Resource Manager token from the az CLI cache and reads its claims; the token itself is never shown (`console/e2e.py:683-689#token`).

**Failure modes and what the presenter should say.** Provenance: Implemented for the board text, Designed for the advice.

**Why and trade-offs.** Provenance: Implemented. A person who fails to authenticate never obtains a token, so every later layer is untouched; the "Never reached" rows show that instead of leaving blanks. **Trade-offs.** The wrong-password request uses the password flow that Microsoft does not recommend; here it is a deliberate refusal generator with a made-up secret, and nothing about it works for a real MFA-protected sign-in. The five-in-ten-minutes budget sits below Entra's default smart-lockout threshold of ten failed sign-ins (https://learn.microsoft.com/entra/identity/authentication/howto-password-smart-lockout), but it is held in the console's memory for all users and starts again at zero when the console restarts (Findings F6a-3). The failed password can be proved only from Entra's own log, which is slow and costs a 40-second Graph call; Sentinel cannot see it until a tenant admin connects the Entra connector, which this demo leaves alone (Findings F6a-4, F6a-17). The alternates' 401 reply gives only a generic reason, not which check failed; the gateway log says which check failed (`infra/apim/policies/mcp-jwt.policy.xml:108#reason`).

#### 9.7.3 Beat 6.2: Keys instead of Entra

**Purpose.** Show that the shortcut every proof of concept takes, one shared key, opens nothing in the governed platform. The console sends the real shared PoC key to the governed Wall MCP API and an API key to Foundry's agent endpoint, reads live that the data stores behind the wall have account keys switched off, and replays the latest real run of the policy script that tries to switch keys back on (`console/catalog.py:630-639#keys_not_entra`). The question the beat answers is the one an auditor asks: "the same key works on the legacy API in Act 1, so why does it not work here?" (`docs/TALK-TRACK.md:200#contrast`). The answer has four parts, one per layer: the gateway demands an Entra token, Foundry has local keys off, the data stores have keys off, and Azure Policy keeps them off. Provenance: Implemented (the scenario and its board), Configured (the APIM APIs, the Foundry account, the data stores, the policy initiative), Platform behaviour (what a switched-off key setting does, cited below).

**Actors and tokens.** Provenance: Implemented. No person acts: the board's actor line is "a shared key - no person" (`console/e2e.py:732#actor`). There are two credentials and no Entra token in either request:

- *The real shared PoC key,* the primary key of the legacy APIM subscription. The console reads it through ARM with a POST to the subscription's list-secrets operation, using the operator's Azure CLI token, keeps it in the console process's memory and, by the function's own docstring, never prints or logs it (`console/azure_probe.py:222-233#listSecrets`). *What "no access to this server" means in Entra terms.* Provenance: Configured (the roles and their assignments), Platform behaviour (what a token carries), Not in this repo (the setting that would make Entra refuse instead).

- The Wall API is an app registration with two app roles, `Wall.Falcon` and `Wall.Orion`, and a delegated scope `Tools.Read`. Access to the server is an assignment of one of those roles to a user on the API's enterprise application (`identity/Setup-Entra.ps1:33-35#Falcon`). Priya's role list has none for the Wall API and Ian's is empty, so neither has an assignment (`identity/Setup-Entra.ps1:50-61#Users`).
- Entra nevertheless issues the token. The delegated scope is consented for every user, and the portal tour records the application's "Assignment required?" property as No, so a person without a role still gets a token, "a visitor's badge" (`docs/TALK-TRACK-PORTAL-TOUR.md:189#Assignment`, `docs/TALK-TRACK-PORTAL-TOUR.md:197#visitor`). The board's first row says exactly that: token issued, "no app roles" for the wall API (`console/e2e.py:376-377#roles`). Platform behaviour: the `roles` claim of a user token lists the user's assigned roles on the target application, and `scp` lists the delegated scopes the client received consent for, so a token can carry the scope and no role (https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference).
- The refusal is the gateway's, not Entra's. The 403 body is written by the gateway policy, and the Entra row stays green because the token request succeeded. The code shows no Entra-side refusal for this beat (`infra/apim/policies/mcp-jwt.policy.xml:65-80#forbidden`).
- The Entra-side alternative is a property, not a role. Platform behaviour: when "Assignment required" is Yes, only users assigned to the application can sign in to it (https://learn.microsoft.com/entra/identity/enterprise-apps/what-is-access-management). The tour says Entra would then stop an unassigned user at sign-in with an error and the gateway would never see the attempt (`docs/TALK-TRACK-PORTAL-TOUR.md:197#visitor`). Not in this repo: no script sets or reads that property, and the tour lists the "No" as a click path to check, not as something the repo observed, so the beat's claim rests on a setting the repo does not enforce (Findings F6a-7).

Nothing in that rule reads the tool's arguments, so the gateway cannot tell a Falcon document from an Orion one (`infra/apim/policies/mcp-jwt.policy.xml:31-46#missing_role`, `infra/05-apim-apis.bicep:45#Falcon`).
6. With nothing to refuse, the policy counts the request in its metric with the decision `allow`, sets `x-abw-request-id` to the gateway's own request id (replacing any value the caller sent) and forwards the call (`infra/apim/policies/mcp-jwt.policy.xml:51-56#metric`, `infra/apim/policies/mcp-jwt.policy.xml:82#x-abw-request-id`).
7. The MCP server validates the same token again itself, builds the caller from the token's `roles` claim and takes the request id from `x-abw-request-id` first (`src/mcp/abw_mcp/auth.py:108-166#roles`, `src/mcp/abw_mcp/auth.py:173-188#RequestContextMiddleware`).
8. `call_tool` checks the tool's own role requirement, `Wall.Falcon` or `Wall.Orion`, which a Falcon token meets, then validates the arguments: ORION-001 matches the pattern `^(FALCON|ORION)-\d{3}$`, so the call is well formed and reaches the handler (`src/mcp/abw_mcp/registry.py:158-178#call_tool`, `src/mcp/abw_mcp/servers/wall.py:130-137#get_deal_document`, `src/mcp/abw_mcp/servers/wall.py:25-26#GetDealDocumentArgs`).
9. `get_deal_document` derives the project from the document id (ORION-001 gives `orion`) and calls `_require_project` before it builds the container name or reads anything. `caller_projects` turns `Wall.Falcon` into `falcon` and `Wall.Orion` into `orion`, so a Falcon-only caller holds `falcon` alone, `orion` is missing, and `_require_project` raises a `ToolError`: code FORBIDDEN, message "Caller is not crossed on that project.", reason `project_not_in_token_roles`, audit event `wall_violation_attempt` (`src/mcp/abw_mcp/servers/wall.py:88-91#_require_project`, `src/mcp/abw_mcp/servers/wall.py:29-36#caller_projects`, `src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`). The on-behalf-of credential is created only inside `read_blob_text`, after this line, so for this call no token exchange is attempted and no Storage request exists (`src/mcp/abw_mcp/data.py:57-60#_obo_credential`, `src/mcp/abw_mcp/obo.py:60-65#user_assertion`).
10. The registry catches the `ToolError`, writes an audit record under the request id (the same id as the gateway's correlation id) and returns a normal tool result. Its structured content says decision DENIED, error FORBIDDEN, the reason and the request id, with a note: "Blocked by policy and written to the audit log. Tell the user what was blocked and the reason code; do not retry, rephrase or look for a workaround." `isError` stays false unless `denial_mode` is `strict`; the default is `soft` (`src/mcp/abw_mcp/registry.py:192-198#ToolError`, `src/mcp/abw_mcp/registry.py:238-270#_tool_error_result`, `src/mcp/abw_mcp/registry.py:272-292#_error_payload`, `src/mcp/abw_mcp/config.py:59#denial_mode`). The answer is HTTP 200. The unit test asserts exactly this for a token whose roles are `["Wall.Falcon"]` asking for ORION-001: `isError` false, decision DENIED, error FORBIDDEN, the reason, "do not retry" in the note, no blob read, and the audit event `wall_violation_attempt` (`src/mcp/tests/test_servers.py:67-86#test_wall_isolation_and_audit`).
11. `http_result` takes the status, the decision from the structured content and the request id (the body's first, then the headers'). `judge` classes the reply as a refusal because the decision is DENIED, and the reason table puts `project_not_in_token_roles` at wall 2, the MCP tool server. `_wall_of` returns 2 because a refusal that came back as HTTP 200 with DENIED was decided by the MCP server, whatever its reason code says (`console/jobs.py:229-250#http_result`, `console/jobs.py:176-203#judge`, `console/catalog.py:47-50#project_not_in_token_roles`, `console/e2e.py:452-459#_wall_of`).

*Hard refusal versus soft refusal.* Provenance: Implemented. Beat 6.3 (9.7.4) and this beat are the two ways the first six beats can refuse a call at the gateway layer or just behind it, and they look different on the wire and in the logs:

| | Wall 1: the gateway (beat 6.3) | Wall 2: the MCP server (this beat) |
|---|---|---|
| Who decides, and from what | The gateway policy, from the token alone: revoked list, allowed apps, scope, role (`infra/apim/policies/mcp-jwt.policy.xml:31-46#missing_role`) | The tool, from the roles in the token and the project named in its arguments (`src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`) |

The server's refusal is soft by default for a reason its own code comment gives: Foundry Agent Service aborts the whole run (HTTP 400 `tool_user_error`) when a tool returns `isError` true, so a policy denial is returned as a normal result with `decision=DENIED`, and `strict` restores the MCP-spec error result (`src/mcp/abw_mcp/registry.py:263-269#Foundry`, `src/mcp/tests/test_servers.py:234#test_strict_denial_mode_uses_mcp_is_error`). The soft default is Implemented; the Foundry behaviour is stated only in that comment and is not re-checked here. The console therefore reads the decision, not the status alone: a reply counts as ok only when the status is 200 and the decision is not DENIED, BLOCKED or ERROR, and counts as a refusal when the decision says so or the status is 401, 403 or 429 (`console/jobs.py:229-250#http_result`, `console/jobs.py:176-203#judge`). The price of the soft answer is that the gateway sees an HTTP 200: its metric and its log row call the Orion request allowed, so a dashboard built on the gateway alone under-reports the refusal. It shows in the MCP audit row, in the queries and rules built on that row (`AbwIdentityChain`, `AbwDenials`, ABW-001 and ABW-006) and on this board, but not in the gateway's metric or row (`observability/kql/AbwDenials.kql:57-66#2-mcp-server`, `observability/sentinel/abw-006-repeated-denials.kql:10-15#Denials`) (Findings F6a-14).

**Why and trade-offs.** Provenance: Implemented, with the Storage assignment Configured. The gateway can decide who the caller is and which server the caller may use, because both are in the token. It cannot decide which deal the caller may read, because the deal is in the tool's arguments and the gateway rule never reads them (`infra/apim/policies/mcp-jwt.policy.xml:31-46#missing_role`). The per-deal rule therefore lives in the tool, which compares the project in the document id with the project roles in the token before it names a container or makes a Storage call. That is plain code, not a prompt asking a model to behave (`src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`, `console/catalog.py:677#entitlement`). Because the check precedes Storage, its answer cannot depend on whether the document exists, and P03 asserts that a search for Orion documents is refused as well (`src/mcp/abw_mcp/servers/wall.py:88-93#_require_project`, `demo/prove.py:652-653#existence`). The refusal also tells the model what to do next: report the block and the reason code, and do not retry, rephrase or look for a workaround (`src/mcp/abw_mcp/registry.py:286-288#retry`). A second wall stands behind it: if the tool's check were wrong or skipped, Storage would still refuse the user's own identity, because `wall-orion` has no person or group role, only service identities, which the playbook marks as seen from the CLI (`docs/PROOF-PLAYBOOK.md:739#wall-orion`). **Trade-offs.** The soft refusal costs visibility at the gateway: the policy counts the request in its metric as allow and the gateway row says HTTP 200, so a dashboard built on the gateway alone would miss the refusal, which shows in the MCP audit row, in the queries and rules built on it (`AbwIdentityChain`, `AbwDenials`, ABW-001 and ABW-006) and on this board, but not in the gateway's metric or row (Findings F6a-14) (`infra/apim/policies/mcp-jwt.policy.xml:51-56#metric`, `docs/PROOF-PLAYBOOK.md:735#AbwIdentityChain`). Detection is slow and can be grouped: the alert needs the audit row ingested and the five-minute rule run, the recorded run took 22 minutes, and incidents group by account over five hours (Findings F6a-13, F6a-16). The beat hard-codes ORION-001 and the premise that nobody holds the role, so it changes meaning the day someone is granted Orion (Findings F6a-11). It shares its button label with beat 1.2, which runs the agent (Findings F6a-15). The MCP audit row carries two values that are not measurements, `obo=True` from a default and `downstream search 403` from a literal (Findings F6a-12) (`src/mcp/abw_mcp/registry.py:65#obo`, `src/mcp/abw_mcp/servers/wall.py:39-47#downstream`). And only the operator's board has been run; the persona variants are design (Findings F6a-6).



#### 9.7.6 Beat 6.5: The last layer says no: Storage RBAC

**Purpose.** Show the one refusal that no earlier layer can make. **How demo/prove.py proves it.** P16 "Entitlement drift: a group change withdraws data access even though the token still says yes (layer 3)". **Failure modes and what the presenter should say.** If the button fails with "no data-plane denial in the last 14 days", run P16 once before the talk (it needs an Azure CLI sign-in with the right to change group membership and takes a few minutes). If Sentinel reads NOT FOUND, either no alert was raised for that request id or the lookup failed (Findings F6b-4); press Refresh from logs and, if it is still empty, do not present an alert. If asked "did you just remove someone from a group?": no, the headline says REPLAY and the date of the real run. If asked why the denial took 27 seconds, say it is a measured value from one run (the catalog and the scenario note speak of "27 and 44 seconds in the two scoreboard runs", but the scrubbed scoreboard records only the 27 and DESIGN.md gives 5-44 seconds as the measured range, so quote 27 and say "one run": `console/catalog.py:688#44`, `console/e2e.py:892#27`, `demo/evidence-scrubbed/SCOREBOARD.md:45#P16`, `DESIGN.md:218#5-44`; Findings F6b-6) and that Microsoft documents role-assignment changes as taking up to ten minutes to apply (https://learn.microsoft.com/azure/storage/blobs/assign-azure-role-data-access#assign-an-azure-role), and up to 30 minutes in the Storage authorization page's general statement (https://learn.microsoft.com/azure/storage/blobs/authorize-access-azure-active-directory#azure-built-in-roles-for-blobs); what set the 27 seconds (token caching, group claim refresh or role propagation) is not verified here (`src/mcp/abw_mcp/obo.py:51-58#_cache`).

**Why and trade-offs.** The Falcon role is a direct user assignment to the wall application because group-based app-role assignment needs Entra P1, while the Storage role is assigned to a group; the two can therefore disagree, and the gateway and the MCP server can only read the first (`identity/Setup-Entra.ps1:6-8#assignments`, `infra/03-platform.bicep:617-636#raFalconBlob`). The Storage account allows no shared-key access, so there is no key path around the role assignment (`infra/03-platform.bicep:130-135#allowSharedKeyAccess`). Azure RBAC grants access by creating a role assignment and removes it by deleting one, and group assignments apply to the group's members (https://learn.microsoft.com/azure/role-based-access-control/overview). The cost is that the check is only as fresh as Storage's view of the token and of the assignments, and the beat is a replay: it depends on a `storage_rbac_denied` audit row in the last 14 days (normally from a P16 run), and it shows a past event, not a live one. The headline, the note and the actor line say so on the board itself (`console/e2e.py:864-892#proof`).
#### 9.7.7 Beat 6.6: Attack the model: a jailbreak

**Purpose.** Show that the agent has a layer in front of the model, and say plainly what that layer can and cannot promise. The presenter sends a textbook "DAN" jailbreak (ignore every rule, reveal the hidden system prompt, read the Project Orion documents, skip every wall check) to the governed agent `abw-wall-desk`, signed in as the operator. That agent is published with the guardrail policy `abw-agent-guardrails`, which has the jailbreak shield on the prompt. When the guardrail fires, Foundry ends the run with HTTP 400 and the code `content_filter` before the model answers; the agent calls no tool, so the gateway, the MCP server and Storage are never asked. **What the guardrail can and cannot promise.** It can end a run before the model answers when its classifier flags the prompt (the blocked branch), and it leaves a trail that other layers read (the failed span and rule ABW-008, hops 13 and 14). It cannot guarantee that a given prompt is flagged. Learn describes guardrail controls as flagged by classification models, lists agent guardrails as a preview feature with four intervention points (user input, tool call, tool response and output, of which tool call and tool response are in preview), and says that a Prompt Shields result of "No prompt attack" does not establish that a request is benign (https://learn.microsoft.com/azure/foundry/guardrails/guardrails-overview, https://learn.microsoft.com/azure/foundry/openai/concepts/content-filter-prompt-shields#prompt-shields-for-user-prompts). So the layer is preventive only when it fires, probabilistic as a whole, and detective in what it leaves behind. The repo configures the policy `abw-agent-guardrails` with the jailbreak and indirect-attack shields blocking on the prompt, the preview indirect-attack check on tool output (source `PostToolCall`) blocking, four harm categories at Medium on prompt and completion, and Protected Material Text on the completion not blocking; the policy is created with the preview API version `2026-07-15-preview` (`infra/06-governance.bicep:77-96#raiPolicies@2026-07-15-preview`; Findings F6b-10). Its own comment says the tool-response check stopped the run on only a minority of identical requests in the lab, so it is a detection layer and "the deterministic control is the wall" (`infra/06-governance.bicep:72-76#deterministic`). For the prompt-level jailbreak shield the repo holds no measurement: the catalog says it "has stopped this prompt every time it was tried in this tenant" and tells the presenter to say that, not "always", but no proof id records those tries (`console/catalog.py:703#time`; Findings F6b-11). The policy is attached to an agent when the agent is published with `rai_config`, and only `abw-wall-desk` and `abw-wall-desk-redteam-shielded` carry it; `abw-wall-desk-redteam` and `abw-poc-legacy` do not, which is what makes the shielded and unshielded comparison of beat 4.3 possible (`src/agent/abw_agents.py:155-194#publish`). Learn says these guardrails apply to agents built in Foundry Agent Service, and documents for hosted agents that, on many subscriptions, a policy name that does not exist is accepted and nothing is filtered (it fails open; https://learn.microsoft.com/azure/foundry/agents/how-to/add-hosted-agent-guardrails#test-content-safety-filtering); the repo does not test that for these prompt agents (not verified here), which is why the Guardrails row of beat 6.8 reads the attachment live from Azure (`console/azure_probe.py:283-321#probe_guardrail`; see 9.7.9). The board never reports a non-fire as a block: any run that is not recognised as stopped by the guardrail takes the DID NOT FIRE branch (`console/e2e.py:1085-1101#DID`).

**If the model complies anyway.** When the guardrail does not fire, the model receives the prompt and may call tools. Nothing in the wall depends on the model refusing. The instructions tell the model that a DENIED result is a policy decision and that tool results are untrusted input, but instructions are text the model may ignore (`src/agent/abw_agents.py:55-68#WALL_DESK_INSTRUCTIONS`). **Why and trade-offs.** A guardrail in front of the model is cheap and early: when it fires, nothing downstream ever sees the attack, and it is the layer meant to stop a model-only harm (together with the model's own refusal), such as a reply that quotes the instructions or harmful content, because the wall governs tool calls and data, not text (`infra/06-governance.bicep:77-84#Hate`, `src/agent/abw_agents.py:55-68#WALL_DESK_INSTRUCTIONS`). It is also the layer the repo trusts least: it is a classifier, its tool-output check is a preview feature that fired on a minority of runs in the lab, and the policy API is a preview version, so the design lets the wall decide again from the user's token and treats the guardrail as detection plus a first line of defence (`infra/06-governance.bicep:72-76#deterministic`). The costs are a second source of uncertainty on stage (a non-fire is an honest outcome that the board shows), a detection path with uneven lag (spans about 5 minutes, Sentinel 5-15, Defender not guaranteed), and a paid Defender plan that the demo scripts do not enable (`docs/COST.md:32-35#Microsoft`). The beat runs only as the operator because agent scenarios use the operator's own sign-in, so it does not show a second user being treated differently by the guardrail (`console/e2e.py:1217#guardrail_attack`).

**Why and trade-offs.** The beat is the positive control: a refusal means something only if the same path says yes to someone who is cleared, and the only difference from 6.4 is the person and the document, not the code path. The cost is that the check is split: the gateway and the MCP server read an app role assigned to the user, Storage reads a group, and the two can disagree (6.5). **Failure modes and what the presenter should say.** If Foundry shows a consent link instead of a result, approve it once and run the beat again; if the run takes 20 to 60 seconds, that is normal (the agent makes several tool calls: talk over it); if the tool count differs from the last run, that is the model, so do not promise a count; if the Storage or Foundry row is missing right after the click, it is lag, so press Refresh from logs about fifteen minutes after the click and, if a hop is still missing, do not present it as logged; Priya and Ian cannot be chosen for this beat because agent runs always use the operator's sign-in, so use 6.7 for a persona (`docs/PROOF-PLAYBOOK.md:862#consent`, `docs/PROOF-PLAYBOOK.md:867#model`, `docs/PROOF-PLAYBOOK.md:904-908#chosen`). The line to land: the agent is one more identity on the same wall; it acts for the user and every layer behind it still decides; the gateway named the user, the tool server named the user and Storage named the user; allowed, and provable at every hop (`docs/PROOF-PLAYBOOK.md:901#provable`, `docs/TALK-TRACK.md:204#Through`). Do not say that disabling the agent's identity would stop these calls: the inventory of agent identities is "not the kill switch", because the tool calls carry the user's token, and the gateway kill switch and group removal are what stop them (`docs/PROOF-PLAYBOOK.md:877-899#startswith`). Do not present the silence of Sentinel and Defender as detection: it is the absence of an alert in the window that was read.

**Why and trade-offs.** The agent adds a model and a token-holding service (Foundry keeps the user's token and the connection's client secret, below) to the chain, but not a new identity: its tool calls carry the signed-in user's token (Platform behaviour: Agent Service stores the user's credentials for the agent's calls to the MCP server, https://learn.microsoft.com/azure/foundry/agents/how-to/mcp-authentication), the MCP server derives the data token from it by on-behalf-of (see 9.7.8), and the dry run's Storage row read `auth=OAuth`, so the checks of 6.7 run unchanged behind the model; the agent's own instructions say that every tool call runs with the user's identity, not the agent's, but that is a statement made to the model, and the proof is the log row (`console/e2e.py:925-928#anywhere`, `src/agent/abw_agents.py:59#identity`, `docs/PROOF-PLAYBOOK.md:873#auth=OAuth`). The agent's instructions also tell it to treat tool results as untrusted data, but the platform guardrail on tool output is the weakest layer: in the project's own tests it stopped a poisoned tool result on only some identical requests (1 in 11 to 5 in 8), which is why the identity walls behind it matter more than the model's good behaviour (`src/agent/abw_agents.py:67#untrusted`, `README.md:140#output`; see 9.7.7). The price is time and variability: a model and several tool calls take 20 to 60 seconds against about four for the raw call, and the model decides how many calls to make, so the number of log rows follows the number of tool calls (15 to 30 over four dry runs) (`docs/PROOF-PLAYBOOK.md:874#layers`). The board shows less than the run did, because it follows only the first document read (Findings F6b-16). Foundry holds the user's tool token for its whole life, and Entra access tokens live 60 to 90 minutes with no continuous access evaluation built for the custom API (the README says it cannot get one, not verified here), so the quick levers are group removal (under a minute at the data plane) and the gateway kill switch (about a minute), while a role change reaches the agent only when the held token expires (one token id was seen in use for 51 minutes): the two must be paired (`README.md:141#removal`, `DESIGN.md:223#references`). The OAuth client's secret sits in the Foundry connection, a standing secret that the user-token flow itself does not remove (`DESIGN.md:237#confidential`, `README.md:142#client`). A run that enters directly (`agent_via` is `direct`) skips the front door's revocation list, per-user rate limit and token budget; the tool servers are named in the agent's own definition, so the hops behind Foundry are the same (`console/agent_run.py:86#project.get_openai_client`, `console/jobs.py:105-107#agent_via`, `infra/apim/policies/agent-frontdoor.policy.xml:51-55#revoked`, `infra/apim/policies/agent-frontdoor.policy.xml:95-96#rate-limit-by-key`, `src/agent/abw_agents.py:129-137#server_url`; see 9.8.3). Finally, how Foundry obtains and refreshes the user's tool token, beyond what the platform page and the repository's own measurements say, was not verified here; what the audit row's `client=` shows for an agent call is the Inferred statement in the Actors paragraph.

**Why and trade-offs.** The twelve-row board is a console feature, not an Azure one: when a path row says no, the rows after it are drawn as never reached (`console/e2e.py:207-221#skip_rest`), so what the board shows at click time is the console's reading of the live result and the logs confirm it later. Refusals are visible in seconds and detection lags, and the lags the console states are observations of one tenant, not promises (`console/e2e.py:1288#LAG`). Silence in the Sentinel row is not detection, and the board names four kinds of it: a blind spot when the Entra sign-in logs are not connected, no rule for a refused key, below threshold for a single refusal, and not found for a request id with no alert (`console/e2e.py:673#BLIND`, `console/e2e.py:753#RULE`, `console/e2e.py:790#THRESHOLD`, `console/e2e.py:885#FOUND`). The guardrail is a probabilistic preview control, so a run it did not stop is drawn as a failure with the headline GUARDRAIL DID NOT FIRE and never as a block (`console/e2e.py:1085-1101#GUARDRAIL`, `demo/prove.py:787-789#preview`); the deterministic control behind it is the wall (9.7.7). The two allowed beats are positive controls: without them every refusal could be a broken stack, and the outcome sentence for an allowed read says that the gateway, the MCP server and Storage all saw the user's own identity (`console/e2e.py:795-807#outcome_for`). Three things are weaker than the rest of the act: 6.5 is a replay that needs a Storage denial row from the last 14 days, normally from a P16 run (Findings F6b-1), 6.3 was written before any persona signed in (9.7.4), and the three presenter documents give three different orders (Findings F6b-20).
