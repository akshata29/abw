### 9.6 Act 5: What InfoSec sees

**What this section proves.** Act 5 answers the question an information-security analyst asks first, "show me exactly what that agent did, and who is using agents at all", from the logs rather than from the presenter's word. Beats 5.1 and 5.2 follow one request id across up to four records written by four systems: the Foundry run, the API Management (APIM) gateway, the MCP server's own audit line and the Azure Storage request log. A refused read has no Storage row, because the MCP server refused before it touched the data; an allowed read names the same person at the MCP server and at Storage, with `auth=OAuth` at Storage. Beats 5.3 to 5.6 aggregate the same tables: usage per user, refusals per wall, the agent's own tool calls, and how long one token kept serving calls. The governance tour then opens twelve service cards, some of which read live facts from Azure and some of which only link to a portal. All six beats are read-only Log Analytics queries run with the operator's own Azure CLI sign-in, never as a persona; the single exception is beat 5.1, which makes one gateway call of its own when no Orion request id was remembered. The section also says what these views cannot see: the private MCP server never passes APIM, Entra sign-in refusals are in no denial layer, usage counts only what the MCP servers logged, and three tour cards (the Agent 365 gateway, Defender for AI services and Purview DSPM for AI) end in an admin-portal step that this repository does not read (`console/catalog.py:497-501#act5`, `console/jobs.py:1160-1181#resolve_tag`, `console/jobs.py:1184-1239#run_kql`).

#### 9.6.1 Act overview

**Purpose.** Show that every call, allowed or refused, leaves a trail that an InfoSec analyst can read without asking the developers. The act states its own point as one sentence: every call leaves one request id that stitches the agent, the gateway, the MCP server and the data plane together, with the user named at every hop (`console/catalog.py:500#story`). The act has six beats and a tour. Beats 5.1 and 5.2 trace one request id through the four systems, first for the Orion denial remembered from beat 1.4 (9.2.5) and then for the latest allowed read made by an agent (beat 1.3, 9.2.4). Beats 5.3 to 5.6 are four aggregate views over the same tables: calls per user, refusals per wall and reason, the agent's last tool calls, and tokens that kept serving calls for more than a minute. The tour is the last card on the page and holds twelve cards, each of which opens a drawer with live facts and links to the real service (not every link is marked verified; `console/web/pages.js:437-455#scenePage`, `console/web/pages.js:121-137#tourCard`). Provenance: Implemented (the console runners, the query texts and the cards), Configured (the diagnostic settings that send the logs to one workspace, and the saved functions the queries call, defined in `observability/kql`; the function pack, the Sentinel rules and the workbook belong to section 11), Platform behaviour (log ingestion delay and token lifetime, with the Learn pages cited where they are used).

**Shared mechanics of the six query beats.** A button posts the run to `POST /api/jobs`, the job manager validates it, starts a daemon thread and the page polls the job (generic path: 9.1.5; `console/server.py:128-135#api_jobs_start`, `console/jobs.py:503-533#start`). For this kind, validation accepts only a query name that exists in the catalog, never `latest_allowed`, and a tag that is `orion`, `allowed` or a GUID (`console/jobs.py:575-580#kql`). The runner is `run_kql`: it says "Querying Log Analytics: <title>", then either traces one request id (beats 5.1 and 5.2) or runs the fixed query and draws a table (beats 5.3 to 5.6) (`console/jobs.py:1184-1239#run_kql`). The REST timespan is `PT<h>H` below 48 hours and `P<d>D` from 48 hours up, so the 72-hour chain window is sent as `P3D` and the 168-hour usage window as `P7D` (`console/azure_probe.py:165-167#la_query`). The table card shows at most the first 40 rows, cuts each cell to 160 characters, and offers the query text with a "Copy query" button and an "Open Log Analytics" link that opens the monitoring card (`console/jobs.py:1150-1157#_kql_table`, `console/web/render.js:91-105#tableCard`).

#### 9.6.2 Beat 5.1: One request id, four hops - the Orion denial

**Purpose.** Follow one refused request through the logs of the four systems that could have seen it, and show which of them did not. The claim to prove is the one on the card: the gateway let the call through because the token was valid, the MCP server refused on the roles in the token, and nothing touched the data (`console/catalog.py:503-514#orion`). Provenance: Implemented (the runner, the function `AbwIdentityChain` and the card), Configured (the diagnostic settings that deliver the logs, 9.6.1), Designed (the gateway cannot tell which project a document belongs to, so the Orion refusal is the MCP server's job; see beat 1.4, 9.2.5).

**Which request id is traced, and where it was captured.** The id of the call that beat 1.4 (9.2.5) made. When that call returned, `http_result` took the id from the result's `structuredContent.request_id`, else from the body's `request_id`, else from the response header `x-abw-request-id` or `request-id` (`console/jobs.py:229-236#http_result`). `run_gateway` then stored `{rid, at, verdict}` under the tag `orion` and said "Request id <request-id> remembered for Act 5." (`console/jobs.py:855-857#save_state`). The store is the console's state file, a small JSON file for "non-secret facts between jobs", which survives a console restart, so a tag can be days old (`console/jobs.py:81-90#save_state`, Findings F5-5).

The value is minted by the gateway, not by the console. The APIM inbound policy writes a trace record whose metadata holds `request_id` = `context.RequestId`, returns the same value in the body of a gateway refusal, and sets the request header `x-abw-request-id` for the backend; the MCP server's request middleware reads that header into its request-scoped id and the soft denial carries it in its payload (`infra/apim/policies/mcp-jwt.policy.xml:57-87#x-abw-request-id`, `src/mcp/abw_mcp/auth.py:173-188#RequestContextMiddleware`, `src/mcp/abw_mcp/registry.py:272-292#_error_payload`). The gateway's own log row carries the same value as the column `CorrelationId`, which `AbwGateway` projects as `RequestId` (`observability/kql/AbwGateway.kql:4-14#CorrelationId`). That the policy's `context.RequestId` and the log's `CorrelationId` are one value is something this repository relies on and proves by finding the gateway row with the id (P10, below); the Learn page of the table lists the column and gives it no definition, so treat the equality as shown by the proof, not as documented (Platform behaviour, not verified on Learn: https://learn.microsoft.com/azure/azure-monitor/reference/tables/apimanagementgatewaylogs#columns).

If no tag exists (the presenter pressed 5.1 before 1.4), `resolve_tag` makes the beat 1.4 call itself, as the operator and with no persona, and stores the result; this is the only way an Act 5 button reaches the gateway (`console/jobs.py:1160-1175#resolve_tag`, Findings F5-2). A pasted GUID is accepted by `validate` only if it matches the GUID pattern and is checked again by `resolve_tag` through the `safe_request_id` helper; the stored id of the `orion` tag gets neither check on the way out, so `run_kql` splices it into the query text as it was stored (`console/jobs.py:575-580#kql`, `console/jobs.py:1162-1163#safe_request_id`, `console/jobs.py:1173-1174#remembered`, `console/jobs.py:1196#replace`; Findings F5-1). No Act 5 button sends a pasted GUID: beats 5.1 and 5.2 are the only buttons that run the `chain` query and they send the tags `orion` and `allowed`. Any other id is traced by pasting `AbwIdentityChain('<request-id>')` into Log Analytics (`console/catalog.py:503-526#chain`, `docs/PROOF-PLAYBOOK.md:450#AbwIdentityChain`).

**Actors and tokens.** Two credentials, in two different moments. The traced call, made earlier by beat 1.4, carried a delegated token for the wall API with scope `Tools.Read`, with the roles `Wall.Falcon` and not `Wall.Orion` (9.2.5). The trace itself carries only the Log Analytics token of 9.6.1 (row 5.1). "Acting as" never changes the trace; it changes whose token made the remembered call when beat 1.4 was run (see "Failure or denial outcomes").

**Preconditions.** Those of 9.6.1, plus: beat 1.4 has run in this console (or the first press of 5.1 makes the call), the operator's token still carries the Falcon role and not the Orion role, and the ingestion delay has passed.

**Sequence.**

1. Browser -> console: "Trace the Orion denial" posts the run object `{"kind":"kql","query":"chain","tag":"orion"}` as the `params` of a `POST /api/jobs`, with the beat id `5.1` (`console/catalog.py:503-514#orion`, `console/web/util.js:160-162#startJob`, `console/server.py:128-135#api_jobs_start`).
2. `validate` accepts it: `chain` is in the catalog's query dictionary and is not `latest_allowed`, and `orion` is a permitted tag (`console/jobs.py:575-580#kql`). The kill-switch precheck does not apply (9.6.1, precondition 7).
3. `run_kql` says "Querying Log Analytics: <query title>" and calls `resolve_tag("orion")`. With a stored tag it returns the id and the tag's age in seconds; without one it says "No Orion denial recorded in this session yet - making one now (the Act 1.4 call).", calls `call_gateway("wall","get_deal_document",{"doc_id":"ORION-001"})`, emits that call's `http` event (the page draws it as a verdict card), stores the tag and returns the new id with an age of about zero (`console/jobs.py:1160-1175#resolve_tag`, `console/web/render.js:577#verdictCard`).
4. `run_kql` puts the id into the query text, says "Tracing request id <request-id>" and sends the query with a 72-hour window, which the REST helper turns into the timespan `P3D` (`console/jobs.py:1184-1198#run_kql`, `console/catalog.py:1262-1266#chain`, `console/azure_probe.py:165-167#la_query`). The query text is, in full:

   ```kusto
   AbwIdentityChain('<request-id>') | order by Step asc, Time asc | project Step, Layer, Actor, Action, Detail, Time
   ```

5. Log Analytics evaluates `AbwIdentityChain`. It builds one sub-query per hop, each filtered to this id, then unions them and orders them by step and time (`observability/kql/AbwIdentityChain.kql:50-51#union`). The four sub-queries are described next.
6. `run_kql` copies each returned row into a step (`step`, `layer`, `actor`, `action`, `detail`, `time`), adds the notes of the next section, and emits one `chain` event with the strip lights `foundry`, `apim`, `m-wall`, `data` and `monitor` set to "ok"; the job finishes with "<n> log rows across <m> layers" (`console/jobs.py:1205-1217#steps`).
7. Browser: `chainCard` draws the request-id row with a copy button, one hop per row (step number, layer and time cut to 19 characters, actor, action, detail) and the notes as a callout; the strip lights are applied only to live events, not to a replayed job (`console/web/render.js:167-181#chainCard`, `console/web/render.js:554-556#apply`, `console/web/strip.js:42-48#apply`).

**Join keys and output columns of the function.** `AbwIdentityChain(requestId, lookback = 7d)` reads four tables and joins nothing: each sub-query keeps the rows of its source that carry the one id, and the results are unioned. The key is the request id in four spellings: the gateway log's `CorrelationId` (projected as `RequestId`), the audit line's `request_id`, the Storage log's `ClientRequestId`, and, for the Foundry step, the id as a substring of the recorded tool result (`observability/kql/AbwIdentityChain.kql:1-4#requestId`, `observability/kql/AbwIdentityChain.kql:5-7#ToolCallResult`). Every sub-query projects the same seven columns, `Time`, `Step`, `Layer`, `Actor`, `Action`, `Detail` and `RequestId`; the console's query keeps all but `RequestId` (`observability/kql/AbwIdentityChain.kql:50-51#union`, `console/catalog.py:1262-1266#chain`). A hop that did not carry the id cannot appear, however close it is in time or person. The catalog's technical note says the function "joins APIM, MCP audit and Storage logs" and leaves the Foundry hop out; the function is a union of four filtered sub-queries (`console/catalog.py:511#tech`). The table behind step 1, `AppGenAIContent`, is read by two functions (`AbwIdentityChain` and `AbwAgentActivity`) and is not described in `DESIGN.md` or in the docs, so this document does not claim how it is filled.

The detail strings are built at `observability/kql/AbwIdentityChain.kql:24#Detail`, `observability/kql/AbwIdentityChain.kql:37#Detail` and `observability/kql/AbwIdentityChain.kql:48#Detail`. The observed values of the two present rows are recorded in the playbook: the gateway row `POST wall - HTTP 200 allowed, backend 9 ms` and the MCP row `deny (project_not_in_token_roles) obo=True ... roles=["Wall.Falcon"]` (`docs/PROOF-PLAYBOOK.md:312-315#project_not_in_token_roles`). The times are not on one clock: the MCP row shows the server's own timestamp (`EventTime`), the other three rows show the `TimeGenerated` column of their own table (`observability/kql/AbwIdentityChain.kql:31-32#EventTime`).

**Why those two hops are missing.** Step 1 is missing because no model took part: the caller was the console itself, an ordinary HTTPS client that writes no row of its own into the workspace (its only record is the tag in its state file, `console/jobs.py:81-90#save_state`). Step 4 is missing because of the order of operations inside the tool, not because of anything the platform filters: the handler derives the project from the document id and calls `_require_project` before it builds the container name and before the blob read, and `_require_project` raises `FORBIDDEN` with reason `project_not_in_token_roles` and the audit event `wall_violation_attempt` when the token's roles do not include the project (`src/mcp/abw_mcp/servers/wall.py:29-47#_require_project`, `src/mcp/abw_mcp/servers/wall.py:88-93#get_deal_document`). No on-behalf-of exchange and no Storage call follow. The registry turns the exception into a soft denial and writes the audit event with `decision` deny and the caller's roles (`src/mcp/abw_mcp/registry.py:238-270#_tool_error_result`, `src/mcp/abw_mcp/audit.py:178-216#build_event`). The gateway is HTTP 200 and `allowed` because a soft denial is an ordinary result with `decision=DENIED` in its body, and the gateway log records the status code and the policy's own decision, not the decision inside the response body (`src/mcp/abw_mcp/registry.py:263-270#isError`, `DESIGN.md:132#Soft`, `observability/kql/AbwGateway.kql:26-32#Outcome`).

Two things in these rows deserve a sentence each when the presenter reads them aloud. First, `obo=True` on the denial row is the default of the error object, not evidence that an exchange happened: the exchange is never reached (`src/mcp/abw_mcp/registry.py:54-75#obo`, Findings F5-13). Second, the gateway row names the person by object id only, because the gateway sees nothing but the claims of the token; the MCP row names the person by UPN. `AbwIdentityChain` does not map one to the other (`AbwDenials` does, for refusals; 9.6.5), so "the same person at every hop" is read by the viewer, not computed by the function (`observability/kql/AbwIdentityChain.kql:22#coalesce`).

**Lag of each source, and what the console shows while a row is missing.** The four rows reach one workspace by different routes: the APIM resource log through a diagnostic setting with a dedicated destination, the MCP server's stdout line through the Container Apps environment's Azure Monitor logging, and the Storage log through the diagnostic setting on the data account's blob service (`infra/05-apim.bicep:154-165#apimDiag`, `infra/03-platform.bicep:428-444#diagCaePriv`, `infra/03-platform.bicep:464-476#diagBlob`). Act 5 itself states one lag for all of them: 5 to 10 minutes on the act page and in the "Not in the logs yet" note, 2 to 18 minutes in the console's general statement for Log Analytics (9.1.3), and Learn says "usually available within 3 to 10 minutes end-to-end" for resource logs, within the 30 seconds to 20 minutes that it gives for Azure metrics, resource logs and activity logs together (9.6.1, precondition 3; Findings F5-4). The console does hold per-source expectations, but only in the "Refresh from logs" board of Act 6 (9.7), which the Act 7 person pages reuse (9.8): the APIM gateway row about 1 minute, the Foundry spans 1 to 5 (the console's figure; the playbook says about a minute), the data-plane row 2 to 8, the MCP server audit row 6 to 10 and the Sentinel alert and incident 9 to 13 minutes; a chain younger than 15 minutes is labelled "still filling in" and an older one "Still missing ... Do not present those hops as logged" (`console/e2e.py:1634-1651#_fc_waiting`, `docs/PROOF-PLAYBOOK.md:938#stages`). These are the repository's own expectations, not Learn statements, and the Act 5 card uses none of that staging. The playbook records the lags it measured for Act 6's runs on one build day: Log Analytics rows for 401 refusals up to about 20 minutes, Sentinel alerts up to about 22, and the ABW-001 alert for a wrong-deal run present at 22 minutes and not at 11 (`docs/PROOF-PLAYBOOK.md:498-501#lags`).

**Why and trade-offs.** The MCP row is the server's own audit line, while the APIM and Storage rows are written by Azure itself, so a wrong audit line could be written by a faulty server but a Storage record could not (`docs/PROOF-PLAYBOOK.md:269#self-reported`). For a denial the platform-written evidence is an absence, and an absence is weaker than a row: the chain finds Storage rows by the `ClientRequestId` that the server stamps on its own Storage calls, and only when the id passes a safe-character check, so a read without that header would not match (`src/mcp/abw_mcp/data.py:21-28#downstream_request_id`, `src/mcp/abw_mcp/data.py:200-204#client_request_id`; Findings F5-16). "Nothing touched the data" therefore rests on three facts together: the MCP row says deny, the handler refuses before it builds the container name or reads (`src/mcp/abw_mcp/servers/wall.py:88-93#_require_project`), and the data plane judges the user's own identity as well, because the server reads the blob with an on-behalf-of credential and maps a Storage 403 to `storage_rbac_denied`, so a read the user is not entitled to would be refused there too and would appear in `AbwDenials` layer 3 (`src/mcp/abw_mcp/data.py:57-70#storage_rbac_denied`, `observability/kql/AbwDenials.kql:67-77#StorageBlobLogs`, 9.6.5). The console's note draws that conclusion from the deny row and the missing Storage row alone (`console/jobs.py:1208-1210#mcp`, Findings F5-10). The gateway row reads "allowed" because it is: the token was valid and the role check passes any wall role, so the Orion decision belongs to the MCP server and the presenter has to explain the 200 (beat 1.4, 9.2.5). Entra token issuance is not a hop of this chain; Act 6 (9.7) adds the sign-in record with `AbwFullChain`, which joins on the token id (`docs/PROOF-PLAYBOOK.md:500#AbwFullChain`). Finally the window: the console traces over 72 hours while the function's own default look-back is 7 days and P10 passes 7 days (Findings F5-5).

#### 9.6.3 Beat 5.2: One request id, four hops - an allowed read

**Purpose.** Draw the same four-record chain for a read that was allowed, so that the analyst sees all four records and, in the last two, the same person: the MCP server's audit line names the user, and Azure Storage's own request log names the user too, with `auth=OAuth`. The claim is the card's: "Foundry agent -> APIM -> MCP server (obo=True) -> Storage (auth=OAuth). The same person is named at the MCP server and at the data plane." (`console/catalog.py:522#expect`). Its contrast is the legacy chain of beat 1.1 (9.2.2), where the actor is blank at the gateway and at the MCP server and the last hop is a managed identity (`docs/PROOF-PLAYBOOK.md:154-159#legacy`). Provenance: Implemented (the id search, the runner, the function and the card), Configured (the diagnostic settings of 9.6.1, and the Storage role assignment that lets the data plane judge the user's group, `infra/03-platform.bicep:617-636#raFalconBlob`), Platform behaviour (what Storage writes into its request log; Learn: https://learn.microsoft.com/azure/azure-monitor/reference/tables/storagebloblogs#columns).

**Which request id is traced, and where it was captured.** Nothing is remembered from an earlier beat. The id is looked up when the button is pressed, by a first Log Analytics query, and then traced by a second. `resolve_tag("allowed")` sends the catalog's text `latest_allowed` with a 24-hour window and takes the `RequestId` of its first row; with no row it returns nothing (`console/jobs.py:1176-1180#allowed`). The text, in full:

```kusto
AbwAgentActivity(24h) | where Tool endswith 'get_deal_document' and Decision == 'allow' and OnBehalfOf == true | top 1 by TimeGenerated desc | project RequestId
```

(`console/catalog.py:1280-1284#latest_allowed`.) The id in that row was captured on the Foundry side of the run. The MCP server puts its request id into the payload of every allowed result, so the tool result that Foundry records and hands back to the model carries it; `AbwAgentActivity` extracts the first 36-character id that follows `"request_id"` in each recorded tool result, joins Foundry's tool span to the same recorded tool call by trace id and span id for the tool name, then left-joins the MCP audit row on that id (for the decision, the reason, the on-behalf-of flag and the user) and the gateway row (for the object id) (`src/mcp/abw_mcp/registry.py:195-200#setdefault`, `observability/kql/AbwAgentActivity.kql:7-15#AppGenAIContent`, `observability/kql/AbwAgentActivity.kql:16-31#spans`, `observability/kql/AbwAgentActivity.kql:87-92#activity`). Four consequences follow from reading the function; none was observed on a live tenant for this document.

1. Only reads made by an agent can be found. A row exists only where Foundry recorded a tool call (its arguments or its result), and the request id exists only where the recorded result carries one, so a raw gateway read, such as the "Quick: raw read of FALCON-001" alternative of beat 1.3 or the direct read of P03, has no row and is invisible to this beat (`console/catalog.py:290-296#Quick`, `observability/kql/AbwAgentActivity.kql:7-15#ToolCallArguments`, `observability/kql/AbwAgentActivity.kql:87-92#activity`).
2. Three records must have arrived: Foundry's recorded tool result (`AppGenAIContent`, which carries the id), Foundry's tool span (`AppDependencies`, named `execute_tool <tool>`, which is the only source of the `Tool` column) and the MCP audit row (the only source of an allow or deny `Decision`, which the function leaves empty for a call it cannot match unless a guardrail stopped the run). A call lacking any one of them fails the query's `Tool` or `Decision` test. So when the beat finds an id, hops 1 and 3 of the chain should already exist (they come from the same sources, inside a 24-hour search window that the chain's 72-hour window contains); hops 2 and 4 may not yet (`observability/kql/AbwAgentActivity.kql:16-22#execute_tool`, `observability/kql/AbwAgentActivity.kql:100-102#Decision`).
3. The latest allowed on-behalf-of `get_deal_document` call is taken, for any user and any document (`console/catalog.py:1280-1284#latest_allowed`). The query has no user filter, although in this demo every agent scenario runs as the operator, because Foundry holds the operator's sign-in (`docs/PROOF-PLAYBOOK.md:935#operator`). It has no document filter either, although the card and the error text say "Falcon" (`console/catalog.py:518#say`, Findings F5-3).
4. `OnBehalfOf == true` is the server's own flag, not a measurement. It is the default of a tool outcome, which the wall server leaves alone; the legacy server sets it False on every outcome of its `get_deal_document`, which is why legacy reads are not found although the tool name matches (`src/mcp/abw_mcp/registry.py:30-39#ToolOutcome`, `src/mcp/abw_mcp/servers/legacy.py:69-83#get_deal_document`).

The id names one tool call. An agent run that calls three tools has three request ids, and this beat traces only the latest `get_deal_document` call; the Act 6 board's `AbwFullChain` widens a chain to the whole run (9.7, `DESIGN.md:112#request_id`).

**Actors and tokens.** Two credentials, one per moment. The traced read was made by the Foundry agent `abw-wall-desk` for the signed-in user: Foundry's OAuth identity passthrough produced a token for the wall API whose client is the agent client application `abw-agent-client`, the APIM gateway validated it, the MCP server validated it again and exchanged it on behalf of the user for a Storage token, and Storage received that token (`DESIGN.md:102-105#passthrough`). The exchange is made by the server's confidential client application, with a client assertion that is a token of the server's managed identity for `api://AzureADTokenExchange`, and the Storage scope is `https://storage.azure.com/user_impersonation` (`src/mcp/abw_mcp/obo.py:53-65#acquire_token_on_behalf_of`, `src/mcp/abw_mcp/obo.py:77-79#AzureADTokenExchange`, `src/mcp/abw_mcp/data.py:57-65#user_impersonation`). Section 6 owns these mechanics. The trace itself carries only the Log Analytics token of 9.6.1 (row 5.2).

**Preconditions.** Those of 9.6.1, plus: the operator ran beat 1.3 "Ask for Falcon" (the agent run, 40 to 60 seconds), not only its quick alternative, within the last 24 hours (`console/catalog.py:283-301#abw-wall-desk`); the operator's token carried the Falcon role, since the read has to have been allowed; and Foundry's tool-result record, Foundry's tool span and the MCP audit line have all arrived, since the search needs the three.

**Sequence.**

1. Browser -> console: "Trace the latest allowed read" posts the run object `{"kind":"kql","query":"chain","tag":"allowed"}` as the `params` of a `POST /api/jobs`, with the beat id `5.2` (`console/catalog.py:515-526#allowed`).

3. `run_kql` says "Querying Log Analytics: <query title>" and calls `resolve_tag("allowed")`, which sends `latest_allowed` as the first query (timespan `PT24H`) and takes the id. No gateway call is made on this path, unlike the `orion` tag (`console/jobs.py:1176-1180#allowed`, `console/azure_probe.py:165-167#la_query`).
4. With no row, the job emits an `error` card and finishes `failed` (see "Failure or denial outcomes").

#### 9.6.4 Beat 5.3: How people are using agents

**Purpose.** Answer the second half of the customer's Act 5 question, "who is using agents at all" (`docs/PROOF-PLAYBOOK.md:448#Customer`): one row per person with calls, allowed, denied, distinct tools and deny rate over seven days, and one row that has no person. The card promises "One user (the operator) plus a '(no user context)' row. That row is the legacy shared-key server and the external vendor stand-in - neither logs a user. With real personas you would see everyone." (`console/catalog.py:534#expect`), and the presenter line is "The visibility question answered - and the legacy row is the shadow-AI row." (`console/catalog.py:536#sales`). Provenance: Implemented (the function, the runner and the card; the audit line that the function counts), Configured (the container-app environments send their console logs to the workspace, `infra/03-platform.bicep:446-462#diagCaePub`).

**What the query counts, and over which window.** The console sends the text below, with a 168-hour window that `la_query` turns into the REST timespan `P7D` (`console/catalog.py:1229-1233#AbwUsageByUser`, `console/azure_probe.py:165-167#la_query`):

```kusto
AbwUsageByUser(7d) | project User, Calls, Allowed, Denied, DistinctTools, DenyRatePct, LastSeen
```

The function reads `AbwMcpAudit(7d)`, which is one row per tool listing, call or denial, parsed from the JSON lines that the MCP servers print to their console and that Log Analytics holds as `ContainerAppConsoleLogs` (`observability/kql/AbwMcpAudit.kql:3-8#ContainerAppConsoleLogs`, `src/mcp/abw_mcp/audit.py:40-51#StdoutLoggerAuditSink`). It drops the listing events (`Event != 'tool_listed'`: listing the tools is not a call), names the user, and summarizes by user: `Calls` (every remaining row), `Allowed` (`Decision == 'allow'`), `Denied` (`Decision == 'deny'`), `Servers` (up to ten server names), `DistinctTools`, `FirstSeen` and `LastSeen`; then `DenyRatePct` is denied over calls to one decimal, and the rows are ordered by calls (`observability/kql/AbwUsageByUser.kql:4-17#countif`). The console keeps seven of the nine columns: it projects away `Servers` and `FirstSeen` (`console/catalog.py:1232#project`). The server code read for this section sets only two decision values, `allow` (the default of an allowed outcome) and `deny` (the default of an error), so `Calls` equals `Allowed` plus `Denied` unless a row carries another value, which would count in `Calls` only; the deny rate is denied rows over all non-listing rows (`src/mcp/abw_mcp/registry.py:30-39#ToolOutcome`, `src/mcp/abw_mcp/registry.py:54-75#ToolError`, `src/mcp/abw_mcp/auth.py:224-239#auth_failed`). One row is therefore one tool call or one refusal by an MCP server, not one agent run and not one conversation.

**How users and agents are identified.** A person is the `user_upn` field of the server's audit line, which is the `preferred_username` claim of the token that the server validated; the same line also carries the object id (`user_oid`), the client application (`azp`), the audience and the token id, and `AbwMcpAudit` exposes them as `UserOid`, `ClientAppId`, `Audience` and `TokenId` (`src/mcp/abw_mcp/auth.py:160-168#preferred_username`, `src/mcp/abw_mcp/audit.py:178-216#build_event`, `observability/kql/AbwMcpAudit.kql:17-20#UserUpn`). This function groups by the UPN string alone, so the table shows neither the object id nor the client application, and a person whose UPN changed would be two rows (inferred from the grouping, not observed). An agent is not identified at all: the audit line has no agent-name field, only the client application of the token, which for a call made through a Foundry connection is the agent client application `abw-agent-client` (`DESIGN.md:103#passthrough`). The agent's name comes from Foundry's own trace and is joined in beat 5.5 (9.6.6).

**What is in the `(no user context)` row.** The function replaces an empty UPN with that label (`observability/kql/AbwUsageByUser.kql:6#isempty`). Four populations have an empty UPN; the first was observed, the second is stated in the playbook but was not separately observed for the vendor server, and the last two are code readings that no beat exercises (Findings F5-7):

| Population | Why its audit line carries no UPN | Status |
|------------|-----------------------------------|--------|
| The legacy server | No bearer-token middleware is installed for it, so no caller exists; its allowed rows carry the reason `no_user_context` and `obo=False` | Observed (`docs/PROOF-PLAYBOOK.md:451#shadow`, `docs/PROOF-PLAYBOOK.md:460#legacy`) |
| The vendor stand-in | Only the key that APIM injects is checked, so no caller exists | Stated in the playbook, not separately observed for the vendor server (`docs/PROOF-PLAYBOOK.md:451#shadow`, `src/mcp/abw_mcp/config.py:100-101#validates_tokens`) |
| Authentication failures at the servers that do check tokens | The `auth_failed` event is built with no caller, decision `deny`, no UPN and no token id | Code reading |
| A valid token with no `preferred_username` claim | The caller's UPN is optional | Code reading |

(`src/mcp/abw_mcp/app.py:115-142#VendorKeyMiddleware`, `src/mcp/abw_mcp/app.py:241-249#BearerAuthMiddleware`, `src/mcp/abw_mcp/servers/legacy.py:54#no_user_context`, `src/mcp/abw_mcp/auth.py:224-239#auth_failed`, `src/mcp/abw_mcp/auth.py:29-40#Caller`, `docs/PROOF-PLAYBOOK.md:451#shadow`, `docs/PROOF-PLAYBOOK.md:460#legacy`.) So the row is where calls that cannot be attributed to anyone show up, which is the message of the beat, but it is not purely "legacy plus vendor". The `Servers` column that the console drops would separate the populations in Log Analytics, and the playbook's own query `AbwMcpAudit(7d) | where Server == 'legacy' | summarize ...` shows the legacy part alone (`docs/PROOF-PLAYBOOK.md:460#legacy`).

**What is not captured.** Three limits, stated before anyone asks (Findings F5-6).

1. A call that is refused before it reaches an MCP server leaves no row here. The gateway's refusals (`revoked`, `client_not_allowed`, `missing_role`, `rate_limit`, `no_valid_token`) are in the gateway log and in beat 5.4, not in this table, so `Denied` and `DenyRatePct` count only the refusals that an MCP server made itself (a wall violation, the restricted list, Storage RBAC, invalid arguments, a failed on-behalf-of exchange). The playbook says it for the same kind of table in Act 7: it "counts what the MCP servers logged; a call the gateway refuses never reaches a server" (`docs/PROOF-PLAYBOOK.md:516#calls-per-user`, `src/mcp/abw_mcp/registry.py:158-191#invalid_arguments`).
2. The table is the servers' own record, written by the code under audit and not by Azure. Every server is built by the same `create_app` and its registry emits the audit line for each call, so the private MCP server, which validates tokens itself and never passes APIM, writes the same line, and its container-app environment sends its console logs to the same workspace (`src/mcp/abw_mcp/app.py:188-194#create_app`, `infra/03-platform.bicep:428-444#diagCaePriv`). The views of this act that read the MCP audit (5.3, the MCP-server layer of 5.4, 5.5 and 5.6) can therefore include that route; the views that read the gateway log (the gateway hop of 5.1 and 5.2 and the gateway layer of 5.4) cannot. 3. Sign-in refusals at Entra never reach any server, so they are in no row of this table (9.6.5 and Act 6, 9.7).

The probe also falls back to a local copy of the function when the deployed function cannot be resolved, so P17 does not by itself show that the function is deployed (Findings F5-18; `demo/prove.py:1054-1059#p17`, `observability/kql/pack.py:38-44#_CHECK_CALLS`, `observability/kql/pack.py:134-150#Failed`, `observability/kql/pack.py:160-171#cmd_check`).

**Failure modes and what the presenter should say.**

- One person row only. Say what the card says: this demo has one real user, the operator, who plays the cast; "with real personas you would see everyone" (`console/catalog.py:534#expect`, `docs/TALK-TRACK.md:189#Path`).
- The `(no user context)` row. Say: "That is the legacy server, plus the vendor stand-in, which logs no user either: InfoSec cannot attribute those calls to anyone." (`docs/TALK-TRACK.md:189#legacy`), and, from the playbook, "That row is where shadow AI shows up." (`docs/PROOF-PLAYBOOK.md:451#shadow`). Do not say the row is only the legacy server: failed authentications at the other servers would land in it too (Findings F5-7).
- A person with a low deny rate who was refused at the gateway. Say that the rate counts what the MCP servers refused; the gateway's refusals are in the next beat (`docs/PROOF-PLAYBOOK.md:516#calls-per-user`).
- Empty table. Run an earlier act and wait the 5 to 10 minutes; do not explain an empty table as "nobody uses agents".

**Why and trade-offs.** The MCP audit is the one source that sees every kind of server, including the legacy and vendor routes, which have no user, and the private route, which has no gateway row. The gateway's own log names a person only by object id (`docs/PROOF-PLAYBOOK.md:515#best`, `observability/kql/AbwGateway.kql:25#UserOid`). The price is that the counts are self-reported by the servers and cover only calls that reached one, so the table understates refusals and cannot see the gateway's. Grouping by UPN makes the table readable and is what the audit line offers as a name, but it makes the table depend on the claim being present, which is exactly what the `(no user context)` row measures; the object id and the client application are in the audit line and could be added as columns without a new data source.

#### 9.6.5 Beat 5.4: What was refused, and by which wall

**Purpose.** Show every refusal in one table, grouped by the wall that made it and by the reason it gave, over the last 24 hours. It answers the refusal side of the customer's Act 5 question, "show me exactly what that agent did" (`docs/PROOF-PLAYBOOK.md:448#Customer`). The card promises "Guardrail, gateway (rate_limit, missing_role, revoked, client_not_allowed, no_valid_token), MCP server (project_not_in_token_roles, restricted_list) and data plane rows." (`console/catalog.py:546#expect`), and the presenter line is "Every layer reports in the same place." (`console/catalog.py:548#sales`). The four walls are the console's own: the Foundry guardrail (wall 0), the APIM gateway (wall 1), the MCP tool server (wall 2) and the data plane (wall 3) (`console/catalog.py:110-115#WALLS`). Provenance: Implemented (the function `AbwDenials`, the runner and the card), Configured (the diagnostic settings and the Foundry telemetry connection that feed each layer, listed under "Evidence produced"), Not in this repository (a denial layer for Entra sign-in refusals).

**What the query counts, and over which window.** The console sends the text below with a 24-hour window, which `la_query` turns into the REST timespan `PT24H`; inside the function the window is rolling, the 24 hours before the moment the query runs (`console/catalog.py:1224-1228#denials`, `console/azure_probe.py:165-167#la_query`, `observability/kql/AbwDenials.kql:2-5#lookback`):

```kusto
AbwDenials(24h) | summarize Denials=count() by Layer, Reason | order by Layer asc, Denials desc
```

The function puts four unlike sources into one stream with the same seven columns, TimeGenerated, Layer, Control, Principal, Target, Reason and RequestId, newest first (`observability/kql/AbwDenials.kql:78-79#union`). The console's query keeps three things, the layer, the reason and a count, so the card says how many refusals each wall made for each reason and not who, what or when. The playbook's version of the query also carries `Last=max(TimeGenerated)` and the console's does not (`docs/PROOF-PLAYBOOK.md:455#AbwDenials`; Findings F5-21). The columns that name the person, the target and the request id are in the unaggregated function, which is what the card's "Show the query" and "Open Log Analytics" buttons lead to; a request id from layers 1 to 3 can then be traced with `AbwIdentityChain('<request-id>')` (`console/web/render.js:91-105#tableCard`, `docs/PROOF-PLAYBOOK.md:450#AbwIdentityChain`). Because every layer name starts with a digit, `order by Layer asc` lists the walls top to bottom and, inside a wall, the commonest reason first. After the table the runner adds one line, "Refusals were recorded by: <layers>.", which names the distinct layers present, sorted (`console/jobs.py:1235-1239#denials`). **What is not captured, and what the counts do not mean.** Eight limits, stated before anyone asks.

1. Entra sign-in refusals are in no layer. A failed sign-in never reaches the gateway, so no wall has a row for it. The Cockpit workbook says so on its Threats tab, and the playbook says the workspace has no `SigninLogs` data in this build; Act 6 (9.7) reads Entra's own export for one run (`observability/workbook/build_workbook.py:373-378#sign-in`, `docs/PROOF-PLAYBOOK.md:500#SigninLogs`).
2. Layer 3 counts every storage account that sends blob logs to the workspace, and anonymous callers, because the function has no account filter. Two accounts send them, the demo's data account and the agent-service account. The `/ Azure RBAC` ending of `Control` is constant text, not a finding about the cause (`observability/kql/AbwDenials.kql:67-77#dataplane`, `infra/03-platform.bicep:464-476#diagBlob`, `infra/06-governance.bicep:122-129#diagAsvcBlob`, `observability/kql/AbwDenials.kql:73#Control`).
3. Who is named depends on the wall. Layer 0 names the agent. Layer 1 knows only the token's object id and shows a UPN only when the same object id also reached an MCP server in the same window, because the mapping is built from the MCP audit; so Ian, who never got past the gateway, shows as an object id (`observability/kql/AbwDenials.kql:38#Principal`, `observability/kql/AbwDenials.kql:42-45#oidToUpn`, `docs/PROOF-PLAYBOOK.md:515#best`).
4. A 401 has no object id. `validate-jwt` rejects the call before the deny variable is set and before the trace is written, so the row's Principal is empty, and the gateway function's own comment says that 401, 429 and 5xx never reach the policy trace. For the 429 the policy text says otherwise: the trace statement comes before `rate-limit-by-key` and the error handler rewrites only the 401, so by policy order a 429 on a governed MCP API carries an allow trace and an object id, and the comment is wrong for that 429. P14 counts the 429s and P13 checks that the ABW-009 incident appeared, but no run shows the decision or the object id that a 429 row carries, so this is read from the policy, not observed (`infra/apim/policies/mcp-jwt.policy.xml:17-31#validate-jwt`, `observability/kql/AbwGateway.kql:3#never`, `infra/apim/policies/mcp-jwt.policy.xml:57-81#rate-limit-by-key`, `infra/apim/policies/mcp-jwt.policy.xml:96-112#on-error`, `demo/prove.py:891-897#traffic`, `demo/prove.py:1071-1078#SecurityIncident`; Findings F5-20).
5. Layer 0's `RequestId` is the trace id of the Foundry run, not the tool-call request id that layers 1 to 3 carry, so a layer-0 row does not join the others by request id (`observability/kql/AbwDenials.kql:41#RequestId`, `observability/kql/AbwDenials.kql:56#RequestId`).
6. `Denials` counts rows, not incidents, and layer 2 counts more than refused access. A `ToolError` defaults to decision `deny` and event `tool_denied`, so a missing document and an invalid-argument call are audited as denials even though the tool's reply labels the first `ERROR`. A read that Storage refuses with 403 is one audit row at layer 2 (`storage_rbac_denied`) and, by code reading, one Storage row at layer 3 that carries the same request id, because the server stamps its request id on the Storage call. By code reading, not observed, a failed authentication at a server that checks tokens is a layer-2 row too, with an empty Principal and the authentication error code as reason (`src/mcp/abw_mcp/registry.py:54-75#ToolError`, `src/mcp/abw_mcp/registry.py:273-276#DENIED`, `src/mcp/abw_mcp/data.py:57-70#downstream_request_id`, `src/mcp/abw_mcp/servers/wall.py:92-96#storage_rbac_denied`, `src/mcp/abw_mcp/auth.py:224-239#auth_failed`; Findings F5-19 and F5-7).
7. The private MCP route never produces a layer-1 row, because it is not behind APIM; a refusal made by the private server can appear only at layers 2 and 3 (`DESIGN.md:107#Direct`, `docs/PROOF-PLAYBOOK.md:511#private`).
8. The card's expected-reasons text is the presenter's promise, not a check. Nothing asserts it, and it omits reasons the table can hold: `missing_scope`, `separation_of_duties`, `storage_rbac_denied`, `obo_failed:<code>`, `invalid_arguments` and `token_quota` (`console/catalog.py:546#expect`; Findings F5-21).

The talk track gives the reading rule for the last wall: "A denial at layer 3 means the three above it let something through - that is the row InfoSec watches." (`docs/TALK-TRACK.md:190#layer`). That holds only for calls that came through the governed path. The layer-3 branch takes every Storage request refused with status 401 or 403 and does not check how the call arrived, so a signed-in user or service principal who calls Storage directly with their own token also leaves a layer-3 row without passing the other walls, and an anonymous request never went through them either (`observability/kql/AbwDenials.kql:67-77#StorageBlobLogs`). A governed call carries the gateway request id into the Storage request, so compare the RequestId with the gateway and MCP rows: once those rows have had time to arrive, a layer-3 row with no matching gateway or MCP row is a direct call (`src/mcp/abw_mcp/data.py:24-28#x-ms-client-request-id`). The rule ABW-007 selects every signed-in layer-3 row, so a hit is a lead that needs that comparison before it is read as drift after the other walls allowed the call (`observability/sentinel/abw-007-entitlement-drift.kql:10-13#signed-in`).

**Lag, and what the console shows while a row is not yet there.** Each wall's rows have their own source and their own delay. The table has no "as of" marker, no age per layer and no pending flag, and `finish` is called the same way whatever arrived (`console/jobs.py:1239#finish`). So a refusal made a minute ago can already be in the gateway layer and not yet in the MCP-server layer, and nothing on the card says so; the layer sentence will simply omit the wall that is late.

**Why and trade-offs.** One function puts four unlike sources into seven shared columns, so an investigator reads one stream top to bottom and three Sentinel rules can use the same stream (`observability/kql/AbwDenials.kql:3#description`). The counts are rows, not incidents, and layer 0's id does not join the others. The console's summary hides the principal and the time, which keeps the card readable and means it says that a wall refused, not whom; the drill-down is the unaggregated function in Log Analytics, or beat 5.5 for the agent (9.6.6).

#### 9.6.6 Beat 5.5: The agent's own tool calls

**Purpose.** Show what the agents themselves did in the last 24 hours: which agent called which tool, for which person, what the server decided, and the request id that ties the row to the hops of beats 5.1 and 5.2. The card says "The last 15 agent tool calls with the on-behalf-of flag and request id." (`console/catalog.py:554#say`), expects "Agent, tool, user, decision, reason, OnBehalfOf = true, request id." (`console/catalog.py:558#expect`), names its source as "AbwAgentActivity(24h)." (`console/catalog.py:559#tech`) and gives the presenter line "The audit trail an examiner asks for." (`console/catalog.py:560#sales`). Beats 5.1 to 5.4 answer the customer's "show me exactly what that agent did" (`docs/PROOF-PLAYBOOK.md:448#Customer`) from the platform's side; this beat answers it from the agent's side. Provenance: Implemented (the function `AbwAgentActivity`, the card and the runner), Configured (the Foundry telemetry connection and the diagnostic settings that fill the tables the function joins, listed under "Evidence produced"), Not in this repository (a file that switches on Foundry's content capture for the table `AppGenAIContent` that the function reads; this document found the table named only in the query functions).

**What the query counts, and over which window.** The console sends the text below with a 24-hour window, which `la_query` turns into the REST timespan `PT24H`; inside the function the window is the rolling 24 hours before the query runs (`console/catalog.py:1234-1238#agent`, `console/azure_probe.py:165-167#la_query`, `observability/kql/AbwAgentActivity.kql:2-3#lookback`):

```kusto
AbwAgentActivity(24h) | project TimeGenerated, Agent, Tool, User, Decision, Reason, OnBehalfOf, RequestId | take 15
```

One output row is one tool call that Foundry recorded for an agent, or one agent run that the guardrail stopped before any tool was called. The first kind starts from the table `AppGenAIContent`: one row per agent name, trace id and span id that holds tool-call arguments or a tool-call result (`observability/kql/AbwAgentActivity.kql:7-15#calls`). Learn documents that table as generative-AI content captured from an OpenTelemetry source, with `ToolCallArguments` and `ToolCallResult` columns (Platform behaviour, https://learn.microsoft.com/azure/azure-monitor/reference/tables/appgenaicontent). The second kind comes from the `invoke_agent` span of a run that the guardrail stopped (a span whose `error.type` is `content_filter`), kept only when no tool-call row carries that trace id (`observability/kql/AbwAgentActivity.kql:32-48#runs`, `observability/kql/AbwAgentActivity.kql:113-132#guardrailOnly`). The function returns both kinds newest first, and the console keeps the first 15 rows and 8 of the 16 columns (`observability/kql/AbwAgentActivity.kql:133-134#union`). "The last 15" holds because `take` returns the top rows when its source is sorted, which the function's last step provides (Platform behaviour, https://learn.microsoft.com/kusto/query/take-operator). The sixteen columns:

| Column | In the card | Where it comes from |

| TimeGenerated | Yes | The earliest `AppGenAIContent` row of the call; for a guardrail-only row, the earliest `invoke_agent` span of the run (`observability/kql/AbwAgentActivity.kql:12#TimeGenerated`, `observability/kql/AbwAgentActivity.kql:38#RunTime`) |

**How users and agents are identified.**

- The agent is a name, not a credential. `Agent` is the name Foundry recorded for the run, for example `abw-wall-desk` for the governed agent and `abw-poc-legacy` for the shared-key one (`console/catalog.py:277#abw-wall-desk`, `console/catalog.py:258#abw-poc-legacy`). The agent's tool calls carry the signed-in user's token, not an agent credential of their own; the repository's own status line calls the Entra agent identities "an inventory" (`DESIGN.md:223#holds`, `DESIGN.md:240#inventory`).
- The user is resolved in four steps and the first non-empty one wins (Platform behaviour: `coalesce` returns the first non-null or non-empty string, https://learn.microsoft.com/kusto/query/coalesce-function). One: the UPN of the MCP audit row that has the same request id, which the server took from the token's `preferred_username` claim. Two: a UPN mapped from the object id that the gateway recorded for that request, using any MCP audit row of the window that carries both an object id and a UPN. Three: the raw object id from the gateway. Four: the text `(not resolved)` (`observability/kql/AbwAgentActivity.kql:101#User`, `observability/kql/AbwAgentActivity.kql:4-6#oidToUpn`, `observability/kql/AbwAgentActivity.kql:29-31#gateway`, `src/mcp/abw_mcp/auth.py:159-170#preferred_username`, `observability/kql/AbwGateway.kql:25#UserOid`).
- `RunBy` answers a different question: who started the run. It is Foundry's `user.id` span property, mapped to a UPN by the same object-id table when it can be and left as the raw value when it cannot (`observability/kql/AbwAgentActivity.kql:41#RunOid`, `observability/kql/AbwAgentActivity.kql:47-48#RunBy`). The function treats the value as an object id; nothing in the repository checks that Foundry fills it that way (Findings F5-26). The workbook explains the pair: `User` is the identity the tool saw and `RunBy` is who started the run (`observability/workbook/build_workbook.py:129-136#RunBy`). In this demo they are the same person, because agent beats always run as the operator (`docs/RUNBOOK.md:45#operator`).
- `OnBehalfOf` is the server's declaration, not a measurement. The audit column is the server's `obo` field (`observability/kql/AbwMcpAudit.kql:23#OnBehalfOf`). The default of a tool outcome and of a tool error is True, and a failed on-behalf-of exchange keeps that default although the exchange did not succeed. False means the server declared a shared or non-user identity: the code sets it for the legacy server's outcomes, for both outcomes of the vendor server, for the restricted-list check (the actions server reads that list with its own identity), for the authentication-failure line, for the invalid-argument denial, and for the tool listings and the unknown-tool and forbidden denials of the legacy and vendor servers. The order tools and the private server report their Cosmos setting `COSMOS_OBO`, which defaults to True (`src/mcp/abw_mcp/registry.py:30-39#ToolOutcome`, `src/mcp/abw_mcp/registry.py:54-75#ToolError`, `src/mcp/abw_mcp/registry.py:179-187#obo_failed`, `src/mcp/abw_mcp/servers/legacy.py:69-83#obo`, `src/mcp/abw_mcp/servers/vendor.py:41#obo`, `src/mcp/abw_mcp/servers/vendor.py:57#obo`, `src/mcp/abw_mcp/servers/actions.py:53#obo`, `docs/PROOF-PLAYBOOK.md:491#restricted`, `src/mcp/abw_mcp/auth.py:229-235#obo`, `src/mcp/abw_mcp/registry.py:151#obo`, `src/mcp/abw_mcp/registry.py:171#invalid_arguments`, `src/mcp/abw_mcp/registry.py:232#obo`, `src/mcp/abw_mcp/servers/actions.py:108#obo`, `src/mcp/abw_mcp/servers/private.py:34#obo`, `src/mcp/abw_mcp/config.py:154#cosmos_obo`). The wall's document read declares True on its allowed outcome and on its project denial (`src/mcp/abw_mcp/servers/wall.py:97-105#ToolOutcome`, `src/mcp/abw_mcp/servers/wall.py:39-47#_require_project`). So "OnBehalfOf = true" on the card is the expected value for the wall calls, not for every row (Findings F5-23).

**What each kind of row looks like.** By code reading, not observed here; the values are what the code paths produce. After an Act 1 run the card expects one green call, the agent's lookup of the deals the user is cleared for, and a refusal row appears only if the model tries an Orion tool anyway (`console/catalog.py:278#expect`).

**What is not captured, and what the rows do not mean.** Seven limits, stated before anyone asks.

1. The function lists only what Foundry recorded. It starts from Foundry's tool-call content and joins the other sources onto it with left joins, so an MCP audit row or a gateway row with no Foundry row, such as every raw gateway read of beats 5.1 and 5.2, is not here, and a call that Foundry did not record has no row (`observability/kql/AbwAgentActivity.kql:87-95#activity`). Learn's reference for the table does not say which Foundry or Application Insights setting switches content capture on, and this repository does not configure it, so whether rows appear is a property of the deployment; P17 checks only that the query runs (Findings F5-25).
2. The route does not decide whether a call is listed, but it decides what the row can say. The private MCP route is not behind APIM, so its calls have Foundry rows and audit rows and never a gateway row: `User` comes from the audit's UPN and, while that row is late, has no object id to fall back on (`DESIGN.md:107#Direct`, `observability/kql/AbwAgentActivity.kql:29-31#gateway`).
3. Twenty-four hours, the newest 15 rows, and eight columns. The card does not say how many calls the window holds. The columns `RunBy`, `Guardrail`, `TraceId`, `ToolArguments`, `Server`, `DataClass`, `AgentVersion` and `DurationMs` are in the function and in Log Analytics; the workbook's agent grid shows up to 200 rows within the workbook Time range (default 7 days; the function itself looks back 30 days) with all of them except `ToolArguments` and `TraceId` (`observability/workbook/build_workbook.py:212-221#ov-agents`).
4. Arguments are Foundry's copy. `ToolArguments` is what Foundry recorded; the MCP audit keeps only a SHA-256 of the arguments (`observability/kql/AbwAgentActivity.kql:13#ToolArguments`, `src/mcp/abw_mcp/audit.py:212#args_sha256`). The Bicep creates the workspace with a 30-day retention and grants the Foundry project identity the role that it says is required to query GenAI content, but the repository does not say whether the content table is protected or how it is classified (Findings F5-25).
5. A guardrail-only row is not a tool call. It has no tool and no server, its `OnBehalfOf` is null, and its `RequestId` holds the trace id, so it does not join the audit or the gateway (`observability/kql/AbwAgentActivity.kql:129#RequestId`).
6. The `Tool` value is the span name without the prefix `execute_tool `. The repository's one recorded example is `execute_tool mcp_vendor.get_headlines`, so a name may carry a server prefix, and beat 5.2 matches the wall tool with `endswith` for that reason; this document did not observe a wall tool's span name (`docs/PROOF-PLAYBOOK.md:799#execute_tool`, `console/catalog.py:1280-1284#endswith`).
7. A decision is the server's own word. `Decision` and `Reason` are what the MCP server wrote; the independent check on the same read is the Storage row of beat 5.4 and the chain of beat 5.1 (9.6.5, 9.6.2). The workbook's legend also colours an `error` decision that the server code read here never sets (`observability/workbook/build_workbook.py:133#error`; Findings F5-27).

**Actors and tokens.** The console's own Azure sign-in, for the Log Analytics query only (9.6.1, row 5.5). The calls in the table were made earlier by Foundry agents on behalf of the signed-in user: Foundry holds that user's OAuth access token for its whole life and presents it to each MCP server, so the server sees the person and not the agent (`DESIGN.md:223#holds`). Beat 5.6 (9.6.7) shows how long one such token serves calls.

**Sequence.**

1. Browser -> console: "Agent activity" posts the run object `{"kind":"kql","query":"agent"}` as the `params` of a `POST /api/jobs`, with the beat id `5.5` (`console/catalog.py:555-557#run`, `console/web/pages.js:88-91#startJob`).

4. Log Analytics evaluates the function, which reads the Foundry content and spans, the MCP audit and the gateway rows, joins them and returns the newest 15 rows.
5. `_kql_table` collects the column names in first-seen order, which here are the eight of the query, keeps up to 40 rows, formats each cell as text (null becomes empty, a boolean prints as `True` or `False`) and emits one `table` event with `total` set to the number of rows returned and the light `monitor` set to ok (`console/jobs.py:1150-1157#_kql_table`, `console/jobs.py:156-160#_cell`, `console/jobs.py:1219#_kql_table`).

- No agent run in the window, or its rows not yet ingested: "0 rows" and the callout "No rows in this window yet - logs reach Log Analytics 5-10 minutes after a call." (`console/web/render.js:103#callout`).
- Rows with an empty `Decision`, an object id or `(not resolved)` in `User`, or an empty `Tool`: not failures, joins that have not completed yet; see the next paragraph.
- More than 15 calls in the window: the card shows the newest 15 and does not say that there are more.

**Lag, and what the console shows while a row is not yet there.** The function joins sources that arrive at different times. The console's own expectations for the Act 6 board are the gateway row about 1 minute after the call, Foundry spans 1 to 5 minutes and the MCP audit row 6 to 10 minutes (`console/e2e.py:1634-1651#_fc_waiting`). The Act 5 page promises 5 to 10 minutes for Log Analytics, and Learn gives 3 to 10 minutes as the usual delay for resource logs, within the 30 seconds to 20 minutes that it gives for Azure metrics, resource logs and activity logs together (Platform behaviour, https://learn.microsoft.com/azure/azure-monitor/logs/data-ingestion-time#factors-affecting-latency; `console/catalog.py:501#Log Analytics`, `console/web/pages.js:450#Timing`; Findings F5-4). Because every join is a left join, a call can appear before its audit row. The row then has an empty `Decision`, `Reason` and `OnBehalfOf`, and a `User` that is a mapped UPN, a raw object id or `(not resolved)` depending on which other rows have arrived. Nothing on the card says the row is incomplete: the pending flag the runner sets for an empty chain does not exist for this query (`console/jobs.py:1203#pending`; Findings F5-24). Beat 5.2 is affected in the same way, because its request-id search needs `Decision == 'allow'` and so does not find a read until the audit row has landed (9.6.3).

**Failure modes and what the presenter should say.**

- The table is empty. No agent ran in the last 24 hours or its rows have not arrived; run beat 1.2 or 1.3 and press the button again after a few minutes.
- A recent row has an empty `Decision`. The audit row has not landed; say so and press again, and do not read it as "no decision was made".
- `OnBehalfOf` is `False`. The server declared a shared or non-user identity. That is the legacy agent's call, the contrast of Act 1 (9.2.2), but a False row is not always the legacy agent: it can also be a vendor tool, the restricted-list check or an `auth_failed` row (the `OnBehalfOf` bullet above lists the cases); on a `deny` row `True` only means the server did not mark the call as using a shared identity, not that Storage accepted the user's token (Findings F5-23).
- `User` shows a long identifier or `(not resolved)`. The first means no UPN was available for that object id in the window; the second means neither the server nor the gateway named anyone: the legacy message, a call whose audit and gateway rows have not landed yet, or a guardrail-only row with no `RunBy` (`observability/kql/AbwAgentActivity.kql:101#not resolved`, `observability/kql/AbwAgentActivity.kql:121#RunBy`).
- "The audit trail an examiner asks for." This is the queryable copy. The tamper-resistant copy is a pattern with a retention policy that is deliberately unlocked, and the repository itself says it is not a compliance attestation (`console/catalog.py:560#sales`, `DESIGN.md:239#unlocked`; Findings F5-28).
- "Where are the arguments?" Not on the card; `ToolArguments` is in the function, and the MCP audit holds only a hash (Findings F5-25).

**Why and trade-offs.** The function answers "which agent, which tool, for whom, decided how" by joining three records that no single system holds: Foundry's record of what the agent did, the MCP server's own record of what it decided, and the gateway's record of whose token it was. The join key is the request id that the server echoes in every tool result and that the gateway forwards (`observability/kql/AbwAgentActivity.kql:3#description`, `src/mcp/abw_mcp/registry.py:195-200#request_id`). The price is that the key lives in the reply text: the function finds it with a pattern match, and a tool that does not return it gives a row with nothing to join (`observability/kql/AbwAgentActivity.kql:10#RequestId`). Left joins keep a call visible while its other records are late, at the cost of a silent partial row. Foundry's copy of the arguments is more useful to an investigator than a hash and more sensitive to store; the repository does not describe who may read it. The card shows a demonstration-sized view, 15 rows and 8 columns over 24 hours; the workbook's grid and the function in Log Analytics are the working views (section 11).

#### 9.6.7 Beat 5.6: How long does one token keep serving calls?

**Purpose.** Show, from the MCP servers' own audit, which access tokens kept serving calls for more than a minute, for which person and which client application, so that "if we remove this person, when does their access stop?" is answered from data and not from a slide. The card says "Token lifetime per user and client - the case for short-lived tokens and the kill switch." (`console/catalog.py:566#say`), expects "Tokens that served calls for more than a minute, by user and client app." (`console/catalog.py:570#expect`), names its source as "AbwMcpAudit grouped by token id (jti)." (`console/catalog.py:571#tech`) and gives the presenter line "Why 'revoke the user' must work at the gateway, not only at sign-in." (`console/catalog.py:572#sales`). The beat uses no request id and no remembered id; it sends one fixed query. It does not measure a token's lifetime. It measures how long a token was seen being accepted, which is a lower bound of its life (see "What is not captured"). Beats 5.1 to 5.5 say what happened; this one says how long an access that was already granted can keep going after someone decides to stop it. Provenance: Implemented (the card, the query text, the stage helper `abw-tokens` and the workbook tile that counts tokens per person), Configured (the diagnostic settings that carry the servers' console logs to the workspace, listed under "Evidence produced"; the gateway kill switch and its script, the control the beat argues for), Not in this repository (a Microsoft Entra token-lifetime policy that shortens access tokens, a continuous-access-evaluation claims challenge from the gateway or the servers, and any proof that asserts this table).

**What the query counts, and over which window.** The console sends the text below, shown here with line breaks, with a 24-hour window, which `la_query` turns into the REST timespan `PT24H`; inside the function the window is the rolling 24 hours before the query runs (`console/catalog.py:1252-1261#tokens`, `console/azure_probe.py:165-167#la_query`, `observability/kql/AbwMcpAudit.kql:2-5#lookback`):

```kusto
AbwMcpAudit(24h)
| where Event in ('tool_listed','tool_call') and isnotempty(TokenId)
| summarize First=min(TimeGenerated), Last=max(TimeGenerated), Calls=count() by UserUpn, ClientAppId, TokenId
| extend UsedMin = round(datetime_diff('second', Last, First)/60.0,1)
| where UsedMin > 1
| order by First desc
| project User=UserUpn, Client=substring(ClientAppId,0,8), Token=substring(TokenId,0,10), Calls, UsedMin, First, Last
| take 12
```

One output row is one access token, identified by its token id, whose audited and allowed use in the window spans more than about a minute. "Serving calls" means that an MCP server accepted the token and wrote a listing or a call row for it. "More than a minute" means the last such row minus the first, in minutes rounded to one decimal, is greater than 1. Because the filter comes after the rounding, a span shorter than about 63 seconds rounds to 1.0 and is dropped (inferred from the arithmetic, not run). The token id is the `uti` claim, else the `jti` claim, of the token the server verified (`observability/kql/AbwMcpAudit.kql:32#TokenId`, `src/mcp/abw_mcp/auth.py:160-170#jti`). The seven columns:

| Column | Meaning | Where it comes from |
|--------|---------|---------------------|
| User | The person's UPN | The audit's `user_upn`, which the server takes from the token's `preferred_username` claim (`observability/kql/AbwMcpAudit.kql:17#UserUpn`, `src/mcp/abw_mcp/auth.py:162#preferred_username`) |
| Client | The first 8 characters of the client application id | The audit's `azp`, the token's `azp` claim (`observability/kql/AbwMcpAudit.kql:19#ClientAppId`, `src/mcp/abw_mcp/auth.py:151#azp`) |
| Token | The first 10 characters of the token id | The audit's `jti` field (`src/mcp/abw_mcp/audit.py:208#jti`) |
| Calls | The number of audit rows of the two counted kinds for that token, listings included | `count()` in the query |
| UsedMin | Minutes between the first and the last counted row | `datetime_diff` in the query |
| First, Last | The earliest and the latest `TimeGenerated` of those rows | The log table's own timestamp; the server's own timestamp is the separate column `EventTime`, which the query does not use (`observability/kql/AbwMcpAudit.kql:10-11#EventTime`) |

The event filter decides what counts. Every audit row that has a caller carries the caller's token id, so refusals are left out by the event list and not for lack of an id:

| Audit event | Written when | Counted here | Code |
|-------------|--------------|--------------|------|
| `tool_listed` | A client lists tools: one row per tool the caller may see, decision `allow` | Yes | `src/mcp/abw_mcp/registry.py:132-156#tool_listed` |
| `tool_call` | A tool call that ran; the default event of a tool outcome | Yes | `src/mcp/abw_mcp/registry.py:30-39#ToolOutcome` |
| `order_placed` | An accepted order, written by the Actions server | No | `src/mcp/abw_mcp/servers/actions.py:107#order_placed` |
| `order_blocked` | An order refused for the restricted list or for separation of duties | No | `src/mcp/abw_mcp/servers/actions.py:58-75#order_blocked` |
| `wall_violation_attempt` | A project the caller is not crossed on, or Storage refusing the user's own token | No | `src/mcp/abw_mcp/servers/wall.py:39-47#wall_violation_attempt`, `src/mcp/abw_mcp/servers/wall.py:95#storage_rbac_denied` |
| `tool_denied` | Any other refusal; the default event of a tool error | No | `src/mcp/abw_mcp/registry.py:54-76#ToolError` |
| `auth_failed` | The token failed verification; there is no caller, so no token id | No, and the token id is empty | `src/mcp/abw_mcp/auth.py:224-239#auth_failed` |

A refusal of an unknown tool also has no caller and so no token id (`src/mcp/abw_mcp/registry.py:161#unknown_tool`). The Cockpit workbook counts differently: its grid "Different people, different tokens (what the MCP servers verified)" counts every event except `tool_listed` that has a person and a token id, per person, with `Tokens = dcount(TokenId)`, within the workbook Time range (default 7 days; the function itself looks back 30 days), so one token can be counted there with its placed orders and with the refusals that carry its id, and here without them (`observability/workbook/build_workbook.py:270-287#id-tokens`, `observability/workbook/build_workbook.py:88-89#timeContextFromParameter`, `observability/workbook/build_workbook.py:680#604_800_000`; section 11 owns the workbook).

**How users and agents are identified.**

- The person is `UserUpn`, the token's `preferred_username` claim. Learn describes that claim as the primary username, to be used for username hints and human-readable display, and says that because the value is mutable it must not be used for authorization decisions; the object id `oid` is the immutable identifier (Platform behaviour, https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference#payload-claims). The audit line also carries the object id, which `AbwMcpAudit` exposes as `UserOid`, but this card groups by the UPN and does not show the object id, so an account that was renamed during the window would appear as two people (inferred from the grouping, not observed; Findings F5-33). The gateway's `revoked` decision is made on the object id, not on the UPN (`infra/apim/policies/mcp-jwt.policy.xml:31-37#abw-deny`, `observability/kql/AbwMcpAudit.kql:18#UserOid`).
- The client application is the token's `azp` claim, which Learn describes as the application id of the client using the token and which appears in v2.0 tokens (Platform behaviour, same URL); the server accepts only v2.0 tokens (`src/mcp/abw_mcp/auth.py:144-153#azp`). The card shows 8 characters, not a name. Three clients can appear: Foundry's OAuth passthrough uses the confidential client `abw-agent-client`; the console's gateway beats present the operator's token, whose client is the Azure CLI, or a persona's token, whose client is the gateway test client; the terminal helpers present the Azure CLI's token (`DESIGN.md:237#abw-agent-client`, `console/jobs.py:428-436#token_for`, `console/personas.py:193-212#token`, `demo/mcpclient.py:76-85#admin_token`). Mapping the 8 characters to a name is done in Entra, not on the card.
- The token is identified by `uti`, else `jti`. Learn describes `uti` as the token identifier claim, equivalent to `jti`, unique per token and case-sensitive (Platform behaviour, same URL). A token is specific to one user, one client and one resource (Platform behaviour, https://learn.microsoft.com/entra/identity-platform/configurable-token-lifetimes). The resource here is one MCP server, so a person who uses the agent against several servers has one token per server, each with its own lifetime; the card has no Server column although the audit has one, so these show as rows with the same User and Client and different Token values (`docs/RUNBOOK.md:49#jti`, `observability/kql/AbwMcpAudit.kql:12#Server`).
- An agent is not identified. The token is the person's, passed through by Foundry's connection; beat 5.5 names the agent from Foundry's own trace (9.6.6).

**What each kind of row means.** By code reading, not observed here.

| Row | What it supports | What it does not show |
|-----|------------------|-----------------------|
| `UsedMin` in the tens of minutes, Client is the agent client | One user token was accepted by one MCP server for at least that long, which is the reuse that `DESIGN.md:223#holds` describes | When the token expires, which server it was for, or whether anything was refused after the last row |
| Several rows with the same User and Client | One token per MCP server, or successive tokens after an expiry (Platform behaviour, Learn: one token per user, client and resource) | Which of the two it is, without the Server column |
| A row whose Client is the Azure CLI or the gateway test client | A token the console or a helper obtained for a gateway beat | Foundry's behaviour; see limit 5 below |
| No row for a person | No token of that person had audited allowed uses more than a minute apart in the window | That the person did nothing: short sessions, orders and refusals are all invisible here |

**What is not captured, and what the rows do not mean.** Nine limits, stated before anyone asks.

1. Only allowed listings and calls count, so `UsedMin` is a lower bound. It is the span between the first and the last allowed use that reached the log. It is not the token's lifetime, not its expiry and not the moment access stopped: a token that is still in use at the end of the window looks the same as one that has expired. Placed orders and the refusals of a verified caller are left out although they carry the same token id; `auth_failed` and unknown-tool refusals have no token id at all (Findings F5-8).
2. `Calls` is not a count of tool calls. A listing writes one `tool_listed` row for every visible tool, and `DESIGN.md:229#tool_listed` adds that the MCP SDK emits extra listing rows, so the figure mixes both (`src/mcp/abw_mcp/registry.py:132-156#tool_listed`).
3. A window and a cut. The window is 24 hours; the stage helper defaults to 12 (`demo/stage.ps1:220#Hours`). Spans of about a minute or less are dropped by the rounding. The query keeps the 12 most recently started tokens, not the 12 longest, and the card says "12 rows" without saying that more were cut (`console/jobs.py:1150-1157#_kql_table`; Findings F5-8).
4. No server and no name. The audit knows the server, and the card does not show it; the client is 8 characters of an id and the token 10 characters of another (Findings F5-32).
5. The console's own tokens are in the table. `token_for` forces a fresh operator token only for the first call per server and scope after the console starts or is reset; later gateway beats go through the library's silent path, which is expected to return a cached token while it is valid, and a persona's token follows the same rule. The terminal helpers force a fresh token by default. So a long row for the Azure CLI client or the gateway test client may be the console's own cached token and not Foundry's reuse; only the Client column separates them (a reading of the code; the library's caching behaviour is not verified here; `console/jobs.py:428-436#token_for`, `console/personas.py:193-212#token`, `demo/mcpclient.py:76-85#admin_token`; Findings F5-32).
6. Routes. The legacy server and the vendor stand-in have no caller and so no token id; shadow AI is not in this table by design (9.6.4). The private MCP server is audited, so its tokens do appear, but it is not behind APIM, so the kill switch this beat argues for does not reach it: a revoked user keeps that path until the token expires, which the repository says it read from the code and did not exercise live (`DESIGN.md:107#Direct`, `docs/PROOF-PLAYBOOK.md:444#private`). The card does not say which rows are private-route tokens.
7. Refusals and sign-ins are elsewhere. A token that failed verification, for example an expired one, is an `auth_failed` row with no token id (`src/mcp/abw_mcp/auth.py:135-136#expired`); a call refused at the gateway, such as `revoked`, never reaches a server and has no audit row, so those attempts are in the gateway log and in `AbwDenials` (9.6.5); and a sign-in that Entra refuses issues no token, so it is in no row of this table or of `AbwDenials`; Act 6 reads the Entra sign-in logs (9.7).
8. Self-reported and mutable. The audit line is the server's own record, written after it verified the token; nothing in this table is written by Azure, and the name it shows is a claim that Learn calls mutable (Findings F5-33).
9. The figures in the documents are dated observations. The repository quotes tokens used for 39 to 51 minutes and a third set that expired at about 73 minutes on the wall and private servers and about 90 minutes on the actions server; they were measured on build day from this same audit and are not re-measured by any proof or by this document (`DESIGN.md:223#holds`, `docs/RUNBOOK.md:49#jti`; Findings F5-31).

**Actors and tokens.** Only the Log Analytics token of 9.6.1 (row 5.6): the console's own Azure sign-in, used for the one query. The tokens in the table are other tokens, presented earlier by other callers, and the beat reads what they left behind. Each row belongs to a person, because the audit records the token's user; Foundry presents that person's own token for the agent's calls, so the table shows the person and not the agent, and the `Client` column is the only hint of which program held the token (`DESIGN.md:223#holds`, `observability/kql/AbwMcpAudit.kql:17-19#UserUpn`).

**Preconditions.** Those of 9.6.1, plus at least one token that an MCP server accepted twice, more than about a minute apart, in the last 24 hours, with both audit rows already in the workspace. Two kinds of earlier beat leave such a token. Two agent runs minutes apart against the wall API, for example beats 1.2 and 1.3, leave one when Foundry presents the same token for both runs (`console/catalog.py:277#abw-wall-desk`, `console/catalog.py:289#abw-wall-desk`, `DESIGN.md:223#holds`). A series of the console's own gateway beats leaves one too, because after the first call per server and scope the console is expected to reuse its cached token (limit 5 above). The beat does not need any of these to have run in this console session, and nothing in it checks that such a token exists: on a new deployment, or after a long idle gap, an empty table is the correct answer.

**Sequence.**

1. Browser -> console: "Token usage" posts the run object `{"kind":"kql","query":"tokens"}` as the `params` of a `POST /api/jobs`, with the beat id `5.6` (`console/catalog.py:569#run`, `console/web/pages.js:88-91#startJob`).
2. `validate` accepts the query name, because `tokens` is in the query dictionary and is not the internal `latest_allowed`; the kill-switch precheck does not apply to a query (9.6.1, `console/jobs.py:575-577#latest_allowed`).
3. `run_kql` says "Querying Log Analytics: Tokens that kept serving calls for more than a minute." and sends the query with `la_query`, which turns the 24-hour window into the REST timespan `PT24H`. No request id is resolved: only the `chain` query does that (`console/jobs.py:1184-1188#run_kql`, `console/jobs.py:1189-1190#chain`, `console/jobs.py:1198#la_query`, `console/azure_probe.py:165-167#la_query`).
4. Log Analytics evaluates the saved function `AbwMcpAudit(24h)` over the container apps' console log, then the event filter, the summary by token, the cut at more than a minute, the order and `take 12`, and returns at most 12 rows (`observability/kql/AbwMcpAudit.kql:4-8#ContainerAppConsoleLogs`, `console/catalog.py:1252-1261#tokens`).

**Why and trade-offs.** The beat rests on one property of bearer tokens: whoever presents an unexpired token is served, whatever has happened to the account since. Learn states the trade-off of an access-token lifetime in the same terms: a longer lifetime means fewer token requests and better performance, and a longer time during which a client keeps its access after the user's account is disabled; the default is a random 60 to 90 minutes, 75 on average, and it varies with the client, the resource and Conditional Access (Platform behaviour, https://learn.microsoft.com/entra/identity-platform/configurable-token-lifetimes). Learn's emergency-revocation page adds that its best practice is for an application to stop accepting Microsoft Entra access tokens even if they are still valid (Platform behaviour, https://learn.microsoft.com/entra/identity/users/users-revoke-access). The gateway's deny list is that practice: on every call it compares the token's object id with the list and answers 403 `revoked` (`infra/apim/policies/mcp-jwt.policy.xml:31-37#abw-deny`, `scripts/kill-switch.ps1:7-17#abw-deny-oids`). This beat supplies the evidence that the window is real, from the servers' own records and not from a slide: one token serving calls for tens of minutes, which the repository's build-day measurement attributes to Foundry holding each user's token for its whole life (`DESIGN.md:223#holds`).

The repository's answer is therefore not shorter lifetimes. A token-lifetime policy could shorten the access token, but Learn gives it a floor of 10 minutes and a ceiling of one day and says it can be managed only through Microsoft Graph, with no setting in the Entra admin center (Platform behaviour, same configurable-token-lifetimes page); the repository configures none (Findings F5-30). What it configures is the pair that the closing line of Act 4 names: group removal, which the repository says the data plane honours within a minute, and the gateway kill switch, whose first refusal the repository puts at 45 to 90 seconds after the command (`DESIGN.md:223#pair`, `DESIGN.md:176#Operator`, `docs/TALK-TRACK.md:183#Land`). They cover different layers. The kill switch does not reach the private route (`DESIGN.md:107#Direct`, `docs/TALK-TRACK.md:275#I have not run it`; read from the code, not run); the repository does not say whether group removal does.

Continuous access evaluation is the platform's own answer to the same gap, and the repository sets it aside in `DESIGN.md:236#CAE`, "CAE isn't available for custom APIs", and again in `docs/TALK-TRACK.md:277#CAE`, which a presenter may say aloud: "custom APIs do not get CAE, which is why the kill switch exists" (the same claim is at `docs/TALK-TRACK.md:244#CAE`). This document did not verify that sentence. Learn says that reduced token lifetimes were tried and found to degrade user experience and reliability without removing the risk; that with CAE a resource can reject a token that has not expired, answering 401 with a `WWW-Authenticate` claims challenge; that CAE tokens can live up to 28 hours; and that both the client and the resource API must be CAE-enabled, so a resource API opts in by implementing it, and the page does not exclude custom APIs (Platform behaviour, https://learn.microsoft.com/entra/identity/conditional-access/concept-continuous-access-evaluation, https://learn.microsoft.com/entra/identity-platform/app-resilience-continuous-access-evaluation). Whether this gateway or the MCP servers could implement it is not verified: the pages read here do not say whether a custom API can enable it, and they describe the first implementation as focused on Exchange, Teams and SharePoint Online. Neither the MCP servers nor the gateway in this repository send a claims challenge, so nothing here tells a client to discard an unexpired token (`src/mcp/abw_mcp/auth.py:250-260#_auth_error_response`, `infra/apim/policies/mcp-jwt.policy.xml:99-109#WWW-Authenticate`; Findings F5-29).

Two limits come with the gateway approach. It covers only the calls that pass through the gateway, and it is an operator action keyed on an object id, so someone has to decide and run it. And the checks tolerate small clock differences: the gateway's token validation allows a clock skew of 60 seconds and the server's verifier a leeway of 60 seconds, so a token can be accepted for up to about a minute after it expires, an inference from the two settings that this document did not test (`infra/apim/policies/mcp-jwt.policy.xml:17#clock-skew`, `src/mcp/abw_mcp/auth.py:126#leeway`; Findings F5-34). The card itself is a small instrument: one query's view of the MCP audit, 12 rows, no server and no object id. The workbook grid counts distinct tokens per person within the workbook Time range (default 7 days; the function itself looks back 30 days), and Act 6 follows one token id into the Entra sign-in log (9.7; section 11).

**What each pill means.** The pill is the probe's own pass rule and nothing more, so it can read Live while a fact beside it is unwelcome, and it cannot read Live for the two cards whose probes always answer "not applicable". Azure Policy is Live whenever at least one policy state is compliant, even when others are not, and its headline ends with the fixed words "(by design)" whatever is non-compliant (`console/azure_probe.py:534-558#probe_policy`). Conditional Access is Live as soon as one policy whose name starts with `ABW` exists; the report-only wording is added to the headline only when such a policy is in the state `enabledForReportingButNotEnforced`, and nothing checks that the policy ever evaluated a sign-in (`console/azure_probe.py:647-674#probe_conditional_access`). Purview and Agent 365 always return the status `na`, so their pills always read Portal step, although each card holds facts that the console did read live: the provisioning status of the Purview agent plans, and the Azure roles that the Agent 365 service principal holds (`console/azure_probe.py:588-602#probe_purview`, `console/azure_probe.py:775-790#probe_agent365`). The Control Room's own legend says what Portal step means: "the configuration lives in a portal with no API we can read - the card shows the click-path" (`console/web/pages.js:495#refresh`). The talk track tells the presenter to say plainly that the Purview and Agent 365 cards read Portal step because the console cannot read those admin portals, which matches that rule (`docs/TALK-TRACK.md:191#Portal`). Two documents drift from the code on this point: the demo guide describes two pill labels, Live and Portal step, while the code draws four (`docs/DEMO-GUIDE.md:140#Portal`, `console/web/pages.js:464#PILL`), and the Purview headline begins "Licensed and ready" whatever the count (Findings F5-11, F5-36).

**The three admin-portal features, said plainly.** Three cards end in an admin-portal step that this repository does not take and the console does not read: the Agent 365 gateway integration, Defender for AI services together with Defender XDR's Security for AI agents, and Purview DSPM for AI. For each, the bullets below separate five things: what the repository configures, what it does not, what the console reads or only links to, what the repository's own documents say about the live tenant, and what Microsoft Learn says about the platform. This document did not check any of them against a tenant, so they are marked "stated in the repository, not verified here" and their dates are left out. The self-deployment guide says the same in its list of what the deployment does not do: it "never turns on tenant admin-portal switches" (`docs/SELF-DEPLOY.md:40#never`). Only two optional scripts touch these features; both describe themselves as idempotent and safe to re-run, and the standard deployment runs them only with `-WithExtras` (`scripts/extras-agent-identity.ps1:7#Idempotent`, `scripts/extras-defender-sentinel.ps1:7#Idempotent`, `scripts/Deploy-AgentWall.ps1:367#extrasOff`). - **Live reads, no lag.** The probes read Azure now with the operator's own token and cache for 120 seconds, so unlike beats 5.1 to 5.6 they have no ingestion lag (evidence tag `probe`, 9.1.3; `console/azure_probe.py:830#TTL`). - **Fixed texts go stale.** Several card texts repeat counts and labels as fixed text that nothing refreshes, although the probe behind the same card reads the live figure for its own headline: the "by design" labels and counts of the Azure Policy card, "all seven" Purview plans, the fixed count of admin directory roles on the Conditional Access card and "four of abw-wall-desk's five tools". - **Platform limits shape what these services would show.** Defender XDR's threat detection covers only published Foundry agents, Purview's integration does not support network-isolated Foundry resources, and its data-security policies apply only to calls that carry user context (an Entra user-context token, or user context passed explicitly). For this deployment (agents not published and a network-injected project, stated in the repository, not verified here) that is why the guide says to claim nothing from these two features beyond "on".
