#### 9.8.10 Admin tab: the governed desk agent

The Admin tab is the one tab of Act 7 that runs agents, and it signs in as exactly one identity: the **operator**, the person who ran `az login` before starting the console (Implemented: `console/jobs.py:45#OPERATOR`; every scenario on the tab carries the actor label "Administrator (operator sign-in)", `console/role_tabs.py:28#ADMIN_LABEL`; the tab is defined at `console/role_story.py:119-131#admin`). Agent beats always run as the operator, whatever persona is selected in Acting as (Implemented: `console/jobs.py:420#PERSONA_KINDS`). What the operator may do comes from the Entra app roles on that account: the tab states that it holds the same data roles as Wes and Tara and no Orion role (Implemented: `console/role_story.py:58-61#HOW_ADMIN`), which is `Research.Read`, `Wall.Falcon`, `Trade.Execute`, `Positions.Read` and `MarketData.Read` (Configured: the persona role sets at `identity/Setup-Entra.ps1:53-56#tara`). That role set is a property of the demo tenant and not of the code: the dev/test helper `identity/Use-AdminAsPersona.ps1:15-18#Also` makes the signed-in administrator mirror one persona or a union of personas (`-As wes -Also tara`), and the audit beat in 9.8.12 reads the roles the operator's token really carries, live (`console/role_tabs.py:199-218#_operator_roles`). A role change does not reach the agent beats at once (Foundry behaviour as the repo's runbook measured it from the MCP audit and its proof harness relies on it; not re-tested here and not checked on Microsoft Learn): Foundry mints the user's tool token at the first agent call after the previous one expired and holds it for its whole life, 60 to 90 minutes, so a role change reaches the agent beats only when that token expires, while the audit beat reads a token that the console fetches itself (`demo/prove.py:1129-1131#Foundry`, `docs/RUNBOOK.md:49#measured`, `docs/RUNBOOK.md:296#agent`). The agent for this subsection is `abw-wall-desk` (`src/agent/abw_agents.py:36#WALL_AGENT`), a prompt agent with five tool connections, one per governed MCP server: research, wall, actions, private and vendor (`src/agent/abw_agents.py:42-48#WALL_DESK_TOOLS`). The same agent and the same operator run all five beats and only the prompt differs; the agent chooses its own tools, so the console traces the one tool call each beat is about (`console/role_story.py:58-61#HOW_ADMIN`). Three tokens carry the identity, all minted for the same person (section 6 has the mechanics): the front-door token, audience `https://ai.azure.com`, which `ask.build_credential(None)` takes from the operator's Azure CLI cache (Implemented: `src/agent/ask.py:109-113#build_credential`, `console/agent_run.py:83-86#build_credential`) and which APIM validates and forwards unchanged (Configured: `infra/apim/policies/agent-frontdoor.policy.xml:18-32#validate-jwt`, `infra/apim/policies/agent-frontdoor.policy.xml:96-107#forward-request`, `infra/08-agent-frontdoor.bicep:54#unchanged`); the tool token that the agent's OAuth identity-passthrough connection `mcp-<server>-oauth` presents on every tool call (Implemented: `src/agent/abw_agents.py:134#project_connection_id`); and the OBO data token an MCP server obtains to read Storage, Search or Cosmos DB as the user (Implemented: `src/mcp/abw_mcp/data.py:57-62#use_user_token`, `src/mcp/abw_mcp/config.py:154-155#cosmos_obo`). Every beat below enters through the front door of 9.8.3 while the agent path is APIM, the baseline that Reset demo restores (Implemented: `console/act7.py:132-139#restore_frontdoor`); beat 7.1 can switch the path to direct (`console/act7.py:161-171#run_agentpath`) and the console falls back to direct when the front door is not deployed (`console/jobs.py:105-107#agent_via`). Each beat then takes the shared path G1 to G9 of 9.1.8 once per tool call, and the vocabulary of allowed, refused and designed outcomes is the one defined in 9.8.2; each beat therefore describes only what differs. None of the five has an alt button, because the beat definitions pass no `alt`. Diagram: docs/diagrams/11-agent-front-door.excalidraw.

##### Beat 7.2-adm-res: The agent researches ACME (ALLOWED, positive, 15-60 s)

**Request.** The operator asks `abw-wall-desk` "What does our research say about ACME?" (`console/catalog.py:33-42#PROMPTS`). On this server the agent can call `search_research`, which queries Azure AI Search and forces the filter `classification eq 'public'`, and `get_research_note`, which reads one note from the `research-public` container (Implemented: `src/mcp/abw_mcp/servers/research.py:22-29#search_research`, `src/mcp/abw_mcp/servers/research.py:47-53#get_research_note`). Both tools need the `Research.Read` role (`src/mcp/abw_mcp/servers/research.py:74#require_any_role`). There is no approval step: only `place_order` is marked as needing one (`src/agent/abw_agents.py:49#APPROVAL_REQUIRED`).

**Sequence.** Before G1 the run enters at the APIM front door (9.8.3), which counts it against the operator's hourly token budget and per-minute call limit. Each tool call then re-enters APIM and follows G1 to G9 of 9.1.8 on its own request id. Three things differ from the shared path. First, the call arrives from Foundry and not from the console, carrying the user's tool token obtained through the identity-passthrough connection (`src/agent/abw_agents.py:134#project_connection_id`). Second, at G8 the research server reads as the user: Search is queried with an OBO token for `https://search.azure.com/user_impersonation` (`src/mcp/abw_mcp/data.py:73-87#search_documents`) and a note is read from Storage with an OBO storage token (`src/mcp/abw_mcp/data.py:57-62#read_blob_text`). Third, the console traces one call only: the named tool on this server first, else a refusal, else the first call on that server (Implemented: `console/role_tabs.py:287-294#_pick`).

##### Beat 7.2-adm-act: The agent places an order, with approval (ALLOWED, positive, 30-90 s)

**Request.** The operator asks `abw-wall-desk` "Check whether ACME is restricted and, if it is not, place an order to BUY 25 shares of ACME." (`console/catalog.py:33-42#PROMPTS`). The tools are `check_restricted_list` (`Trade.Read` or `Trade.Execute`), `place_order` (scope `Tools.Execute` and role `Trade.Execute`) and `list_my_orders` (`src/mcp/abw_mcp/servers/actions.py:130-156#build_tools`). `place_order` is the only tool that needs approval: Foundry pauses the run on it (`src/agent/abw_agents.py:49#APPROVAL_REQUIRED`, `src/agent/abw_agents.py:119-139#wall_desk_tools`).

**Sequence.** The approval is the step that differs. When Foundry asks, the run returns an `mcp_approval_request`; the console prints it, answers it and continues the same response with an `mcp_approval_response` (`console/agent_run.py:125-145#mcp_approval_response`). With approvals set to "yes" the console grants it automatically, as a desk supervisor would (`console/jobs.py:768-778#approval`); the Presenter can see the request and the answer in the run log. The approval is not the control that matters. Behind it the server reads the restricted list with its own managed identity, because the list is firm-wide reference data (`src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`; the data row reads SERVER IDENTITY, `console/e2e.py:429#SERVER`), then writes the order to Cosmos DB with the user's OBO token while `COSMOS_OBO` is true, which is its default (`src/mcp/abw_mcp/servers/actions.py:91#cosmos_obo`, `infra/04-apps.bicep:30#cosmosObo`, `infra/04-apps.bicep:65#COSMOS_OBO`), and stamps it with the user's object id, UPN, app id, token id and request id (`src/mcp/abw_mcp/servers/actions.py:77-98#user_oid`). A restricted ticker would be refused before any write, with `restricted_list` (`src/mcp/abw_mcp/servers/actions.py:68-75#restricted_list`); the `separation_of_duties` branch beside it needs a `Wall.*` role inside an actions-audience token, which cannot occur because roles belong to one API each (`src/mcp/abw_mcp/servers/actions.py:40-41#_has_wall_role`; section 7.6 explains why it is covered by a unit test only).

##### Beat 7.2-adm-pri: The agent reads firm positions on the private server (ALLOWED, positive, 15-60 s)

This beat is the fourth pill of the first Admin group, between the action desk and the vendor beat (`console/role_story.py:128#7.2-adm-pri`), so it is described here with the other four beats of that group (Findings F7b-2).

**Request.** The operator asks `abw-wall-desk` "Show the firm positions for the rates desk and the credit limit headroom for counterparty Northwind Capital." (`console/catalog.py:33-42#PROMPTS`). The tools are `get_firm_positions` and `get_credit_limit`, both requiring `Positions.Read` (`src/mcp/abw_mcp/servers/private.py:59-76#build_tools`). There is no approval step.

**Sequence.** The private server is reachable only inside the virtual network, so the path is shorter and different. G1 to G5 do not exist: APIM is not on the path, and the agent's subnet calls the server directly (Designed: `console/role_story.py:348-350#expect`; proved by P06, `demo/prove.py:711-732#p06`). G6 to G9 still apply, and G6 is the server's own: the same bearer middleware as the other token-checking servers (`src/mcp/abw_mcp/app.py:243-249#BearerAuthMiddleware`) validates the user's token itself (signature, audience, issuer, expiry, tenant, a user and not an app token, the client allow-list when one is configured, and the required scope, `Tools.Read` by default: `src/mcp/abw_mcp/auth.py:108-157#verify_token`, `src/mcp/abw_mcp/config.py:141#Tools.Read`), and each tool then checks `Positions.Read` (`src/mcp/abw_mcp/servers/private.py:59-76#build_tools`). G8 reads Cosmos DB with the user's OBO token (`src/mcp/abw_mcp/servers/private.py:19-34#get_firm_positions`, `use_user_token=runtime.settings.cosmos_obo` at line 26). Because APIM is absent there is no `x-abw-request-id` header and no gateway decision row: the server takes whichever of `x-request-id`, `x-ms-request-id` or `traceparent` arrives, or makes up a `req-<ms>` id (`src/mcp/abw_mcp/auth.py:179-184#request_id`), and the beat expects one request id across the Foundry agent and the MCP server only (`console/role_story.py:349-350#monitor`). The board follows the first of the two calls (`console/role_tabs.py:405-410#sc_admin_private`).

#### 9.8.13 Beat 7.3: What it costs and who spends the tokens

**Purpose.** After the control story comes the question a finance owner asks: what does this platform cost, who is spending the model tokens, and is anyone watching the bill (`console/catalog.py:814#say`). What it proves is narrow: spend and token use are visible per resource group and per Entra user. It does not limit anything; the limit is beat 7.4 (9.8.14). Provenance: the console code, the policy and the KQL are Implemented; the budget and the metric path are Configured; Azure's refresh and evaluation cadence is platform behaviour, verified on Microsoft Learn where it is cited; the dollar readings quoted from the playbook are tenant facts of one day, the day of the testing reading, that this repo's code cannot show.

**Actors and tokens.** Nobody signs in for this beat, no gateway is called and no agent runs. The console process reads Azure as the signed-in operator: `token()` mints a delegated token for the resource it is asked for (Azure Resource Manager for Cost Management, the budget and the two APIM named values; the Log Analytics API for the KQL) silently from the az CLI's cache (`console/azure_probe.py:73-89#token`, `console/azure_probe.py:30-32#ARM`). The templates grant the operator neither a Cost Management role nor a Log Analytics role: its operator role assignments are Foundry User on the account (`infra/02-foundry-rbac.bicep:26-34#raOperatorAccount`), Key Vault, ACR and Search (`infra/03-platform.bicep:736-764#raOpSearchSvc`), and only the infosec group gets Log Analytics Reader (`infra/03-platform.bicep:713-721#raInfosecLaReader`; Findings F7b-11). Platform behaviour, verified on Microsoft Learn (https://learn.microsoft.com/azure/cost-management-billing/costs/manage-automation): Cost Management data is refreshed every four hours and calling the Query API more often than once a day does not provide more data; the API is limited per tenant by query processing units (12 per 10 seconds, 60 per minute, 600 per hour) and answers 429 with the header `x-ms-ratelimit-microsoft.costmanagement-qpu-retry-after`; budget costs are evaluated once a day, and a GET on the Budgets API does not return the current costs shown in Cost Analysis but the last evaluated cost. Budget notifications do not affect resources and do not stop consumption (https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), which is why the beat's own FAQ calls the budget "an alert, not a cap" (`console/catalog.py:826#alert`).

**The monthly cost figure and its basis.** The board shows no monthly estimate. Its "Spend this month" is Azure's month-to-date actual cost for this resource group, so it grows through the month and is not comparable with a full-month number. The repo's only monthly figure is the run-rate estimate in `docs/COST.md`: about USD 1,100 a month, about USD 37 a day, if the platform is left running 24x7 at list price, with API Management Standard v2 about 63 percent of it (`docs/COST.md:3#USD`). It is a bottom-up estimate from the Azure Retail Prices API as pulled in the build session for 730 hours a month, written when Cost Management had no rows yet: "a bottom-up estimate, not an invoice" (`docs/COST.md:6-7#estimate`). Rows 1 to 9 of its table are fixed hourly charges and only rows 10 to 12 move with use (`docs/COST.md:38#fixed`), which is the split the board draws with its always-on and usage-based tiles. The headline says about USD 1,100, the table's total line about USD 1,110 and its rows add up to USD 1,112 to 1,119 (`docs/COST.md:11-25`), a difference of under two percent (Findings F7b-21). The estimate leaves out Microsoft Defender for Cloud, a subscription-level setting that pre-dates the demo, while the board's always-on figure includes that line (`docs/COST.md:32-35`; USD 1.16 in the reading below). The budget amount, default USD 1,200, is described in its own template as the list-price run-rate of the platform left running 24x7 and points at that file (`infra/09-budget.bicep:12-14#monthlyBudgetUsd`). The documented reading of the board on the day of the testing reading, a tenant fact the code cannot show, was USD 38.84 month to date, API Management USD 23.97 of it (62 percent, against about 63 percent in the estimate), always-on USD 38.24 (98 percent), usage-based USD 0.60, and 48,008 tokens in 24 hours by one user (`docs/PROOF-PLAYBOOK.md:1496-1527`, `docs/COST.md:75`). Month-to-date dollars and a monthly run-rate are different quantities; only the shape agrees.

**How tokens per user are attributed.** Attribution happens at the front door, not in the model and not in the console. The policy computes three values from the request: the caller's `oid` claim (else "unknown"), the first of the claims `upn`, `unique_name` and `preferred_username` (else "unknown"), and the agent name from `agent_reference.name` in the request body (else "n/a") (`infra/apim/policies/agent-frontdoor.policy.xml:33-50#abw-agent`). `llm-emit-token-metric` then writes the token counts to Application Insights with exactly those three custom dimensions (`infra/apim/policies/agent-frontdoor.policy.xml:97-101#llm-emit-token-metric`). The same `oid` is the counter key of the hourly budget of beat 7.4 (`infra/apim/policies/agent-frontdoor.policy.xml:96#counter-key`), which is why the function's description says that a cost line and a quota line always name the same person (`observability/kql/AbwTokenUsage.kql:3#same`). The function keeps the three token types and returns, per hour, user, user object id and agent: the number of total-token events as "Runs", the input, output and total tokens, and the first and last sighting (`observability/kql/AbwTokenUsage.kql:4-17#AppMetrics`). The console folds the hourly rows into one row per user and agent; "Agent calls" is the number of front door requests whose response carried a usage section, which in this console is one per agent run plus one for each round of approvals it answers, and each request can hold several model calls inside Foundry that the front door cannot see (Inference) (`console/act7.py:507-526#_per_user`, `observability/kql/AbwTokenUsage.kql:11#Runs`, `console/agent_run.py:124-145#create`). The playbook says "model calls the front door metered" and that one agent run makes several, which is looser than that (`docs/PROOF-PLAYBOOK.md:1529`).

**What is not attributable.** The board can name a spender only where the front door saw the call, so five things are missing by construction. (1) Tokens spent outside the front door: the legacy agent is sent straight to Foundry on purpose (`console/jobs.py:719-720#legacy`), and Foundry's own endpoint still answers a valid Entra token in this demo because its public network access is on (`console/act7.py:48-49#HONEST_PUBLIC`). (2) Calls without an `agent_reference`, which count under the agent "n/a". (3) MCP calls with no user context: the calls table lists them as "(no user context)" and they are calls, not tokens (`observability/kql/AbwUsageByUser.kql:3-6#AbwMcpAudit`). In the playbook's seven-day reading those were 197 calls to the vendor and legacy servers, against 279 for the operator and 8 for Priya, and its comment is that the FinOps gap and the audit gap are the same gap (`docs/PROOF-PLAYBOOK.md:1566-1574#gap`). (4) Dollars: the console does not know the negotiated model price and invents none (`console/act7.py:612#invent`, `console/catalog.py:833-834#honestly`). (5) Tokens Azure cannot count or keep. Platform behaviour, verified on Microsoft Learn (https://learn.microsoft.com/en-us/azure/api-management/llm-emit-token-metric-policy): the policy takes counts from the usage section of the model response when there is one, counts are inaccurate if a stream is interrupted, and API Management limits each custom dimension to 100 unique values and each namespace to 1,000 active time series, silently discarding new values beyond that. With oid and upn as dimensions the first ceiling is reached at a hundred distinct users. The repo's documents and catalog do not mention this limit, and at bank scale it is a design point to size, not something the demo shows. In this demo every token row belongs to the operator, because every console agent run (the Admin tab, the agent alternate of 7.1 and the real runs of 7.4) uses the operator's sign-in (`console/jobs.py:420#PERSONA_KINDS`, `console/catalog.py:758#abw-wall-desk`, `console/act7.py:748#agent_once`) and a person tab never runs an agent (`docs/DEMO-GUIDE.md:246#operator`); the tour shortens this to "only the Admin tab runs agents" (`docs/TALK-TRACK-PORTAL-TOUR.md:724#operator`).

**Why and trade-offs.** Two meters on one board, because the fixed platform and the usage-based tokens are different problems with different owners, and because one identity names both the spender and the budget (`console/catalog.py:821#sales`). Real sources only, so every number can be checked in the portal; the price is that the board is only as fresh as Azure. Cost Management is hours behind and budgets are evaluated about once a day, which is why the tile says "billed so far" and why a ten-minute cache costs nothing: the code's own comment says Cost Management "throttles hard and lags by hours anyway" (`console/act7.py:47#COST_TTL`). The always-on and usage-based split is a rule on service names, cheap and explainable but not accounting. Metering per user and per agent as metric dimensions is easy to read, but it has a ceiling of 100 unique values per dimension that a bank with thousands of users would reach; the repo has no design for that (not in this repo). The budget is an alert and cannot stop spend; the control that stops a runaway agent is the per-user token budget of 7.4, and a per-department budget is a design option, not built (`console/catalog.py:865#department`). A price per token is left out on purpose because the console cannot know the customer's rate, and the workbook tab has no dollar panel for the same reason. What the beat does not show is any token that never passes the front door, which Foundry's public endpoint and the legacy agent still allow in this demo (`console/act7.py:48-49#HONEST_PUBLIC`).

#### 9.8.14 Beat 7.4: A runaway agent hits a ceiling

**Purpose.** Show that an agent stuck in a loop stops at a ceiling that belongs to its own user, at the front door and before the model is called, so the refused call costs nothing and one user's runaway does not become everybody's outage (`console/catalog.py:852#sales`). The console makes one real call of the `abw-wall-desk` agent through the front door and lets the gateway count its tokens, cuts that user's hourly token budget to a single token, shows a probe that spends no token refused with HTTP 403 `token_quota_exceeded`, runs the real agent again and shows it refused the same way, then puts the budget back and waits until the front door forwards calls again (`console/catalog.py:850#expect`). It is the one beat of Act 7 that changes gateway settings: the catalog's order text says the Overview and 7.3 only read, and 7.4 changes two APIM settings for about a minute and puts them back (`console/catalog.py:744#order`).

**Actors and tokens.** The Presenter clicks. The console process acts as the operator, the signed-in user of the Admin tab (9.8.10), with two tokens it mints from the operator's Azure CLI sign-in (`console/azure_probe.py:73-89#token`): the user's front-door token (audience `https://ai.azure.com`) for the probes and the agent runs (`console/act7.py:38#AI_AUDIENCE`, `console/act7.py:666#AI_AUDIENCE`), and an Azure Resource Manager token for the named-value writes (`console/act7.py:123-129#_set_named_value`). The APIM agent front door (API `abw-agent-frontdoor`, path `agents`) enforces the budget; the budget itself is two non-secret APIM named values, `abw-agent-token-quota` and `abw-agent-rpm` (`infra/08-agent-frontdoor.bicep:27-47`, `infra/08-agent-frontdoor.bicep:49-62`). The agent `abw-wall-desk` sits behind the front door and the wall MCP server behind the agent, but only the first run reaches them. Section 6 has the token mechanics, and the front-door token is the first token of the shared path (9.8.3, 9.1.8).

**Preconditions.**

1. The front door is deployed and the agent path is APIM. Otherwise the beat refuses to start, with "The APIM agent front door is not deployed in this environment - run scripts\deploy.ps1 -Stage frontdoor first." or "The agent is switched to the direct path, which has no budget to cut. Switch the front door on first (Beat 7.1), then run this."; an unknown mode is refused with "Unknown budget mode." (`console/act7.py:142-157#validate`). The tour says the beat also needs the Agent entry light to be green (`docs/TALK-TRACK-PORTAL-TOUR.md:728#green`), but the code checks only the two conditions above, so an amber light, for example after an interrupted earlier run, does not block it (Findings F7b-26).
2. The gateway is open. 7.4 is in `NEEDS_OPEN_GATEWAY`, and `Manager.start` refuses it while the kill switch is engaged and tells the Presenter to click Reset demo first (`console/jobs.py:495#NEEDS_OPEN_GATEWAY`, `console/jobs.py:511-518#killEngaged`).
3. Nothing else that changes the gateway or runs an agent is running. 7.4 is in the `DISRUPT` set, which conflicts with every other member of the set and with every beat that uses the gateway or an agent; read-only beats such as 7.3 and the log buttons never conflict (`console/jobs.py:473-492#conflicts`). A refused start names the running beat and says to wait or press Stop on it (`console/jobs.py:521-524#conflicts`).
4. The UTC hour is not about to roll over. The counter is per calendar hour, so if fewer than 150 seconds remain the beat waits for the next hour first, and the click then takes correspondingly longer (`console/act7.py:702-708#_clear_of_the_hour`).
5. The operator can write APIM named values. No template grants that: the operator's template role assignments are Foundry User on the Foundry account, Key Vault Administrator, AcrPush and Search Service Contributor (`infra/02-foundry-rbac.bicep:28-31`, `infra/03-platform.bicep:736-764#raOpSearchSvc`), so the right rests on the documented Owner prerequisite (`docs/SELF-DEPLOY.md:55-58#Owner`), an Azure role that is a tenant fact and not visible in this repo's templates (Findings F7b-11). The policy only reads the value; who may change a user's budget is whoever holds an Azure role that allows the write.
6. The agent `abw-wall-desk` is published and the operator may invoke it (9.8.1, 9.8.3).

**Sequence.**

1. Click. The Presenter clicks "Cut the token budget" (about 40 s), which posts `{"kind": "quota", "mode": "quota"}` (`console/catalog.py:843-845#quota`). `Manager.start` runs `validate`, the kill-switch and conflict checks above and starts the job in its own thread (`console/jobs.py:503-533#start`).
2. Wait for a safe hour if needed (`console/act7.py:746#_clear_of_the_hour`).
3. Baseline: one real call, counted. The job runs `abw-wall-desk` with the prompt "List my wall crossings." through the shared agent path (`console/act7.py:748#agent_once`, `console/catalog.py:36#crossings`). The call takes G1 to G9 of 9.1.8 as in 9.8.3, and its tool call goes to the wall server (normally `list_my_wall_crossings`, answered from the roles in the token, 9.8.10; `src/mcp/abw_mcp/servers/wall.py:112-136#build_tools`). Every model round is one request through the front door, and the policy counts its tokens against the operator's counter. The console reads the two headers the policy adds, `x-abw-tokens-consumed` and `x-abw-tokens-remaining`, on each response (`console/agent_run.py:99-104#x-abw-tokens-remaining`) and prints "The front door counted N tokens for that call; budget left this hour: X of 250,000" (`console/act7.py:751-754#counted`). Platform behaviour, verified on Microsoft Learn (https://learn.microsoft.com/en-us/azure/api-management/llm-token-limit-policy): the remaining-quota header is an estimate that may be larger than expected, yet the step prints it as a figure (Findings F7b-27). If the call fails or has no answer the beat stops with "The baseline agent call did not complete" before it changes anything (`console/act7.py:749-750#baseline`).
4. Cut. `_set_named_value` sends one ARM PATCH to the named value `abw-agent-token-quota` on the APIM service, body `{"properties": {"value": "1"}}`, header `If-Match: *`, API version `2024-06-01-preview`, with the operator's ARM token; a status of 400 or more raises (`console/act7.py:123-129#_set_named_value`, `console/act7.py:755-757#NV_QUOTA`). Nothing else changes: the new value replaces `{{abw-agent-token-quota}}` in the `llm-token-limit` line of the policy, which keeps its hourly period and its per-user counter (`infra/apim/policies/agent-frontdoor.policy.xml:96#token-quota`). The cut is global: it applies to every user's counter, not only the operator's.
5. Wait until the cut has arrived. APIM applies a changed named value route by route; the catalog records that the GET and POST routes flipped 5 to 10 s apart and 5 to 20 s in all (`console/catalog.py:851#tech`, `console/act7.py:664#Measured`). One probe is therefore not proof that the agent route has changed, so `_settle` probes both routes, a GET of a response id and an empty POST to `/responses`, until three rounds in a row both answer HTTP 403 with code `token_quota_exceeded`, up to 24 tries 2 s apart (`console/act7.py:662-694#_settle`, `console/act7.py:758#Probe`). The probes spend no token: the GET asks for a well-formed id that does not exist, which Foundry answers with 404, and the empty POST would be answered by Foundry with 400, so before the cut they pass the front door and are rejected downstream, and after the cut the gateway refuses them first (`console/act7.py:39-40#PROBE_ID`, `console/act7.py:91-96#_probe_post`). The probes carry the operator's front-door token.
6. Show the refusal. The first accepted pair is shown as the card "Token budget used up - refused at the front door": HTTP 403, the `Retry-After` header, wall 1, reason `token_quota_exceeded`, lights user ok, entra ok, apim deny, and the plain-language text of the reason (`console/act7.py:759-765#_front_card`, `console/catalog.py:87-92#token_quota_exceeded`).
7. The real agent, refused. The job runs `abw-wall-desk` again with the same prompt and the same token, up to two attempts (`console/act7.py:766-777#attempt`). The front door answers the first request of the run with the 403 described under Success outcome, before Foundry is reached. `agent_run` turns a refused request into a `failure` event (status, code, message, request id, the front-door flag, reason and `retry_after`; exit code 4) and does not retry it: its retry loop only retries connection errors (`console/agent_run.py:107-118#create`, `console/agent_run.py:146-154#APIStatusError`). When the failure is a front-door refusal with code `token_quota_exceeded` the job prints "The agent run was refused at the front door - 0 model rounds, 0 tokens spent: the model was never called."; the zero text is replaced by "after N model rounds" if the run had completed a round (`console/act7.py:767-774#front_door_refusal`, `console/act7.py:772-773#rounds`). The zero is derived from the run's round count, not measured (Findings F7b-28). If the run is admitted instead, because the cut had not reached the agent route, the step says so and tries once more; a second admitted run fails the beat (`console/act7.py:775-777#admitted`).
8. Restore, always. A `finally` block puts `abw-agent-token-quota` back to 250,000 and `abw-agent-rpm` to 60 and waits until both routes answer 400 or 404 again for two rounds in a row, up to 24 tries 2 s apart, with cancellation ignored so that Stop cannot skip it (`console/act7.py:780-794#finally`, `console/act7.py:788#ignore_cancel`). The numbers come from the console's constant `FRONT_DOOR_DEFAULTS`, which today equals the template's parameters (`console/jobs.py:635#FRONT_DOOR_DEFAULTS`, `infra/08-agent-frontdoor.bicep:17-21#tokenQuotaPerHour`); the beat restores that constant and not the value it found before the cut (Findings F7b-29).
9. Finish. The beat ends `done` only if the refusal was seen, the real agent was refused and the restore was confirmed, and `failed` with one of three messages otherwise (`console/act7.py:795-806#ok`).

Why one token is enough to make the next call fail: the policy keeps one counter per user per UTC hour, and the baseline call has already put the operator's counter above one token, so the next request is over the new quota. The code does not say this in a comment; it follows from the fixed hourly window (Platform behaviour, verified on Microsoft Learn, same page as above: the quota period starts at the UTC timestamp truncated to the unit, so an hourly quota resets at the top of the UTC hour) and from the beat making the baseline call first, and it was not measured here.

**Success outcome.** The beat succeeds when the cut is seen on both routes, the real agent run is refused and the restore is confirmed. The refusal that the probe, the real run and any other client of the front door receive is the front door's own error, in the shape of 9.1.7:

```
HTTP/1.1 403 Forbidden
Content-Type: application/json
Retry-After: <seconds>
x-abw-request-id: <request-id>
x-abw-gateway: apim-agent-front-door

{"error": {"code": "token_quota_exceeded",
           "message": "Blocked at the agent front door: this user's token budget for the hour is used up (enforced per Entra user by llm-token-limit).",
           "reason": "token_quota",
           "retry_after_seconds": "<seconds>",
           "request_id": "<request-id>"}}
```

The policy builds this answer in its `on-error` section when the status is 403 (budget) or 429 (rate); the retry value is the `Retry-After` header that `llm-token-limit` set, or "60" when there is none (`infra/apim/policies/agent-frontdoor.policy.xml:142-187#Retry-After`). Platform behaviour, verified on Microsoft Learn (https://learn.microsoft.com/en-us/azure/api-management/api-management-error-handling-policies): when a policy raises an error, processing jumps to the `on-error` section, which is why the metric policy that follows the limit in the inbound section does not run for a refused call (`infra/apim/policies/agent-frontdoor.policy.xml:96-101#llm-emit-token-metric`). The body's `reason` is `token_quota` while the console, 9.1.6 and the reason table call the same reason `token_quota_exceeded` (`console/catalog.py:87-92#token_quota_exceeded`, `console/catalog.py:128-133#FRONT_DOOR_REFUSALS`), and the log functions record `token_quota` (`observability/kql/AbwGateway.kql:24#Reason`, `observability/kql/AbwDenials.kql:52-55#token_quota`; Findings F7b-30). The summary line is "real call answered -> budget cut to 1 token -> next call refused at the front door (403 token_quota_exceeded, model never called) -> restored" (`console/act7.py:799#real`), and the documented live run took 37.9 s (`docs/PROOF-PLAYBOOK.md:1595`).

What the user sees: the probe card of step 6, then the real run's failure card, which carries wall 1, the title "Token budget used up", the text "This user spent their hourly LLM token allowance, so the gateway refused the call and nothing more was spent. The allowance resets at the top of the hour, or when an admin raises it." and the added sentence that the refusal came from the APIM front door in front of the agent, so the model was never called (`console/catalog.py:87-92#token_quota_exceeded`, `console/catalog.py:141-169#explain_failure`, `console/jobs.py:779-788#front_door`). What the agent sees: nothing. The refusal is returned before `forward-request`, so Foundry is never called: no model round, no agent output, no tool call and no tool result exist for the refused run, and the model has no chance to talk its way past the ceiling (`infra/apim/policies/agent-frontdoor.policy.xml:96-107#forward-request`). The caller that receives the 403 is the console's agent runner, which does not retry; a client framework of the bank's own would have to treat a 403 with this code, and a 429, as a stop signal and not as a transient error.

Platform behaviour, same `llm-token-limit` page: a quota overrun returns 403 and a token-rate overrun returns 429. This demo's 429 is a different policy. It comes from `rate-limit-by-key`, calls per minute, because the `llm-token-limit` line sets only a quota and no tokens per minute (`infra/apim/policies/agent-frontdoor.policy.xml:95-96#token-quota`).

**If the console stops between cutting and restoring.** The restore is not a stored job: it is the `finally` block of the thread that cut the budget. Three cases follow from that.

1. The beat is stopped or fails: the `finally` runs (the Stop row above) and the budget comes back. This is the designed path.
2. The console process ends during the minute: the window is closed, Ctrl+C, a crash or a power loss. Each beat runs in a daemon thread (`console/jobs.py:532#daemon`), and the web app's lifespan hook only starts the warm-up thread and has no shutdown step (`console/server.py:343-345#lifespan`). Platform behaviour, verified in the Python documentation (https://docs.python.org/3/library/threading.html): daemon threads are abruptly stopped at shutdown and their resources may not be released properly. The `finally` is therefore not guaranteed to run on a normal exit and cannot run after a hard kill. The named value then stays at 1 (token mode) or at one call per minute (rate mode), and nothing in the repo puts it back by itself: the values are ordinary non-secret named values with no expiry (`infra/08-agent-frontdoor.bicep:27-47`), `demo/prove.py --restore` does not touch them (`demo/prove.py:339-352#restore_all`), and only Reset demo does (`console/jobs.py:1067-1069#restore_frontdoor`; Findings F7b-32).
3. The write is applied but its reply is lost: `changed` is set only after `_set_named_value` returns (`console/act7.py:755-757#changed`), so that run does not restore it either.

What the Presenter sees afterwards: the Per-user cap tile of 7.3 turns amber with "not the baseline, click Reset demo" (`console/act7.py:605-607#limits`), and so does the Agent entry light (`console/jobs.py:643-653#_agent_entry_light`); both read the named values live from APIM (`console/jobs.py:638-640#frontdoor_limits`). What every user sees: the agent runs of any user whose counter is already above one token are refused with the 403 above, and a user with no call yet in the hour gets one call through before the counter goes over, because the budget is counted after the response (`console/catalog.py:851#tech`). The clock does not heal this. The counters restart at the top of the UTC hour, but the quota is still one token, so the first call of each hour is admitted and the next one refused (an inference from the fixed hourly window, not tested). The way back is Reset demo: it writes each named value only when it differs from the console's constant and sets the agent path back to APIM (`console/act7.py:132-139#restore_frontdoor`), then waits, even through a Stop, until both routes forward again, up to 60 tries 3 s apart (`console/act7.py:697-699#wait_open`, `console/jobs.py:1067-1071#wait_open`). A re-deployment of the front-door template would also write the template's parameter values back (an inference about the template, not tested).

**The alt button (rate mode).** "Rate limit: one call a minute" runs the same job with `{"kind": "quota", "mode": "rate"}` (`console/catalog.py:846-849`). It changes four things. First, the setting: the named value `abw-agent-rpm` goes to 1 instead of the token quota, and the policy line that enforces it is `rate-limit-by-key` with a renewal period of 60 s and the user's object id as the counter key (`infra/apim/policies/agent-frontdoor.policy.xml:95#renewal-period`, `console/act7.py:729-731#NV_RPM`). Second, no model is called at all: the branch makes no agent run, only probes. A baseline probe must answer 404, otherwise the beat stops before changing anything with "The front door is not forwarding calls right now (throttled or revoked). Wait a minute or click Reset demo, then try again."; after the cut the probes run until two answer 429 `rate_limited`, up to 16 tries 3 s apart (`console/act7.py:726-728`, `console/act7.py:732#rate_limited`). Third, the answer: HTTP 429 in the same error shape, code `rate_limited`, reason `rate_limit` and the message "Blocked at the agent front door: too many agent calls per minute for this user (enforced per Entra user by rate-limit-by-key).", shown as the card "Rate limit - refused at the front door" with wall 1 (`infra/apim/policies/agent-frontdoor.policy.xml:178-183#rate_limited`, `console/act7.py:738-740`). Platform behaviour, verified on Microsoft Learn (https://learn.microsoft.com/en-us/azure/api-management/rate-limit-by-key-policy): a call above the rate gets 429 Too Many Requests with a `Retry-After` header by default, and the page warns that rate limiting is never completely accurate because throttling is distributed.

Fourth, the wait. The console says the limiter locks the caller out for about the `Retry-After` and that raising the limit does not cut an armed lock-out short (`console/act7.py:741-742`, `console/catalog.py:851#tech`), so the `finally` waits for the lock-out to run out, up to 60 tries 3 s apart, with cancellation ignored (`console/act7.py:786-788#ignore_cancel`). The tour records `Retry-After` values of 100 to 114 s (`docs/TALK-TRACK-PORTAL-TOUR.md:736`), longer than the policy's 60 s renewal period; why the lock-out outlasts the renewal period is not explained in the repo and not verified here. The finish text is "baseline OK -> 1 call per minute -> calls beyond it refused (429 rate_limited, Retry-After N s) -> limit restored, lock-out waited out" (`console/act7.py:797#lock_s`), the documented live time is 132.7 s against 37.9 s (`docs/PROOF-PLAYBOOK.md:1595`), and success needs no agent run in this mode (`console/act7.py:795#rate`). Reset demo waits for the same lock-out when it is clicked early (`console/act7.py:697-699#wait_open`).

**Evidence produced.** Token mode, in the order the click produces it:

Log rows arrive after the ingestion lag of two to eighteen minutes (`console/catalog.py:745#wait`), so the card is the live proof and the log the afterwards proof.

Rows that do not exist: no token-metric row for the refused run (platform behaviour, verified on Microsoft Learn, https://learn.microsoft.com/en-us/azure/api-management/api-management-error-handling-policies: an error jumps to `on-error`, so the metric policy that follows the limit does not run), no MCP audit row and no wall row for it (the agent never ran), and no request at Foundry. **Why and trade-offs.** The ceiling sits at the front door because that is the one place that sees every call of every agent before money is spent. The policy keys a single counter on the caller's Entra object id, so a loop in any agent under one user's token spends that user's budget and nobody else's, and the refusal returns before `forward-request`, so the model is never called and the refused call costs nothing (`infra/apim/policies/agent-frontdoor.policy.xml:95-107#forward-request`). The model cannot argue with it, because the model is not in the path of the decision: the same principle as the attacks of 9.8.11. The USD budget of 9.8.13 only tells you afterwards, while the token budget acts before the spend (`docs/TALK-TRACK.md:283-284`, `docs/COST.md:80`).

The trade-offs are these. (1) One number for everyone: a single quota for all users, 250,000 tokens an hour by default, about fifty demo runs (`infra/08-agent-frontdoor.bicep:17-18`). A per-agent, per-department or per-tier quota means changing the counter key and where the quota comes from, and is a design option, not built (`console/catalog.py:865`, `docs/PROOF-PLAYBOOK.md:1652`). The policy defines no counter shared by all users, so the front door has no organisation-wide token ceiling: the most it admits per hour is the quota times the number of users who may call the agents (an inference from the policy line `infra/apim/policies/agent-frontdoor.policy.xml:96#llm-token-limit`). (2) Counted after the response: with the prompt estimate switched off the gateway learns the cost from the response, so the call that crosses the line is admitted and finished, and concurrent calls can briefly exceed the quota (Platform behaviour, verified on the `llm-token-limit` page; `infra/apim/policies/agent-frontdoor.policy.xml:96#estimate-prompt-tokens`, `console/catalog.py:851#tech`). (3) A fixed hourly window: the counter resets at the top of the UTC hour, so a user who spends the budget at one minute past waits 59 minutes, while one who spends it at 59 past has a new budget a minute later, and across a boundary a user can spend up to twice the quota in a short time (an inference from the fixed window). The console avoids the edge by waiting when fewer than 150 s remain (`console/act7.py:702-708`). (4) The setting is global: the named values apply to every user of the front door, so for about a minute everybody has a budget of one token. Run it alone, in the demo tenant (`console/catalog.py:851#tech`, `docs/PROOF-PLAYBOOK.md:1650`). (5) The platform applies a changed value route by route, 5 to 20 s in all as measured on this gateway, so the beat probes instead of sleeping and pays with tens of cheap probe rows (`console/act7.py:664#Measured`, `docs/PROOF-PLAYBOOK.md:1624`). (6) Not every path goes through the front door: the legacy PoC agent always runs direct (`console/jobs.py:719-720`), and Foundry's own endpoint still answers a valid token because its public network access is on, which 7.1 says plainly (`console/act7.py:48-49#HONEST_PUBLIC`, 9.8.3). The budget is a control on the governed path, not a property of the model account. (7) Who may change a budget is whoever holds an Azure role that writes named values on the APIM service, not an Entra app role. The policy gives a caller no way to raise their own budget, and the Activity log names the writer (`docs/PROOF-PLAYBOOK.md:1634`; Findings F7b-11). (8) The restore target is a console constant, so a deployment that overrides the template parameters must change the constant too (Findings F7b-29). (9) A spent budget answers 403, not 429 (Platform behaviour, `llm-token-limit` page): a client that treats every 403 as a permanent authorization failure stops retrying, which is right for the rest of the hour, but it must read `retry_after_seconds` to know when to come back.

**Why and trade-offs.**

- **No proof of its own, and three designed lanes.** The proof grades are neighbours, not coverage (Findings F7b-25). Wes, Tara and Carla are the designed result until each signs in once, and the console says "designed, not run" for them (`console/catalog.py:744#order`, `docs/TALK-TRACK.md:219`).
- **The Admin tab is one identity.** Every Admin beat runs as the operator (`docs/DEMO-GUIDE.md:132`), whom the console labels "Operator (Wes + Tara)" (`console/personas.py:47#OPERATOR_LABEL`) and who holds no `Wall.Orion` (9.8.12). It shows what the wall does to an agent acting for that one identity. Inferred judgement: it does not show what an agent acting for Priya or Carla would do, because the person tabs make one direct call each and never run an agent, while every agent run, from the Admin tab, from the agent alternate of 7.1 or from 7.4, uses the operator's sign-in (`console/catalog.py:745#wait`, `docs/DEMO-GUIDE.md:246#operator`, `console/jobs.py:420#PERSONA_KINDS`).
- **A refusal is a state, not a prevention.** Nobody holds `Wall.Orion` in the demo, so the Orion refusal is a fact about the role assignments. The repo's own helper assigns app roles to the signed-in administrator through Graph (`identity/Use-AdminAsPersona.ps1:32-49#appRoleAssignments`), and the documents say PIM and the Activity log are not shown (`docs/TALK-TRACK-PORTAL-TOUR.md:809#PIM`; Findings F7b-17).
- **The budget is an alert, and the cap is per user.** The Azure budget mails the resource-group owners at 50, 80 and 100 percent of actual spend and at 100 percent forecast, and stops nothing (`console/catalog.py:820#tech`). The hard stop is the hourly token budget at the front door, 250,000 tokens by default for every user and only on the governed path (`infra/08-agent-frontdoor.bicep:17-18`, 9.8.14; Findings F7b-29). A budget per agent, department or tier is a design option and not built (`console/catalog.py:865`, `docs/PROOF-PLAYBOOK.md:1652`).
- **The attacks are decided in layers.** The shield at wall 0 is the first layer and is not promised to fire; when it does not, the wall servers decide at wall 2 (9.8.11). The beat wording around the rules has quirks (Findings F7b-7), and one of the three attacks has never been run live (Findings F7b-9).
