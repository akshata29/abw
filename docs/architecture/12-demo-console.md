## 12. Demo Console architecture

The Demo Console is the presentation and proof surface of the project. A presenter presses a button; the console makes a real request against the deployed stack (an MCP tool call through the gateway, an agent turn, a policy read, a KQL query) and draws the answer next to the log evidence the stack produced for that request. It is a client of the governed path, not part of it (its own docstring says the server owns no state, **Implemented**: `console/server.py:1-11#Starlette`): the path itself is described in sections 6 to 9 (authentication, authorization, MCP internals, scenarios), and the correlation keys, tables, functions and rules that its "Refresh from logs" button reads back are described in sections 10 and 11. This section covers the process model (12.1), how personas sign in (12.2), the modules (12.3), the evidence tags and replay data (12.4), the safety rails (12.5) and the jump-box installation (12.6).

Provenance labels as in section 10: **Implemented** (code), **Configured** (Bicep, policy XML, JSON), **Designed** (DESIGN.md or docs), **Platform behaviour** (a Microsoft Learn page, linked in the text), **Inference** (my own deduction, labelled as such).

### 12.1 Process model

What this section proves: the console is one local Python process with no database. A Starlette application bound to the loopback address serves a dependency-free browser UI and 24 routes; every button press becomes a job that runs on its own thread, streams child-process output into an in-memory event list, and is read back by the browser through polling. Every request the console sends to the gateway carries a real Entra token of the operator or of a persona (12.2); nothing is simulated except the rows explicitly tagged replay or portal (12.4) (**Implemented**: `console/server.py:359-391#build_app`, `console/jobs.py:256-272#Job`, `console/web/util.js:130-158#pollOnce`).

#### 12.1.2 Start-up sequence

1. **Import-time requirements.** `server.py` puts the console folder and the demo folder on `sys.path` and imports `azure_probe`, `catalog`, `jobs` and `personas` (**Implemented**: `console/server.py:29-32#HERE`, `console/server.py:43-46#azure_probe`). Importing `azure_probe` loads the nine generated-output JSON files immediately, so the console cannot start before a deployment has produced them (**Implemented**: `console/azure_probe.py:35-47#_load`).
2. **Arguments.** `main` accepts `--port` (default 8787), `--no-browser` and `--skip-az-check` (**Implemented**: `console/server.py:418-422#main`).
3. **Azure CLI check.** Unless `--skip-az-check` is given, `ensure_az_login` runs first (**Implemented**: `console/server.py:426-427#skip_az_check`). It requires the `az` command, compares the tenant of `az account show` with the demo tenant and, when they differ, runs `az login --tenant <tenant-id>` (a browser sign-in); it also notes when the Azure CLI is signed in as a different user than the configured operator (**Implemented**: `console/server.py:394-415#ensure_az_login`). Its docstring says every token the console uses comes from the operator's `az login` cache; that is true of the operator's tokens only, because each persona's tokens come from that persona's own MSAL cache (12.2.1) (**Implemented**: `console/server.py:395#Every`, `console/personas.py:193-212#token`). The jump-box launcher passes `--skip-az-check` because it has already done its own device-code sign-in (12.6).
4. **Port.** `free_port` tries 25 consecutive ports starting from the requested one, binding the loopback address each time, and exits with a message when none is free (**Implemented**: `console/server.py:348-356#free_port`, `console/server.py:428#free_port`).
5. **Browser.** Unless `--no-browser` is given, a `threading.Timer` opens the page 2.0 seconds after the server starts (**Implemented**: `console/server.py:429-433#Timer`).
6. **Serve.** `uvicorn.run(build_app(), host="127.0.0.1", ...)` serves the app (**Implemented**: `console/server.py:433#uvicorn`). Binding the loopback address means no other machine can connect to the page or the API (**Inference**: operating-system behaviour of a loopback bind).
7. **Warm-up.** The Starlette lifespan hook starts a daemon thread named `warm-up` that calls `jobs.status_lights()` and `ap.run_many(["foundry", "apim", "monitor"])`. The first call fills the 15-second status cache (and therefore makes the gateway call described in 12.1.7); the second pre-reads three probes. A failure is only logged, so the real error appears when a button is pressed (**Implemented**: `console/server.py:333-345#warm_up`).
8. **State.** There is no database. The only file the console writes about itself is the optional state file holding non-secret facts such as the path of the last violations evidence file (**Implemented**: `console/jobs.py:38-45#STATE_FILE`, `console/jobs.py:74-90#save_state`).

Trade-off / limitation: none of these guards authenticates the caller. No route checks a login, token or session (**Inference** from reading all 24 handlers), so any process on the same machine that sends a matching Host and Origin can start jobs; the guards defend the operator's browser against other web pages, not the API against local programs.

#### 12.1.5 The job engine and the streaming model

**The job object.** A `Job` has a 10-character hex id, a kind, parameters, a title, a beat id, a status (`running`, `waiting`, `done`, `failed`, `cancelled`), start and end times, an append-only event list, a result dictionary, a re-entrant lock, a cancel event, a queue of pending approval ids, the set of answered ids, the list of child processes and a handle to the agent child's stdin (**Implemented**: `console/jobs.py:256-272#Job`).

**Events.** `emit` appends `{"i": index, "t": seconds-since-start, "type": ..., **data}` under the lock; `say` and `step` are thin wrappers (**Implemented**: `console/jobs.py:276-286#emit`). The event types in use are:

| Type | Emitted by | Meaning |
|---|---|---|
| `say`, `step` | any runner | A line of narration; `step` carries a state (`run` by default). |
| `done` | `Job.finish` | Final status and summary; `finish` is idempotent (a finished job is never re-finished). |
| `approval` | `Job.need_approval` | An agent tool call is waiting for a human decision. |
| `raw` | `run_ps` | One output line of a PowerShell script. |
| `http` | gateway runners | One governed call: verdict, wall, server, tool, HTTP status, decision, reason, request id, plain-language text, lights. |
| `call`, `answer` | `agent_once` | A tool call the agent made, and its final answer. |
| `table` | KQL, matrix, FinOps | Columns and up to 40 rows. |
| `probe` | `run_probes` | One probe result. |
| `chain`, `trace` | `e2e` | The correlated chain rows (section 10.3) and the twelve-layer board. |
| `error` | `Manager._run` | A failure turned into a card through `jobs.friendly`, never a stack trace. |

(**Implemented**: `console/jobs.py:296-304#finish`, `console/jobs.py:317-323#need_approval`, `console/jobs.py:535-548#_run`, `console/e2e.py:346#trace`.)

**Reading events.** `Job.view(since)` returns the job header, `events[since:]`, a `next` cursor, the result and `pending`, which holds only the first unanswered approval id (**Implemented**: `console/jobs.py:288-294#view`). The browser keeps `next` per job and calls `GET /api/jobs/<id>?since=<next>`; while any job is live it re-polls every 600 ms, and a 404 (the console restarted and forgot the job) marks the job failed in the UI (**Implemented**: `console/web/util.js:130-158#pollOnce`). Every API call is made with `cache: "no-store"` (**Implemented**: `console/web/util.js:29-47#api`).

**No push channel.** A search of the whole console folder for WebSocket, EventSource, StreamingResponse and event-stream finds none, so "streaming" means: a child process's stdout is streamed line by line into the event list (12.1.6) and the browser fetches the list incrementally by polling (**Inference** from absence).

**Approvals are strictly ordered.** `need_approval` appends the id to `pending` and sets the status to `waiting`. The UI posts `{id, approve}`; `Job.answer` accepts it only when that id is the first unanswered one and the agent child's stdin is open, then writes one JSON line `{"approve": true|false}` to the child, which reads one line per request in order (**Implemented**: `console/jobs.py:317-343#need_approval`, `console/agent_run.py:135-146#approval_answer`, `console/web/render.js:60#approve`).

**Starting and finishing jobs.** `Manager.start` rejects an unknown kind, runs `validate`, applies the kill-switch precheck and the conflict rules (12.5), creates the job, keeps the newest 60 jobs in memory (never evicting a running one) and starts a daemon thread named `job-<id>`. `_run` calls the runner; a normal return becomes `done`, `Cancelled` emits a "Stopped." step and becomes `cancelled`, any other exception is logged and becomes an `error` event plus `failed`; the `finally` clause invalidates the status-light cache (**Implemented**: `console/jobs.py:503-533#start`, `console/jobs.py:535-548#_run`).

Trade-off / limitation: jobs live only in memory, so a restart loses the job list and the trace store (12.4); polling costs up to 600 ms of latency per update but needs no long-lived connection.

#### 12.1.6 Child processes

- **`stream_process`.** Runs an argument list with the repository root as working directory; the child environment is the console's plus `PYTHONIOENCODING=utf-8`, `PYTHONUNBUFFERED=1` and `NO_COLOR=1`; stdin is a pipe only when requested; stdout and stderr are merged; a pump thread feeds a queue; the main loop wakes every 0.25 s to check Stop and the deadline; ANSI codes are stripped and blank lines dropped; after the loop it waits 15 s for the exit; it raises `Cancelled` after a Stop (unless `ignore_cancel`) and `TimeoutError` after the hard timeout (**Implemented**: `console/jobs.py:358-407#stream_process`).
- **Stop.** `Job.cancel` sets the cancel event and calls `_kill_tree` for each child, which runs `taskkill /PID <pid> /T /F` (20 s timeout, no console window), so a Stop also ends grandchildren (**Implemented**: `console/jobs.py:345-348#cancel`, `console/jobs.py:351-355#_kill_tree`).
- **`run_ps`.** `pwsh -NoProfile -NonInteractive -File <script> <args>`; every output line becomes a `raw` event; the default timeout is 300 s (**Implemented**: `console/jobs.py:410-412#run_ps`).
- **`agent_once`.** Starts `console/agent_run.py` with `--agent`, `--approve`, `--via` and the prompt, with stdin attached only when approvals are interactive; `--via` is `direct` for the legacy agent and otherwise whatever `agent_via()` returns: the APIM front door when it is deployed, unless the presenter switched the agent path to direct in Beat 7.1 (**Implemented**: `console/jobs.py:717-740#agent_once`, `console/jobs.py:105-107#agent_via`, `console/act7.py:161-171#run_agentpath`). The child prints one JSON event per line (`who`, `tools`, `call`, `consent`, `retry`, `approval`, `approval_answer`, `failure`, `final`); it retries `APIConnectionError` up to 10 times with a delay that starts at 3 s, grows by 1.5 and is capped at 15 s; it exits 0 on success, 3 when an OAuth consent is requested, 4 on an API status error (with the gateway request id and retry-after), 5 when no credential is available and 6 otherwise; it records the gateway's `x-abw-request-id` and token-accounting headers when called through the front door (**Implemented**: `console/agent_run.py:33-34#emit`, `console/agent_run.py:90-118#tally`, `console/agent_run.py:146-170#exit_code`).
- **Programs behind the buttons.** `run_burst` starts `demo/burst.py` (400 calls, 48 workers, research server, 180 s timeout; it needs at least one throttled answer to count as success); `run_violations` starts `demo/try-violations.py` (nine requests, 900 s); `run_preflight` starts `demo/prove.py --only P00` (read-only, 180 s); `run_restore` starts `demo/prove.py --restore` (12.5); `run_allowlist` and `run_kill` start the two PowerShell scripts (12.5) (**Implemented**: `console/jobs.py:925-940#run_burst`, `console/jobs.py:994-1000#run_violations`, `console/jobs.py:1082-1090#run_preflight`, `console/jobs.py:1055-1065#run_restore`).
- **The registry of kinds.** 22 kinds are registered: agent, gateway, xpia, xpia_agent, burst, violations, violations_last, restore, preflight, private, probes, kql, allowlist, kill, e2e, e2e_agent, e2e_logs, matrix, finops, quota, agentpath, frontdoor (**Implemented**: `console/jobs.py:1401-1424#RUNNERS`).

#### 12.1.7 Status lights

The header of the console shows six lights in the normal case: Signed in, Roles in token, Gateway, Kill switch, Client allow-list and Agent entry. Fewer appear when a read fails: a failed token mint leaves only the Signed in light, shown as bad, and a failed ARM read is shown as one warning on the Kill switch light in place of the Kill switch and Client allow-list pair (**Implemented**: `console/jobs.py:656-714#_compute_status`).

- **Cache.** `status_lights` serves a cached result for 15 s. `invalidate_status` empties the cache in five places: the `finally` clause of `Manager._run` (after every job), the end of the burst job, the clean-up of the allow-list job, the clean-up of the kill-switch job (right after its `forget_tokens()` call, which does not clear the cache itself) and a request carrying `?fresh=1`. The shipped page calls `refreshStatus` only without the fresh flag (**Implemented**: `console/jobs.py:612-628#status_lights`, `console/jobs.py:548#invalidate_status`, `console/jobs.py:962#invalidate_status`, `console/jobs.py:1297#invalidate_status`, `console/jobs.py:1345#invalidate_status`, `console/server.py:118-125#api_status`, `console/web/app.js:163-164#refreshStatus`).
- **How the lights are computed.** A four-worker pool runs up to four tasks at once: one mints operator tokens for the wall, research and actions servers and decodes their claims for the first two lights; one reads the gateway state (deny list, kill-switch flag, allow-list, baseline flag) through ARM; one makes the Gateway call described next; and one reads the front-door limits from the APIM named values `abw-agent-token-quota` and `abw-agent-rpm`. The Gateway call and the limits read are skipped while a disruptive job is running, and the limits are also skipped when the front door is not deployed; the Agent entry light then shows the path without the numbers (**Implemented**: `console/jobs.py:635-653#frontdoor_limits`, `console/azure_probe.py:203-216#gateway_state`).
- **The Gateway light is a real call.** It performs a genuine MCP `tools/list` request to the research server through APIM as the operator (`list_gateway("research", timeout=25)`), not a ping; while a disruptive scene is running the light is skipped (shown as not applicable, "a gateway scene is running") so the status poll does not fight the scene (**Implemented**: `console/jobs.py:665-670#list_gateway`, `console/jobs.py:465-470#list_gateway`).
- **Browser cadence.** The page requests `/api/status` once at load, then every 15 s, and once more each time a job started from a button on a page has finished (**Implemented**: `console/web/app.js:91-104#refreshStatus`, `console/web/app.js:163-164#setInterval`, `console/web/pages.js:25#refreshStatus`, `console/web/pages.js:86#refreshStatus`). Because the server reuses a result for 15 s, an open console reaches the gateway about every 15 to 30 s, plus once per finished job (**Inference**; not measured). These calls appear in the gateway logs under the operator's identity (**Inference** from section 11.1).

Trade-off / limitation: an idle open console is not silent. It produces background gateway traffic about every 15 to 30 s (**Inference**), plus one more call per finished job; none is made while a disruptive job is running. These calls count against the operator's rate limit (**Inference**), which matters when someone later counts requests in `AbwGateway`.

#### 12.1.8 Headless runs with `smoke.py`

`console/smoke.py` runs one console job in-process, with the same `jobs.MANAGER` the web UI drives and no browser, and prints every event: `python console\smoke.py kql '{"query": "denials"}'`. It takes the kind, a JSON parameter string, `--approve ask|yes|no` and `--raw`; it prints `REFUSED: <reason>` and returns 1 when `Manager.start` refuses; it polls `job.view(seen)` every 0.3 s; it auto-approves any pending approval ("auto-approving in the harness"); and it returns 0 only when the job finished `done` (**Implemented**: `console/smoke.py:1-8#in-process`, `console/smoke.py:54-84#main`, `console/smoke.py:21#jobs`). It is the quickest way to test a runner or `validate` rule without a browser, and it shows that the job engine has no dependency on the web layer (**Inference**: `smoke.py` imports only `jobs`).

### 12.2 How personas sign in

What this section proves: persona sign-in is the standard OAuth 2.0 device authorization grant driven through MSAL; each persona has its own token-cache file in the secrets folder; a gateway call made during a job never prompts (it renews silently or reports "needs sign-in"); and the browser API returns only non-secret facts (**Implemented**: `console/personas.py:241-260#start_login`, `console/personas.py:263-293#_login_worker`, `console/personas.py:193-212#token`, `console/personas.py:587-603#state`). This section cites code only and does not describe the contents of any cache file or store.

#### 12.2.2 The device-code sign-in, step by step

Platform behaviour: the device authorization grant (RFC 8628) returns a `device_code`, a `user_code`, a `verification_uri`, an `expires_in` (15 minutes by default) and an `interval`; the client polls the token endpoint at that interval until the user finishes or the code expires; Microsoft recommends MSAL for this flow. https://learn.microsoft.com/entra/identity-platform/v2-oauth2-device-code

1. The browser posts to `/api/personas/<id>/login`; the route validates the persona id and calls `personas.start_login` (**Implemented**: `console/server.py:224-237#persona_action`, `console/server.py:254-256#api_persona_login`).
2. `start_login` reuses a pending flow if it has not expired; otherwise it builds a fresh MSAL app over the loaded cache and calls `initiate_device_flow` with the research server's `Tools.Read` scope. If Entra returns no `user_code` it raises an error carrying the Entra error text. It then starts a daemon thread named `persona-login-<id>` (**Implemented**: `console/personas.py:241-260#start_login`).
3. While the flow is pending, `login_view` returns the flow state, the user code, the verification URI and the seconds left, plus any error text. Once the flow is no longer pending, the code, the URI and the countdown come back empty, and ten minutes after the flow ended the view is hidden again (**Implemented**: `console/personas.py:305-324#login_view`).
4. The presenter (or the optional "open private window" button) goes to the verification URI and signs in. `open_private_window` requires a pending login, insists that the URI is https and that its host is `microsoft.com` or a `.microsoft.com` or `.microsoftonline.com` subdomain, starts Edge with `--inprivate` or Chrome with `--incognito` on a throwaway profile folder (`abw-persona-<id>-*` in the OS temp folder, older ones swept after a day), launches it detached so the browser outlives the console, and copies the user code to the clipboard (**Implemented**: `console/personas.py:554-585#open_private_window`, `console/personas.py:47-52#DETACHED`, `console/personas.py:537-546#_BROWSERS`).
5. The worker thread is blocked in `acquire_token_by_device_flow`, which polls Entra's token endpoint. With no token it records `expired` or `failed` plus the error code and the first 200 characters of the description (**Implemented**: `console/personas.py:263-293#_login_worker`).
6. With a token, the worker compares the `preferred_username` (or `upn`) claim of the ID token with the persona's UPN. A mismatch ends as `failed` with "Nothing was saved" and a warning log that does not name the account. A match writes the serialized cache atomically (temporary file, then `os.replace`) under the persona's lock, drops the cached app so the next call rebuilds it from disk, and records `ok` (**Implemented**: `console/personas.py:263-293#_login_worker`, `console/personas.py:119-123#_atomic_write`).
7. "Cancel" sets the flow's `expires_at` to 0, which the code comments as MSAL's documented way to stop the polling loop (**Implemented**: `console/personas.py:296-302#cancel_login`).

The UPN check in step 6 is what stops a presenter from signing the wrong person in and then running a scenario "as" the persona (**Inference** from the code comparing the claim with the persona's UPN before saving).

#### 12.2.3 Silent renewal and the forced first refresh

`token(pid, server, scope)` never prompts. With no account in the cache it raises `NeedsSignIn`; otherwise it calls `acquire_token_silent` for the server's scope with the first cached account and `force_refresh=key not in _fresh`, persists the cache when MSAL reports a state change, and raises `NeedsSignIn` ("expired or was revoked") if no token comes back (**Implemented**: `console/personas.py:193-212#token`, `console/personas.py:159-164#_persist`). The first call per (persona, server, scope) key in a console process therefore goes to the token endpoint instead of the access-token cache. The function's own docstring states the purpose: the first token after the console starts is forced fresh so that the role claims are current (**Implemented**: `console/personas.py:193-197#token`). `demo/prove.py` waits for role claims to settle after it flips roles, which fits the same reason (**Inference**; `demo/prove.py:323-337#become`). `forget_tokens` empties the operator's "fresh" set and, through `personas.forget`, the personas' "fresh" set, so the next token for each key is forced fresh again; the MSAL slots (app and cache) stay in memory (**Implemented**: `console/jobs.py:439-442#forget_tokens`, `console/personas.py:167-169#forget`).

Platform behaviour: a refresh token is bound to a user and a client but not to a resource or tenant, is replaced whenever it is used, can be revoked at any time (so an application must handle revocation by asking the user to sign in again, which is exactly the `NeedsSignIn` path), and must be stored as safely as an application credential. https://learn.microsoft.com/entra/identity-platform/refresh-tokens (bare URL only). MSAL's silent acquisition pattern: https://learn.microsoft.com/entra/msal/python/getting-started/acquiring-tokens

**Shared cache with the command-line tools.** Each persona slot holds the app, the cache and the cache file's modification time and is rebuilt when the file changes on disk; the code comment says why: the CLI shares the file (**Implemented**: `console/personas.py:132-156#_Slot`). A sign-in done in the console is therefore visible to `demo/mcpclient.py` (`persona_token`, which falls back to a device code when the cache has no account or the silent renewal returns nothing) and the other way round (**Implemented**: `demo/mcpclient.py:88-107#persona_token`).

**Cheap check versus real check.** `signed_in` is offline: it looks for an account whose username equals the persona's UPN in the serialized cache and memoises the answer by file time; it proves that someone signed in once, not that the refresh token still works (**Implemented**: `console/personas.py:172-190#signed_in`). `verify` is the real check: it acquires a silent token for each of the five servers and returns only non-secret claims (UPN, object id, `azp`, roles, scopes, expiry) plus a `checkedAt` stamp (**Implemented**: `console/personas.py:215-234#verify`).

#### 12.2.4 One-time codes, stored passwords, the clipboard

- **One-time codes.** `totp` implements RFC 6238 (HMAC-SHA1, 30-second step, six digits). `set_totp` accepts a base32 key or an `otpauth` link; it takes the `secret=` value from a link (or the whole text), strips spaces, upper-cases it, refuses a secret that is shorter than 10 characters once trailing `=` padding is removed, proves the rest by computing a code (a key that is not valid base32 fails there), and writes the store atomically; `totp_now` computes the current code (**Implemented**: `console/personas.py:332-338#totp`, `console/personas.py:353-367#set_totp`, `console/personas.py:370-375#totp_now`).
- **Stored passwords.** `clip_password` copies the stored password to the clipboard and returns only `{"copied": true, "clearsInSeconds": n}`; the value never reaches the browser (**Implemented**: `console/personas.py:527-534#clip_password`). Both stores are files in the secrets folder (`totp.json`, `personas.json`) (**Implemented**: `console/personas.py:40-43#TOTP_STORE`); the stores are plain JSON, which is why 12.6 treats persona files as real secrets (see Findings).
- **Clipboard hygiene.** The copy is written with registered clipboard formats that keep it out of Windows clipboard history and the cloud clipboard, and a 60-second timer clears the clipboard only if it still holds the same text (**Implemented**: `console/personas.py:378-390#_PRIVATE_FORMATS`, `console/personas.py:486-504#_wipe_later`).
- **What `state()` returns.** Only booleans for the secret facts (signed in, has a one-time-code seed, has a stored password). Everything else is display data: for each persona the id, name, job, label, UPN, role pairs, group names, story and login view, plus the operator entry (label, UPN, story) and the browser name (**Implemented**: `console/personas.py:587-603#state`).

#### 12.2.5 The operator, and the one password grant

The operator never uses a password grant. Its sign-in is `az login` (browser, or device code on the jump box). Platform behaviour: on Windows, `az login` uses Web Account Manager by default from Azure CLI 2.61.0, and `az config set core.enable_broker_on_windows=false` returns it to a browser-based sign-in (the jump-box launcher sets exactly that, 12.6) https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively

The single password grant in the console is a negative test: the failed-sign-in scenario (`sc_auth_failed`) calls `acquire_token_by_username_password` with a made-up password to produce a real failed sign-in at Entra, which later shows up in Entra's sign-in log and in the Sentinel rules (**Implemented**: `console/e2e.py:639-678#sc_auth_failed`). Platform behaviour: Microsoft recommends against the resource-owner password grant (it is incompatible with MFA and works only inside the tenant) https://learn.microsoft.com/entra/identity-platform/v2-oauth-ropc. The guard that keeps this scenario below Entra's smart-lockout threshold is described in 12.5.

#### 12.3.2 What the probes cover

`azure_probe` exposes 19 probes under the ids in `PROBES` (foundry, guardrail, apim, mcp, data, worm, monitor, sentinel, policy, defender, purview, licenses, entra, conditional access, agent identity, control plane, legacy, Agent 365, API Center). Each returns a result with a status of ok, warn, fail or na (**Implemented**: `console/azure_probe.py:236-244#_res`, `console/azure_probe.py:806-826#PROBES`). The rules of the module:

- **Read-only.** The docstring limits it to GET requests and POST-style read APIs, with no secret stored or printed (**Implemented**: `console/azure_probe.py:1-6#probes`). The one POST that returns a secret is the retrieval of the legacy subscription key (ARM `listSecrets`), which is cached in memory and never printed (**Implemented**: `console/azure_probe.py:222-233#legacy_key`).
- **Tokens.** `token(resource)` requests the `<resource>/.default` scope silently from the Azure CLI cache and reuses a cached token while more than 300 s remain. If the cache holds no account it tells the user to run `az login`; if the silent request fails for another reason it reports the first line of the Entra error text, clipped to 200 characters (**Implemented**: `console/azure_probe.py:73-89#token`).
- **Retries.** Three attempts. A transport error (DNS, TLS or connection failure) is retried after a short, growing pause; an HTTP 429, 502, 503 or 504 answer is retried after 1 s and then 2 s, and the third answer is returned whatever it is. If the attempts end in a transport error, the call raises a `ProbeError` that carries only the error type (**Implemented**: `console/azure_probe.py:103-116#_retrying`).
- **Log Analytics.** `la_query` sends the timespan as `PT<hours>H` below 48 hours and `P<days>D` above (**Implemented**: `console/azure_probe.py:165-180#la_query`).
- **Running many.** `run_many` mints the ARM, Graph and Log Analytics tokens serially and then runs the probes in a pool of six threads; `run_probe` caches each result for `TTL = 120` seconds (**Implemented**: `console/azure_probe.py:833-857#run_probe`).
- **Gateway state.** `gateway_state` reads two APIM named values over ARM, `abw-deny-oids` and `abw-allowed-azp`, and derives the rest: the kill-switch flag is true when the deny list is not empty, the allow-list is shown as short aliases and compared with the baseline set, and the operator-revoked flag is true when the operator's object id is on the deny list (12.5) (**Implemented**: `console/azure_probe.py:190-216#gateway_state`).

#### 12.3.3 How a scenario is registered and run

A scenario is an entry in `e2e.SCENARIOS` (title, polarity `negative` or `positive`, an `agent` flag, a persona rule and an optional default) plus a handler in `e2e.HANDLERS`. Nine of the 11 built-in scenarios are negative; the two positive ones are "cleared user, allowed end to end" and "the agent reads Falcon, allowed end to end". Three run through the agent action (jailbreak stopped by the guardrail, poisoned tool output, the positive agent run) (**Implemented**: `console/e2e.py:1209-1221#SCENARIOS`, `console/e2e.py:1223-1228#HANDLERS`).

The persona rule decides who the scenario runs as: `none` (the scenario makes its own tokens or none), `pinned` (a fixed default persona unless the beat names another), `follow` (whoever "Acting as" selects, else the operator) and `fixed` (set by the role tabs) (**Implemented**: `console/e2e.py:1230-1241#persona_for`).

`validate` returns, in the presenter's words, why a scenario cannot run (unknown scenario, scenario sent through the wrong action, unknown persona, persona not signed in) (**Implemented**: `console/e2e.py:1243-1263#validate`). `_execute` re-checks the kind, stores the effective persona in the job parameters, builds a `Ctx` (a three-worker thread pool, a board and a probe helper), runs the handler, calls `ctx.finish()` and always `ctx.close()` (**Implemented**: `console/e2e.py:1265-1278#_execute`, `console/e2e.py:279-315#Ctx`). `run` handles non-agent scenarios and `run_agent` agent scenarios (**Implemented**: `console/e2e.py:1279-1286#run_agent`).

`role_tabs` adds its scenarios by calling `_register`, which writes `e2e.SCENARIOS[id]` and `e2e.HANDLERS[id]`: the person cases (19 of them, plus Ian's audit read) get `persona="fixed"` and the person's id. The 11 operator-lane (Admin tab) scenarios differ: nine run a deployed agent with the console signed in as the operator, one is an audit-trail read with no refresh, and one is a direct gateway call for the Orion document. The agent runs enter through the APIM agent front door unless the presenter switched the agent path to direct in Beat 7.1, and the legacy agent always runs direct (`via = "direct" if legacy else agent_via()`). Eight of the 11 have their own handler; three reuse existing handlers (`agent_e2e`, `guardrail_attack`, `guardrail_xpia`). Together that makes 31 role-tab scenarios: one per beat (21) plus one per alternate run (10) (**Implemented**: `console/role_tabs.py:541-575#_spec`, `console/role_tabs.py:555-558#_register`, `console/jobs.py:717-740#agent_once`).

#### 12.3.4 Scene 7 in `act7.py`

`act7` implements five job kinds (matrix, finops, quota, agentpath, frontdoor) imported lazily by `jobs` (**Implemented**: `console/act7.py:37#KINDS`, `console/jobs.py:477#ACT7_KINDS`).

- **Role matrix.** Six lanes (the five personas and the operator); each cell is a real gateway call (`live`), an Azure role-assignment read (`rbac`), or a Log Analytics read of `AbwDenials(24h)` (`logs`); a person who has not signed in is shown as a dashed lane tagged `design`, "predicted by the role model, not run" (**Implemented**: `console/act7.py:223#LANES`, `console/act7.py:320-332#_gateway_cell`, `console/act7.py:354-359#_rbac_cell`, `console/act7.py:363-369#_audit_cell`, `console/web/render.js:206-211#MX_EVIDENCE`).
- **FinOps.** Reads up to five sources in parallel: month-to-date cost (Cost Management) and the budget (Consumption API), the per-user token meter (`AbwTokenUsage(24h)`) and calls per user (`AbwUsageByUser(7d)`) from Log Analytics, and, when the front door is deployed, its current limits from APIM. Only the cost query is cached (600 s; a throttled call falls back to the last reading, flagged stale); the other sources are read on every run. The module states that the console does not invent a price per token (**Implemented**: `console/act7.py:47#COST_TTL`, `console/act7.py:464-466#_month_cost`, `console/act7.py:547-560#run_finops`, `console/act7.py:612#invent`).
- **Quota.** Rate mode lowers the APIM named value `abw-agent-rpm` to 1 and expects HTTP 429 `rate_limited`; quota mode lowers `abw-agent-token-quota` to 1 and expects HTTP 403 `token_quota_exceeded`; the `finally` clause restores both values and waits until the front door is open again (**Implemented**: `console/act7.py:729-732#NV_RPM`, `console/act7.py:755-758#NV_QUOTA`, `console/act7.py:780-788#finally`, `console/act7.py:697-699#wait_open`).
- **Front door.** Three requests to the APIM agent front door (no token, a token for the wrong target API, a valid token), then a fourth, honest check against Foundry's own endpoint, with and without a token, after which the job says `HONEST_PUBLIC`: Foundry's own endpoint still answers a valid Entra token in this demo because public network access is on, so the front door can be bypassed here (**Implemented**: `console/act7.py:174-219#run_frontdoor`, `console/act7.py:48-49#HONEST_PUBLIC`).
- **Agent path.** A switch, not a read-only look: `run_agentpath` stores the chosen path (`apim` or `direct`) as `agent_via` in the console's state file and makes no network call, so the next agent beats enter through the APIM front door or straight at Foundry (the path also reads `direct` whenever the front door is not deployed) (**Implemented**: `console/act7.py:161-171#run_agentpath`, `console/jobs.py:81-90#save_state`, `console/jobs.py:105-107#agent_via`).

### 12.4 Evidence tags and replay

What this section proves: the console never shows a result without saying how it knows it. Every row of an Act 6 trace board, every cell of an Act 7 role matrix and every click-path carries a tag, set in code at the moment the row is written (**Implemented**: `console/e2e.py:186-200#Board`, `console/e2e.py:7-14#replay`, `console/act7.py:303-309#_design_cell`) and turned into a chip by the browser (**Implemented**: `console/web/render.js:287-298#TR_EVIDENCE`, `console/web/render.js:323-329#evidenceChip`). The only data that is not a fresh observation is the replay data: real earlier runs, scrubbed of identifiers before they are shipped (**Implemented**: `demo/scrub_evidence.py:54-91#Scrubber`). A replay never re-executes anything; the console only reads files or log rows that already exist.

#### 12.4.2 How a state and a tag become a chip

A row has two independent properties: the state says what happened and the tag says how the console knows. The nine states are pass, block, skip, na, info, due, quiet, seen and portal, drawn with a glyph and the words Passed, Stopped here, Never reached, Not used, Note, Waiting, Quiet, Seen and Portal step (**Implemented**: `console/web/render.js:285-286#TR_STATE`). `Board.finalize` fills every row no scenario wrote with state `na` ("Not part of this scenario." on the path, "Nothing to see here for this scenario." on a watchtower) (**Implemented**: `console/e2e.py:215-221#finalize`). The chip rules are four lines of code (**Implemented**: `console/web/render.js:323-329#evidenceChip`):

| Row state | Tag | What the browser draws |
|---|---|---|
| waiting (`due`) | any | Always a "wait" chip, and its text comes from `TR_DUE` by tag: the empty tag gives "expected - not seen yet", `logs` gives "waiting for the logs", `graph` gives "waiting for Entra's log", `arm` gives "waiting for an alert", `probe` gives "plan read live; alert not seen yet". Any other tag, every combined tag included, falls back to the logs text. |
| skipped or not used | `live` or empty | No chip. |
| anything else | a known tag | A chip with the colour class and text of the tag table above. |
| anything else | an unknown tag | No chip. |

Only two states colour the diagram: `Board.lights` turns a node green for pass or seen and red for block, and lights the user node when the Entra node is green (**Implemented**: `console/e2e.py:235-248#lights`). A waiting row never lights anything, which is why a gateway refusal reads as red immediately while its Sentinel row stays grey until a refresh finds the alert.

#### 12.4.3 The click-path tags

Every layer has a "Where to click" path in the Azure or Microsoft Defender portals, held in `CLICK`. Each path ends with a bracketed tag saying whether the author has seen that path in the demo tenant, for example "seen", "path from docs, not seen" or "policy list seen; Report-only tab path from docs" (**Configured**: `console/e2e.py:65-79#CLICK`). `_fill` replaces `{upn}`, `{server}`, `{rid}`, `{nonce}` and `{corr}` from the run's reference and four deployment names (project, API Management, storage account, workspace) taken from the generated-output JSON, so the path names the real resources (**Implemented**: `console/e2e.py:80-81#_NAMES`, `console/e2e.py:113-118#_fill`). The browser splits the trailing bracket off the path, renders exactly "seen" as "seen in this tenant", and colours the chip amber when the tag contains "not seen" or "from docs", green when it contains the word "seen", and neutral otherwise (**Implemented**: `console/web/render.js:316-321#splitClick`, `console/web/render.js:381#tr-tag`). Because "from docs" is tested first, a mixed tag such as the Report-only example is amber, the conservative reading.

Trade-off / limitation: "seen" is the author's hand-written claim about the last time the path was clicked, not a check the console performs; the playbook header gives the date of its last live pass (**Designed**: `docs/PROOF-PLAYBOOK.md:7#Last`). A portal that has since moved a blade would still show "seen in this tenant" (**Inference**).

#### 12.4.5 Replay: what is replayed and why

**The replay switch.** `_replay` is true for exactly one scenario, the data-plane denial. A replay can be days old, so `default_query` widens the query window from 3 days to 14 and the board keeps the shorter `AbwIdentityChain` view, because reading 14 days of `AbwFullChain` takes about 50 seconds according to the code's own docstring (**Implemented**: `console/e2e.py:126-128#_replay`, `console/e2e.py:154-158#_replay`). The two functions are described in 10.3 and 11.2.

**The data-plane denial (Act 6.5).** The handler asks Log Analytics for the newest `AbwMcpAudit` row whose reason is `storage_rbac_denied` in the last 14 days, then joins the layers for that request id with `AbwIdentityChain`. The Entra, Gateway, MCP and Data rows are tagged `replay` (their text is rebuilt from the old request's audit rows); the Monitor and Sentinel rows are tagged `logs` because they are read now, by that request id; the Sentinel row says "not found" when no alert names the request. The headline starts with "REPLAY" and the time of the original request, and the actor line says the row is a replay of the data-plane proof. When no denial exists in 14 days the handler stops with an instruction to run proof P16 once. The request id read back from the log is passed through `safe_request_id` before it is placed in the next query (**Implemented**: `console/e2e.py:849-853#sc_data_plane`, `console/e2e.py:855#safe_request_id`, `console/e2e.py:867-873#replay`, `console/e2e.py:875-885#logs`, `console/e2e.py:890-892#REPLAY`). It is a replay on purpose: the scenario's own note says it is not run on click because it changes a group membership (P16 removes the operator from the Falcon group, waits for Storage to refuse, which took 27 and 44 seconds in the two scoreboard runs, and restores the membership), and the Act 6 module states that it changes no role (**Implemented**: `console/e2e.py:892#note`, `console/e2e.py:16#Nothing`; **Designed**: `console/catalog.py:683-688#P16`, `docs/PROOF-PLAYBOOK.md:597#replay`). The module's claim that nothing in Act 6 writes to Entra is contradicted by the failed-sign-in scenario (12.5 and Findings).

**The policy row of the keys scenario.** `_keys_policy_row` reads the newest `try-violations-*.json` in the console's own `demo/evidence` folder, keeps the attempts whose id contains one of five key-related fragments, counts their outcomes and tags the Azure Policy row `replay` with the label ENFORCED. When there is no file, no valid JSON or no matching attempt it falls back to the live policy row; the compliance headline it appends is a live read (**Implemented**: `console/e2e.py:589-603#_violations_replay`, `console/e2e.py:719-726#_keys_policy_row`). The run behind the file is nine requests, not seven: the shipped scrubbed file holds nine attempts, of which seven match the key-related fragments (four BLOCKED and three CORRECTED, the figure the playbook quotes) and the other two are the unapproved-MCP attempt (BLOCKED) and a positive control that is expected to be ALLOWED (**Implemented**: `demo/evidence-scrubbed/try-violations-20261022-174305.json:238-247#foundry-unapproved-mcp`, `demo/evidence-scrubbed/try-violations-20261022-174305.json:262-269#positive-control`, `docs/PROOF-PLAYBOOK.md:685#replay`, `console/catalog.py:325#Nine`).

**What the three outcomes mean.** The script sends real ARM requests with throw-away names; BLOCKED is an HTTP 403 `RequestDisallowedByPolicy`, CORRECTED means another policy rewrote the request to a safe shape before it could be denied, ALLOWED is either the positive control or a real hole (**Implemented**: `demo/try-violations.py:1-9#CORRECTED`, `demo/try-violations.py:298-309#CORRECTED`). Platform behaviour: Azure Policy evaluates `modify` before `deny`, and a modify can change the request so that a deny never triggers https://learn.microsoft.com/azure/governance/policy/concepts/effect-basics. The script records the run as `runUtc`, the assignment name and the per-attempt results (**Implemented**: `demo/try-violations.py:481-482#runUtc`).

**Show the last run.** The "Show the last run" button is the other consumer of the same file: `run_violations_last` reads the newest `try-violations-*.json` (with a BOM-tolerant read) and prints its table, introduced by the time of the run and the evidence file's name (**Implemented**: `console/catalog.py:329#violations_last`, `console/jobs.py:1033-1052#run_violations_last`).

#### 12.4.6 The scrubbed replay data

Replay data starts as raw evidence written next to the code and ends as a scrubbed folder that is safe to show on screen or ship to the jump box. The pipeline (**Implemented**: `demo/scoreboard.py:78-96#main`, `demo/scrub_evidence.py:108-163#main`):

```
demo\prove.py            -> demo\evidence\prove-<stamp>.json
demo\try-violations.py   -> demo\evidence\try-violations-<stamp>.json
src\agent\ask.py --save  -> demo\evidence\<stamp>-<agent>-<persona or operator>.json
demo\scoreboard.py       -> demo\evidence\SCOREBOARD.md and scoreboard.json  (reads prove-*.json only)
        |
        v  demo\scrub_evidence.py  (pseudonymise, then leak check; exit 1 on a leak)
demo\evidence-scrubbed\  (same file names, plus a generated README.md)
        |
        v  scripts\jumpbox-console.ps1  (stage, scan, send)
VM: demo\evidence\       (the scrubbed copy, which the console reads as its replay data)
```

| Stage | What it does | Citation |
|---|---|---|
| Proof harness | Writes `prove-<stamp>.json`; the JSON carries the run time, the operator's UPN, the resource group and every result, which is why scrubbing is needed | `demo/prove.py:1224-1228#EVIDENCE` |
| Violations script | Writes `try-violations-<stamp>.json` | `demo/try-violations.py:481-482#runUtc` |
| Agent CLI | With `--save`, writes one transcript per question, named from the time, the agent and the persona or "operator" | `src/agent/ask.py:274-275#EVIDENCE` |
| Scoreboard | Keeps the latest result per proof id from `prove-*.json` only, expects proofs P00 to P17, writes `SCOREBOARD.md` and `scoreboard.json`, and with `--check` exits 1 unless all eighteen pass | `demo/scoreboard.py:19-43#load_latest` `demo/scoreboard.py:78-96#main` |
| Scrubber | Copies every non-hidden file, replaces identifiers, validates each JSON file, writes a README, then runs a leak check | `demo/scrub_evidence.py:108-163#main` |
| Package | Copies the scrubbed folder into the package as `demo\evidence\`; refuses to build when `scoreboard.json` is missing | `scripts/jumpbox-console.ps1:277-280#scrubbed` |

**What the scrubber replaces.** GUIDs become stable pseudonyms (uuid5 of the original under a fixed namespace constant, so one id maps to one pseudonym in every file and every run; upper case is preserved); seven first-party Microsoft app ids and any GUID that directly follows a role-definition, policy-definition or policy-set-definition path segment are kept. The tenant domain (any `onmicrosoft.com` name) becomes a fixed placeholder domain; the resource-name suffix becomes "xxxx"; the Container Apps domain's unique prefix becomes a fixed token; global IPv4 addresses become documentation addresses numbered from .10 (private addresses are kept); JWTs become a redaction marker (**Implemented**: `demo/scrub_evidence.py:38-51#KEEP_AFTER`, `demo/scrub_evidence.py:61-72#_guid`, `demo/scrub_evidence.py:73-83#_ip`, `demo/scrub_evidence.py:84-91#JWT`). The two deployment-specific values (the tenant domain and the suffix) are read as literals from the generated config file, and only those two (**Implemented**: `demo/scrub_evidence.py:94-105#_literals`). Dot-files and `.tmp` files are skipped, a JSON file that no longer parses after scrubbing aborts the run, and the destination folder is deleted and recreated on every run (**Implemented**: `demo/scrub_evidence.py:121-132#rmtree`).

**The leak check.** After writing, the script searches the written text for every original GUID or IP it replaced, for each literal and for a JWT pattern; a hit prints "LEAK CHECK FAILED" and returns 1 (**Implemented**: `demo/scrub_evidence.py:143-160#LEAK`). Three properties follow from the code and are recorded in Findings: the check only looks for values the scrubber itself recognised (it cannot find an identifier no pattern matches); the files are already written when the check fails, so a failed run leaves the folder behind; and without the generated config the suffix literal is neither replaced nor checked, because the script only logs a warning (**Inference**: `demo/scrub_evidence.py:94-99#_literals`, `demo/scrub_evidence.py:121#rmtree`).

**What ships.** The scrubbed folder holds 13 entries: eight agent transcripts, one `prove-*.json`, one `try-violations-*.json`, `SCOREBOARD.md`, `scoreboard.json` and a README stating that the data is synthetic. The scoreboard reports 18 of 18 proofs and 109 of 109 checks in the latest run of each proof (**Implemented**: `demo/evidence-scrubbed/SCOREBOARD.md:3#proofs`, `demo/evidence-scrubbed/README.md:3#synthetic`). The runbook states the rule: raw `demo\evidence\` is git-ignored and must not be shared; share only the scrubbed folder and re-run the scrubber after every proof run (**Designed**: `docs/RUNBOOK.md:326#scrub`).

**What the console serves.** `/api/scoreboard` returns `scoreboard.json` (an empty list when missing) and `/api/evidence/<name>` returns a file only when its name matches `prove-`, `try-violations-` or `burst-` followed by a timestamp and the file exists; anything else is a 404. The browser repeats the same regular expression and shows an "open" link only for matching names (**Implemented**: `console/server.py:56#EVIDENCE_NAME`, `console/server.py:204-216#api_evidence`, `console/web/pages.js:502#SAFE_EVIDENCE`, `console/web/pages.js:519#SAFE_EVIDENCE`). The transcripts are never served and the scoreboard never reads them. On the laptop the console reads the raw `demo/evidence` folder, so an evidence link there opens unscrubbed JSON; on the jump box the same folder holds only the scrubbed copy (**Implemented**: `console/server.py:50#EVIDENCE`, `scripts/jumpbox-console.ps1:277-280#scrubbed`).

Trade-off / limitation: the filename allow-list admits `burst-*` names that no code in the repository writes (**Inference**: `console/server.py:56#EVIDENCE_NAME`; see Findings).

#### 12.4.7 The trace store and "Refresh from logs"

Every scenario run is a `Ctx` with a 12-character trace id and a reference dictionary holding exactly what is needed to find the request in the logs later: scenario, start time, request id, marker, Foundry trace id, correlation id, UPN, object id, server and persona (**Implemented**: `console/e2e.py:279-300#saved`). Each `emit` publishes the board to the job and then stores the rows (as a deep copy), the reference and the extras (each as a shallow copy of its dictionary), the server, the actor, outcome, headline and note in an in-memory ordered dictionary of at most 40 traces; the oldest is dropped when the 41st arrives, and a read returns a deep copy of the whole entry (**Implemented**: `console/e2e.py:344-348#_remember`, `console/e2e.py:255-261#_remember`, `console/e2e.py:264-267#_recall`, `console/e2e.py:250-267#_TRACE_MAX`). Tokens are never stored: `_note_token` keeps only the `uti` claim of a token about to be sent, at most three (**Implemented**: `console/e2e.py:364-368#uti`). The row text does contain user identifiers such as the UPN, so the store holds identifiers but no credentials (**Inference**). Every identifier that is later placed into a KQL string (request id, marker, UPN, trace id, token id) is first matched against a strict pattern, and a value that does not match is dropped, so a stored value cannot inject query text (**Implemented**: `console/e2e.py:97-101#_ID`, `console/e2e.py:104-106#_clean`). The store is process memory: a restart empties it, and the runbook tells the presenter to re-run the scenario (**Designed**: `docs/RUNBOOK.md:314#memory`).

The "Refresh from logs" button starts an `e2e_logs` job for the card's trace id (**Implemented**: `console/web/render.js:445#e2e_logs`). `run_logs` recalls the saved trace (a miss is an error that says the trace is no longer in memory), rebuilds the context from the copy with mode `logs` (the Azure probes are not prefetched again, so `probe` rows keep their click-time text), prints the age of the click with the lag reminder, runs `_refresh` and ends with either "Still waiting for ..." or "Nothing is still waiting" (**Implemented**: `console/e2e.py:1858-1872#run_logs`, `console/e2e.py:279-300#saved`). `_refresh` branches on the scenario: a scenario flagged `refresh == "none"` says it already read the logs live; the failed-sign-in scenario reads Entra's sign-in log; the three 401 scenarios search the raw gateway log table, over one day, for the `?e2e=<marker>` query string the click added to the URL (`_wall_call` adds it, and APIM logs the URL); every other scenario reads App Insights spans (agent runs), the identity chain and the full chain, writes the Monitor row `seen` with the `logs` tag (ONE REQUEST ID or IN APP INSIGHTS) or leaves it `due` through `_waiting`, then looks for Sentinel alerts, and for agent runs asks Defender for Cloud through ARM (**Implemented**: `console/e2e.py:88-89#Q_NONCE`, `console/e2e.py:1402-1412#_refresh_401`, `console/e2e.py:1833-1855#_refresh`, `console/e2e.py:1333-1335#_waiting`, `console/e2e.py:1654-1660#_refresh_fullchain`, `console/e2e.py:1750-1760#_refresh_sentinel`, `console/e2e.py:1806-1830#_refresh_defender`). The Defender read starts five minutes before the click, while the row text says "since your click"; the text does tell the presenter to check the alert's time against the run (**Implemented**: `console/e2e.py:1812#since`, `console/e2e.py:1821#Check`). The chain it reads is the one walked in 10.3, and the card it fills is the one in 11.7.

**Timing.** The console carries three authored lag figures, 2-18 minutes for logs, 5-15 for Sentinel alerts and 10-20 for Entra's own sign-in log, once in Python and once in the browser beside the button (**Implemented**: `console/e2e.py:1288#LAG`, `console/web/render.js:300#TR_LAG`, `console/web/render.js:482#TR_LAG`). When a hop the click says should exist has not been logged, a run younger than 15 minutes is reported as "still filling in", and an older run is reported as "Still missing" those hops, with the instruction not to present them as logged; the full-chain query spans 35 days because the Entra sign-in that earned a token can be days older than the run that reused it (**Implemented**: `console/e2e.py:1521-1522#_FC_MATURE_MIN`, `console/e2e.py:1634-1651#_fc_waiting`, `console/e2e.py:1526-1528#_FC_SCOPE`). Beside the button the card shows "Last refreshed", a clock time and either the number of rows updated or "nothing new yet"; the card's age label updates every 15 seconds; and the browser's copy of the lag text adds the promise that a row changes only when the service really shows this request (**Implemented**: `console/web/render.js:438#nothing`, `console/web/render.js:313#AGES`, `console/web/render.js:300#TR_LAG`). Platform behaviour: Log Analytics ingestion time varies with the data source, so no single latency is guaranteed https://learn.microsoft.com/azure/azure-monitor/logs/data-ingestion-time. The figures above are constants chosen by the author, not measurements the code takes; where they disagree with other repository statements, section 10.4 and the Findings list the differences.

Trade-off / limitation: a refresh is a read, never a re-run, so it can only upgrade `due` rows to `seen` or `quiet`; it cannot change what the click observed, and a row that stays `due` after the lag is itself the evidence that nothing was found (**Inference**).

### 12.5 Safety rails

**What this section proves.** The console is not a read-only viewer: a handful of its buttons change real state in the demo tenant. This section lists which ones (12.5.1), what never starts without a click (12.5.2), how the single job manager refuses combinations that would fight each other (12.5.3), how the three scenes that degrade the platform on purpose always end in a restore step that Stop does not skip, and where that guarantee has edges (12.5.4), where the one built-in human decision sits (12.5.5), what the PowerShell scripts add (12.5.6), and the sign-in cap, the input checks and the HTTP guards (12.5.7). **Implemented**: `console/jobs.py:473-492#DISRUPT`, `console/jobs.py:1276-1301#run_allowlist`, `console/jobs.py:1304-1350#run_kill`, `console/act7.py:780-793#finally`, `src/agent/abw_agents.py:49#APPROVAL_REQUIRED`. #### 12.5.2 What never runs automatically

**Implemented.** Everything in 12.5.1 is started by a person. The evidence, with the search method labelled as such:

1. Only two callers can start a job: the HTTP route that the page posts to (`console/server.py:132#MANAGER.start`) and the command-line smoke harness (`console/smoke.py:65#MANAGER.start`). The harness answers yes to every pending approval it meets (`console/smoke.py:79-81#answer`), so it is a test driver and must not be pointed at a tenant you care about.
2. In the browser, every `startJob` call site is a click handler: the ops buttons (`console/web/pages.js:19-29#startJob`), the beat cards (`console/web/pages.js:81-95#startJob`), the board's "Refresh from logs" button, which starts only the read-only log reader (`console/web/render.js:343#startRefresh`, `console/web/render.js:443-445#startJob`), and the top-bar Preflight and Reset demo buttons (`console/web/app.js:143-144#btn-reset`). All of them go through one helper (`console/web/util.js:160-166#startJob`). The single keyboard handler only navigates between pages (`console/web/app.js:129-138#keydown`).
3. There is no scheduler (**Inference**: a search of the console folder for timers and scheduling libraries found two timers). One wipes a copied password from the clipboard after 60 s (`console/personas.py:486#_wipe_later`, `console/personas.py:502#threading.Timer`); the other opens the browser two seconds after start (`console/server.py:431#Timer`).
4. What does run on its own is read-only. The page asks for the status lights every 15 s and again each time a job started from a button on a page finishes (`console/web/app.js:163-164#refreshStatus`, `console/web/pages.js:25#refreshStatus`); the server reuses a result for 15 s (12.1.7). Computing them includes a real `tools/list` call through the gateway as the operator, which is skipped while a disruptive job runs (`console/jobs.py:621#status_lights`, `console/jobs.py:666-675#f_gw`, `console/jobs.py:556-557#disruptive_running`). At start-up a background thread fills the same cache and runs three probes (`console/server.py:333-340#warm_up`, `console/server.py:343-345#lifespan`).
5. The start-up check of the operator's Azure CLI sign-in runs only when the console is started without the skip option, and it starts a browser sign-in only if the Azure CLI holds no sign-in for the demo tenant; a sign-in under another account only prints a note (`console/server.py:394-415#ensure_az_login`, `console/server.py:426-427#skip_az_check`; 12.6). That is a sign-in, not a platform change.
6. Jobs live only in memory (`console/jobs.py:498-501#OrderedDict`, `console/jobs.py:560#MANAGER`), so a restart forgets running jobs and nothing resumes. If the console dies in the middle of a scene the platform stays degraded, because the setting lives in APIM and not in the console. The Kill switch light shows it at the next start (`console/jobs.py:687#killEngaged`) and Reset demo restores it.

**Why:** a demo that can degrade its own platform must make "who pressed the button" unambiguous, and a scheduled disruption would corrupt the evidence boards (12.4). **Trade-off / limitation:** while a page is open, the console makes a real `tools/list` call through the gateway about every 15 to 30 s, plus one more per finished job (**Inference**; 12.1.7); it is an ordinary gateway request and appears in the gateway logs like any other (see Findings and section 10).

#### 12.5.3 Guards in the job manager

**Implemented.** Every job, whatever started it, goes through `Manager.start`, which applies these checks in this order (`console/jobs.py:503-533#start`):

1. The kind must be a known runner, otherwise the start is refused (`console/jobs.py:503-510#validate`). The runner table holds 22 kinds, five of them implemented in act7 (`console/jobs.py:1401-1424#RUNNERS`).
2. The parameters must pass `validate` (`console/jobs.py:563-592#validate`): the agent name must be one of four known agents, the prompt a catalogue prompt or a free text of 3 to 500 characters (never for the legacy PoC), the approval mode one of ask, yes or no, a gateway call a known server (never the private one) and one of twelve listed tools, a KQL name one from the catalogue, a request id a GUID, probe ids known ones, end-to-end and act7 kinds their own validators. The kill-switch runner takes no victim parameter at all: its only parameter is `include_agent` (`console/jobs.py:1305#include_agent`), and the script call is hard-wired to the operator.
3. For every kind that needs an open gateway (and for the kill scene) the manager reads the gateway state over ARM (`console/jobs.py:511-520#gateway_state`). If the kill switch is engaged the start is refused and the presenter is told to click Reset demo first (this also stops a second kill scene); if the allow-list scene is requested while the allow-list is not at its baseline it is refused the same way. The read goes to APIM's management plane, not through the gateway, so it still works while the operator is revoked (`console/azure_probe.py:203-217#gateway_state`, which returns the deny list, the allow-list, a kill flag, a baseline flag and whether the operator is revoked).
4. Under a lock, any other job that is running or waiting and conflicts with the new kind causes a refusal that tells the presenter to wait or press Stop (`console/jobs.py:521-524#conflicts`).
5. Otherwise the job is created and stored; once more than 60 jobs are held, the oldest is dropped unless it is still running or waiting (eviction then stops); and a daemon thread runs the job (`console/jobs.py:525-532#Thread`).

The conflict rules are a small pure function over four sets (`console/jobs.py:473-477#GATEWAYISH`, `console/jobs.py:480-492#conflicts`):

| Set (members) | In `conflicts` | In the precheck | Citation |
|---|---|---|---|
| `DISRUPT`: burst, allowlist, kill, restore, quota | Two members always conflict, even the same kind twice; a member conflicts with every GATEWAYISH and AGENTISH kind, except that the allow-list scene may run beside an AGENTISH kind | burst, allowlist and quota are in the open-gateway set, kill is checked separately, restore is not | `console/jobs.py:473#DISRUPT`, `console/jobs.py:485-491#GATEWAYISH`, `console/jobs.py:495#NEEDS_OPEN_GATEWAY` |

Three consequences follow, each labelled:

- **Reset demo works while the switch is engaged.** `restore` is not in the open-gateway set (`console/jobs.py:495#NEEDS_OPEN_GATEWAY`), so the precheck does not refuse it. It still waits for any running DISRUPT, GATEWAYISH or AGENTISH job, because it is itself a DISRUPT kind (**Implemented**, `console/jobs.py:485-491#GATEWAYISH`).
- **The allow-list-versus-agent exemption has a plausible reason, which is an inference.** The front-door policy lists the named values it reads and the allow-list is not one of them (`infra/apim/policies/agent-frontdoor.policy.xml:13#Named`), and the allow-list scene removes only the Azure CLI's entry while the agent's own client application stays on the list (`scripts/client-allowlist.ps1:11-14#azcli`). The code carries no comment explaining the exemption (**Inference**).
- **The page is not the guard.** The page disables a button only after the POST has returned (`console/web/pages.js:23#disabled`), so a fast double click reaches the manager twice and the conflict check refuses the second one. A refusal is returned as HTTP 409 (`console/server.py:128-135#api_jobs_start`) and shown as a failure notice headed "Can't start that right now" (`console/web/pages.js:27#notice`, `console/web/pages.js:95#notice`).

**Trade-off / limitation:** the precheck fails open. If `gateway_state` raises, the failure is only logged and the job starts anyway, so that the job itself can report the real problem (`console/jobs.py:514-516#log.warning`). The kill-switch refusal blocks only the kinds in the open-gateway set; read-only kinds still run, so a stuck engaged switch is visible mainly in the Kill switch light (`console/jobs.py:687#killEngaged`).

#### 12.5.4 Restore blocks that Stop does not skip

**Implemented.** Three scenes degrade the shared platform on purpose: the client allow-list scene, the kill-switch scene and the front-door quota scene (its rate mode and its budget mode). They share one shape: read a baseline, arm a flag, change a setting, watch the refusal, then restore in a `finally` block that ignores cancellation (`console/jobs.py:1276-1301#run_allowlist`, `console/jobs.py:1304-1350#run_kill`, `console/act7.py:711-722#run_quota`). The allow-list and kill scenes arm their `cleanup` flag before the script that changes anything runs, so a script that dies half-way, or hits its 300 s limit, still gets a restore (`console/jobs.py:1278-1281#cleanup`, `console/jobs.py:1307-1311#cleanup`). The quota scene sets its `changed` flag right after each PATCH returns (`console/act7.py:720-721#changed`). The kill scene's optional agent run happens inside the same `try`, as the revoked user (`console/jobs.py:1326#agent_once`). The violations scene changes no platform setting and leaves its cleanup to its child process (table below).

How Stop works, in three steps:

1. **Implemented.** The Stop button posts to the cancel route (`console/server.py:164-170#api_job_cancel`), which calls `Job.cancel`. It sets the job's cancel event and then kills the process tree of every child the job has registered: `taskkill` on the process id with the tree and force switches, a 20 s timeout, and only a debug log line if that fails (`console/jobs.py:345-348#cancel`, `console/jobs.py:351-355#taskkill`). Every child started by `stream_process` is registered in `job.procs` while it runs and removed when it ends, whatever its `ignore_cancel` setting (`console/jobs.py:366#procs`, `console/jobs.py:401-402#remove`).
2. **Implemented.** `ignore_cancel` has exactly two effects. `Job.sleep` then uses a plain sleep instead of waiting on the cancel event (`console/jobs.py:306-310#ignore_cancel`), and `stream_process` neither stops the child because the cancel flag is set nor raises `Cancelled` when the child ends (`console/jobs.py:385#ignore_cancel`, `console/jobs.py:403-404#Cancelled`). The hard timeout still applies to such a child (same line 385).
3. **Implemented.** `Cancelled` travels up through the runner's own `finally` block, so the restore runs first. Only then does the job wrapper catch it, record a Stopped step and mark the job cancelled (`console/jobs.py:535-549#Cancelled`).

It appears in `console/jobs.py:1244#minute`, in `console/act7.py:123-125#PATCH` (a change applies "within seconds to about a minute") and in `scripts/kill-switch.ps1:12#propagation`. Two platform facts explain the shape of the quota scene's waits. A token-limit policy answers 429 when the rate is exceeded and 403 when the quota is exceeded, and its hourly quota period is a fixed window that starts at the UTC time truncated to the hour, so a window can roll over in the middle of a scene (the reason for `_clear_of_the_hour` is my reading, **Inference**), see https://learn.microsoft.com/azure/api-management/llm-token-limit-policy. A rate limit by key keeps one counter per counter key and is, in a distributed gateway, never completely accurate, see https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy.

**Why:** each of these scenes changes a setting that every later scene depends on (and, for the kill switch, the operator's own access), so the restore must run on every exit path and must not depend on the presenter's patience. The `wait_open` docstring says it exists so that Reset demo waits even through a cancel (`console/act7.py:697-699#wait_open`).

**Trade-off / limitation:** the guarantee has edges. All are read from the code, not exercised live.

1. **A Stop that lands while a restore script is already running kills that script (Inference).** `Job.cancel` does not know which children are cleanup children: it kills every registered child (`console/jobs.py:345-348#cancel`), and a restore script is registered like any other (`console/jobs.py:366#procs`). `ignore_cancel` only stops the Python side from reacting. At the normal end of a scene the job is still "running" and the page still shows the Stop button (`console/web/render.js:524#stopBtn`), so a click while the script runs kills it half-way. The Python side then neither raises nor looks at the return code (`console/jobs.py:1295#ignore_cancel`, `console/jobs.py:1337#Restore`); it still polls the gateway and, finding it blocked, tells the presenter to click Reset demo. The kill scene gets a second chance, because its fallback reset switch starts after the first script is gone (`console/jobs.py:1339-1340#Reset`); the allow-list scene has no second attempt. A Stop during the baseline check restores nothing because the flag is not armed yet, and a first Stop during a scene's main phase is safe because the restore children have not started. The page disables the button after the first click (`console/web/render.js:506-509#stopBtn`), but the route accepts any number of cancel requests for the same job (`console/server.py:164-170#api_job_cancel`). The quota scene is not affected, because its restore is a PATCH from the console's own thread.
2. **Reset demo is itself stoppable (Inference).** `run_restore` starts the proof script's restore without `ignore_cancel` (`console/jobs.py:1055-1058#run_restore`). A Stop while that script runs kills it and raises `Cancelled`, so the gateway check, the front-door restore and the final wait never run, and the job ends "cancelled" with no verdict. A Stop during the final front-door wait does not shorten it, because `wait_open` ignores cancellation (`console/act7.py:697-699#wait_open`). A second click on Reset demo starts the whole restore again.
3. **Violation attempts can leave resources behind (Inference).** All throw-away names of one run share one random 6-hex suffix (`demo/try-violations.py:72-73#token_hex`), only requests that ARM accepted are queued for deletion (`demo/try-violations.py:354-356#cleanup`), and deletion happens in the script's `finally` block (`demo/try-violations.py:463-468#finally`). A Stop kills the process tree, and a force-terminated process does not run its Python `finally` (no Learn link; my reading). A later run uses a different suffix and Reset demo never deletes them, so such leftovers in the demo resource group need a manual clean-up. `_delete` retries up to 60 times, 15 s apart, while a resource is still provisioning (its own comment names a Cosmos DB account that takes minutes before it can be deleted), which can add up to 15 minutes per resource and so exceeds the console's 900 s job limit (`demo/try-violations.py:362-369#_delete`, `console/jobs.py:1024#timeout`).
4. **`changed` is set after the PATCH returns (Inference).** If ARM applied a change but the call reported an error (for example a transport timeout after the service accepted it), the quota scene skips its restore (`console/act7.py:730-731#NV_RPM`, `console/act7.py:756-757#NV_QUOTA`). Reset demo repairs it, because `restore_frontdoor` puts both values back (`console/act7.py:132-139#restore_frontdoor`).
5. **The deadline check sits in the idle branch (Inference, low severity).** In `stream_process` the poll-time Stop check and the hard-timeout check run only when no output line arrived for 0.25 s (`console/jobs.py:383-389#queue.Empty`). A child that prints without a pause would delay or prevent the hard timeout; Stop still works because `Job.cancel` kills the tree directly.
6. **Reset demo's verdict is weaker than its steps.** `prove.py --restore` exits 0 whatever happens (`demo/prove.py:1182-1184#restore_all`). Its four steps are independent: `run_ps` returns the exit code and output without raising (`demo/prove.py:179-182#run_ps`), so a kill-switch or allow-list script that exits non-zero is still printed as "restored", while an exception, such as a missing `pwsh`, a timeout or a Graph error in the group re-add or the persona flip, prints "RESTORE FAILED" for that step (`demo/prove.py:339-353#restore_all`). `run_restore` shows those lines on the board but takes its verdict from the exit code, the gateway state and the front-door wait only (`console/jobs.py:1075#good`), so it never reads them. A failed script is caught only through the gateway state check, and a failed persona flip or group re-add is not noticed. "Baseline restored." therefore means the gateway settings are back, not that the console verified the operator's roles (see Findings).
7. **A crashed console runs no restore.** Jobs run on daemon threads (`console/jobs.py:532#daemon`); 12.5.2 item 6 covers the consequence and the Kill switch light.

#### 12.5.5 The approval gate

**Configured.** On the agent side exactly one tool needs a human decision: `place_order` on the actions server (`src/agent/abw_agents.py:49#APPROVAL_REQUIRED`). The tool definition built for the wall-desk agents sets approval to "always" for that tool, "never" for the server's other allowed tools, and the plain string "never" for every other server (`src/agent/abw_agents.py:119-139#MCPToolRequireApproval`). The legacy PoC agent's tool is "never" (`src/agent/abw_agents.py:142-152#require_approval`). The governed agent, the red-team agent and the shielded red-team agent are all built from the same helper (`src/agent/abw_agents.py:172-191#wall_desk_tools`), so all three carry the gate.

**Platform behaviour.** For a remote MCP tool, Foundry returns `mcp_approval_request` items when approval is required. The client continues the conversation with `mcp_approval_response` items that carry the decision (`approve`) and the request id (`approval_request_id`), and it passes the earlier response's id as `previous_response_id`. Learn advises approving only after reviewing the tool name and arguments and building your own approval experience, see https://learn.microsoft.com/azure/foundry/agents/how-to/tools/model-context-protocol. The per-tool always/never form is **Implemented** here from the SDK call alone; I did not find it on that page.

**Implemented.** The relay is in `agent_run.py`. It loops for at most 60 rounds; each round collects the `mcp_approval_request` items and the OAuth consent requests of the last response (`console/agent_run.py:125#range`). For every approval request it emits an `approval` event with the server label, the tool and the arguments cut to 400 characters, decides, emits an `approval_answer` event, and continues with the decisions as `mcp_approval_response` items on the previous response id (`console/agent_run.py:133-145#mcp_approval_response`). In ask mode the decision is one JSON line read from standard input: end of input means deny, a JSON object with a true `approve` value approves, and a line that is not a JSON object, a blank line included, makes the runner fail with exit code 6; in yes mode it approves; in no mode it denies (`console/agent_run.py:138-142#readline`, `console/agent_run.py:158-160#exit_code`).

Who decides in practice:

**Implemented.** The job side of an ask-mode approval:

- `Job.need_approval` queues the request id, sets the job status to "waiting" and emits an `approval` event (`console/jobs.py:317-321#need_approval`). In `agent_once` the `approval` event reaches it only in ask mode; in the other modes the console emits an `approval` event marked auto and no job state changes (`console/jobs.py:768-778#need_approval`). The child's standard input is a pipe only in ask mode (`console/jobs.py:803#stdin`).
- The page's card is decidable only while the job is "waiting" and the card's id is the first pending id; otherwise it shows a waiting notice. It prints the arguments cut to 400 characters, tells the presenter that the agent will act under their identity, and disables both buttons while the POST is in flight (`console/web/render.js:42-70#approvalCard`). An auto card reads as pre-approved for this run (`console/web/render.js:578-584#approval`).
- The approve route returns HTTP 409 when the answer is refused (`console/server.py:155-161#api_job_approve`). `Job.answer` accepts an answer only for the first unanswered pending id (otherwise it says the approval is no longer waiting), writes one JSON line with the decision to the child's standard input under a lock, and says the agent process has already finished if the pipe is closed (`console/jobs.py:331-343#answer`).

**The consent gate is separate.** When a response holds an OAuth consent request (the first-use consent for a user-delegated MCP connection, see section 6), the runner stops with exit code 3 (`console/agent_run.py:127-130#consent`) and the job shows a failure card headed "One-time consent needed", not an approval card (`console/jobs.py:761-765#consent_required`).

**What approval does not do.** The MCP server's own checks run after a yes. The actions server refuses `place_order` for a restricted name when the caller holds a wall role (reason `separation_of_duties`) and refuses any restricted name (reason `restricted_list`); nothing in `place_order` reads an approval flag, so the outcome depends only on the role and the restricted list (**Inference** from reading the handler; sections 7 and 8 cover the checks) (`src/mcp/abw_mcp/servers/actions.py:58-76#separation_of_duties`). An allowed order is written with the user's token when on-behalf-of is on (`src/mcp/abw_mcp/servers/actions.py:91-98#use_user_token`), and the durable record is the server's own audit event (`src/mcp/abw_mcp/servers/actions.py:107-108#order_placed`; 10.1). The click itself lives only in the in-memory job (**Inference**; `console/jobs.py:772-778#approval_answer`). How long Foundry keeps approval items is not in this repo and I did not verify it.

An approval that nobody answers in ask mode ends only by Stop or by the 420 s hard timeout of `agent_once` (`console/jobs.py:717#timeout`); nothing else in the code resolves a pending approval (**Inference** from reading the manager).

**Trade-off / limitation:** only `place_order` is gated, and only beat 4.2 puts a person in the loop; everywhere else the console pre-approves, and its card says so. The likely reason is that an approval card in every beat would stall a scripted demo (**Inference**). Beat 4.2's own talking points say approval is one layer and not the control, because the compliance rules still apply after a yes (`console/catalog.py:446-448#require_approval`). The job default (yes) and the runner default (ask) differ, so a hand-started runner asks while a console job does not (see Findings).

#### 12.5.6 Script-level guards

**Implemented.** Both scene scripts start with a `#requires -Version 7` line (`scripts/kill-switch.ps1:1#requires`, `scripts/client-allowlist.ps1:1#requires`), and the console launches them with `pwsh`, `-NoProfile`, `-NonInteractive` and `-File` (`console/jobs.py:410-412#run_ps`, `console/jobs.py:42#PWSH`). **Platform behaviour:** a `#Requires -Version` line makes PowerShell refuse to run the script under an older version, https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_requires. That is why the jump-box installer puts PowerShell 7 on the VM (12.6).

The console passes only constants to these scripts: the block switch with the Azure CLI's alias (`console/jobs.py:1283#azcli`), the literal `operator` as the kill target (`console/jobs.py:1313#operator`), and the restore and reset switches during cleanup (`console/jobs.py:1337#Restore`, `console/jobs.py:1340#Reset`). A search of the console's Python files found no other call to either script, so the console never passes the session-revocation switch, the force switch, the allow switch or any text from the browser (**Inference** from a search). The same search found no shell string and no `shell=True`: a child is always started from an argument list, and the agent prompt is its last element (`console/jobs.py:721#argv`).

**How the gateway matches.** Each policy splits its named value on commas and tests membership. The user gateway checks the deny list first (reason `revoked`), then the allow-list against the token's `azp` claim (`client_not_allowed`), then the scope and the role (`infra/apim/policies/mcp-jwt.policy.xml:31-46#abw-deny-oids`). The agent front door checks only the deny list (`infra/apim/policies/agent-frontdoor.policy.xml:51-55#abw-deny-oids`). The policy compares the `oid` exactly as it appears in the token, with no case folding, while the scripts write lower-case ids, so a deny entry matches only if the token's `oid` claim is lower-case, which the repo does not assert (**Inference**). **Where the controls stop.** The private server is reached directly and never touches APIM, so the deny list does not reach it (`DESIGN.md:107#APIM`; 10.5). The legacy PoC path has no deny list, no allow-list and no token validation. Its policy holds one rate limit of 120 calls per 60 s, keyed by the subscription (or by client address when there is none), and two headers (`infra/apim/policies/mcp-legacy.policy.xml:8#rate-limit-by-key`); a search of the Bicep found no global-scope APIM policy that could add more (**Inference** from a search). **Trade-off / limitation:** the kill-switch scene therefore demonstrates the governed path only, and the legacy and private paths are outside what it can revoke.

#### 12.5.7 Sign-in guard, input hygiene and the HTTP surface

**Sign-in guard (Implemented).** The failed-sign-in scenario makes a real password sign-in attempt for one of the demo personas with a made-up password and expects no token; if a token ever came back it raises an error (`console/e2e.py:646-651#acquire_token_by_username_password`). Before it, `_ropc_guard` allows at most 5 attempts in any 600 s window and refuses more with a message about smart lockout (`console/e2e.py:512-525#_ropc_guard`). The counter lives in memory, so a restart resets it (**Inference**). **Platform behaviour:** Entra smart lockout counts failed sign-ins per account (the Learn default is 10 failed attempts in the public cloud, 3 in the US Government cloud) and remembers the last three bad password hashes, so repeating the same wrong password does not add to the count, see https://learn.microsoft.com/entra/identity/authentication/howto-password-smart-lockout. A fresh made-up password each time therefore does count (**Inference**), which is why the cap of 5 is below the default threshold. The password grant itself is not recommended and cannot satisfy multi-factor authentication, see https://learn.microsoft.com/entra/identity-platform/v2-oauth-ropc.

**Input hygiene (Implemented).** The browser never supplies a command line, a script name or a path. `validate` (12.5.3) restricts the agent name to a fixed list of four (`console/jobs.py:47#ALLOWED_AGENTS`), and a request id must match a GUID pattern (`console/jobs.py:63#_GUID`). The id is checked a second time before it is substituted into a catalogue query (`console/jobs.py:1160-1163#resolve_tag`, `console/jobs.py:1196#replace`, `console/azure_probe.py:183-186#safe_request_id`). A GUID holds only hex digits and hyphens, so it cannot close the string literal it is placed in (**Inference**; that is the evident purpose of the check). The persona check refuses a persona who has not signed in, or who lacks the role the beat needs (`console/jobs.py:595-608#persona_error`; I do not copy its text because it names the personas).

### 12.6 Jump-box installation of the console

**Designed.** Every data plane in the platform is reachable only through private endpoints, so the strongest proof that the controls sit "behind the wall" is a browser that is itself inside the virtual network. The driver script gives the reason for the shape of the solution: the console stays a local app bound to the loopback address and uses the operator's own `az` sign-in, and hosting it in a Container App would need a second identity model (`scripts/jumpbox-console.ps1:7-10`, `docs/RUNBOOK.md:102#console`). The console is therefore not deployed as a service. Four scripts copy it onto a jump-box VM that sits in the platform's virtual network, and the operator reaches that VM through Azure Bastion. 12.6.1 lists what the scripts automate, 12.6.2 what they ship, 12.6.3 how they refuse to ship a secret, 12.6.4 how the files travel, 12.6.5 what runs inside the VM, 12.6.6 the first sign-in on the VM, 12.6.7 the optional persona files and 12.6.8 what stays manual. How the console itself works is in 12.1 to 12.5, and how tokens are issued is in section 6.

#### 12.6.1 Why the console runs on the VM and what is automated

**Platform behaviour.** Azure Bastion gives browser-based connections to a VM through the portal, and the VM does not need a public IP address; the Developer SKU is a free SKU on shared infrastructure that supports one VM at a time and is available in select regions (https://learn.microsoft.com/azure/bastion/bastion-overview). **Configured.** The runbook describes the jump box as a Windows Server 2022 VM without a public IP, in its own subnet `snet-jump` with its own network security group, with outbound traffic through the existing NAT gateway, resolving the private endpoints through the virtual network's private DNS zones, and states that nothing in the platform depends on it (`docs/RUNBOOK.md:86#Bastion`). The VM name follows the generated pattern `vm-<workload>-jump-<region>-<instance>` (`scripts/common.ps1:175#jumpVm`). The VM itself is created by a separate script, which the driver names in its "not deployed" error (`scripts/jumpbox-console.ps1:123-131#Assert-VmRunning`); this section covers only what is put on the VM afterwards.

**Implemented.** Switch combinations that make no sense throw before anything runs: `-Remove` with `-Status` or `-Verify`; `-RemovePersonaFiles` with `-Remove`, `-Status`, `-Verify` or `-IncludePersonaFiles`; `-IncludePersonaFiles` with `-Remove`, `-Status` or `-Verify` (`scripts/jumpbox-console.ps1:811-813#combined`). Only the install starts a stopped VM; the other modes call the same helper with the start option off, and it throws when the VM is not running (`scripts/jumpbox-console.ps1:126-128#StartIfStopped`).

A default run, in order:

1. **Build and scan on the laptop.** `Build-Package -Scan -Zip` stages the whitelist, hashes it, scans the staged folder and zips it; a scan finding throws before anything is sent (`scripts/jumpbox-console.ps1:604#Build-Package`, `scripts/jumpbox-console.ps1:332-339#Test-StageSafety`; 12.6.2 and 12.6.3).
2. **`-WhatIf` stops here.** The plan is printed and nothing is sent or started (`scripts/jumpbox-console.ps1:606-625#WhatIf`).
3. **Collect the persona files, only if asked.** With `-IncludePersonaFiles` the driver lists the eligible files and throws if there are none (`scripts/jumpbox-console.ps1:628-632#Get-PersonaSources`).
4. **Start the VM** if it is stopped, through the VM helper script (`scripts/jumpbox-console.ps1:634#Assert-VmRunning`, `scripts/jumpbox-console.ps1:128#jumpbox`).
5. **Probe.** The `probe` phase reads what is on the VM: tool versions, the recorded package hash, missing key files, the virtual environment, the shortcut, any running console, the persona file names and the `az` user and tenant of the VM's local account. The plan text says it reads no tokens (`scripts/jumpbox-console.ps1:636-640#probe`, `scripts/jumpbox-console.ps1:610#probe`).
6. **Decide what is needed.** Tools are needed unless Python 3.11, the Azure CLI and PowerShell 7 are all present. The package is needed when `-Force` is set, when the VM has no recorded content hash, when the recorded hash differs, or when any key file is missing (`scripts/jumpbox-console.ps1:642-643#needPackage`).
7. **Install the missing tools** (`tools` phase), only if needed (`scripts/jumpbox-console.ps1:653-660#tools`).
8. **Upload the package** in parts, only if needed (`scripts/jumpbox-console.ps1:662-667#Send-PackageParts`; 12.6.4).
9. **Run the remaining phases in one call**: `package` (only if a package was uploaded), `venv`, `launcher`, and `verify` unless persona files are about to be sent (`scripts/jumpbox-console.ps1:669-678#launcher`; 12.6.5).
10. **Send the persona files last**, only if asked and only after steps 1 to 9 worked (`scripts/jumpbox-console.ps1:680-698#personas`; 12.6.7).
11. **Record the result** in the jump-box state file in the generated-output folder (content hash, zip hash, file count, tool versions, the verify verdict, the verify console block and the persona file names; the message it prints says no secrets, and 12.6.5 comes back to what the console block holds) and print the steps to do once on the VM (`scripts/jumpbox-console.ps1:700-721#consoleOnVm`).
12. **Delete the local staging folder and zip** in a `finally` block, as a best-effort delete (`scripts/jumpbox-console.ps1:722-724#Remove-Package`, `scripts/jumpbox-console.ps1:365-368#Remove-Package`).

#### 12.6.3 The secrets scan and the scrubbed-evidence copy

**Implemented.** The scan runs on the staged folder, that is on exactly the files that will be zipped, before the zip is made. `Build-Package -Scan` calls `Test-StageSafety`; any finding is printed as "file : rule" (never a value) and throws "Nothing was sent". The install builds with `-Scan -Zip`; `-Status` and `-Verify` build without the scan because they upload nothing (`scripts/jumpbox-console.ps1:332-339#Test-StageSafety`, `scripts/jumpbox-console.ps1:240#Findings`, `scripts/jumpbox-console.ps1:604#Build-Package`). A clean run reports how many files were scanned and how many secret values from how many files in the laptop's secrets folder were compared, in memory (`scripts/jumpbox-console.ps1:338#safety`).

Four layers, applied to every staged file:

| Layer | What it matches | Finding text | Citation |
|---|---|---|---|
| 1. Blocked names | The persona list, the one-time-code seed file, the agent client file, the vendor key text file and the jump-box password file (`.json` or `.txt`); cached sign-in files named `msal-*.json`; parameter files named `params.*.json`; `.pfx`, `.pem`, `.key` and `.tfstate` files; any name starting with a dot-env prefix | "blocked file name" | `scripts/jumpbox-console.ps1:243#blockedName` `scripts/jumpbox-console.ps1:259#blocked` |
| 2. Text patterns | Six patterns, on text files only (a fixed extension list): a private-key header; a JWT-shaped string (two dot-separated segments that start the way a JWT's do); a storage account key; a shared access key; a SAS signature; a connection-string prefix | "rule name + pattern" | `scripts/jumpbox-console.ps1:244-252#textExt` `scripts/jumpbox-console.ps1:260-262#textExt` |
| 3. JSON secret values | In `.json` files, a key named password, secret, client_secret, primaryKey, secondaryKey, apiKey, subscriptionKey, access_token or refresh_token with a value of six or more characters, unless the value is all asterisks, starts with `<` or `[`, or starts with the word redacted in any letter case | "secret-looking JSON value" | `scripts/jumpbox-console.ps1:253#jsonSecret` `scripts/jumpbox-console.ps1:263#jsonSecret` |
| 4. Known values | Every secret value held in the laptop's own secrets folder, searched as an exact substring in every staged text file; one finding per file | "contains a value held in" the secrets folder | `scripts/jumpbox-console.ps1:223-239#Get-KnownSecretValues` `scripts/jumpbox-console.ps1:264-266#IndexOf` |

**Implemented.** How layer 4 decides what a "known secret" is: `Get-KnownSecretValues` reads, at the top level of the laptop's secrets folder only, every `.json` file (a file that does not parse is skipped) and every `.txt` file (the trimmed text counts if it is 10 to 300 characters with no whitespace). For JSON it walks every string leaf; a leaf is a secret value when its field name contains pass, secret, seed, key, token, totp or credential, the name is not a label, meaning one of 16 words (type, kind, name, id, scope, scopes, environment, realm, authority, username, provider, version, algorithm, format, status, mode) that is the whole name or the part after an underscore, as in `token_type` (`scripts/jumpbox-console.ps1:209#SecretMetaName`), and the value is at least 10 characters, is not an http or https URL and is not a GUID. Array elements inherit the name of their array (`scripts/jumpbox-console.ps1:207-221#Add-SecretLeaves`, `scripts/jumpbox-console.ps1:223-239#Get-KnownSecretValues`). The values live in an in-memory hash set, are never printed and are discarded with the process. The cached persona sign-ins are in that folder, so their tokens are among the known values; a token that leaked into a staged file would be caught by layer 4 even if no pattern matched.

**Implemented.** The persona files never pass through the package scan, by design: their names are on the blocked list for the package, and they travel by a separate opt-in route with its own name filter (12.6.7, `scripts/jumpbox-console.ps1:372-377#personaNameRx`).

**Implemented.** The evidence the VM shows is the scrubbed set. `New-Stage` throws if the scrubbed scoreboard file is missing and tells the operator to run the scrubber; otherwise it copies every file of the scrubbed evidence folder into the package under the name `demo\evidence`, so the console's evidence routes need no special case on the VM (`scripts/jumpbox-console.ps1:277-280#evDir`; the scrubbed data itself is described in 12.4.6 and the evidence route in 12.5.7). The in-VM `package` phase never overwrites evidence that the VM produced itself (12.6.5).

**Implemented.** The package's identity is a content hash: SHA-256 over the sorted lines "relative path | file hash" of every staged file, so a change to any staged file, including `README-VM.txt`, `requirements.txt` and `constraints.txt`, changes it. The driver uploads again only when this hash differs from the one recorded on the VM, when a key file is missing or when `-Force` is set (`scripts/jumpbox-console.ps1:299-307#Get-StageItems`, `scripts/jumpbox-console.ps1:324-328#ContentSha`, `scripts/jumpbox-console.ps1:643#needPackage`). A change to the laptop's `pip freeze` therefore also forces a re-send (**Inference**: `constraints.txt` is built before the items are hashed, `scripts/jumpbox-console.ps1:285-299#Write-StageText`).

**Trade-off / limitation:** The scan is pattern-based and value-based. It reads files with a listed text extension only, so a secret inside a binary file or a file with another extension is not examined (`scripts/jumpbox-console.ps1:244#textExt`, `scripts/jumpbox-console.ps1:260#textExt`). A secret that matches none of the six patterns, is not under one of the nine JSON key names and is not held in the laptop's secrets folder would not be caught (**Inference**). **Why:** the whitelist is the main control, because only files the repo names can enter the stage; the scan is the backstop for a whitelisted file that someone later edited to contain a secret (**Inference**).

#### 12.6.4 Transport through run-command

**Platform behaviour.** The classic Run Command (https://learn.microsoft.com/azure/virtual-machines/windows/run-command) runs a script inside the VM as System; it runs one script at a time; it does not support interactive prompts; a running script cannot be cancelled; a run is capped at 90 minutes; every call takes at least about 20 seconds; the output returned is limited to the last 4,096 bytes; returning results needs outbound port 443 to Azure public IP addresses; and calling it needs the `Microsoft.Compute/virtualMachines/runCommand/action` permission. Every design choice below follows from those limits (**Inference**).

**Implemented.** The flow for one call:

1. `Send-Setup` reads the setup script and replaces 17 `__NAME__` placeholders: the phase list, the VM's local account name, the zip and content hashes, the part counts, the persona count, hash and overwrite flag, the tenant id, the tenant domain, the gateway host name and the tool versions and download URLs. It throws if any placeholder is left, and throws if the finished text contains a non-ASCII character. The setup script itself keeps to plain ASCII and Windows PowerShell 5.1 syntax (`scripts/jumpbox-console.ps1:431-454#Send-Setup`, `scripts/jumpbox-console-setup.ps1:5#ASCII`). The reason for the ASCII guard is not stated in the code; my reading is that the script text travels as a command argument file and has to survive the VM's script host unchanged (**Inference**).
2. `Invoke-VmScript` writes the text to a temporary `.ps1` file on the laptop and runs `az vm run-command invoke -g <resource-group> -n <vm> --command-id RunPowerShellScript --scripts @<file>` inside `Invoke-Retry` with 8 attempts and a base delay of 8 seconds. The temporary file is deleted in a `finally` block. The `StdOut` and `StdErr` messages are read from the `value` array of the answer (`scripts/jumpbox-console.ps1:406-424#Invoke-VmScript`).
3. `Invoke-Retry` retries on any thrown error, and before attempt N+1 sleeps for the base delay times N, so the waits are 8, 16, 24, 32, 40, 48 and 56 seconds. That is 224 seconds in total before the eighth and last failure is rethrown (arithmetic from `scripts/common.ps1:115-123#Invoke-Retry`). The comment on the call says the retry covers "the extension is busy or the agent is not ready" (`scripts/jumpbox-console.ps1:405#Retries`).
4. The in-VM script prints exactly one compressed JSON line at the end (12.6.5 gives its fields). The laptop takes the last output line that starts with an opening brace and parses it; if there is none it throws with the first 600 characters of stdout and of stderr (the `Limit` helper keeps the start of a text, not its tail) (`scripts/jumpbox-console.ps1:426-428#Get-LastJsonLine`, `scripts/jumpbox-console.ps1:455-458#Get-LastJsonLine`, `scripts/jumpbox-console.ps1:85#Limit`).
5. Because Run Command returns only the last 4,096 bytes, the setup script trims its result once, at the end: when the JSON is longer than 3,800 characters and the verify phase produced a console result, it empties the role list and cuts the error text to 60 characters in each persona sign-in row of that result, and trims nothing else (`scripts/jumpbox-console-setup.ps1:679-689#3800`). The file's header comment says details go to the setup log on the VM, `C:\abw-stage\setup.log` (`scripts/jumpbox-console-setup.ps1:3-4#setup.log`), but the code writes only phase lines, download and install steps and file counts to that log (`scripts/jumpbox-console-setup.ps1:70-74#Log`), so the trimmed role lists and error text are not kept anywhere.

**Implemented.** The package upload is the same call repeated for slices of one base64 string, as the code comment says: each part is one small run-command that writes a file (`scripts/jumpbox-console.ps1:461-463#Uploads`):

- The zip is read whole and base64-encoded. The slice size is 140,000 characters, a multiple of 4 and, in the code comment's words, well under the run-command script limit; the number of parts is the encoded length divided by that size, rounded up (`scripts/jumpbox-console.ps1:70#chunkChars`, `scripts/jumpbox-console.ps1:354-355#b64Len`).
- Each part script writes `part-0001.b64`, `part-0002.b64` and so on into `C:\abw-stage\parts` (the persona upload uses `C:\abw-stage\persona-parts`). The slice sits in a here-string, wrapped at 4,000 characters per line; the script strips whitespace and writes the file as ASCII (`scripts/jumpbox-console.ps1:464-486#Send-PackageParts`).
- Part 1 deletes any older `part-*.b64` first, so a retry after a failed upload starts clean (`scripts/jumpbox-console.ps1:481#part`).
- Each part prints `{"part":N,"chars":M}`. The laptop throws if the character count the VM stored differs from what it sent, and also throws, quoting the first 400 characters of each output stream, if a part printed no JSON at all (`scripts/jumpbox-console.ps1:487-493#chars`, `scripts/jumpbox-console.ps1:491#printed`).
- The end-to-end check is on the VM: the `package` phase reassembles the parts, compares the SHA-256 of the result with the zip hash the laptop passed in, and throws on a mismatch (12.6.5; `scripts/jumpbox-console-setup.ps1:343-358#Invoke-Package`, `scripts/jumpbox-console.ps1:495#reassembled`).

**Trade-off / limitation:** `Invoke-Retry` retries every failure of `az vm run-command invoke`, not only a busy extension, so a permanent error such as a missing permission is tried 8 times and takes 224 seconds of waiting before it surfaces (`scripts/jumpbox-console.ps1:410-414#Invoke-Retry`; arithmetic from the code). **Why:** the wrapper cannot tell a busy agent from other errors without parsing the message (**Inference**).

**Trade-off / limitation:** Because Run Command takes one script at a time and every call takes at least about 20 seconds, the upload is strictly sequential and its duration grows with the number of parts (**Inference** from the Learn limits above and the loop in `scripts/jumpbox-console.ps1:467-494#Invoke-VmScript`). A failed upload leaves the parts already written on the VM until the next upload's first part, the `package` phase or the `remove` phase deletes them (`scripts/jumpbox-console.ps1:481#part`, `scripts/jumpbox-console-setup.ps1:383-384#partDir`; **Inference**). The parts hold base64 of a package that holds no secrets (12.6.3).

#### 12.6.5 What runs inside the VM: the nine phases

**Implemented.** The in-VM script is one file that the laptop driver sends once per step through run-command. It runs as SYSTEM in Windows PowerShell 5.1 (`scripts/jumpbox-console-setup.ps1:1-5#run-command`). Before every send the driver replaces the double-underscore placeholders at the top of the file with this run's values, and throws if one is left over or if the text is not plain ASCII (`scripts/jumpbox-console-setup.ps1:24-41#filled`, `scripts/jumpbox-console.ps1:431-459#Send-Setup`; 12.6.4 covers the transport and the Run Command limits). The phase list is a comma-separated string. The phases run in the order given, the first failure stops the run, and every phase can be repeated (`scripts/jumpbox-console-setup.ps1:7-19#first`). The run loop calls one function per phase, keeps the last object that function emits, records a throw as `ok = false` with the first 700 characters of the error text, and breaks out of the loop at the first phase that is not ok (`scripts/jumpbox-console-setup.ps1:654-678#switch`). The result is one compressed JSON line (`scripts/jumpbox-console-setup.ps1:679-689#ConvertTo-Json`; 12.6.4 covers the trim that keeps it inside run-command's output limit). No phase starts a sign-in or a device code. Two phases do touch credentials: the `probe` phase reads the VM account's Azure CLI profile file for a default user name and tenant id (`scripts/jumpbox-console-setup.ps1:292-301#azureProfile.json`), and the `verify` phase has the throw-away console silently redeem the refresh token of every persona whose sign-in cache is already on the VM, which asks Entra for a new token for each MCP API (`scripts/jumpbox-console-setup.ps1:451-480#Test-PersonaSignIns`, `scripts/jumpbox-console-setup.ps1:543#Test-PersonaSignIns`, `console/personas.py:215-229#verify`).

**Implemented (tools).** A tool is installed only when it is missing, and any existing version of the right family counts: Python `3.11.*`, any Azure CLI, PowerShell `7.*`. The versions pinned in the driver are therefore installed only on a VM that lacks the tool (`scripts/jumpbox-console-setup.ps1:305-341#Invoke-Tools`, `scripts/jumpbox-console.ps1:72-77#python`, `scripts/jumpbox-console.ps1:642#needTools`). A tool counts as present only when it is found at a fixed default install path: a Python folder named after the pinned version's major and minor numbers, one of two fixed `az.cmd` paths (under Program Files and under Program Files (x86)), or the default PowerShell 7 folder. A copy installed anywhere else is not seen, so the phase would install another one beside it (**Inference**) (`scripts/jumpbox-console-setup.ps1:49-52#azCmds`, `scripts/jumpbox-console-setup.ps1:174-190#Get-ToolState`). The Azure CLI's version comes from its uninstall registry entry and reads `installed` when that entry carries no version (`scripts/jumpbox-console-setup.ps1:180-184#DisplayName`). For each missing tool the phase downloads the installer with up to three attempts and a pause of 5 seconds times the attempt number, using a browser-like User-Agent, and then checks the Authenticode signature: the status must be `Valid` and the signer certificate's subject must contain the expected publisher name (Python Software Foundation for Python, Microsoft Corporation for the other two) (`scripts/jumpbox-console-setup.ps1:211-233#Get-Installer`, `scripts/jumpbox-console-setup.ps1:227-231#Get-AuthenticodeSignature`). **Platform behaviour:** `Get-AuthenticodeSignature` returns the signature information of a file, including its `Status` and `SignerCertificate`, and is available on Windows only (https://learn.microsoft.com/powershell/module/microsoft.powershell.security/get-authenticodesignature). **Inference:** the publisher test is a wildcard match on the subject text, so it is not a pin on a thumbprint or on an exact subject; a certificate whose subject merely contains the name passes if its signature is valid (`scripts/jumpbox-console-setup.ps1:229-230#notlike`).

**Implemented (tools, install).** The installers run silently: Python for all users with PATH updated and the launcher, tests, docs and Tcl/Tk left out (the meaning is read from the option names, **Inference**), the Azure CLI MSI with `/qn /norestart` and a verbose log, and the PowerShell 7 MSI with `/qn /norestart` and six properties (`scripts/jumpbox-console-setup.ps1:313#InstallAllUsers`, `scripts/jumpbox-console-setup.ps1:320#msiexec`, `scripts/jumpbox-console-setup.ps1:327#ENABLE_PSREMOTING`). The installer is called up to six times, because its exit code is read: 0 and 3010 count as installed, 1618 waits 30 seconds and retries, and anything else throws with the log folder named (`scripts/jumpbox-console-setup.ps1:235-246#Invoke-Installer`). **Platform behaviour:** for Windows Installer, 0 is success, 1618 is "another installation is already in progress" and 3010 means a restart is required and "indicates success" (https://learn.microsoft.com/windows/win32/msi/error-codes). The PowerShell MSI properties are documented: `ADD_PATH` adds PowerShell to the PATH, `REGISTER_MANIFEST` registers the event-logging manifest, `USE_MU` and `ENABLE_MU` control the Microsoft Update opt-in, `ENABLE_PSREMOTING` controls whether remoting is enabled during the install, and `DISABLE_TELEMETRY` sets the telemetry opt-out variable (https://learn.microsoft.com/powershell/scripting/install/install-powershell-on-windows). The Python installer is an executable bootstrapper rather than an MSI, and the code applies the same three exit codes to it; that is the repo's assumption (**Inference**). A 3010 sets `reboot` in the result, and the laptop then prints a warning to restart the VM from the portal before the demo, adding that the console itself does not need it (`scripts/jumpbox-console-setup.ps1:314#reboot`, `scripts/jumpbox-console.ps1:530#reboot`). The phase re-reads the versions, deletes the download folder and is ok only when all three tools exist (`scripts/jumpbox-console-setup.ps1:332-339#pwsh`).

**Implemented (package).** The phase first checks that the number of uploaded part files equals the count the laptop sent, then reassembles them into one zip and compares its SHA-256 with the value the laptop sent; a mismatch of either throws (`scripts/jumpbox-console-setup.ps1:345-355#zip`). A running console is stopped first, found by the Python processes whose command line contains the server script (`scripts/jumpbox-console-setup.ps1:357-358#Stop-ConsoleProcs`, `scripts/jumpbox-console-setup.ps1:199-209#Get-ConsoleProcs`). The zip is extracted to a scratch folder and copied into `C:\abw` by two robocopy calls. The first copies everything except the `evidence` folder, with subfolders and two retries. The second copies the `evidence` folder with the flags that exclude changed, newer and older files, and the code comment states the aim: evidence that the VM produced itself is never overwritten, only files that are not there yet are copied. A robocopy code of 8 or more throws (`scripts/jumpbox-console-setup.ps1:366-373#robocopy`). The local account that runs the console then gets modify rights on the app folder; a non-zero code from that grant is only logged (`scripts/jumpbox-console-setup.ps1:376-378#icacls`). The phase writes `package.json` (content hash, zip hash, time, file count) as UTF-8 without a byte-order mark, deletes the part files and the extracted copy, and sets ok (`scripts/jumpbox-console-setup.ps1:380-385#package.json`). **Inference:** neither robocopy call uses a mirror or purge flag, so a file deleted from the checkout stays on the VM and an update is additive; and the code reads robocopy's convention that codes below 8 mean success or a partial copy and 8 or more mean failure (not verified here, so it is stated without a link).

**Implemented (venv).** The phase needs Python and `requirements.txt` under `C:\abw`, creates the virtual env if it is missing, and compares the hash of `requirements.txt` (plus `constraints.txt` when present) with the stored marker `requirements.sha256`. Only when they differ does it run `pip install` with `--disable-pip-version-check --no-input --prefer-binary -r requirements.txt` (and `-c constraints.txt`), send pip's output to `pip.log`, throw on a non-zero code and rewrite the marker (`scripts/jumpbox-console-setup.ps1:400-414#requirements.sha256`, `scripts/jumpbox-console-setup.ps1:408-412#pip`). Whether pip ran or not, the phase then imports 11 packages with the venv's Python (the Azure identity, AI project and Monitor query SDKs, httpx, MSAL and its extensions, the OpenAI client, PyJWT, requests, Starlette and Uvicorn) and throws unless the check prints its success word (`scripts/jumpbox-console-setup.ps1:416-420#imports-ok`). **Implemented (launcher).** The phase creates the all-users desktop shortcut "ABW Demo Console". It runs the launcher with `-NoProfile -ExecutionPolicy Bypass -File` in `C:\abw`, under PowerShell 7 when that is installed and Windows PowerShell 5.1 otherwise. It deletes older portal shortcut files, writes two internet shortcuts (the Azure portal scoped to the tenant domain and the Foundry portal scoped to the tenant id), and then calls `Initialize-SecretsDir` and reads back `secretsLocked` from `Get-SecretsInfo`; 12.6.7 describes both. **Implemented (verify).** The phase repeats the tool, package, key-file, venv and shortcut checks; its package check passes when a package record exists and its content hash equals the laptop's, or when the laptop sent none (`scripts/jumpbox-console-setup.ps1:485-493#package`, `scripts/jumpbox-console-setup.ps1:490#package`). The `apim` block holds the host, the addresses, `private` (true when at least one returned address starts with 10.), `noToken` (the status code) and `prmHeader` (whether the challenge header carries the pointer to the resource's discovery document) (`scripts/jumpbox-console-setup.ps1:509-515#noToken`). **Platform behaviour:** `Resolve-DnsName` performs a DNS query for a name, `-Type A` asks for A records and `-DnsOnly` uses the DNS protocol only (https://learn.microsoft.com/powershell/module/dnsclient/resolve-dnsname). For a private endpoint, Azure puts a CNAME in public DNS that redirects to the private domain name, and a private DNS zone linked to the virtual network overrides the answer with the private endpoint's address without changing the connection URL (https://learn.microsoft.com/azure/private-link/private-endpoint-dns). The check therefore tests that the VM sees the private answer (the network design is in section 3), and the 401 shows the gateway challenging a caller with no token (section 6 explains the challenge).

**Implemented (verify, throw-away console).** The phase starts the console hidden, as SYSTEM, with `--no-browser --skip-az-check --port 8799`, logs under `C:\abw\logs`, and polls its health route up to 60 times at one-second intervals (`scripts/jumpbox-console-setup.ps1:517-531#8799`, `scripts/jumpbox-console-setup.ps1:524#skip-az-check`). If the console does not answer its health route in 60 tries, or exits first, `consoleLog` holds the last six lines of its error log followed by the last six lines of its output log (the lines of each joined with a vertical bar), cut to the first 500 characters; a `finally` block stops the console on port 8799 whatever happened (`scripts/jumpbox-console-setup.ps1:548-555#consoleLog`, `scripts/jumpbox-console-setup.ps1:65-68#Limit`). Because the process runs as SYSTEM, it has no operator sign-in and starts with the sign-in check skipped (**Inference**); it proves that the pages load and that persona caches redeem, and it never makes a governed tool call. The runbook records one real run of this phase: tools present, 99 package files identical to the checkout, the throw-away console answering every page and the scoreboard read as 18 proofs, the gateway answering 401 with the discovery challenge when called with no token, and silent sign-ins for two cached personas from the VM's NAT address (**Designed**: a runbook record that this document did not re-run, `docs/RUNBOOK.md:128#observed`). The same record lists what was not observed: the Bastion browser session, the device-code `az login` on the VM, the console signed in end to end there and the portal data pages (`docs/RUNBOOK.md:128#observed`, `scripts/jumpbox-console.ps1:596-597#Bastion`).

**Implemented (stage folder, setup log, state file).** Every run, including `probe`, creates the stage folder `C:\abw-stage` and its install-log folder, and the `Log` helper appends a time-stamped line to `C:\abw-stage\setup.log`, ignoring any write error; installer and pip logs go to `C:\abw-stage\logs` (`scripts/jumpbox-console-setup.ps1:62#stage`, `scripts/jumpbox-console-setup.ps1:70-74#Log`, `scripts/jumpbox-console.ps1:188#setup.log`). **Trade-off / limitation:** the `ok` flags are narrow. `probe` is always true, `launcher` reports only the shortcut, `personas` ignores script copies that could not be emptied, and `verify` requires none of the gateway 401, the private DNS answer or a persona result; a VM whose private DNS is broken can therefore still return an overall pass, with only the laptop's warning row for the gateway to show it (`scripts/jumpbox-console-setup.ps1:261#ordered`, `scripts/jumpbox-console-setup.ps1:447#shortcut`, `scripts/jumpbox-console-setup.ps1:558-559#health`, `scripts/jumpbox-console.ps1:565#APIM`, `scripts/jumpbox-console.ps1:580#bool`). **Implemented.** What the launcher does, in order (the launcher is `scripts/jumpbox-console-start.ps1`; it runs under Windows PowerShell 5.1 or PowerShell 7):

1. Takes `-Port`, default 8787, validated to 1024-65535 (`scripts/jumpbox-console-start.ps1:7#Port`).
2. Rereads the machine and user PATH, because the installers changed the machine PATH after this VM's last sign-in (`scripts/jumpbox-console-start.ps1:13-18#Update-EnvPath`).
3. Resolves the venv's Python and reads the generated configuration file shipped in the package; with no venv it throws and tells the operator to run the laptop script (`scripts/jumpbox-console-start.ps1:44-47#Get-Content`).
4. Prints a banner that includes the operator's UPN from that configuration (`scripts/jumpbox-console-start.ps1:49-51#operator`).
5. If a console already answers its health route on that port within 3 seconds, it only opens Edge and returns (`scripts/jumpbox-console-start.ps1:20-25#Test-Console`, `scripts/jumpbox-console-start.ps1:53-57#already`).
6. Throws if `az` is missing (`scripts/jumpbox-console-start.ps1:59#Get-Command`).
7. Switches the Azure CLI to a plain token cache and turns the interactive subscription selector off: `az config set core.enable_broker_on_windows=false core.login_experience_v2=off` (`scripts/jumpbox-console-start.ps1:61-64#enable_broker_on_windows`).
8. Compares the tenant of the current `az` sign-in with the configured tenant, case-insensitively and without looking at the user. When they differ it prints the one-time instruction, opens the Microsoft device-login page in Edge and runs `az login --tenant <tenant-id> --use-device-code`; a non-zero exit throws (`scripts/jumpbox-console-start.ps1:32-39#Get-AzTenant`, `scripts/jumpbox-console-start.ps1:66-76#use-device-code`, `scripts/jumpbox-console-start.ps1:71#devicelogin`).
9. Runs `az account set --subscription <subscription-id>`, checks the tenant again and throws if it is still wrong (`scripts/jumpbox-console-start.ps1:79-80#subscription`).
10. Starts the server with the venv's Python in the same window: `console\server.py --no-browser --skip-az-check --port <port>` (`scripts/jumpbox-console-start.ps1:82-85#skip-az-check`).
11. Waits up to 60 times at one-second intervals for the health route on the requested port, stops waiting early if the process has exited, and throws "did not start" otherwise (`scripts/jumpbox-console-start.ps1:86-92#HasExited`).
12. Opens Edge (or the default browser when Edge is not at its usual path) on the console URL and waits for the process, so closing the window ends the console (`scripts/jumpbox-console-start.ps1:27-30#msedge`, `scripts/jumpbox-console-start.ps1:93-94#WaitForExit`).
13. Any exception prints its message, waits for Enter and exits with 1 (`scripts/jumpbox-console-start.ps1:95-99#Read-Host`).

**Platform behaviour.** Learn's Azure CLI sign-in guidance says that from Azure CLI 2.61.0 the Windows broker (WAM) is the default way to sign in on Windows, that `az config set core.enable_broker_on_windows=false` reverts to the browser-based flow, that the browser flow falls back to the device-code flow when no browser can be opened, that `az login --use-device-code` forces the device-code flow, that `core.login_experience_v2=off` turns the interactive subscription selector off, and that a refresh token is stored when a user signs in; it also states that user sign-ins in the CLI require multifactor authentication from September 2025 (https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively). The device authorization grant itself is described in 12.2.2 (https://learn.microsoft.com/entra/identity-platform/v2-oauth2-device-code).

**Implemented.** The launcher applies those settings before it looks at the sign-in state, and the comment gives the reason: a plain token cache instead of the broker, because the console reads the Azure CLI cache for its operator tokens (`scripts/jumpbox-console-start.ps1:61-64#enable_broker_on_windows`). The console's own start-up check does the same job when someone starts the server by hand: `ensure_az_login` exits if `az` is missing, reads the configured operator UPN, notes but accepts a user mismatch when the tenant matches, and otherwise prints the instruction (it says a browser window will open) and runs `az login --tenant` with no device-code option, so the sign-in method is the CLI's own default: the Windows broker unless it has been switched off, and then the browser flow (`console/server.py:394-415#ensure_az_login`, `console/server.py:413-414#browser`). The launcher and the verify phase both start the server with `--skip-az-check`, which skips that call (`console/server.py:422#skip-az-check`, `console/server.py:426-427#ensure_az_login`). **Inference:** the flag is harmless for the launcher because it has just completed the sign-in itself, and it is required for the verify console because that process runs as SYSTEM, has no sign-in and has nobody to answer a prompt (Run Command does not support interactive prompts, 12.6.4). The server binds the loopback address only, tries up to 25 ports from the requested one and exits if none is free, and its middleware checks the Host header on every request (only the two loopback host names pass) and, for methods other than GET, HEAD and OPTIONS, also requires an Origin header equal to the Host header (`console/server.py:348-356#free_port`, `console/server.py:284-298#SameOriginMiddleware`, `console/server.py:386-390#Middleware`, `console/server.py:433#uvicorn`; 12.1).

**Designed.** The runbook's notes match: the first start prints a device code and multifactor authentication applies, and the Azure CLI keeps that sign-in in the local account's own token cache (`docs/RUNBOOK.md:116`). When the "Signed in" light is red or the shortcut asks for a sign-in again, the cause is the first start or an expired Azure CLI sign-in, and the fix is a device code and then Preflight (`docs/RUNBOOK.md:310#Signed`). After the first sign-in the console obtains operator tokens from that cache for every job that acts as the operator (12.2.1). Persona sign-ins are separate: a persona signs in with its own device code from the "Acting as" panel, and the optional cached files only save that step (12.2.2, 12.6.7).

**Trade-off / limitation:** turning the broker off keeps the operator's tokens in the Azure CLI's own cache, which is what the console reads (`scripts/jumpbox-console-start.ps1:61-64#enable_broker_on_windows`). How the Azure CLI protects that cache on disk is not described in this repo and is not verified here; the sign-in stays on the VM after `-Remove` (12.6.8). **Why:** the console's operator-token path is built on `az` (12.2.1).

**Trade-off / limitation:** the launcher compares only the tenant, so any account already signed in to that tenant on the VM is accepted (`scripts/jumpbox-console-start.ps1:66#ToLowerInvariant`; **Inference**, low). `ensure_az_login` makes the same choice on purpose and only notes a user mismatch (`console/server.py:408-412#want_user`).

**Trade-off / limitation:** the launcher waits for the health route on the port it was given, while the server may move up to 24 ports along. If the requested port is held by something that does not answer the health route, the launcher throws "did not start" although a console may be running on a nearby port (`scripts/jumpbox-console-start.ps1:86-92#HasExited`, `console/server.py:348-356#free_port`, `console/server.py:428#free_port`; **Inference**, low).

**Trade-off / limitation:** the console lives in the shortcut's window, so closing that window ends it and drops the in-memory job list and trace store (`scripts/jumpbox-console-start.ps1:94#WaitForExit`; 12.1). The device-code sign-in on the VM has never been observed in this repo's evidence (`docs/RUNBOOK.md:128#observed`), so what the portal and Conditional Access do to that sign-in is not known here.

The code comment names three files that never qualify: the agent client file, the jump-box password file (the comment says it holds the VM's local-account password) and the vendor key text file (`scripts/jumpbox-console.ps1:372-374#personaNameRx`). **Implemented (selection and order).** The laptop asks the probe which persona files the VM already has and sends only the others, or all of them with `-Force`; when the VM has them all it says so and uploads nothing. The code comment gives the reason: the VM may hold newer refresh tokens. With the switch but no persona file on the laptop it throws before anything is sent (`scripts/jumpbox-console.ps1:629-632#IncludePersonaFiles`, `scripts/jumpbox-console.ps1:645-651#personaToSend`). The ordinary run sends `package` only when the VM's copy is missing, incomplete or different (or `-Force` is given), always sends `venv` and `launcher`, and adds `verify` only when no persona upload follows (`scripts/jumpbox-console.ps1:642-651#needPackage`, `scripts/jumpbox-console.ps1:669-678#phases`). The persona flow then runs last and sends one run that executes `personas` and then `verify`, so a failed `personas` phase stops before `verify` (`scripts/jumpbox-console.ps1:680-698#personasRes`, `scripts/jumpbox-console.ps1:690#personas`, `scripts/jumpbox-console-setup.ps1:677#break`; the run loop is in 12.6.5).

**Implemented (container and upload).** `New-PersonaZip` puts the selected files, with flat entry names, into a zip in a randomly named file in the laptop user's temp folder. The laptop prints the file names and sizes, the zip size, the first 16 hex characters of its SHA-256 and the part count, and nothing from inside the files (`scripts/jumpbox-console.ps1:381-401#New-PersonaZip`, `scripts/jumpbox-console.ps1:683-687#names`). The zip is sent as base64 text in parts of up to 140,000 characters, wrapped at 4,000 characters per line inside a here-string, one run-command call per part (`scripts/jumpbox-console.ps1:70#chunkChars`, `scripts/jumpbox-console.ps1:466-471#wrapped`; the transport limits are in 12.6.4). A persona upload differs from a package upload in three ways (`scripts/jumpbox-console.ps1:464-496#Send-PackageParts`):

1. The parts go to a separate folder, `C:\abw-stage\persona-parts`.
2. The first line of every upload script is a marker comment, which the VM later searches for (`scripts/jumpbox-console.ps1:473#Persona`).
3. Before it writes anything, each script creates that folder, removes inheritance from it and grants SYSTEM full control only; it throws if that command's exit code is non-zero (`scripts/jumpbox-console.ps1:477-480#icacls`).

Each part is acknowledged with the number of characters the VM stored, which the laptop compares with the number it sent (`scripts/jumpbox-console.ps1:487-493#ack`). The zip's SHA-256 and the part count reach the VM as filled-in placeholders of the setup script (`scripts/jumpbox-console.ps1:438-440#PERSONA_SHA`). The laptop's own temporary files, the zip and the per-call script file that carries one part, are deleted in `finally` blocks (`scripts/jumpbox-console.ps1:407-416#GetTempPath`, `scripts/jumpbox-console.ps1:365-368#Remove-Package`, `scripts/jumpbox-console.ps1:691-693#Remove-Package`). **Inference:** while a call runs, only the laptop user's own temp-folder permissions protect those files; the repo does not restrict them further.

**Implemented (install on the VM).** The `personas` phase runs these steps in order (`scripts/jumpbox-console-setup.ps1:563-615#Invoke-Personas`):

1. It needs `C:\abw` and an upload part count equal to the laptop's (`scripts/jumpbox-console-setup.ps1:565-568#personaCount`).
2. It decodes the parts in memory and compares the SHA-256 of the result with the laptop's value; a mismatch throws "nothing was installed" (`scripts/jumpbox-console-setup.ps1:569-574#personaSha`).
3. It locks the secrets folder before the first file is written, which the code comment says is so that no readable copy sits anywhere (`scripts/jumpbox-console-setup.ps1:576-577#Initialize-SecretsDir`). `Initialize-SecretsDir` creates the folder, grants SYSTEM full control and the VM's local account modify rights with inheritance removed, throws on a non-zero code, and resets every existing file in it so that it inherits from the folder (`scripts/jumpbox-console-setup.ps1:124-136#Initialize-SecretsDir`).
4. It opens the zip from memory, not from disk (`scripts/jumpbox-console-setup.ps1:580-581#ZipArchive`).
5. It rejects the whole zip, before writing any file, if an entry has a path or a name outside the pattern (`scripts/jumpbox-console-setup.ps1:583-585#unexpected`). **Inference:** this also stops an entry from reaching outside the folder.
6. For each entry it keeps a file already on the VM unless overwrite was requested, otherwise writes it (`scripts/jumpbox-console-setup.ps1:586-596#personaOverwrite`).
7. It reports the file names, the principals on the folder and `locked`. `locked` means the folder's inheritance is switched off and no principal other than SYSTEM and the VM's local account is on it; it does not test who owns the folder (**Inference**) (`scripts/jumpbox-console-setup.ps1:139-149#Get-SecretsInfo`, `scripts/jumpbox-console-setup.ps1:602-605#principals`).
8. It deletes the upload folder, then calls `Clear-PayloadCopies` (next paragraph) (`scripts/jumpbox-console-setup.ps1:606-610#partsDeleted`).
9. `ok` is the folder being locked and the upload folder being gone (`scripts/jumpbox-console-setup.ps1:611-613#locked`).

**Implemented (script copies).** The run-command agent keeps a copy of every script it runs under `C:\Packages\Plugins`, and the code comment says Everyone can read it. After the install, `Clear-PayloadCopies` looks in the directories named like `RunCommand` under that path for files named `script*.ps1`, searches each for the marker, and overwrites every hit with an empty string; it reports how many it emptied and how many it could not (`scripts/jumpbox-console-setup.ps1:151-166#Clear-PayloadCopies`). The marker is built from two string pieces, so the setup script's own copy does not contain it (**Inference**) (`scripts/jumpbox-console-setup.ps1:154#mark`). **Platform behaviour:** Learn's Run Command page documents the output limit, the System account, one script at a time and the permission to call the feature, but not where the agent keeps copies of the scripts it ran (https://learn.microsoft.com/azure/virtual-machines/windows/run-command). The statements about the copies are therefore the repo's own. The runbook says the agent keeps an encrypted copy that only privileged local users can read plus a plain-text copy that the persona step empties, records that after the real run a search of the agent's folder found no marker, and states that PowerShell script-block logging on the VM was not checked (`docs/RUNBOOK.md:127#real`). If script-block logging were on, the payload text inside an upload script could also reach a Windows event log, and nothing in the repo removes that (**Inference**; also in Findings).

**Implemented (silent verification).** The `verify` phase calls `Test-PersonaSignIns` against the throw-away console. It lists the personas, takes those the console reports as `signedIn`, and POSTs the per-persona verify route for each with a 120-second timeout (`scripts/jumpbox-console-setup.ps1:451-461#Test-PersonaSignIns`). On the console side, `signedIn` is an offline check that the persona's cache file holds an account for the persona's UPN (`console/personas.py:172-190#signed_in`, `console/personas.py:587-603#state`). The route runs `personas.verify` in a thread pool and turns a `NeedsSignIn` into HTTP 409 (`console/server.py:262-263#api_persona_verify`, `console/server.py:224-237#persona_action`). `verify` asks `token()` for a delegated token for each of the five MCP APIs and summarises the non-secret claims (`console/personas.py:46#SERVERS`, `console/personas.py:215-229#verify`). `token()` only ever redeems the cached refresh token with `acquire_token_silent`, forces a refresh on the first use per persona, API and scope, and raises `NeedsSignIn` when there is no account or the token has expired or was revoked, so a device code is never started (`console/personas.py:193-212#acquire_token_silent`). The in-VM script builds each row from a count of working APIs, the UPN, up to eight unique role names and a shortened error text with non-printable characters replaced, and it never reads a token, a password or a seed into a row (**Inference**, from the fields it copies) (`scripts/jumpbox-console-setup.ps1:464-479#roles`). These rows are the only part of the result that the trim in 12.6.4 shortens: when the result line is over 3,800 characters and the verify phase produced a console result, the script makes one pass that empties each row's role list and cuts any error longer than 60 characters to its first 60, so a long run can reach the laptop with counts and UPNs only (`scripts/jumpbox-console-setup.ps1:680-688#3800`). Those rows end up in the jump-box state file (12.6.5), and the laptop prints one line per persona (`scripts/jumpbox-console.ps1:566-579#silent`). Section 6 covers what the five tokens are and who signs them.

**Platform behaviour.** Learn says that a refresh token is bound to a user and a client but not to a resource or a tenant; that it replaces itself with a fresh token on every use while the platform does not revoke the old one when it is used; that the default lifetime is 90 days except for single-page apps and email one-time-passcode sign-ins (24 hours); that it can be revoked before it expires, for example when all of a user's refresh tokens are revoked; and that it must be stored as safely as an access token or an application credential (https://learn.microsoft.com/entra/identity-platform/refresh-tokens). **Inference:** the persona caches come from a public-client device-code sign-in (`console/personas.py:126-129#PublicClientApplication`), so the 90-day default applies unless a tenant policy changes it (not checked here). Because the old token is not revoked when a new one is issued, the laptop's copy and the VM's copy can both stay valid and then drift apart as each side refreshes its own. That matches the runbook's note that the VM refreshed its own tokens during the verify, and the code's rule of keeping the VM's file (`docs/RUNBOOK.md:127#real`, `scripts/jumpbox-console-setup.ps1:588#newer`). A silent call that changes the cache is written back by the console with a temp-file-and-rename write, so merely verifying a persona can rewrite its file on the VM (`console/personas.py:159-164#_persist`, `console/personas.py:119-123#_atomic_write`).

**Trade-off / limitation:** the files are plain JSON, protected by an access-control list and not encrypted; a privileged local user of the VM can take ownership of the folder, and the runbook says to copy the files only if that is accepted and to wipe them after the call (`docs/RUNBOOK.md:127#real`). The `locked` flag does not test ownership (**Inference**, `scripts/jumpbox-console-setup.ps1:146-147#extra`). **Why:** the switch saves each persona one device-code sign-in on the VM before the talk (**Inference**; the runbook only says that without the switch every persona signs in once on the VM, `docs/RUNBOOK.md:118`).

**Trade-off / limitation:** `-Force` replaces the VM's files with the laptop's, which can be older than the VM's refreshed copies (**Inference**, `scripts/jumpbox-console-setup.ps1:588-589#personaOverwrite`). The `ok` of the phase ignores script copies that could not be emptied, and only the laptop prints a warning for them (`scripts/jumpbox-console-setup.ps1:608-612#scriptCopiesLeft`, `scripts/jumpbox-console.ps1:543#scriptCopiesLeft`). **Why:** a failed clean-up of the agent's folder is not something the phase can repair; it is reported and left to the operator (**Inference**).

**Implemented (wipe).** `-RemovePersonaFiles` deletes every item in the secrets folder, the upload folder and any marked script copy, and keeps the console; 12.6.8 describes it with the other modes. If the persona step fails, the driver's error message tells the operator to run `-RemovePersonaFiles` to clear whatever is left on the VM (`scripts/jumpbox-console-setup.ps1:617-634#Invoke-PersonasRemove`, `scripts/jumpbox-console.ps1:696#RemovePersonaFiles`).

**Trade-off / limitation:** only upload scripts that carry the marker are emptied. The filled-in setup script travels through run-command on every call and carries the tenant id, the tenant domain and the gateway host as filled placeholders, and the package parts carry the package's code; nothing empties those copies (`scripts/jumpbox-console.ps1:441-443#TENANT_ID`, `scripts/jumpbox-console-setup.ps1:153-162#Clear-PayloadCopies`). **Inference:** they hold identifiers and code, not secrets, so the exposure is low, and the no-secrets rule for the package is enforced by the scan of 12.6.3. **Why:** the clean-up targets the one payload that is a secret (**Inference**).

**Trade-off / limitation:** the installer needs outbound HTTPS from the VM to three download hosts (python.org, the Azure CLI download blob host and github.com) and pins three versions, one of them an MSI link for PowerShell (`scripts/jumpbox-console.ps1:72-77#python`). **Platform behaviour:** Learn's PowerShell install page says that beginning with release 7.7.0 no MSI package is available and WinGet installs only the MSIX package; its example MSI links name 7.6.6 while the repo pins 7.6.8 (https://learn.microsoft.com/powershell/scripting/install/install-powershell-on-windows). **Inference:** a pin bump to a 7.7 release would break the MSI link, and the Learn page may lag the releases, so the pin was not compared with the release list. **Why:** a pin makes the install repeatable, and it matters only on a VM that lacks the tool (12.6.5, **Inference**).

**Trade-off / limitation:** `-WhatIf` covers three of the five modes. `-Verify -WhatIf` still starts a throw-away console on the VM and writes the verify record, which the name of the switch does not suggest (**Inference**, `scripts/jumpbox-console.ps1:745-758#consoleOnVmVerify`). **Why:** the two read modes only read the VM, so the driver gives them no dry run, although verify also writes a state record (**Inference**). Retries and the run-command limits are in 12.6.4.

**Key takeaways**

- **One local process, no database.** The console is a Starlette application bound to the loopback address with 24 routes. Each button press becomes a job on its own thread, child-process output is streamed into an in-memory event list, and the browser polls for it. The console is a client of the governed path, not part of it (12.1; `console/server.py:359-391#build_app`, `console/jobs.py:256-272#Job`).
- **Real tokens, and only tagged rows are not live.** Gateway calls carry a real Entra token of the operator (from the Azure CLI sign-in) or of a persona (device-code sign-in, cached and renewed silently). The one password grant is the Act 6 wrong-password scenario with a made-up password, capped at five attempts in ten minutes (12.2; `console/e2e.py:519-525#_ropc_guard`). The persona stores are plain JSON files in the secrets folder (`console/personas.py:40-43#TOTP_STORE`).
- **Every row says how it was obtained.** The trace board's seven tags are live, probe, logs, graph, arm, replay and portal (12.4.1). A row whose log has not arrived says so and is never filled in. Replay rows come from scrubbed copies of earlier runs, and the scrub's leak check covers only the values the scrubber recognised (C25).
- **A few buttons change real state, and none starts by itself.** The five disruptive job kinds are burst, allow-list, kill, restore and quota (`console/jobs.py:473-492#DISRUPT`). The job manager refuses overlapping disruptive jobs, restore blocks run with `ignore_cancel`, and the order write waits for an approval (12.5). The edges: Stop still kills a restore script that is already running (C1), the green Reset demo verdict ignores a failed membership or persona step (C3), and the page asks for no confirmation (C13).
