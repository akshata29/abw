### 9.5 Act 4: When it goes wrong

**What this section proves.** Act 4 shows that the platform stays safe when something misbehaves, and that every safeguard is a mechanism an operator can see and drive, not a habit of the model. A runaway loop meets a per-user limit at the gateway: of 400 calls fired in a few seconds, about 125 to 133 are served and the rest are answered with HTTP 429, and only that user's budget is spent (beat 4.1, `console/catalog.py:421-431#burst`). A human sits in the loop: Foundry pauses the run on `place_order` until a person decides, and even a yes is refused for a restricted ticker by the trading-actions server (beat 4.2, `console/catalog.py:433-450#approve`). A poisoned vendor headline is replayed step by step, and the Orion read and the restricted order it asks for are each refused by a tool server whatever the model believes; the Foundry guardrail on tool output is a preview, probabilistic, detective layer that stops only some runs (beat 4.3, `console/catalog.py:452-469#xpia`). A token from an application that is not on the gateway's allow-list is refused with 403 `client_not_allowed` (beat 4.4, `console/catalog.py:471-481#allowlist`), and a user on the gateway's deny list is refused with 403 `revoked`, at the gateway and at the agent front door, within about a minute of the list changing and without revoking any token (beat 4.5, `console/catalog.py:483-493#kill`). Beats 4.4 and 4.5 each change one APIM named value, prove the effect and put the value back in a `finally` block (`console/jobs.py:1276-1301#run_allowlist`, `console/jobs.py:1304-1350#run_kill`).

#### 9.5.1 Act overview

**Purpose.** Show that the controls hold when the system is stressed or attacked, and that each one is deterministic and operable. The act has five beats and a prescribed order: the rate limit first, then the two agent beats, then the two gateway scenes one at a time, each of which resets itself (`console/catalog.py:414-418#order`). Beats 4.1 to 4.3 change no configuration. Beats 4.4 and 4.5 change one APIM named value each, wait for APIM to apply it, show the refusal and put the value back. #### 9.5.2 Beat 4.1: Runaway loop -> rate limit

**Purpose.** Show that one runaway agent or script cannot become everybody's outage or an unbounded bill, because the gateway meters each user separately. The beat fires 400 `tools/list` calls at the Research server in a few seconds, all with one user's token. About 125 to 133 are served, the rest are answered with HTTP 429 and a `Retry-After` header, and no other user is affected (`console/catalog.py:421-431#burst`). The deciding control is the per-user limiter at wall 1, whose console reason is `rate_limit` (`console/catalog.py:82-86#rate_limit`). No model, agent or Foundry connection takes part and no configuration changes. The line for the room is "One runaway agent is not everybody's outage - and not an unbounded bill" (`console/catalog.py:429#sales`). Provenance: Implemented (runner and script), Configured (the policy line), Platform behaviour (the limiter's algorithm: https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy and https://learn.microsoft.com/azure/api-management/api-management-sample-flexible-throttling#rate-limits-in-classic-versus-v2-tiers).

**Actors and tokens.** The operator, or the persona selected in "Acting as", and one delegated Research token with scope `Tools.Read`, minted once and sent on all 400 calls (table in 9.5.1; section 6 owns the mechanics). The child process `demo/burst.py` is a plain HTTP client that stands in for the agent loop. The judge is wall 1, and the limiter never sees the person: its counter key is the token's `oid` claim (`infra/apim/policies/mcp-jwt.policy.xml:47-50#abw-oid`, `infra/apim/policies/mcp-jwt.policy.xml:81#rate-limit-by-key`). A call that is served reaches the Research server, which lists only the tools the caller's roles allow (`infra/apim/policies/mcp-jwt.policy.xml:7-8#LIST_OPEN`); a call that is throttled is answered by the gateway before the backend section (`infra/apim/policies/mcp-jwt.policy.xml:81-92#backend`). There is no Foundry connection, front door or model, so the model sees nothing in this beat, and the console shows only the status codes the script counted.

**Preconditions.** Those of 9.5.1, plus one: a full bucket. A bucket that is not full gives fewer served calls, because the burst starts from whatever the user's recent calls left, and the bucket refills two calls per second (see the numbers below). That is why the beat is first in the act (`console/catalog.py:418#order`). A persona run needs that persona signed in and holding a Research role (9.5.1, item 5).

**Sequence.**

1. Browser -> console: the button "Fire 400 calls" calls `startJob`. It first lets `withPersona` add `"persona":"<id>"` to the run when someone other than the operator is selected in "Acting as", then posts `{"kind":"burst","params":<the run>,"title":<the beat title>,"beat":"4.1"}` to `POST /api/jobs` (`console/catalog.py:421-431#burst`, `console/web/pages.js:88-98#startJob`, `console/web/util.js:160-166#startJob`, `console/web/personas.js:29-31#withPersona`).
2. Job manager: `api_jobs_start` hands kind, params and beat to `Manager.start`, which validates the persona, reads the gateway state from ARM and refuses while the kill switch is engaged (`burst` is on the open-gateway list), refuses while another disruptive, gateway-level or agent job runs (`burst` is itself disruptive), and otherwise creates the `Job` and starts a daemon thread (`console/server.py:128-135#api_jobs_start`, `console/jobs.py:503-533#start`, `console/jobs.py:473-495#NEEDS_OPEN_GATEWAY`).
3. `run_burst`: for a persona it first refreshes that persona's cached token, so a missing sign-in becomes a presenter-facing message instead of a device-code prompt that the child would wait on; then it says "Firing 400 calls as fast as possible with ONE user's token - what a buggy agent loop does." (for a persona the sentence reads "with <label>'s token", the persona's label standing in for "ONE user") (`console/jobs.py:925-931#run_burst`).
4. Console -> child process: `stream_process` starts `python demo/burst.py --calls 400 --workers 48 --server research`, with `--persona <id>` appended for a persona, a 180 s ceiling and one callback per output line (`console/jobs.py:945-948#argv`, `console/jobs.py:358-407#stream_process`).
5. Script start-up: mint one token for the Research server with scope `Tools.Read`. The operator's is a silent MSAL refresh of the Azure CLI sign-in, forced so that the token is fresh, and its `azp` is the Azure CLI client; a persona's is a silent refresh of that persona's own cached sign-in. Then print the caller and "target : research MCP server through the APIM gateway - 400 tools/list calls, 48 in flight" (`demo/burst.py:38-42#persona_token`, `demo/mcpclient.py:76-85#admin_token`, `demo/mcpclient.py:88-107#persona_token`).
6. Script: build one `tools/list` JSON-RPC body that every call reuses (`demo/burst.py:43#jsonrpc`).
7. Script -> gateway, 400 times: 48 worker threads share one HTTP client that allows 64 connections; each call posts the body to the Research API URL with a fresh `x-abw-request-id` GUID and returns the status code and the `Retry-After` header. The gateway overwrites that header with its own request id, so the logs carry the gateway's own correlation id and not these GUIDs, and burst calls are found by `UserOid` and time (`demo/burst.py:46-59#ThreadPoolExecutor`, `infra/apim/policies/mcp-jwt.policy.xml:82-84#x-abw-request-id`).
8. Wall 1, `validate-jwt`: signature, issuer, tenant claim, expiry (60 s of clock skew) and the Research API's audience; a failure is HTTP 401 and stops the call (`infra/apim/policies/mcp-jwt.policy.xml:17-30#validate-jwt`).
9. Wall 1, claim checks: the deny reason is computed in a fixed order: `revoked`, `client_not_allowed`, `missing_scope`, then `missing_role`, except that on a server published list-open the discovery methods `initialize`, `ping`, `tools/list` and `notifications/*` skip the role test. The Research server is list-open, so the burst's token, which carries the scope and an allowed client, ends with an empty reason (`infra/apim/policies/mcp-jwt.policy.xml:37-44#discovery`, `infra/05-apim-apis.bicep:30-39#listOpen`).
10. Wall 1, telemetry: the policy emits the metric `abw-gateway-decisions` and the trace `gateway decision server=research decision=allow` with the oid and the gateway request id. Both come before the limiter in the XML, which is why a throttled call is logged with decision `allow` (`infra/apim/policies/mcp-jwt.policy.xml:51-63#emit-metric`; Findings F4-2).
11. Wall 1, limiter: `rate-limit-by-key` with `calls="120"`, `renewal-period="60"` and the oid as counter key. While the bucket has capacity the call goes on to the Research server, which answers HTTP 200 with that user's tool list. When the bucket is empty the policy returns HTTP 429 with a `Retry-After` header itself. The 403 JSON body with `reason` belongs to the deny branch only, so a throttled reply carries no `reason`. Wherever the console judges a single reply (`judge`, which calls `explain`; step 14 uses it for the operator's call in a persona run) it derives `rate_limit` from the status 429 alone, whereas the burst card is built from counted status codes and never calls `judge` (`infra/apim/policies/mcp-jwt.policy.xml:64-81#rate-limit-by-key`, `console/jobs.py:176-192#judge`, `console/catalog.py:118-125#status`; Platform behaviour: https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy).
12. Script, summary: count the status codes, remember the position of the first 429 in the order the replies came back and the first `Retry-After` value, print one bar per code labelled served (200), throttled (429), no token (401), refused (403), error (a request that failed) or nothing for any other code, print "N calls in X s - first 429 came back as response #M; Retry-After: Ns", and exit 0 only if at least one 429 was seen (`demo/burst.py:62-72#Counter`).
13. Console parse: every line becomes a `raw` event; the `_BAR` pattern turns bar lines into `{code, count, label}` rows and `_BURST_SUM` reads the summary line into total, seconds, first-429 position and Retry-After (`console/jobs.py:921-922#_BAR`, `console/jobs.py:935-943#on_line`).
14. Console end: emit one `stats` event with the rows, the lights (the APIM node turns "deny" if anything was throttled) and the summary values. Only if something was throttled does it then say how many calls were served and how many were answered with 429, adding "Other users were not affected". For a persona run, again only if something was throttled, it also lists the Research tools once with the operator's own token, labelled "Operator - a different user", shows that call as an `http` card, and says the operator still gets through if that call is allowed. With the operator as burster nothing measures the other-users sentence (`console/jobs.py:949-961#stats`; Findings F4-3).
15. Console finish: the job is `done` only if the script exited 0 and something was throttled, otherwise `failed`, with the summary "N served, M throttled (HTTP 429)" (`console/jobs.py:963#finish`).
16. Browser: `statsCard` draws one bar per status code ("200 OK", "429 Slow down", any other code as its number) and a line with the call count and elapsed time, plus "as <name>" for a persona run, "the limit kicked in after call M" and "Retry-After N s" (`console/web/render.js:106-117#statsCard`).

**What the numbers mean.**

- 400 and 48 are the click's own constants, and 64 is the script's connection pool. Forty-eight calls in flight is what lets the loop outrun the refill: the proof's own comment says a runaway loop "has to outrun the refill, so share one pooled client" (`console/jobs.py:945#argv`, `demo/burst.py:55#max_connections`, `demo/prove.py:878#refilled`).
- 120 and 60 are `calls` and `renewal-period` in the policy. The deployment uses the Standard v2 tier, where the limiter is a token bucket: the bucket starts with as many tokens as `calls` and refills at `calls` per `renewal-period`, here 2 per second (`infra/apim/policies/mcp-jwt.policy.xml:81#renewal-period`, `infra/05-apim.bicep:48#StandardV2`; Platform behaviour: https://learn.microsoft.com/azure/api-management/api-management-sample-flexible-throttling#rate-limits-in-classic-versus-v2-tiers).
- Served calls are therefore about 120 plus 2 per second of burst: a burst of 3 to 6 s serves 126 to 132, which is why the catalog says "About 125-133 served" and the guide "125-133 served and 267-275 throttled", 400 minus served (`console/catalog.py:427#expect`, `docs/DEMO-GUIDE.md:460#Expect`). The two recorded runs: the guide's sample, 129 served and 271 throttled in 5.4 s, and the scrubbed live proof run, 124 served and 276 throttled in 3 s, two below the 126 the arithmetic gives (`docs/DEMO-GUIDE.md:456-458#served`, `demo/evidence-scrubbed/prove-20261022-172919.json:467-501#P14`). Learn says the limiter "is never completely accurate" and that its result varies with request volume and rate and with backend latency.
- Why the count varies from run to run: how long the burst lasts (network and gateway latency), how full the bucket was at the start, the limiter's own accuracy, and whose bucket it is, since each `oid` has its own. These bands are observed values, not guarantees: the proof asserts only at least 60 served and at least 20 throttled (`demo/prove.py:893-894#counts`). Provenance: Designed for the bands.
- "The limit kicked in after call 85" in the sample is a position in the order the replies came back, not the order the calls went out, which is why it is below 120. Inference, not stated in the repository: the gateway answers a throttled call itself, while a served call waits for the Research server, so quick 429s overtake slower 200s among the 48 calls in flight.
- `Retry-After` was 1 in the guide's sample and in the proof's evidence (`docs/DEMO-GUIDE.md:456-458#Retry`). On the documented refill of two calls per second, the next call would be served within seconds, yet the same user was served again only after 84 s in the scrubbed proof run, which polls every 5 s for up to 120 s. The catalog says "about a minute", the guide says wait 30 to 60 s, and the console's own baseline waits up to seven times 12 s (`console/catalog.py:427#minute`, `docs/DEMO-GUIDE.md:461#wait`, `console/jobs.py:1261-1273#_baseline`). The repository gives no mechanism for the gap between a 1 s hint and an 84 s recovery, and this document does not offer one as fact (Findings F4-4).

**Restoring the state.** There is nothing to restore and no one to do it: the user's counter refills by itself. Stop kills the child process and its calls stop at once, but the calls already sent stay counted. A console that dies midway leaves nothing behind: the burst changes no setting, and an orphaned script finishes by itself because every call has a 45 s timeout (`console/jobs.py:345-348#cancel`, `console/jobs.py:540-542#Cancelled`, `demo/burst.py:55#timeout`). What the burst leaves is a drained bucket, and the console does not wait for it before the agent beats or the 4.3 replay; only the two gateway scenes begin with a baseline call that waits (`console/jobs.py:1261-1273#_baseline`). The guide warns that the next gateway call or agent run can report 429, which suggests the agent's own tool calls draw on the same per-user budget. **Failure modes and what the presenter should say.**

- Fewer served than the band, for example about 60 to 110: the bucket was not full because the user had already spent part of the budget. Say that the limit is a budget, not a count of clicks, and do not fire again at once.
- Nearly all 400 answered 429: a burst or an agent run happened in the minute before. Wait for the bucket and say why.
- The next gateway call or agent run answers 429 within the first minute or two: expected after a burst. The guide says wait 30 to 60 s, and the scrubbed proof run needed 84 s. Make a successful gateway call before starting the approval beat (Findings F4-4, F4-5).
- The card says "Retry-After 1s s" (the double unit is cosmetic; Findings F4-6). Do not promise that the next call works after a second: the recorded recovery was much longer. Say that the reply tells a well-behaved client to back off, and let the bucket refill.
- The console says "Other users were not affected" after an operator burst, although that run measures nothing about other users. For a live demonstration select a persona: the operator's call after the persona's burst is the measurement (Findings F4-3).
- "Is the limit 120 a minute or 2 a second?" It is a token bucket: up to 120 calls at once, then two more every second.

**Why and trade-offs.**

- The key is the token's `oid`, not an IP address or a subscription key. It comes from a validated token, so one person's laptop, scripts and agents share one budget, and nobody can dodge it by changing address. The contrast is the shared-key legacy API, whose limiter keys on the subscription id or the caller's IP address, so one runaway client there spends the budget of everyone who uses the key (`infra/apim/policies/mcp-legacy.policy.xml:8#rate-limit-by-key`). Provenance: Configured; the reasoning is Designed.
- A refused call returns before the limiter, so denied calls spend no budget and a flood of refused calls is not throttled by this policy; it is detected instead (ABW-006 alerts on three or more refusals by one principal in 30 minutes, and the throttled calls of a burst are themselves `AbwDenials` rows, so the rule can fire on a burst too; Findings F4-8) (`infra/apim/policies/mcp-jwt.policy.xml:64-81#choose`, `observability/sentinel/abw-006-repeated-denials.kql:10-15#Denials`).
- The policy has no `increment-condition`, so every call that reaches the limiter counts, including calls that the Research server or wall 2 later refuses (`infra/apim/policies/mcp-jwt.policy.xml:81#calls`).
- The limiter counts calls, not cost. What a user's agent spends in model tokens is capped by the agent front door, with its own per-user call and token limits, which Act 7 exercises (`infra/apim/policies/agent-frontdoor.policy.xml:95-96#llm-token-limit`).
- A 429 does not always come from this limiter. Learn describes gateway capacity throttling as a separate service-level feature that can also return 429 (https://learn.microsoft.com/azure/api-management/service-limits#gateway-capacity-throttling). The console and `AbwGateway` label every 429 as the per-user rate limit (`console/catalog.py:121-122#429`, `observability/kql/AbwGateway.kql:28#rate_limited`).
- The token bucket allows a burst of up to the full bucket and then a steady refill, which is kinder to a legitimate client that sends a quick batch than a fixed window would be, and equally hard on a loop that never stops.

#### 9.5.3 Beat 4.2: A human in the loop

**Purpose.** Show that a consequential tool can be made to wait for a person, and that the person's yes is not the control. The click asks the Wall Desk agent to check whether ACME is on the restricted list and, if it is not, to buy 25 shares. Foundry pauses the run before the order, and the presenter, who is the signed-in operator, answers on a card. Reject: no order. Approve: the order goes through the gateway and the Actions server and is placed under the operator's identity (`console/catalog.py:433-450#approve`, `console/catalog.py:37#order`). The gate is a setting on the agent's tool definition and not one of the four numbered walls (0 Foundry guardrail, 1 gateway, 2 MCP tool server, 3 data plane); the console's own architecture text calls it "a Foundry control, before the gateway even sees the call" (`console/catalog.py:110-115#WALLS`, `console/catalog.py:1141-1145#approval`). Neither wall 1 nor wall 2 can tell that a person approved: the order's arguments are ticker, side and quantity and nothing else, and a direct gateway call with the execute scope places an order with no approval at all, as proof P04 does. The tool description, the API description in Bicep and the agent module's docstring nevertheless speak of human approval as if it were a property of the tool (`src/mcp/abw_mcp/servers/actions.py:20-23#PlaceOrderArgs`, `demo/prove.py:659-679#place_order`, `src/mcp/abw_mcp/servers/actions.py:142#approval`, `infra/05-apim-apis.bicep:54#approval`, `src/agent/abw_agents.py:8#approval`; Findings F4-9). The line for the room is "Approval is one layer, not the control: compliance rules still apply after a yes" (`console/catalog.py:448#sales`). The alternative button asks for 100 ZYNX, a restricted name, with the approval pre-granted, so that the room sees a refusal after a yes; whether that refusal comes from wall 2 depends on the model (`console/catalog.py:439-445#alt`; Findings F4-10). Provenance: Implemented (console, agent runner, Actions server), Configured (the approval setting on the agent's tool definition, the role assignments), Platform behaviour (Foundry pauses a run at an approval request and resumes it on the answer: https://learn.microsoft.com/azure/foundry/agents/how-to/tools/model-context-protocol), Designed (the line for the room).

**Actors and tokens.** The operator and nobody else: agent beats always run as the operator, whatever is chosen in "Acting as", because `agent` is not a persona kind (`console/jobs.py:420#PERSONA_KINDS`, `console/web/personas.js:29-31#withPersona`). Three tokens take part (table in 9.5.1; section 6 owns the mechanics). First, the Azure CLI sign-in gives the child process a token for the Foundry project, which goes to the agent front door, or straight to Foundry when the presenter has switched the front door off (`console/agent_run.py:83-86#build_credential`, `console/jobs.py:98-107#agent_via`). Second, the tool calls carry a different token: the OAuth token that Foundry holds for the operator on the connection `mcp-actions-oauth`, with the scopes `Tools.Read` and `Tools.Execute` and the agent's own client application as `azp` (`scripts/foundry-connections.ps1:55-62#mcp-actions-oauth`, `scripts/foundry-connections.ps1:12-20#abw-agent-client`, `src/agent/abw_agents.py:119-139#wall_desk_tools`). Third, the Actions server writes the order to Cosmos as the user through an on-behalf-of token while `COSMOS_OBO` is on, which is the default, but reads the restricted list with its own identity, so the operator's rights cannot touch it (`src/mcp/abw_mcp/config.py:154-155#cosmos_obo`, `src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`). The person who presses the button is the operator again, in the browser; the browser holds no token, and the console relays the decision to the child's standard input (`console/jobs.py:331-343#answer`). The two walls ask different things of the same `place_order` call: wall 1 tests only for the `Tools.Read` scope and for any one of the Actions API's roles, wall 2 requires `Tools.Execute` and `Trade.Execute` (`infra/apim/policies/mcp-jwt.policy.xml:37-44#missing_scope`, `src/mcp/abw_mcp/registry.py:111-121#require_scope_and_role`, `src/mcp/abw_mcp/servers/actions.py:145#require_scope_and_role`).

**Preconditions.** Those of 9.5.1, plus these. (1) The operator mirrors Tara, so its token carries the `Trade.Execute` role and the operator belongs to the traders group. Without the role `place_order` is absent from the tool list; without the group the order cannot be written, because the Cosmos data-plane role on the `orders` container is assigned to that group (`identity/Setup-Entra.ps1:55-56#tara`, `identity/Use-AdminAsPersona.ps1:27-30#wantRoles`, `infra/03-platform.bicep:650-661#orders`). (2) The one-time OAuth consent for the `mcp-actions-oauth` connection has been given; otherwise the child stops with exit code 3 and the console shows "One-time consent needed" (`console/agent_run.py:129-131#consent`, `console/jobs.py:763-767#consent`). (3) The token Foundry holds for the operator is current. In this deployment's MCP audit, Foundry minted the user's OAuth token at the first agent call after the previous one expired and kept using it until it expired, which is 60 to 90 minutes for an Entra access token by default (9.5.6; an observation of this deployment, not a Learn statement), so a token minted while the operator's roles were flipped keeps hiding `place_order` until it expires, and then no approval card appears at all. The proofs wait for this with `settle_agent`; the console's tools card lets the presenter see which tools were offered (`DESIGN.md:221-225#Foundry`, `docs/RUNBOOK.md:49#jti`, `demo/prove.py:405-428#settle_agent`, `console/web/render.js:573-576#gateway`). (4) A bucket that 4.1 has not drained: the agent's tool calls pass the wall 1 limiter like any other call (9.5.2; Learn documents one counter per counter-key value across all scopes that use it, so the Actions API would be expected to share the user's counter with the Research API, although no run here measures it, Findings F4-5). (5) The kill switch is off and no conflicting job is running. A job that waits for a decision still counts as running, so while the card is open the console refuses a second agent job and the burst, kill, restore and quota jobs; read-only jobs and the allow-list scene are not refused (`console/jobs.py:517-520#killEngaged`, `console/jobs.py:553-554#active`, `console/jobs.py:480-492#conflicts`).

A refusal for `missing_scope` or `missing_role` comes back as code `FORBIDDEN` with `decision` DENIED and a note not to retry; a refusal for `invalid_arguments` comes back as code `INVALID_ARGUMENT` with `decision` ERROR and a note to fix the arguments and retry once; the audit decision is `deny` in both cases (`src/mcp/abw_mcp/registry.py:158-193#call_tool`, `src/mcp/abw_mcp/registry.py:42#DENIED_CODES`, `src/mcp/abw_mcp/registry.py:274-291#INVALID_ARGUMENT`, `src/mcp/abw_mcp/servers/actions.py:20-23#PlaceOrderArgs`).

A caller whose token carries any `Wall.` role is refused with `separation_of_duties`; any other caller is refused with `restricted_list`. Both are `WALL_VIOLATION` with the audit event `order_blocked`. The first rule cannot be reached live: roles are issued per API audience, so the Actions token never carries a Wall role, and the branch is covered by a unit test only (`src/mcp/abw_mcp/servers/actions.py:58-75#separation_of_duties`, `DESIGN.md:225-227#audience`, `src/mcp/tests/test_servers.py:109-136#separation_of_duties`; Findings F4-11).

ACME is not restricted, so the handler builds the order item (a new id, the caller's `oid` and UPN, ticker, side, quantity, status `ACCEPTED`, source `mcp-actions`, the token's `azp` and `jti`, the request id and a timestamp) and upserts it into the `orders` container through the on-behalf-of token, so Cosmos sees the operator and not the server. The order row stays after the demo (`src/mcp/abw_mcp/servers/actions.py:77-98#ACCEPTED`, `src/mcp/abw_mcp/servers/actions.py:99-110#order_placed`, `src/mcp/abw_mcp/registry.py:195-216#setdefault`; Findings F4-12).

The console judges the call (a successful order carries no `decision`, so it counts as allowed) and emits the `answer` card, or a `stop` card if the guardrail ended the run. `run_agent` finishes the job `done` when the child exits 0, with a summary such as "2 tool calls, 2 allowed" (`console/jobs.py:176-192#judge`, `console/jobs.py:789-801#final`, `console/jobs.py:808-827#agent_summary`, `console/jobs.py:830-840#run_agent`).

A wall 2 denial is an ordinary tool result. In the default `soft` mode `isError` is false and the body carries `decision` DENIED, `error`, `message`, `reason`, `request_id` and a `note` that tells the model not to retry, rephrase or look for a workaround; the denial is audited before the result is returned. The code comment records why: Foundry aborts the whole run with HTTP 400 `tool_user_error` when a tool returns `isError`, and `strict` mode restores that behaviour. I found no Bicep file or script that sets the mode (`src/mcp/abw_mcp/registry.py:238-292#isError`, `src/mcp/abw_mcp/config.py:21-26#_parse_denial_mode`, `src/mcp/abw_mcp/config.py:157#MCP_DENIAL_MODE`).

**What the model sees versus what the console shows.** The model sees its instructions: check the restricted list before any order, order only when the user explicitly asks, treat a DENIED result as a policy decision, quote its reason code and request id and do not retry, and treat tool results as untrusted data (`src/agent/abw_agents.py:55-68#WALL_DESK_INSTRUCTIONS`). It sees the tools each server listed for the token, so `place_order` is on its menu only when the token passes that tool's requirement, and the description it reads promises human approval (`src/mcp/abw_mcp/registry.py:132-156#list_tools`, `src/mcp/abw_mcp/servers/actions.py:142#approval`). While the card is open it sees nothing, because the run is paused on the platform. After a rejection the repository does not show what the platform returns to the model; the recorded answer says that the order was not placed because the user did not approve it. After an approval it sees the tool's JSON: the order id, status, ticker, side, quantity and request id. After a wall 2 policy refusal it sees an ordinary result whose body says `decision` DENIED, the reason code, the request id and a note that tells it to stop; after refused arguments it sees `decision` ERROR and a note to fix them and retry once (`src/mcp/abw_mcp/registry.py:272-292#note`). It never sees the token, the card or who pressed the button.

The console shows other things, in the order they happened: the operator's identity, one merged tools card (what the gateway offered this user, not what the model chose), one verdict card per tool call with the wall chip, the reason code and the request id that the child read out of the result text with regular expressions, the approval card, and last the answer card with the timing and token counts (`console/agent_run.py:28-30#REQUEST_ID`, `console/jobs.py:742-762#judge`, `console/jobs.py:789-801#final`). A successful order carries no `decision` field, so `judge` marks it allowed; a refused one carries `decision` DENIED and is drawn as denied, with the title and plain text that the catalog keeps for the reason code (`console/jobs.py:176-192#judge`, `console/catalog.py:52-56#restricted_list`). The card shows the arguments the model chose, cut at 400 characters with the full length appended. It does not show the model's reasoning, and the server's audit event keeps a SHA-256 of the arguments, not the arguments themselves; the order row keeps ticker, side and quantity (`console/agent_run.py:37-39#_text`, `console/agent_run.py:134-135#args`, `src/mcp/abw_mcp/audit.py:178-216#args_sha256`).

The guide's terminal backups took about 24 s for a reject, 27 s for an approve and 28 s for the pre-approved ZYNX run, and the scrubbed proof run took 39.2 s for its reject run and approve run together. The recorded proof run shows the first two cases exactly (`demo/evidence-scrubbed/prove-20261022-172919.json:287-319#P05`).

**Restoring the state.** The only state this beat can change is one row in the `orders` container, written when the presenter approves an unrestricted order. Nothing in the console, the scripts or the proofs removes that row, and "Reset demo" does not touch it, so the demo leaves it in place; proofs P04 and P05 each leave one as well (Findings F4-12; `console/jobs.py:1055-1076#run_restore`, `demo/prove.py:673-679#list_my_orders`). The decision itself leaves no state at all: it is a line on a pipe.

If something goes wrong while the card is open:

- The presenter presses Stop: the console kills the child's process tree, the job becomes `cancelled` and its pending list is cleared, so the card can no longer be answered. Foundry is left with a request that nobody answers; the repository says nothing about how long the platform keeps it, but every run starts with a fresh `responses.create` and the child that held the response id is gone, so no code path can send the answer later and no order is placed (`console/jobs.py:345-348#cancel`, `console/jobs.py:351-355#_kill_tree`, `console/jobs.py:296-304#clear`).
- The presenter does nothing: at 420 s from the start the child is killed, the job fails with the network wording of `friendly`, and nothing is written. A job that waits blocks the conflicting jobs until then (`console/jobs.py:405-406#TimeoutError`, `console/jobs.py:170-171#timeout`, `console/jobs.py:521-524#conflicts`).
- The console process dies: the pipe to the child closes, `readline()` returns an empty string and the child treats it as a rejection. What an orphaned child does when its output pipe is also gone is not shown in the repository (`console/agent_run.py:139-140#readline`).
- The browser tab is closed: the job belongs to the console process, not to the page, so it stays `waiting` until it is answered, stopped or timed out.

Nobody has to restore a kill switch, an allow-list or a limiter for this beat, because it changes none of them. The record of who answered is not durable: the `approval_answer` event lives in the job's memory, and only the 60 newest jobs are kept (`console/jobs.py:527-531#popitem`).

**Failure modes and what the presenter should say.**

- Say what is on the card before pressing: tool, ticker, side and quantity. It is where the arguments are visible before the call, and "It will act under your identity" is the console's own sentence for what an approval means.
- Reject first, then run the beat again and approve, as the talk track does. For a rejection say "Placing an order requires a human to approve. I say no - not placed." (`docs/TALK-TRACK.md:177#Reject`). For an approval say that the order is placed and carries the operator's identity, which the row and the audit event show.
- No approval card and an answer that says orders cannot be placed: look at the tools card. If `place_order` is missing, the token that Foundry holds was minted before the operator held the role and stays in use until it expires, which is 60 to 90 minutes after it was minted by default (9.5.6). The proofs wait for this with `settle_agent`. Pressing the button again does not help. Say that the agent is offered only what the user's roles allow, and go on to the next beat.
- The card says "Waiting...": the request is not the oldest unanswered one, or the job is no longer `waiting`. Answer the older request first.
- "Is approval the control?" No. The gate sits in Foundry, before the gateway sees the call, and neither the gateway nor the Actions server can tell that a person said yes. What protects the firm is the restricted list, which the server checks after any yes with its own identity, and the data-plane role (Findings F4-9). Use the line "Approval is one layer, not the control: compliance rules still apply after a yes" (`console/catalog.py:448#sales`).
- ZYNX: if a `place_order` card appears and Wall 2 refuses, say that the person said yes and the server still said no, and show the incident. If only `check_restricted_list` appears, say that the model stopped itself because the list said so, that the server would have refused anyway, and show proof P04 or the replay in 9.5.4 for the deterministic version (Findings F4-10). The talk track's wording is "Zynx is on the restricted list because of Project Falcon. Even approved, refused. Approval is one layer, not the control." (`docs/TALK-TRACK.md:177#restricted`).
- "Who approved?" The operator, at the console. The repository keeps no record of the click, so do not claim an approval trail beyond the order row and the audit event.

**Why and trade-offs.**

- The gate is set per tool on the agent's definition: the one consequential tool waits, and the other tools are set to run without approval, because the platform's default would otherwise pause every call. This is a configuration of Foundry, so the Actions server cannot verify it, and a caller that reaches the gateway without Foundry places an order without any approval. The decision about who may trade therefore stays with the roles, the scope and the restricted list (`src/agent/abw_agents.py:119-139#MCPToolRequireApproval`, `demo/prove.py:659-679#place_order`; Findings F4-9). Provenance: Configured; the reasoning is Designed.
- A yes must not become a violation. The restricted-list check runs in the tool server after the approval and reads the list with the server's own identity, so neither the user's rights nor the approval can change it (`src/mcp/abw_mcp/servers/actions.py:30-37#_read_restricted`, `src/mcp/abw_mcp/servers/actions.py:68-75#restricted_list`).
- The relay fails closed: one line per request, in order; anything other than a true `approve`, an empty read included, is a refusal (`console/agent_run.py:139-142#approve`).
- The approver and the requester are the same person in the demo, and the console has no second approver and no per-click authentication that I found. Its protection is that it listens only on the local machine and refuses requests from another origin or host name (`console/server.py:284-296#SameOriginMiddleware`, `console/server.py:386-390#TrustedHostMiddleware`).
- The card shows what the agent will do, not why. The audit trail shows which application acted for which user, not who clicked, so a deployment that needs the approver on record has to log the decision itself; this repository does not (Not in this repo).
- Approval is per call. If the model asks for a second order, a second card appears, and the pending list handles several requests one at a time (`console/jobs.py:288-294#pending`).
- The order is synthetic and the Cosmos write uses the user's own on-behalf-of token, so the data plane records the user, not the server, as the writer; if the on-behalf-of exchange fails, the registry refuses the call with the reason `obo_failed:<code>` (code `FORBIDDEN`, so the payload decision is DENIED and the audit event is `tool_denied`), and nothing falls back to the server's own identity (`src/mcp/abw_mcp/data.py:170-181#OboError`, `src/mcp/abw_mcp/registry.py:179-191#obo_failed`, `src/mcp/tests/test_servers.py:150-160#obo_failed`, `src/mcp/abw_mcp/servers/actions.py:91-98#use_user_token`).

**Purpose.** Show that an attack that arrives inside a tool result, and not from the user, still cannot read the wall or place the trade, whatever the model believes. **What the guardrail does and does not guarantee.** The guardrail is the Foundry guardrail policy `abw-agent-guardrails`. Its rule for this beat is the filter `Indirect Attack` on the tool response with the action BLOCKING. The same policy sets the harm categories to Medium on prompts and completions, adds jailbreak detection and `Indirect Attack` on the prompt, and lists `Protected Material Text` without blocking. It is attached to the agent and not to the model deployment, and only to two agents, the governed Wall Desk and the shielded red-team agent. The plain red-team agent has none, which is what makes it the unguarded half of the comparison (`infra/06-governance.bicep:72-99#PostToolCall`, `src/agent/abw_agents.py:167-193#guard_kwargs`, `docs/DEMO-GUIDE.md:229#DefaultV2`).

Platform behaviour: Learn describes the tool-response intervention point, which is in preview, as scanning the payload that a supported tool sent back for attempted indirect prompt injection before the content is added to the agent's memory and, on a detection, stopping the agent immediately without saving the content. It says that the controls do not take effect for a tool outside its list of supported tools, and MCP is not in that list (https://learn.microsoft.com/azure/foundry/guardrails/intervention-points; the attack type is described at https://learn.microsoft.com/azure/foundry/openai/concepts/content-filter-prompt-shields). In the stored transcript of a stopped run the model made one tool call and the response ended `incomplete`, no stored artifact names the control that ended it, and proof P09 asserts that a stopped run called neither injected tool, so no Orion read and no order (`demo/evidence-scrubbed/20261022-123252-abw-wall-desk-redteam-shielded-operator.json:6-24#incomplete`, `demo/prove.py:853-857#incomplete`).

What it does not guarantee:

- That it fires. The policy file calls the control a preview and best effort and says that it stopped the run on only a minority of identical requests, so the file itself treats it as a detection layer and names the wall as the deterministic control (`infra/06-governance.bicep:72-99#PostToolCall`). The documents quote stop counts from 1 run in 11 to 5 in 8 that change over time, and the only stored proof run stopped one of two attempts, so the rates are a Designed claim (`DESIGN.md:228#skipped`; Findings F4-13).
- That a miss shows. Nothing at the gateway or in the servers screens for injection, so a miss leaves an ordinary run behind and raises no alert. The design file says that when the guardrail does not fire, the whole tool-stage guardrail is skipped, and it names a deterministic screen for injection at the gateway or the server as an alternative that this repository does not build (Not in this repo; `DESIGN.md:228#skipped`).
- That the platform supports it for this kind of tool. The documented list of tools that support the tool-call and tool-response points names Azure AI Search, Azure Functions, OpenAPI, SharePoint Grounding, Fabric Data Agent, Bing Grounding, Bing Custom Search and Browser Automation, and MCP is not among them; Learn says that the controls do not take effect for a tool outside that list. Runs that used an MCP tool did end `incomplete` with the tool call reporting no result (`DESIGN.md:228#skipped`, `demo/prove.py:811-812#guardrail_stopped`), but no stored artifact names the intervention point that ended them, and the repository does not explain how a tool outside the list was covered. It is an observation, and a platform change could alter the behaviour without any change here (https://learn.microsoft.com/azure/foundry/guardrails/intervention-points).
- That the console can say which point stopped the run (Findings F4-16).
- That an alert follows. ABW-008 fires only on a stop, from the `0-agent-guardrail` rows of `AbwDenials`. A Defender alert of the Prompt Shields kind is documented, but the hop from it to Sentinel has not been seen, so do not claim it (`observability/sentinel/abw-008-guardrail-intervention.kql:1-13#0-agent-guardrail`, `docs/PROOF-PLAYBOOK.md:428#Defender`, `docs/DEMO-GUIDE.md:230#Defender`).

|-------|----------------|----------------|
| 0, the guardrail | Stops the run if it fires; a miss changes nothing below | The same |

**What the numbers mean.**

- Three gateway calls. The replay makes three: the feed, the Orion read and the order. Each call that passes wall 1 spends one unit of the user's bucket of 120 calls per 60 seconds, including the two that wall 2 refuses with HTTP 200, and a call that wall 1 refuses spends none. The key is the caller's object id in the policy of each governed server, so a replay started in the seconds after 4.1 may meet HTTP 429 at its first call: Learn says that one counter is kept for each counter-key value across all scopes that use it (https://learn.microsoft.com/azure/api-management/rate-limit-by-key-policy), so one counter for all the governed APIs is what the documentation leads one to expect, although no run in this repository measures it (`infra/apim/policies/mcp-jwt.policy.xml:81-84#rate-limit-by-key`; Findings F4-5).
- "About 10 s" is the catalog's estimate for the replay, and the console records no timing for it. The first token of each server after a start or a reset is forced fresh, which adds a token request per server. The recorded agent runs took 8.8 s (unguarded), 10.4 s (shielded, not stopped) and 9.4 s (shielded, stopped); they are agent runs and not the replay (`console/catalog.py:456#eta`, `console/jobs.py:428-436#token_for`, `demo/evidence-scrubbed/20261022-123226-abw-wall-desk-redteam-operator.json:22-24#completed`, `demo/evidence-scrubbed/20261022-123239-abw-wall-desk-redteam-shielded-operator.json:22-24#completed`, `demo/evidence-scrubbed/20261022-123252-abw-wall-desk-redteam-shielded-operator.json:6-24#incomplete`).
- Six attempts. The default is 6, and the runner clamps the value to at least 1 and at most 8. The catalog says "up to ~3 min, runs in the background". Six runs of the recorded length would take about a minute (derived), so the estimate carries slack and its basis is not stated in the repository. A stop ends the loop, so the time on screen is the time to the first stop, or the whole loop if none comes (`console/jobs.py:891-894#tries`, `console/catalog.py:458-464#guardrail`).
- The chance that none of the attempts is stopped. If each attempt were stopped independently at the documented rates, the chance that none of six is stopped would be about 56 % at 1 in 11, 49 % at 1 in 9, 38 % at 3 in 20 and 0.3 % at 5 in 8. This is arithmetic on rates that the repository cannot reproduce, and attempts may not be independent (derived; Findings F4-13). At the lowest documented rate the alternative therefore ends more often than not with the honest sentence that the guardrail did not intervene in this window, which is why the talk track says not to press it on stage (`docs/TALK-TRACK.md:178#stage`).
- Forty attempts. Proof P09 asks the shielded agent up to 40 times (`demo/prove.py:790#GUARD_TRIES`); at 1 in 11 the chance of no stop in 40 attempts would be about 2 % (derived). The recorded run stopped on its second attempt (`demo/evidence-scrubbed/prove-20261022-172919.json:384-401#attempts`).
- 5,000 shares of ZYNX are the notice's arguments, not a limit. The tool accepts 1 to 1,000,000 shares of any ticker of one to six capital letters, and ZYNX is refused only because it is on the restricted list (`src/mcp/abw_mcp/servers/actions.py:20-23#PlaceOrderArgs`, `src/seed/seed.py:210-214#ZYNX`).
- Two refusals per replay. Both are wall 2 refusals under the operator's name, and ABW-006 needs three denials for one principal in 30 minutes from any layer, so a second replay within the window brings the operator to four and adds an ABW-006 incident to the two that the first replay raises (derived from the rule's threshold; `observability/sentinel/abw-006-repeated-denials.kql:10-15#Denials`).

**Restoring the state.** Nothing has to be restored. The replay changes no state: both injected actions are refused, no order row is written, and no kill-switch value, allow-list or limiter setting is touched. The only budget it uses is up to three units of the limiter's bucket, which refills at two a second (9.5.2). The one way a replay could leave a trace is an order for an unrestricted ticker, which would be an ACCEPTED row that nothing deletes (Findings F4-12); the injected order names a restricted ticker, so with the walls as built that does not happen (`src/mcp/abw_mcp/servers/actions.py:77-98#ACCEPTED`).

If something goes wrong while the beat runs:

- Stop pressed during the replay: nothing visible happens. `cancel` sets an event and kills child processes, but the replay starts no process, makes only blocking HTTP calls and never checks the event, so it runs to its end and the job finishes as `done` or `failed` (Findings F4-18). The calls take seconds, but each may wait up to 60 s if the gateway does not answer (`console/jobs.py:345-348#cancel`, `console/jobs.py:862-888#run_xpia`, `console/jobs.py:452-462#call_gateway`).
- Stop pressed during the alternative: the console kills the child's process tree, the job becomes `cancelled` and the attempt in progress is lost. The repository does not show whether Foundry stops a response that is in flight (`console/jobs.py:351-355#_kill_tree`, `console/jobs.py:540-542#Cancelled`).
- The console stops: nothing is left behind by either button. What the alternative's child does when its output pipe is gone is not shown in the repository, as in 9.5.3.

No kill switch, allow-list or limiter state is involved, so nobody has to restore one.

**Why and trade-offs.**

- The control is the wall, and the scene is built to show it. The replay takes the model out of the experiment and sends what an obedient model would send, so the result does not depend on how the model behaves on the day, and the repository's own line for the room is that the action itself must be unauthorizable. Provenance: Implemented (the replay); Designed (the conclusion) (`console/jobs.py:862-888#run_xpia`, `console/catalog.py:467#sales`).
- What the replay shows and what it leaves out. It shows the decisions of wall 1 and wall 2 for one identity on the day. It uses the token that the Azure CLI holds for the operator, whose application is the Azure CLI, and not the token that Foundry holds for the agent, whose application is the agent's client and which can be older than the operator's current roles. At baseline both applications are on the allow-list, so wall 1 admits both and the role decisions are the same when the tokens carry the same roles. It leaves out the front door and the agent's own token. Provenance: Implemented; the equivalence is derived (`console/jobs.py:428-436#token_for`, `scripts/foundry-connections.ps1:16-17#abw-agent-client`, `console/azure_probe.py:195-200#BASELINE_ALLOW`, `scripts/deploy.ps1:178-180#Get-AllowedAzp`).
- The scene is weighted against the model on purpose. The prompt and the red-team instructions tell the agent to carry out notices that arrive in tool results, so the scene tests the walls and not the model, and it does not show how a well-instructed production agent would behave. Provenance: Configured (`src/agent/abw_agents.py:70-76#REDTEAM_INSTRUCTIONS`, `console/catalog.py:40#headlines`).
- The guardrail is an extra, detective layer and not a wall. The platform documents the tool-response control as a preview, its list of supported tools does not name MCP, so it is not shown to apply to this tool, and the repository's own policy file calls it best effort. If the platform stopped honouring it, the walls would be unchanged and only the alarm would be lost. Provenance: Platform behaviour (https://learn.microsoft.com/azure/foundry/guardrails/intervention-points); Configured (`infra/06-governance.bicep:72-99#PostToolCall`).
- The console buffers each attempt of the alternative and discards it unless the guardrail fired or an injected call was not refused. That keeps the screen short, but an attempt in which the model did follow the notice and the wall refused it, the best picture of the wall at work, is never drawn; the audit log holds it. Provenance: Implemented (`console/jobs.py:899-909#bad`).
- The console decides that the guardrail stopped the run by matching text, and its stop card says that the guardrail found an attack in the tool result, which is stronger than the evidence it has. Provenance: Implemented (`console/jobs.py:789-797#stop`; Findings F4-16).
- A deterministic injection screen at the gateway or the server, which would catch what the guardrail misses, is Not in this repo; the design file names it as an alternative (`DESIGN.md:228#skipped`).
- The vendor is kept away from the user's token. The gateway removes it and adds the vendor's key, so the user's token never reaches the vendor server and the key never reaches the user or the agent, and for the same reason the vendor server's audit event cannot say who asked. Provenance: Implemented (`infra/05-apim-apis.bicep:75-78#x-vendor-key`, `src/mcp/abw_mcp/app.py:115-142#VendorKeyMiddleware`).
- The order refusal rests on one rule in one server. The restricted list lives in the Actions handler, and no data-plane rule backs it, so a ticker that was missing from the list would be accepted. Provenance: Implemented (`src/mcp/abw_mcp/servers/actions.py:68-75#restricted_list`, `infra/03-platform.bicep:650-661#orders`; Findings F4-14).

#### 9.5.5 Beat 4.4: Stolen token from the wrong application

**Purpose.** Show that a token which is valid in every other respect, signed by Entra, issued to the right user and addressed to the right API, is still refused at the gateway when the client application that obtained it is not on the gateway's allow-list. The scene needs no second application. It removes the Azure CLI's application id from the APIM named value `abw-allowed-azp`, replays the operator's own token, which was issued to the Azure CLI, against the Research server, expects HTTP 403 with the reason `client_not_allowed`, puts the list back and expects HTTP 200 again (`console/catalog.py:471-481#allowlist`, `console/jobs.py:1276-1301#run_allowlist`). The claim that the gateway tests is `azp`. Platform behaviour: in a v2.0 access token `azp` is the application id of the client that is using the token, and the Learn reference says it may be used in authorization decisions (https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference). The MCP API apps are created to issue v2.0 tokens, and the setup script pre-authorizes the Azure CLI application, a Microsoft first-party application, on each of them with all their delegated scopes; its comment says that this is for dev and test tokens, and it is why the operator can obtain such a token at all (`identity/Setup-Entra.ps1:130#requestedAccessTokenVersion`, `identity/Setup-Entra.ps1:189-196#preAuthorizedApplications`).

What the scene shows is narrower than the sales line (Findings F4-20). The allow-list decides which client applications may present tokens at all: a rogue or consent-phished application, a developer's script, a first-party tool such as the Azure CLI. It does not bind a token to the party that holds it. `azp` is a claim inside the signed token, so a token that was issued to a listed application, the agent's OAuth client or the test client, passes this test from wherever it is replayed, and the gateway has no per-user or per-device condition. I found no proof-of-possession or token-binding check anywhere in the repository. The catalog's sales line, "A leaked token is only useful from the application it was issued to", and the runner's opening line go further than that (`console/catalog.py:479#leaked`, `console/jobs.py:1277#stolen`). For a token stolen from a listed application the controls are the kill switch of 4.5 and the token's own lifetime. Provenance: Implemented (the runner and the policy test); Configured (the named value with its three entries, the pre-authorization); Platform behaviour (the `azp` claim); Designed (the sales line, which claims more than the code enforces).

**Actors and tokens.** The operator is the only caller. `{"kind":"allowlist"}` is not one of the three persona kinds, so the "Acting as" choice does not apply and no persona can run the scene (`console/jobs.py:420#PERSONA_KINDS`, `console/web/personas.js:29-31#withPersona`). Two things run. The probes are JSON-RPC `tools/list` requests to the Research API at the gateway, sent by `list_gateway` with the operator's delegated token for that API and the scope `Tools.Read`. The console takes the token from the Azure CLI's cached sign-in, so its `azp` is the Azure CLI application; the first token for the Research API after a start or a reset is forced fresh and every later probe reuses the cached one, so the baseline, the refused call and the call after the reset normally carry one and the same token, which is what the step label "Same user, same token, blocked client" says (`console/jobs.py:465-469#list_gateway`, `console/jobs.py:428-436#token_for`, `demo/mcpclient.py:76-85#admin_token`). The state change is made by `run_ps`, which starts PowerShell 7 with `scripts/client-allowlist.ps1`; the script calls `az apim nv show` and `az apim nv update` as whoever is signed in to the Azure CLI on the console's machine, so the change is an Azure control-plane write made with the operator's own Azure rights, and the repository does not name the role they need (`console/jobs.py:410-412#run_ps`, `scripts/client-allowlist.ps1:58-68#Get-List`; Findings F4-1). No model, no Foundry and no MCP server takes part: the gateway refuses before it forwards the call.

The agent is not affected, for two reasons. The front door of the agent has no `azp` test, only the deny list on the user's object id, so the operator's agent run is not refused there (`infra/apim/policies/agent-frontdoor.policy.xml:51-55#abw-deny`). And the list keeps Foundry's own OAuth client: the deployment parameter names its three entries as that client, the test client and the Azure CLI, and the catalog's explanation is that Foundry's own client stays on the list (`infra/04-apps.bicep:22-27#allowedAzp`, `console/catalog.py:477#unaffected`). The guides say that this was tested, "an agent run completed normally while the Azure CLI client was blocked", but no stored artifact shows it, and two other lines of the guides name the allow-list as a cause of an agent run that fails closed (`docs/DEMO-GUIDE.md:483#tested`, `docs/RUNBOOK.md:219#Path`, `docs/DEMO-GUIDE.md:185#allow-list`, `docs/DEMO-GUIDE.md:568#allow-list`; Findings F4-21).

**Preconditions.** Those of 9.5.1, plus these. (1) The allow-list is at its baseline of three entries, the agent's OAuth client, the test client and the Azure CLI. When the job starts, the console reads the named value over ARM and refuses to start otherwise; if that read itself fails, it logs a warning and skips the check without telling the presenter (`console/jobs.py:511-520#allowIsBaseline`, `console/azure_probe.py:195-216#BASELINE_ALLOW`). (2) The kill switch is off. The console refuses to start the scene while the deny list is not empty, and the policy would in any case answer `revoked` before `client_not_allowed`, so with both engaged the allow-list could not be shown (`console/jobs.py:517-518#killEngaged`, `infra/apim/policies/mcp-jwt.policy.xml:37-38#client_not_allowed`, `docs/RUNBOOK.md:219#Path`). (3) The operator's Azure CLI session can read and write named values on the APIM instance (Findings F4-1), and the script can find the deployment's generated Entra configuration, which it uses for the agent's and the test client's application ids (`scripts/client-allowlist.ps1:35-45#aliases`). (4) The operator's bucket is not empty. The baseline call needs an HTTP 200; a drained bucket makes the scene wait, up to seven tries of 12 seconds, and the runbook's terminal sequence runs the burst before the block (`console/jobs.py:1261-1273#_baseline`, `docs/RUNBOOK.md:221#BEFORE`). (5) No conflicting job is running. The scene conflicts with the other disruptive scenes (4.1, 4.5, Reset demo, the quota scene) and with gateway-level jobs, but it may overlap an agent job, which is how the guides fill the wait with the approval runs of 4.2 (`console/jobs.py:480-492#conflicts`, `docs/RUNBOOK.md:223-229#fills`). (6) The order of the scenes: run 4.4 before 4.5, and finish the session with Reset demo (`docs/TALK-TRACK.md:181#Timing`).

**Sequence.**

1. Browser -> console: the button "Run the allow-list scene" calls `startJob` with `{"kind":"allowlist"}`. The kind is not a persona kind, so `withPersona` adds nothing, and the request goes to `POST /api/jobs` (`console/catalog.py:471-481#allowlist`, `console/web/personas.js:29-31#withPersona`, `console/web/util.js:160-166#startJob`).
2. Job manager: `Manager.start` validates the request and reads the gateway state over ARM. It refuses to start while the kill switch is engaged or the allow-list is off its baseline, and while a conflicting job is running; otherwise it creates the job and starts its thread (`console/jobs.py:503-533#start`, `console/jobs.py:521-524#conflicts`).
3. `run_allowlist` says what the scene is about: "A stolen token is only useful from the application it was issued to. The gateway keeps an allow-list of client applications; we block the Azure CLI app and replay a perfectly valid token from it." (`console/jobs.py:1277#stolen`).
4. Baseline, console -> gateway. The step "Baseline: the Azure CLI client calls the gateway - expecting HTTP 200" is followed by a `tools/list` probe with the operator's token. On HTTP 200 the step "Baseline: HTTP 200" is drawn and the scene goes on. On HTTP 429 the console says that the gateway is throttling this user because a burst just ran, waits 12 seconds and tries again, at most seven times. On any other status it stops with "Baseline call returned HTTP <status> <reason>. Click Reset demo, then try again." Nothing has been changed up to here, so a stop at this point leaves nothing to restore (`console/jobs.py:1261-1273#_baseline`).
5. The state change, console -> PowerShell -> ARM. From here the runner remembers that it must clean up. The step "Blocking the Azure CLI client on the gateway allow-list (changes the APIM named value abw-allowed-azp)" is drawn and `run_ps` starts `scripts/client-allowlist.ps1 -Block azcli` with a 300 second timeout. The script reads the named value before the write (`az apim nv show`), splits it on commas, trims and lower-cases the entries, removes the Azure CLI's id, refuses to write an empty list, writes the rest joined by commas (`az apim nv update`), prints that it removed the application "within about a minute" and a hint line, and then reads the named value again and prints the list as Azure now stores it. Every output line becomes a `raw` event. A non-zero exit code stops the scene with "The allow-list script failed - see the technical output." (`console/jobs.py:1282-1285#Blocking`, `scripts/client-allowlist.ps1:58-68#Get-List`, `scripts/client-allowlist.ps1:91-96#Block`).
6. The poll, console -> gateway. `_gw_poll` sends a `tools/list` probe with the same token, up to nine times, 10 seconds apart, until it sees HTTP 403 with the reason `client_not_allowed`. A miss draws "Same user, same token, blocked client: attempt <i> - HTTP <status> <reason> (Azure applies the change in about a minute)", where the reason is the one in the response body and is left out when the response has none; a probe that raises, for example on a network timeout, draws the console's friendly message and the loop goes on (`console/jobs.py:1243-1258#_gw_poll`).
7. Wall 1 on each probe, in the gateway. `validate-jwt` accepts the token, since the signature, the issuer, the tenant and the audience are all right. The deny reason is then computed in a fixed order: `revoked` first, then `client_not_allowed`, which splits the named value on commas and tests whether the token's `azp` is one of the entries. Once the change has reached the gateway, the Azure CLI's id is not, and the gateway returns HTTP 403 with a JSON body, before the limiter is reached, so a refused probe spends none of the operator's 120 calls a minute (`infra/apim/policies/mcp-jwt.policy.xml:17-30#validate-jwt`, `infra/apim/policies/mcp-jwt.policy.xml:35-38#azp`, `infra/apim/policies/mcp-jwt.policy.xml:64-80#return-response`, `infra/apim/policies/mcp-jwt.policy.xml:81-84#rate-limit-by-key`).
8. First hit, in the console. `http_result` reads the status and the reason from the body, gives the decision `BLOCKED` to any status of 400 or more that carries no structured decision, and `judge` turns that into the verdict `denied`; the catalog maps the reason `client_not_allowed` to wall 1 with the title "Wrong application". The poll draws "Same user, same token, blocked client: HTTP 403 client_not_allowed", the runner emits the `http` event and says "A valid user and a valid audience - refused because the token was minted for an application that is not on the list." (`console/jobs.py:229-252#http_result`, `console/jobs.py:176-198#judge`, `console/catalog.py:72-76#client_not_allowed`, `console/jobs.py:1286-1289#denied`).
9. If nine probes pass without a 403, the step "The block had not reached the gateway after 90 seconds - Azure is slow today. Resetting." is drawn as a failure and the scene goes on to the reset (`console/jobs.py:1290-1291#Resetting`).
10. Restore, always. A `finally` block runs whenever the baseline has passed, whatever happened in between. It draws "Resetting the allow-list (always, even if a step above failed)" and runs `scripts/client-allowlist.ps1 -Reset`, which writes exactly the three baseline ids into the named value, whatever it held before. The console does not look at the script's exit code. It then polls for HTTP 200 with the same helper, nine times 10 seconds apart, and refreshes the cached gateway state. If no 200 arrives, it draws "Access has not come back yet - click Reset demo." as a failure. The reset script and the polls ignore Stop (`console/jobs.py:1292-1299#Reset`, `scripts/client-allowlist.ps1:84-89#Reset`, `console/jobs.py:306-310#sleep`).
11. Finish. When the refusal was observed, the job ends `done` with "200 -> blocked (403 client_not_allowed) -> restored (200)", whether or not the check after the reset found a 200; otherwise it ends `failed` with "The block was not observed." If any step raised an exception, the job manager ends it `failed` with the console's friendly message after the `finally` block has run (`console/jobs.py:1300-1301#finish`, `console/jobs.py:535-548#_run`; Findings F4-22).

**Who decides.**

| Decision point | Decider | Outcomes | Reason code | HTTP status |
|----------------|---------|----------|-------------|-------------|
| Is the token signed by the tenant, unexpired and addressed to this API | Wall 1, `validate-jwt` | Pass, or refuse | `unauthorized` in the body's `error` field, with the sentence "a valid Entra access token for this MCP server is required" as its `reason`; `AbwDenials` labels the row `no_valid_token` | 401 |
| Is the user on the deny list | Wall 1, first test of the claim policy | Pass: the list is empty in this beat | `revoked` | 403 |
| Is the token's `azp` on the allow-list | Wall 1, second test | Pass while the Azure CLI is listed, refuse after the block | `client_not_allowed` | 403 |
| Does the token carry the scope and the role | Wall 1, third and fourth tests | Scope: passed by the operator before the block. Role: not applied to this scene's `tools/list` probe, because discovery calls on Research are exempt. Neither is reached after the block | `missing_scope`, `missing_role` | 403 |
| Has the user spent the 120 calls of the minute | Wall 1, `rate-limit-by-key`, after the deny tests | Pass: a refused probe never reaches it | `rate_limit`, the console's label | 429 |
| Is the `azp` on the server's own list | Wall 2, the MCP server | Not reached in this scene, because the gateway answers first (Findings F4-23) | `bad_azp` | 401 |
| The same question for an agent run | The agent's front door | Not asked: it tests the deny list and nothing about `azp` | None | None |

Wall 1 decides alone, in one expression. The policy takes the first value of the `azp` claim, or an empty string when there is none, splits the named value on commas and refuses when the claim is not one of the entries (`infra/apim/policies/mcp-jwt.policy.xml:35-38#azp`). Read as written, the comparison is exact: nothing is trimmed and the case is not folded, so an entry that someone typed with a space or in capitals would not match, whereas the script that edits the list reads and writes its entries trimmed and in lower case (`scripts/client-allowlist.ps1:58-62#Get-List`). A token with no `azp` is refused as well, because the empty string is on no list; the claim exists only in v2.0 tokens, which the MCP API apps are set to issue (`identity/Setup-Entra.ps1:130#requestedAccessTokenVersion`). The test comes before the role test and before the exemption that lets discovery calls through, which is why the scene's probe, a `tools/list`, is refused like any other call (`infra/apim/policies/mcp-jwt.policy.xml:37-44#missing_scope`). The refusal is returned before the limiter, so the polls spend none of the 120 calls (`infra/apim/policies/mcp-jwt.policy.xml:81-84#rate-limit-by-key`). A 401 from `validate-jwt` is a different answer: its body carries the sentence "a valid Entra access token for this MCP server is required" as the reason and the policy gives it no request id, so the console's fallback to `no_valid_token`, which applies only to an empty reason, does not fire, and the scene writes a missed poll as a step line with that sentence (`infra/apim/policies/mcp-jwt.policy.xml:96-112#reason`, `console/jobs.py:185-187#no_valid_token`, `console/jobs.py:1243-1258#_gw_poll`).

Wall 2 asks the same question again, against a list of its own. The Research, Wall and Actions servers and the Private MCP server receive `MCP_ALLOWED_AZP` as a container setting at deployment, filled from the same three ids, and a server whose list is not empty refuses a token whose `azp` is not in it with `bad_azp` and HTTP 401, not the gateway's 403 (`infra/04-apps.bicep:77-83#MCP_ALLOWED_AZP`, `src/mcp/abw_mcp/config.py:40-43#mcp_allowed_azp`, `src/mcp/abw_mcp/auth.py:151-153#bad_azp`, `src/mcp/abw_mcp/auth.py:40-56#status_code`). The scene never reaches that test, and nothing that the scene changes reaches it either: it edits the gateway's named value only (Findings F4-23).

**What the numbers mean.**

- **The list.** Three entries at baseline, the agent's OAuth client, the test client and the Azure CLI, and two while the block is on. The console keeps its own copy of the baseline, the set of the three names agent, test and azcli, and compares the stored list with it (`console/azure_probe.py:195-216#BASELINE_ALLOW`, `scripts/client-allowlist.ps1:91-96#Block`).
- **120 calls in 60 seconds, per user.** The scene sends at most 19 probes: one for the baseline, nine polls and nine after the reset, and refused probes are free. Only a bucket left drained by the burst can get in the way, and the baseline waits for it, up to seven tries 12 seconds apart (`console/jobs.py:1261-1273#_baseline`).
- **About 3 minutes.** The catalog's estimate for the whole scene. The guides time the block script at 55 to 85 seconds and the reset script at 40 to 55 seconds, which with the probes comes to about 100 to 150 seconds (derived), so the estimate leaves slack (`console/catalog.py:475#eta`, `docs/DEMO-GUIDE.md:477-481#abw-allow`).
- **About a minute.** The console says that Azure applies the change in about a minute and gives the poll nine tries, 10 seconds apart, that is, 90 seconds of pauses after the script returns, plus the time of the probes (`console/jobs.py:1243-1258#_gw_poll`, `console/jobs.py:1290-1291#Resetting`). Both the guides and the runbook say that the script returns once the gateway enforces the change, so the first poll normally hits (`docs/RUNBOOK.md:188#abw-allow`). The stored proof run measured 46 seconds from the change to the first refusal, and the clock starts before the block script runs, so the figure includes the script's own duration (`demo/evidence-scrubbed/prove-20261022-172919.json:530-533#seconds`, `demo/prove.py:911-912#t0`). The documents quote other figures: 46 to 59 seconds across harness runs, 59 in the final one, and 56 to 83 seconds by hand (`docs/RUNBOOK.md:336#allow-list`, `DESIGN.md:217#harness`; Findings F4-24).
- **What Learn says about the lag.** The page on API Management named values gives no figure for how long a changed plain value takes to apply; the only timing on it concerns Key Vault secrets (https://learn.microsoft.com/azure/api-management/api-management-howto-properties). The repository measured a different pair of named values in the quota scene of Act 7 and found that the GET and POST routes of one API flipped 5 to 10 seconds apart, 5 to 20 seconds in all, so a change need not arrive everywhere at once (`console/catalog.py:851#route`). I treat that only as a hint for this value.
- **The incident.** ABW-004 runs every five minutes over a 30-minute window and raises one High incident per user; Sentinel incidents appear about 8 to 15 minutes after the event (`observability/sentinel/abw-004-client-not-allowed.kql:1-13#client_not_allowed`, `docs/RUNBOOK.md:188#Sentinel`, `docs/PROOF-PLAYBOOK.md:193#Allow`).

**Restoring the state.** One setting changes: the APIM named value `abw-allowed-azp`, a comma-separated string of application ids, three at baseline and two while the block is on. It is one value for the policies of all four governed APIs, so while the block is on the operator's Azure CLI token is refused by every one of them, although the scene probes only Research (`infra/05-apim.bicep:199-207#nvAzp`, `infra/05-apim.bicep:30-36#allowedAzp`, `scripts/deploy.ps1:178-180#Get-AllowedAzp`). The scene restores it itself. The `finally` block of `run_allowlist` runs `scripts/client-allowlist.ps1 -Reset`, which writes exactly the three baseline entries whatever the value held before, and then polls for HTTP 200; because it overwrites, it also repairs a list that someone edited by hand (`console/jobs.py:1292-1299#Reset`, `scripts/client-allowlist.ps1:84-89#Reset`). When the presenter has to do it, any of four things does the same: the Reset demo button, which runs `demo/prove.py --restore`, reads the list back and shows "Client allow-list: ..." as ok or failed; that command in a terminal; `scripts\client-allowlist.ps1 -Reset`; or the terminal function `abw-allow -Reset` (`console/jobs.py:1055-1076#run_restore`, `demo/prove.py:339-352#restore_all`, `demo/stage.ps1:155-164#abw-allow`). The script refuses to write an empty list, because every call, the agents' included, would then be rejected (`scripts/client-allowlist.ps1:64-68#agents`).

If something goes wrong while the beat runs:

- Stop pressed during the baseline: nothing has been changed, the job ends `cancelled` and there is nothing to restore (`console/jobs.py:1261-1273#_baseline`, `console/jobs.py:540-542#Cancelled`).
- Stop pressed after the block has started: the block script, if it is still running, is killed, and the update may or may not have reached Azure. The reset runs anyway, because the reset script and the polls after it ignore Stop, and the job then ends `cancelled`. Stop pressed during the reset has no effect (`console/jobs.py:345-348#cancel`, `console/jobs.py:1292-1299#ignore_cancel`).
- The console process dies after the block: nothing can run the reset, the list stays without the Azure CLI, the operator's gateway calls answer 403 `client_not_allowed`, and the next start of the scene is refused with the baseline message. A new console finds the same state, because the state lives in Azure and the console reads it back. Nothing in the code ties the life of the script to the console's, so assume that a running block script still finishes its write. Reset demo, or one of the other three commands above, puts it right; the agent runs are unaffected in the meantime, by the guides (`console/jobs.py:519-520#baseline`, `docs/DEMO-GUIDE.md:483#tested`).
- The reset itself fails: the console does not look at the script's exit code, so only the polls notice, with "Access has not come back yet - click Reset demo." (`console/jobs.py:1295-1299#run_ps`).
- With the kill switch also engaged, a raw call reports `revoked` first, so the allow-list state cannot be seen until the kill switch is cleared (`docs/RUNBOOK.md:219#Path`).

**Why and trade-offs.**

- The test is on `azp`, at the gateway. `azp` names the client application, so one expression refuses every token that was minted for an application that is not listed, before the limiter and before any server. Provenance: Implemented; Platform behaviour (https://learn.microsoft.com/entra/identity-platform/access-token-claims-reference) (`infra/apim/policies/mcp-jwt.policy.xml:35-38#azp`, `infra/apim/policies/mcp-jwt.policy.xml:42-44#discovery`, `infra/05-apim-apis.bicep:30-40#listOpen`).
- One global list with no per-user dimension. A single named value feeds the policies of all four governed APIs, so the block takes the Azure CLI off all four at once, and the list cannot say that an application may be used by one person or on one API. Provenance: Implemented; Configured (`infra/05-apim.bicep:199-207#nvAzp`, `infra/05-apim.bicep:30-36#allowedAzp`).
- The agent's front door and the servers follow their own rules. The front door has no `azp` test, and the Research, Wall and Actions servers each apply a static list from their deployment settings that the named value does not change, so an application added at runtime would pass the gateway and be refused by those three servers (Findings F4-23). Provenance: Implemented (`infra/apim/policies/agent-frontdoor.policy.xml:51-55#abw-deny`, `infra/04-apps.bicep:77-83#MCP_ALLOWED_AZP`, `src/mcp/abw_mcp/auth.py:151-153#bad_azp`).
- A plain named value with no documented delay. The change is an ARM write and the platform gives no figure for how long a plain value takes to reach the gateway, so the scene makes nine probes with 10 second pauses, 90 seconds of pauses in all plus the time of the probes, and resets when the refusal does not come (Findings F4-24). Provenance: Implemented (the polls); Platform behaviour (https://learn.microsoft.com/azure/api-management/api-management-howto-properties) (`console/jobs.py:1243-1258#_gw_poll`).
- Whoever can write named values on the APIM instance can add or remove an application, with no approval step, and the activity log is the only record. The role is not named in the repository (Findings F4-1), and an alert on a change of the list is Not in this repo (Findings F4-26). Provenance: Implemented (`scripts/client-allowlist.ps1:64-68#Set-List`, `docs/PROOF-PLAYBOOK.md:436#named-value`).
- The list is edited by read, change and write, and the baseline is spelled out in three places. `-Block` and `-Allow` read the list once before the write, change it in memory and write all of it, so two edits at the same moment would lose one; the console runs one scene at a time, a terminal command is not serialised. `-Reset` writes the three baseline entries whatever the value held, so a change made on purpose is lost by Reset demo. The script's aliases, the console's own set of names and the deployment parameter must all agree. Provenance: Implemented (`scripts/client-allowlist.ps1:76-77#current`, `scripts/client-allowlist.ps1:84-89#Reset`, `scripts/client-allowlist.ps1:41-45#aliases`, `console/azure_probe.py:195-200#BASELINE_ALLOW`, `scripts/deploy.ps1:178-180#Get-AllowedAzp`).
- ABW-004 cannot tell the cases apart. It raises a High incident of the tactic InitialAccess for any refusal of this reason, whether it comes from a tool that nobody listed or from a token replayed from elsewhere, and it does not name the application (Findings F4-25). Provenance: Implemented (`observability/sentinel/abw-004-client-not-allowed.kql:1-13#client_not_allowed`).

#### 9.5.6 Beat 4.5: The SOC kill switch

**Purpose.** Show that one change at the gateway cuts a named user off from every governed MCP server and from the front door of the agents at once, while the user's token is still valid, and that the change can be put back. The scene makes a baseline call, adds the signed-in operator's object id to the APIM named value `abw-deny-oids`, polls until the gateway answers HTTP 403 with the reason `revoked`, runs one agent call that is expected to fail, takes the id off again and polls for HTTP 200 (`console/catalog.py:482-493#kill`, `console/jobs.py:1304-1350#run_kill`). The deny list is the first test of the claim policy that guards each of the four MCP APIs and the only test in the deny variable of the agent front door, so a listed object id is refused whatever roles the token carries, and before the tests of client application, scope and role are asked (`infra/apim/policies/mcp-jwt.policy.xml:37#revoked`, `infra/apim/policies/agent-frontdoor.policy.xml:51-55#abw-deny`). Nothing is revoked at Entra. The token stays valid and the gateway refuses it on every call; the runner's own line says that the token "is still valid for an hour - and useless" (`console/jobs.py:1320#hour`). Platform behaviour: the default lifetime of an access token is a random value between 60 and 90 minutes, 75 on average (https://learn.microsoft.com/entra/identity-platform/access-tokens). The named value starts as the placeholder `none`, which matches no object id (`infra/05-apim.bicep:209-217#nvDeny`). One thing in the catalog describes another path than the one that runs by default. **Who decides.**

| Decision point | Decider | Outcomes | Reason code | HTTP status |
|----------------|---------|----------|-------------|-------------|
| Is the token signed by the tenant, unexpired and addressed to this API (for the agent call: to the Foundry audience) | Wall 1, `validate-jwt` at the MCP gateway or at the front door | Pass: the scene does not touch the token | At the MCP gateway the body's `error` is `unauthorized` and its `reason` is the sentence "a valid Entra access token for this MCP server is required"; at the front door the code `unauthorized`, which the console maps to `no_valid_token` | 401 |
| Is the user's object id on the deny list, for a call to an MCP API | Wall 1, first test of the claim policy | Pass while the list is `none` or lacks the id, refuse once the change has reached the gateway | `revoked` | 403 |
| Is the user's object id on the deny list, for the agent call | The agent front door, its deny variable | The same; on a refusal no model is called | `revoked` in the body's `reason`, with the error code `forbidden` | 403 |
| Do the token's `azp`, scope and role pass | Wall 1, the later tests | Not reached once the id is listed, so a revoked user always gets `revoked` | `client_not_allowed`, `missing_scope`, `missing_role` | 403 |
| Has the user spent the calls of the minute | `rate-limit-by-key` at the MCP gateway (120 per 60 seconds); the front door's own limits | Not reached: a refused call spends nothing | `rate_limit`, the console's label | 429 |
| Does a tool call of the agent get through, on the direct path | Wall 1 on each call that Foundry makes with the user's token, then Foundry itself | Designed, no stored run, not verified here on Learn: the gateway refuses with 403 and Foundry ends the whole run | `revoked` at the gateway, `tool_user_error` from Foundry | 403 to Foundry, then 400 to the caller, as the guide has it |
| The servers' own checks and the data layer | Walls 2 and 3 | Not reached: no server runs | None | None |

Wall 1 decides alone, and the order of its tests matters. The claim policy builds one string, the reason, by testing in a fixed order and returning at the first test that fails: the deny list, the client application, the delegated scope, and last the app role, which is skipped for discovery calls on servers that filter their own tool list. The deny test is the first, so it also refuses discovery calls: the scene's probe is a `tools/list`, which would otherwise pass without a role (`infra/apim/policies/mcp-jwt.policy.xml:31-46#abw-deny`, `infra/apim/policies/mcp-jwt.policy.xml:42-44#discovery`). The comparison is exact. The policy splits the named value on commas and asks whether the token's `oid` is one of the pieces, with no trimming and no case folding, whereas the script that writes the list reads and writes its entries trimmed and in lower case; the scene works and proof P12 passes, so the claim arrives in lower case (derived) (`infra/apim/policies/mcp-jwt.policy.xml:36-37#oid`, `scripts/kill-switch.ps1:63-68#Get-DenyList`). The `none` placeholder cannot match an object id. The refusal is returned before the limiter, so the polls spend none of the 120 calls (`infra/apim/policies/mcp-jwt.policy.xml:81-84#rate-limit-by-key`). The scene does not touch the token; where the token test does fail, the MCP gateway's 401 body carries `unauthorized` and the sentence given in the first row, and the front door's body carries the code `unauthorized`, which the console maps to `no_valid_token` (`infra/apim/policies/mcp-jwt.policy.xml:96-112#reason`, `infra/apim/policies/agent-frontdoor.policy.xml:118-140#unauthorized`, `console/catalog.py:128-133#FRONT_DOOR_REFUSALS`).

The agent front door asks the same question with a smaller policy. It takes the object id of the validated token, tests it against the same named value and returns HTTP 403 with its own JSON body: the error code `forbidden`, the message "Blocked at the agent front door: revoked", the reason and the request id, with the headers `x-abw-request-id` (the request id again) and `x-abw-gateway` (set to `apim-agent-front-door`). The policy sets both on its own refusals and on the responses that pass through it, so they show that a response passed through the front door and not that it refused the call. The child process copies `x-abw-request-id` into the `gateway_id` of its failure event, and the console treats the failure as the front door's own refusal when the call went through the front door (`via` is `apim`), `gateway_id` is present and the code is one of the four that the front door shapes (`unauthorized`, `forbidden`, `token_quota_exceeded` and `rate_limited`). I found no read of `x-abw-gateway` in the console code (an absence, not a test). The refusal comes before the front door's per-minute limit and token budget, so a refused call spends none of the user's agent budget (`infra/apim/policies/agent-frontdoor.policy.xml:33-36#abw-oid`, `infra/apim/policies/agent-frontdoor.policy.xml:71-94#return-response`, `infra/apim/policies/agent-frontdoor.policy.xml:95-96#rate-limit-by-key`, `console/agent_run.py:149-153#gateway_id`, `console/catalog.py:128-133#FRONT_DOOR_REFUSALS`, `console/catalog.py:136-139#front_door_refusal`, `infra/apim/policies/agent-frontdoor.policy.xml:109-132#x-abw-gateway`).

**Why and trade-offs.**

- One named value, tested first, read in two kinds of place. The deny list is a single APIM named value. The four MCP policies and the agent front door each compare the token's `oid` with it before any other test, so one change cuts a user off from all of them with no redeploy, no policy edit and no wait for the token to expire, and a refused call costs no limiter budget. The price is that the unit of revocation is the user and nothing else: there is no list per API, per tool or per session. Provenance: Implemented; Configured (`infra/05-apim.bicep:209-217#nvDeny`, `infra/apim/policies/mcp-jwt.policy.xml:37#revoked`, `infra/apim/policies/agent-frontdoor.policy.xml:51-55#abw-deny`).
- The token itself is not revoked. Nothing in the scene touches Entra: the access token stays valid for its lifetime, 60 to 90 minutes by default (https://learn.microsoft.com/entra/identity-platform/access-tokens), and the gateway only refuses to honour it. The script has an optional second layer, `-RevokeSessions`, which asks Entra to invalidate the user's refresh tokens and sign-in sessions so that no new token can be minted from them. The Graph page on revokeSignInSessions (https://learn.microsoft.com/graph/api/user-revokesigninsessions) says that the call invalidates the user's refresh tokens (and the session cookies in the user's browser), that an application that redeems an invalidated refresh token gets an error, and that there might be a small delay of a few minutes before tokens are revoked; it does not say that an access token that was already issued stops working. Learn's page on revoking user access in Microsoft Entra ID (https://learn.microsoft.com/entra/identity/users/users-revoke-access) says that after an administrator disables the account and revokes the refresh tokens the user cannot gain new tokens, that for applications that use access tokens the user loses access when the access token expires (this page gives 1 hour as the default lifetime; the access-token page cited above gives a random 60 to 90 minutes), and that continuous access evaluation allows administrators to revoke the session and access tokens of applications that are CAE capable. The page on continuous access evaluation (https://learn.microsoft.com/entra/identity/conditional-access/concept-continuous-access-evaluation) lists an administrator revoking all refresh tokens as a critical event, gives near real time as the goal with a latency of up to 15 minutes that might be observed, and says that its initial implementation focuses on Exchange, Teams and SharePoint Online and that not all client and resource provider combinations are supported; the page on CAE-enabled APIs (https://learn.microsoft.com/entra/identity-platform/app-resilience-continuous-access-evaluation) says that to use CAE both the app and the resource API must be CAE-enabled. Whether the four MCP APIs accept CAE tokens, and whether the Azure CLI and Foundry ask for them, is not shown here, and the talk track's statement that custom APIs do not get CAE is not verified here. The scene never runs the optional layer, so the "about a minute" is the gateway's and the identity-layer half is described, not shown (Findings F4-28). **Running the proofs and putting the tenant back.** `python demo\prove.py` runs the proofs in a fixed order in which the agent proofs go before P02, because P02 flips the operator's roles and Foundry would freeze a wrong role into the agent's token (`demo/prove.py:1129-1132#ORDER`). `--list` prints the proofs, `--only P14,P15,P12` selects some, `--group` selects `core`, `agent`, `ops`, `policy` or `verify`, `--verify` runs only P10, P17 and P13, `--restore` runs the panic button below and exits, `--force` goes on after a failed preflight and `--timeout` sets how many minutes the proofs wait for log ingestion and Sentinel alerts, 25 by default (`demo/prove.py:1165-1173#restore`, `docs/SELF-DEPLOY.md:305#core`). `--group ops` also runs P16, which removes the operator from the Falcon group and waits up to `--drift-timeout` seconds for Azure RBAC to notice (`demo/prove.py:970-977#drift_timeout`), so the three Act 4 proofs of that group, P14, P15 and P12, are selected with `--only`. A selected proof that is not a verification proof pulls in P00 first, and a baseline that is not clean stops the run unless `--force` is given (`demo/prove.py:1201-1202#P00`, `demo/prove.py:1157-1159#baseline`). A full run clears the stored stamps, while `--only`, `--group` and `--verify` keep them, so P13 can judge traffic stamped by earlier partial runs, but it reads back only the alerts and incidents of the last 12 hours, so a rule with no alert or no incident inside that window fails its check (`demo/prove.py:1206-1207#traffic`, `demo/prove.py:1087-1088#query_rows`, derived).

Each of the two Act 4 proofs that change gateway settings, P15 and P12, restores its own change in a `finally` block (`demo/prove.py:923-924#finally`, `demo/prove.py:951-952#finally`); P05 and P04 each leave one order row that no restore step removes (Findings F4-12). When the whole run is interrupted, the runner calls `restore_all` and re-raises (`demo/prove.py:1210-1215#restore_all`). `restore_all` is a best-effort panic button of four independent steps, each of which prints "restored" or "RESTORE FAILED" on its own: the kill-switch reset, the client allow-list reset, the operator back in the Falcon group and the persona baseline (`demo/prove.py:339-352#restore_all`). A hard kill of the process skips Python's handlers (derived), and for that case the runbook's `abw-restore` is the same call as `python demo\prove.py --restore` (`docs/RUNBOOK.md:297#abw-restore`). During a full run do not call the gateway yourself, because P12 and P15 flip settings that block your calls for 1 to 2 minutes (`docs/RUNBOOK.md:148#Full`), and keep the console closed, because its status lights call the gateway every 15 seconds and could disturb the count-based proofs (`docs/DEMO-GUIDE.md:175#console`). **Why:** the five scenes end in five reason codes, and the exhibit says which wall gave each of them. `rate_limit`, `client_not_allowed` and `revoked` come from the gateway (layer `1-gateway`), `restricted_list` and `project_not_in_token_roles` come from a tool server (layer `2-mcp-server`), and a row at layer `0-agent-guardrail` appears only when the preview guardrail stops a run. Only that last layer looks at the text that the model reads. The other four decide on facts that a poisoned sentence cannot change: the application and the roles in the token, the user's object id against a list, a per-user counter, and the ticker against a list that the server holds. That is why the talk track says "the model is not the control" (`docs/TALK-TRACK.md:292#model`), why it calls the approval gate "one layer, not the control" (`docs/TALK-TRACK.md:177#Approval`), and why the proof of beat 4.3 rests on the walls: the guardrail fires on a minority of identical requests and the walls refuse every time (`demo/prove.py:787-789#deterministic`). Provenance: Implemented (the layers and the proof); Designed (the talk track's sentences).

**Why and trade-offs.**

- Each control has one unit, and the unit is all it can express. The rate limit counts calls per object id, the allow-list names client applications, the deny list names users, the approval setting belongs to one tool, the restricted list names tickers and the guardrail judges one run of one agent. A narrower question, such as one tool for one session or one application for one person, needs a policy change and not a setting (derived). Provenance: Implemented; Configured (`infra/apim/policies/mcp-jwt.policy.xml:81#rate-limit-by-key`, `infra/05-apim.bicep:199-207#nvAzp`, `infra/05-apim.bicep:209-217#nvDeny`, `src/agent/abw_agents.py:119-139#wall_desk_tools`, `src/mcp/abw_mcp/servers/actions.py:68-75#restricted_list`, `infra/06-governance.bicep:92-97#Indirect`).
- The one layer that reads the model's input is the weakest, so the walls carry the weight. The platform documents the tool-response control as a preview whose list of supported tools does not name MCP, the proof's own comment records that it fires on only some identical requests, and the console cannot tell which intervention point stopped a run (Findings F4-13, F4-16).
